3. 项目目标演变：弹珠 → 状态同步沙盒

3.1 方向已转，分支名已过时

分支原名 feature/pinball-tech-demo，Plan/弹珠技术演示/弹珠技术演示-阶段总目录.md 已明确把弹珠降级为历史方向，原文写明三条转向理由：

  1. 面向 Gameplay 岗求职时，单纯弹珠物理容易被理解成物理小品，而不是角色行为状态同步能力。
  2. 当前更需要证明「可玩的角色行为」在弱网下如何预测、校验、回滚和重播。
  3. Dash、体力、Recover、占点这些行为状态比弹珠得分更适合展示 Gameplay 同步思维。

新方向：求职用的极简俯视角 Gameplay 状态同步沙盒。小球角色 + 小房间 + Dash/体力/Recover + 占点，配弱网、ghost、轨迹、调试面板。明确非目标：完整技能系统、Buff 伤害命中、复杂动画、大量美术。

3.4 新发现：四面墙是纯视觉，没有 Box2D body

反向印证 §4.5

本次核实：FrameSyncPhysicsWorld.cs 全文只有一处 CreateBody（玩家圆形），无 EdgeShape / PolygonShape / SetAsBox / StaticBody。P1 的四面墙是 GameObject.CreatePrimitive(PrimitiveType.Cube)，属于 Unity 渲染层，与 Box2D 世界无关。

三条推论：

  1. pair 顺序隐患仍然潜伏，没有被这次改动激活——§4.5 的"一旦加墙体必触发"还没发生，因为加的是视觉墙不是物理墙。
  2. Box2D 求解器现在更空转了：玩家间 GroupIndex=-1 不产生 Contact，边界靠手写钳制，挤位靠手写 ResolvePlayerOccupancy。Box2D 实际只剩「圆形 body 速度积分」。§4.5 末尾那个"是否仍需 Box2D 求解器"的问题比之前更值得问。
  3. 好处是确定性风险没有增加：钳制是纯定点比较 + SetTransform，顺序由 _sortedBodyIdsBuffer（已排序）决定，可控。

3.5 新发现：LoginUI 被完全跳过

GameApp.cs 的启动逻辑从「automation 开启 → BattleMainUI，否则 → LoginUI」简化为无条件 GameplaySandboxView.Create()：

await GameClient.Instance.InitAsync(_hotfixAssembly);

取舍评价

对「一键进 demo」的求职展示目标是合理简化——省掉点击登录的步骤，录屏更干净。但要意识到两点：

  • 登录流程在主路径上变成了死代码。LoginUI 仍在仓库里，但正常启动不再经过。Timeline 完成记录写「GameApp 与登录成功兜底路径均进入 Gameplay Sandbox」，说明兜底路径也改了。
  • P5 要写「新环境能按 README 跑起服务端和客户端」时，README 需说明这个跳过是故意的，否则读者会以为登录坏了。

3.6 术语风险：这不是帧同步

首要风险

守望先锋不是帧同步：它是状态同步 + 客户端预测 + 服务端权威 + 回滚重播，服务端下发状态快照而非输入帧。本项目属同一路线：服务端每帧广播 S2C_FrameSnapshot，不是纯 lockstep。

开口说"我做了帧同步"会被反问"那为什么要下发状态"。

建议表述：状态同步架构下的确定性模拟 + 预测回滚——沿用帧同步的固定逻辑帧与确定性约束，但服务端是权威状态下发。

这也正是 Source SDK 的路线，所以它是高度对标的参考，而非"另一套思路"。

两次核实（2026-08-02 白天 + P1 提交 55d8c97d 之后）：GameScripts/ 全树搜索 WarmStarting 仍只命中 Box2DSharp.dll 二进制，.cs 源码零命中——Box2D 报告落地清单第 1 项（标注"高（立即）"）依然没做，也是本报告 §7 优先级 #1。

P1 这次改的正是 FrameSyncPhysicsWorld.cs（+49 行），顺手加一行的机会已经错过一次。

已确认 Box2DSharp.dll 导出 set_WarmStarting，即 World.WarmStarting 可写，加一行即可编译通过：

_world = new World(in gravity);
_world.WarmStarting = false;   // 确定性优先：消除跨帧隐藏状态

代价为零：本项目零重力 + 俯视角 + 圆形 body + 无堆叠，VelocityIterations = 12 足够单帧收敛。

6.1 无错误则不重放（性能 + 消除抖动源）

Source 怎么做

CPrediction::ComputeFirstCommandToExecute()（prediction.cpp:1434）由 cl_pred_optimize 控制三条路径：

条件动作
没收到新世界更新，或更新没确认任何新命令 直接跳到本帧最后一条命令。RestoreEntityToPredictedFrame(skipahead - 1)。
注释点睛："Always restore since otherwise we might start prediction using an 'interpolated' value instead of a purely predicted value"
cl_pred_optimize >= 2 且 上次 ack 无误差（!m_bPreviousAckHadErrors） 恢复到上一帧最终预测状态 RestoreEntityToPredictedFrame(m_nCommandsPredicted - 1)，再 ShiftIntermediateDataForward() 把中间数据前移已确认的命令数，只预测最新那一条命令

对应本项目

ReconcileAuthoritativeSnapshot 每次收到权威快照都无条件恢复快照 + 重放。但 CheckConsistency 已经能判一致性——一致时其实不必重放。

怎么落地

当 CheckConsistency 返回一致：只更新快照缓存基线与权威帧号，跳过 RollBack 与 AdvancePredictionTo。省 CPU，也消除一个抖动来源（重放本身可能因浮点差异引入微小扰动）。

6.2 预测误差平滑（成本最低的观感改善）

Source 怎么做

核心是不硬拉误差：累积到一个向量，在表现层按时间线性衰减。

// c_baseplayer.cpp:2641  记录误差（累加，不覆盖）
void C_BasePlayer::NotePredictionError( const Vector &vDelta ) {
    Vector vOldDelta;
    GetPredictionErrorSmoothingVector( vOldDelta );
    m_vecPredictionError = vDelta + vOldDelta;   // 叠加未衰减完的旧误差
    m_flPredictionErrorTime = gpGlobals->curtime;
}

// c_baseplayer.cpp:2715  取衰减后的偏移
void C_BasePlayer::GetPredictionErrorSmoothingVector( Vector &vOffset ) {
    float errorAmount = ( gpGlobals->curtime - m_flPredictionErrorTime )
                        / cl_smoothtime.GetFloat();
    if ( errorAmount >= 1.0f ) { vOffset.Init(); return; }   // 衰减完毕
    errorAmount = 1.0f - errorAmount;
    vOffset = m_vecPredictionError * errorAmount;            // 线性衰减
}

关键认识：逻辑状态立即修正为权威值（一致性不打折），只有渲染层拿到逐渐衰减的偏移。手感与一致性两者都不牺牲。cl_smooth 可关、demo 回放时不平滑。

对应本项目

§5.2——完全缺失，回滚时位置直接跳变。

怎么落地

  • 在 GameplaySandboxView / BattleEntityView 层加 predictionErrorOffset：回滚时记录「权威位置 − 预测位置」+ 时间戳。
  • 渲染位置 = 逻辑位置 + 衰减偏移。不要动 BattleWorldState，避免污染哈希与确定性。
  • 顺带打通 P4：ghost 画权威位置、实心球画「逻辑位置 + 偏移」，两者共享同一份数据 —— 平滑与可视化是一次实现。

6.3 误差判定的双阈值（区分噪声与传送）

Source 怎么做

CPrediction::CheckError()（prediction.cpp:128）：

len = VectorLength( predicted_origin - origin );
if ( len > MAX_PREDICTION_ERROR ) {
    len = 0;                       // 传送/重生：静默清零，不平滑
} else if ( len > MIN_PREDICTION_EPSILON ) {
    player->NotePredictionError( delta );   // 真误差：记录 + 平滑
}
// 落在 epsilon 以下：什么都不做

两个阈值各司其职：下界 MIN_PREDICTION_EPSILON 滤掉浮点噪声（否则每帧告警）；上界 MAX_PREDICTION_ERROR 防止把传送/重生当误差平滑（否则会拖出一条长尾巴）。

对应本项目

状态比对是逐字段精确相等。对定点字段没问题，但本项目是混合架构——Box2D 内核仍是 float，PhysicsBodySnapshot 的位置/速度是 float，精确比较零容错空间。

怎么落地

  • 按字段类型分策略：Fixed64 与整型 → 精确比较；float 物理字段 → epsilon 容差 + 上界豁免。
  • 保留两套：离线确定性验证用精确哈希（零容差，本来就该零容差）；运行时同步检查用带阈值版本。
  • 附带收益：这正好回答"你怎么区分真失同步和浮点噪声"。

6.4 声明式字段表驱动 diff（打印真实差异字段）

Source 怎么做

predictioncopy.cpp（2263 行）用一张字段描述表（typedescription_t）同时驱动三件事：拷贝、对比、打印。CheckError 里通过 FindFieldByName("m_vecNetworkOrigin", player->GetPredDescMap()) 按名字查字段偏移，再 memcpy 取值——字段位置不是硬编码的。

对应本项目

Timeline 要求「mismatch 日志必须打印真实差异域」（位置/速度/体力/状态机/占点进度），并区分 PositionMismatch / StaminaMismatch / StateMismatch。手写比较函数的老问题：加字段要改三处（快照、哈希、diff 输出），漏一处就静默失同步。

怎么落地

给 BattleWorldSnapshot 定义字段描述表（字段名 + 取值委托 + 比较策略），让快照序列化、StateHasher、CheckConsistency 三者共用同一张表。加字段只需在表里加一行，三处自动生效。

6.5 插值与仿真解耦（远端玩家表现）

Source 怎么做

C_BaseEntity::GetInterpolationAmount()（c_baseentity.cpp:5916）按实体类型给不同的插值量：

if ( GetPredictable() || IsClientCreated() )
    return TICK_INTERVAL * serverTickMultiple;   // 本地预测实体：跑在当前时刻

if ( bPlayingMultiplayer || ... )                // 远端实体：回溯插值
    return AdjustInterpolationAmount( this,
        TICKS_TO_TIME( TIME_TO_TICKS( GetClientInterpAmount() ) + serverTickMultiple ) );

设计要点：本地预测实体跑在当前时刻（零延迟操作感），远端实体在时间上回溯，用历史样本容器（interpolatedvar.h，1591 行）插值出平滑表现。两条路径分开。

对应本项目

§5.4——缺远端插值层。当前是单人 demo（测过 2 人），多客户端下远端小球会以 30Hz 阶跃移动。

怎么落地

  • GameplaySandboxView / BattleEntityView 区分本地与远端：本地读预测状态直接输出；远端维护位置历史环，按「渲染时间 = 当前时间 − interpDelay」采样插值。
  • interpDelay 参考 Source 取 2×帧间隔 + 抖动余量，30Hz 下约 66~100ms。
必踩的坑：回滚后必须清插值历史

Source 在 m_bPreviousAckHadErrors 时除了重算，还要重置 latch（prediction.cpp:1495-1553），并分全量重置与局部重置（只重置 m_EntsWithPredictionErrorsInLastAck 里的实体）。

注释解释了为什么要把 curtime 往回调一个 tick：

// 若不减一个 tick interval，会出现 3 个时间戳相同的插值样本，
// 导致无法插值 —— 表现为任何实体（哪怕只是枪）出现预测误差时，
// 玩家角色都会抖动

本项目现在没有插值层，所以这个坑还没显形。一旦 §6.5 落地，回滚 + 插值同时存在，必然踩到。解决：回滚时清掉受影响实体的插值历史，优先做局部重置。

6.6 延迟补偿（Source 最成熟的部分，含现成反外挂逻辑）

Source 怎么做：先算「该回溯到哪个 tick」

player_lagcompensation.cpp:366-436：

float correct = 0.0f;
correct += nci->GetLatency( FLOW_OUTGOING );      // 出向延迟
correct += TICKS_TO_TIME( lerpTicks );            // 客户端插值量
correct = clamp( correct, 0.0f, sv_maxunlag.GetFloat() );   // 硬上限 1.0s

// 用实测延迟交叉校验客户端声称的 tick
float deltaTime = correct - TICKS_TO_TIME( gpGlobals->tickcount - targettick );
if ( fabs( deltaTime ) > 0.2f )                   // 偏差 > 200ms
    targettick = gpGlobals->tickcount - TIME_TO_TICKS( correct );  // 不信客户端，用延迟推导
这段就是反外挂

客户端声称"我在第 N 帧开火"，服务端用实测延迟推导应然帧号，偏差超 200ms 就不采信客户端声称值，改用自己算的。这是一个免费拿到的反外挂机制。

Source 怎么做：回溯到历史位置

// 找第一条 simulationTime <= 目标时间 的记录
if ( record->m_flSimulationTime <= flTargetTime ) break;

// 落在两条记录之间 → 线性插值
frac = ( flTargetTime - record->m_flSimulationTime )
     / ( prevRecord->m_flSimulationTime - record->m_flSimulationTime );
Assert( frac > 0 && frac < 1 );   // should never extrapolate

配套细节：按 sv_maxunlag 裁剪过期记录（flDeadtime）；LAG_COMPENSATION_EPS_SQR（0.1²）判断位置变化是否值得回溯；sv_unlag_fixstuck 处理回溯后卡墙里。

对应本项目

项目无命中判定，因此不需要延迟补偿——这个结论本身是对的。但两点仍可借：

  • P3 的「占点」本质也是时空问题：客户端预测进入区域 vs 服务端权威判定，可用同一套思路。
  • 输入帧号交叉校验（上面那段反外挂）可以现在就加：本项目目前只做窗口上下界检查（迟到丢弃 / 超前 24 帧拒收），缺 RTT 交叉校验。成本极低。

怎么落地

在 PlayerState 保留位置历史环（约 1 秒），注释标明这是延迟补偿的接入点。这样面试时能从架构角度解释"为什么现在不接"，而不是"没做"。特别值得提"永不外插"这条边界——它能体现实现者是否真想清楚过问题。

6.8 架构前提：client / server 共用同一份源码

Source 最根本的一条：src/game/shared/ 下的代码在客户端与服务端同时编译运行。gamemovement.cpp 4951 行的移动逻辑，两端跑的是同一份源文件。

预测正确性的根基是共享代码，而不是"努力让两套实现保持一致"。

本项目已经做了同样的架构选择：GameScripts/HotFix/GameShared/（82 个文件），服务端 .csproj 引用同一批源文件。这条可以直接和面试官对齐为架构共识。

两个衍生认识：

  • 这解释了为什么 FrameSyncValidationRunner 要用正则禁掉 using UnityEngine——这批代码必须能在没有 Unity 的服务端进程里编译运行。守门人不是洁癖，是架构约束的自动化执行。
  • §6.4 的字段表能同时驱动两端的拷贝与对比，前提也是两端共享同一份字段声明。
  • P1 新增的 GameplayRoomSettings 放进 GameShared 并注明"客户端和服务端必须使用同一份配置"，正是这条原则的正确应用。
