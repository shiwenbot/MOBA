球场与羽毛球物理引擎

📖 背景

当前项目已具备完整的状态帧同步框架（v0.5a 已完成），包括确定性帧驱动基础设施、Box2D 物理集成、快照/回滚系统、Buff 系统同步和输入缓冲区。

本阶段的目标是在帧同步框架之上搭建羽毛球游戏的基础物理层——球场边界和羽毛球弹道。这不是一个独立的物理 Demo，而是为后续所有羽毛球玩法铺设地基。

已锁定的设计决策

  • 弹道模型：高空气阻力模型，水平速度指数衰减约 60%/s
  • 物理引擎：羽毛球弹道不使用 Box2D 刚体，复用帧同步基础设施
  • 坐标约定：2.5D 模型 — XZ 为水平面，Y 为独立高度标量
  • 帧率：30Hz 逻辑帧（dt = 33.333ms）

1球场场景

标准羽毛球单打球场（13.4m × 5.18m），含网、边界线、半场划分

⚙ 技术决策

TD-1 2.5D 逻辑模型（XZ + Y） ▶

XZ 平面表达地面运动，Y 轴作为独立高度标量。与 LoL 思路一致："3D 渲染表现 + 2D/平面逻辑"。羽毛球比 LoL 多一个真正重要的高度维度，但不需要完整 3D 刚体物理。

落地方式：ShuttlecockState 包含 Vector2 xz + float y，速度同理。每帧分别更新水平运动（阻力衰减）和垂直运动（重力 + 竖直阻力），渲染层将 (xz.x, y, xz.y) 映射到 Unity Transform.position。

TD-2 羽毛球弹道不使用 Box2D ▶

复用的是帧同步基础设施，不是 Box2D 物理引擎。

  • 复用：TickAccumulator 世界时钟、SnapshotBuffer 快照回滚、ITickable 帧驱动管线、DeterminismRules 确定性校验
  • 不复用：Box2D 刚体/碰撞求解。羽毛球不创建 Box2D Body
  • 原因：弹道是纯数学模拟；扣杀球速可达 22m/s，Box2D 有穿透风险；2.5D 高度维度超出 Box2D 能力
TD-3 弹道物理模型 ▶

水平分量（XZ 平面）：指数衰减 v_h(t+dt) = v_h(t) × exp(-drag × dt)，drag ≈ 0.92，方向不变只衰减速度大小。

垂直分量（Y 轴）：重力 g = 9.8 m/s²，竖直阻力系数约 0.3，Y ≤ 0 时球触地。

浮点确定性：MVP-a 允许 System.Math.Exp 做本地验证。双端阶段前（MVP-d）做定点化评估，用实际不一致率数据决定。

TD-4 击发语义为帧命令 ▶

ShuttlecockLaunchCommand 实现 IResettable，携带 TargetFrame、ShotType、位置和方向。命令只在 ShuttlecockEntity.Tick(frameIndex) 中当 frameIndex == TargetFrame 时消费。

为什么不直接 Launch()：即时调用与"状态变化只能在 Tick 中发生"原则冲突；回滚重播时无法复现击发时刻；客户端预测与服务端权威必须共享同一帧语义。

TD-5 球路配置表设计 ▶

使用 Luban 配置表 TbShuttlecockShot，包含 6 种球路：高远球 / 吊球 / 扣杀 / 平抽 / 网前球 / 挑球。

Luban 链路不通时：使用纯 C# 静态配置类 ShuttlecockShotConfigFallback 兜底。不使用 ScriptableObject（无法在服务端加载）。

TD-6 落地/出界状态机 ▶
Idle → Flying → (Landed | OutOfBounds)
  • Flying → Landed：Y ≤ 0 且位于球场有效区域内
  • Flying → OutOfBounds：触地时位于界外
  • 互斥：终态不再转换，先检查触地位置界内/界外
  • 空中出界：MVP-a 采用"触地后判定"策略，与真实裁判规则一致
TD-7 快照设计 ▶

ShuttlecockSnapshot 不可变结构体：FrameIndex、XZ、Y、Vxz、Vy、Phase、LastValidFlyingFrame、LandingXZ、IsInBounds。

ShuttlecockEntity : ISnapshotable<ShuttlecockSnapshot> 内部持有可变 ShuttlecockState，负责 TakeSnapshot / RestoreSnapshot 生命周期。
