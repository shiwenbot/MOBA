## 两个缺陷的由来

2026-08-05 排查「哈希对账会不会产生持续的错误失配」时，通读 `StateHasher` 与两侧快照构建通路发现的。

**先说一个不是问题的点**：集合顺序已经防住了。服务端 `FrameSyncPhysicsWorld.cs:155,164` 排 bodies 和 contacts，客户端 `BattleClientController.cs:691-692` 排 players 和 bodies，两侧同一个 comparer；玩家列表服务端走 `BuildSortedPlayerBuffer`。FNV 顺序敏感，但排序保证了输入序列一致。**不要再去查顺序问题。**

真正的两个缺陷：

### B1：增量 baseline 遇丢包永久分叉（真 bug）

属性和 Buff 都有。服务端发完快照**无条件**更新自己的 baseline，等于断言「客户端收到了」；客户端丢包时 `ConvertSnapshot` 根本不执行，baseline 完全没更新。两份 baseline 一旦分叉**永不收敛**，之后每帧增量都基于错误前提计算。

关键认知：**diff/merge 代码是完全共享的**（`PlayerAttributeSync.cs` 在 GameShared，服务端 `Entity.csproj:24` 链接编译），分叉的是各自持有的**可变 baseline 状态**。这不是「双端实现不一致」，共享代码解决不了——baseline 天生是两个进程的两份内存。

哈希失配是这个 bug 的**症状**，不是原因。

### B2：物理体四字段是客户端编造的（隐患）

`Rotation / AngularVelocity / IsAwake / IsEnabled` 协议里没有，客户端 `BattleClientController.cs:673-682` 写死成 `Zero / Zero / true / true`，而服务端哈希混入了真实值（`StateHasher.cs:67-91`）。

现在对得上纯属巧合，靠服务端恰好满足四条不变量。任一条被破坏（加朝向、睡眠、昏迷、投射物 body），每客户端每次上报全部失配，且客户端物理世界是**真的错**——回滚重放会从错误基准出发。

## 执行顺序与理由

**B1 先修**。它是真 bug，影响实际体验（血量显示错、Buff 冻结），弱网测试必然踩到。

**B2 后修**。当前能对上，且改 proto 工作量更大。

两者相互独立：B2 的四个字段协议里根本不存在，B1 的周期性全量传不了它们。

## 一个已作废的顾虑

早期讨论提过「wire type 变化要求 CS 双端同时发布，不能滚动升级」。**这条不成立，已删除**：`GameServer/Tools/ProtocolExportTool/Run.bat` 一次导出两端代码（服务端 `Entity/Generate/NetworkProtocol/OuterMessage.cs` + 客户端 `GameProto/Generate/NetworkProtoco/OuterMessage.cs`），同一份 proto 同一次生成，改完一起编译，**版本错配在物理上不可能发生**。

因此 B2 不需要兼容性章节。字段取反（`IsAsleep`/`IsDisabled`）的理由**只剩带宽**，与兼容性无关。

唯一将来要留意的场景：`GameProto` 在 HybridCLR 热更程序集里，若以后客户端热更包独立于服务端发布，才会出现版本错配。届时取反的写法反而是保险的（缺字段 → `false` → `IsAwake = !false = true`，恰好还原常态）。现在不用管。

按 `CLAUDE.md` 的计划编写规范，B1、B2 各自的实现步骤里都必须包含测试场景代码，并产出验收指南到：

- `Tools/AutomationAcceptance/属性与Buff增量恢复-验收测试指南-20260805.md`
- `Tools/AutomationAcceptance/物理体字段协议化-验收测试指南-20260805.md`
