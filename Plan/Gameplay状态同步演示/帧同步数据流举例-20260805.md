# 帧同步数据流举例：一次「按下 D 键」的完整旅程

> 配套 [帧同步代码导读-20260805.md](帧同步代码导读-20260805.md)。导读给的是读什么，本文给的是这些文件怎么串起来的。
> 例子里的所有数字都来自代码实际常量，可自洽验算。

## 一句话总览

客户端**跑在服务端前面**若干帧，先自己算（预测）并把输入按帧号寄给服务端；服务端到点了才执行那一帧并广播权威结果；客户端拿到权威结果后**倒带回那一帧、重新推演到当前**。整套机制的坐标系是同一个全局逻辑帧号。

## 场景设定

参数全部取自 `InputBufferTuning.cs` 与 `TickAccumulator.cs`：

| 量 | 值 | 出处 |
|---|---|---|
| 逻辑帧率 | 30Hz，`dt = 1/30` 秒固定 | `TickAccumulator.DefaultFixedDeltaTime` |
| RTT | 133ms（4 帧），单程 2 帧 | 例子设定 |
| `_baselineLeadFrames` | 5 = 抖动缓冲 2 + 发送安全 1 + `ceil(RTT/2/33.3)` 2 | `RefreshBaselineLeadFrames` `BattleSimulation.cs:589` |
| `_leadFrames` | **8**（闭环反馈从 5 抬上来的，baseline 只是下限） | `UpdateLeadFramesFromAcceptedInput` `:606` |
| 服务端输入缓冲健康区 | `[4, 6]` 帧 | `MinAcceptedInputBufferFrames` / `Max...` |
| 未来帧硬上限 | `LastFrameIndex + 24` 拒收 | `MaxFutureInputFrames` |

**此刻状态**：客户端本地帧 106，服务端权威帧 100（客户端领先 6 帧的墙钟差）。玩家按下 D 键，`dx = 1, dy = 0`。

## 完整时间线

### 第 1 幕：客户端本地帧 106，采集与发送

入口 `BattleClientController.Tick` (`:195`)，注意这两步的顺序是硬约束：

```
_networkGate.PumpDownlink(nowMs);        // ← 先放行下行（:198）
_simulation.Tick(106, dt, dx=1, dy=0);   // ← 再跑逻辑（:225）
_networkGate.PumpUplink(nowMs);          // ← 最后放行上行（:226）
```

> 上行 Pump 必须在 `Tick` **之后**。若放前面，零延迟配置下也会凭空多出一帧偏差。

进入 `BattleSimulation.Tick` (`:204`)，按序做四件事：

1. **存输入历史** `SaveInputHistory(106, dx, dy)` (`:217`) → `_inputHistory[106]`。这份历史是回滚重放的燃料，容量 128 帧。
2. **发送输入** `_onSendInput(106, ++_inputSeq, dx, dy)` (`:220`) → `C2B_PlayerInput { FrameIndex=106, DxRaw=4294967296, DyRaw=0 }`。

   `DxRaw` 是 `Fixed64.m_rawValue`，Q32.32 定点，`1.0` 的原始位值就是 `2^32 = 4294967296`。**协议里传的是这个整数，不是 float** —— 这是 S3 修掉的精度地基（`SendInputCommand` `BattleClientController.cs:908`）。
3. **消化排队的权威快照** `ApplyPendingServerSnapshot` (`:222`) —— 本幕暂无，见第 6 幕。
4. **本地预测推进** `AdvancePredictionTo(106, dt)` (`:228`) → `ApplyLocalPrediction` (`:751`)：

   ```
   MoveSystem.Apply(worldState, self, dx, dy, dt);   // 只动自己
   _worldState.PhysicsWorld.Step(dt);                 // 手写定点物理，全场
   SyncAllPlayersFromPhysics();
   SaveSelfPrediction(106, self);                     // 存进 _selfPredictions[106]
   ```

   **关键**：只有自己的输入被预测。远端玩家的位置停在上一次权威快照，客户端不替他们猜输入。这是后面产生 mismatch 的根源，也是刻意的设计。

### 第 2 幕：网络传输（2 帧）

`C2B_PlayerInput` 经 Fantasy 的 KCP 通道上行。若开了弱网注入，`BattleNetworkGate` 在这里按种子决定延迟/丢弃（`NetworkConditionSimulator`）。

### 第 3 幕：服务端收到 —— 但不执行

服务端此刻在帧 102。`C2B_PlayerInputHandler` (`:10`) → `BattleComponent.SubmitInput` (`:82`) → `BattleLogic.SubmitInput` (`:105`)：

```
if (_hasProcessedFrame && frameIndex <= LastFrameIndex) → LateInputDrop（迟到，丢）
if (frameIndex > LastFrameIndex + 24)                   → FutureInputReject（太超前，拒）
否则 → _pendingInputsByPlayerId[playerId][106] = input   // 排队等到点
```

106 落在 `(102, 126]` 之间，收下入队。同时记 `_latestAcceptedInputFrameByPlayerId[1] = 106`。

**服务端输入缓冲深度 = 106 - 102 = 4 帧**，正好踩在健康区下沿。这个数字稍后会随快照回传给客户端做闭环。

### 第 4 幕：服务端权威帧 106 —— 到点执行

`ServerTickDriver.TickOnce` (`:44`) 驱动 `BattleComponent.Tick` (`:112`) → `BattleLogic.Tick` (`:177`)。一帧内的严格顺序：

```
DeterminismRules.AssertFixedDt(fixedDt);   // dt 必须逐位等于 1/30，否则抛异常
BuildSortedPlayerBuffer();                 // 按 playerId 排序 ← 确定性要求，遍历顺序不能靠字典
QueueSkillRequests / SkillGraph.Step / ProcessBuffCommands
foreach 玩家:
    取 _pendingInputs[106]，取到就消费；取不到就复用上一帧输入（ReusedInputCount++）
    _physicsWorld.SetBodyMovementInput(...)
_physicsWorld.Step(fixedDt);               // 与客户端同一份 FrameSyncPhysicsWorld 代码
SyncPlayerStatesFromPhysics(); RecalculateNumericStates(); ApplyBuffTicks(106);
_authoritativeHashHistory.Save(106, StateHasher.Hash(...));   // ← S3 的对账基准
OnBroadcast?.Invoke(snapshot);
```

**缺帧复用上一帧输入**，不是补零 —— 丢一个输入包不会让角色抽一下停住。

### 第 5 幕：服务端广播

`BattleComponent.BroadcastSnapshot` (`:153`) 为**每个 session 单独构造**一条 `S2C_FrameSnapshot`（因为脏同步基线是 per-observer 的）：

```
XRaw = player.X.m_rawValue,  YRaw = player.Y.m_rawValue,     // int64 原始位值
LatestAcceptedInputFrame = 110,                              // ← 闭环控制的反馈量
AttributeDirtyMask = 只发变了的属性,                          // 脏同步
ActiveBuffs = 增量或全量（IsBuffFullSync 标记）
```

`LatestAcceptedInputFrame` 为什么是 110 而不是 106：服务端跑到帧 106 时，客户端已经在本地帧 112 了，其中帧 110 之前的输入都已抵达。

### 第 6 幕：客户端收到 —— 此时本地已在帧 114

`OnFrameSnapshot` (`:451`)，两步顺序又是硬约束：

```
if (!_networkGate.TryAcceptSnapshotMessage(nowMs)) return;     // ← 丢包判定必须在前（:451）
BattleWorldSnapshot s = ConvertSnapshot(snapshot, out uint accepted);  // ← 转换在后（:457）
_networkGate.EnqueueConvertedSnapshot(...);
```

> 丢包判定必须在 `ConvertSnapshot` **之前**。`ConvertSnapshot` 会把增量合并进基线（`PlayerAttributeSync.Merge`），一旦合并过再丢，基线已经被污染，就测不出脏同步的丢包缺陷了。

`ConvertSnapshot` (`:641`) 做位精确还原：`Fixed64.FromRaw(player.XRaw)`，并把排序重做一遍（`Array.Sort`）保证与服务端遍历顺序一致。

此刻 `_lastAppliedFrame` 从 105 → 106，而 `targetFrame = 106 + 8 = 114` = 当前本地帧。**稳态闭合**。

### 第 7 幕：对账

`CheckConsistency` (`:400`) 把「帧 106 的权威自己」与「帧 106 的预测自己」逐位比：

```
matched = prediction.X.m_rawValue == authoritativeSelf.X.m_rawValue
       && prediction.Y.m_rawValue == authoritativeSelf.Y.m_rawValue
       && ArePlayerSnapshotsEquivalent(...);
```

**严格相等，没有 epsilon**。S2 全定点化之后浮点噪声不存在了，任何差异都是真失同步 —— 这也是 `#6`（epsilon 豁免）被作废的原因。

### 第 8 幕：分叉

`ReconcileAuthoritativeSnapshot` (`:482`) 不管一致与否都跑同一条路：

```
_authoritativeSnapshots.Save(106, snapshot);      // S3 哈希上报依赖它
ApplyAuthoritativeSnapshot(snapshot);             // 状态硬置为权威值，_lastPredictedFrame 回到 106
DiscardPredictionsAtOrAfter(106);
AdvancePredictionTo(114, dt);                     // 用 _inputHistory 重放 107..114
if (logRollback) CapturePredictionErrorAfterReconciliation();   // S1 平滑，仅 mismatch 时重设基线
```

**一致时（`_hits++`）**：照样倒带 + 重放 8 帧，只是不打日志不计数。重放结果与原预测逐位相同，玩家无感。

**不一致时（`_misses++`）**：比如远端玩家撞了过来 —— 客户端没预测他的输入，所以撞击时机算错了。此时
- 打印字段级 diff（位置/属性/Buff 都在日志里，`:429`）
- `_rollbackCount++`、记录 `replayFrames` 与耗时
- `PredictionErrorSmoother.SetOffset` 记下「渲染位置 - 权威位置」的差值，在 `SmoothingDurationSeconds = 0.12s` 内衰减掉（S1）。**逻辑状态立刻跳到权威值，只有表现层在平滑**，超过 `MaxSmoothingDistance = 6.0` 才硬跳。

另外每 30 帧一次，`SendHashReportIfNeeded` (`:554`) 把 `_lastAppliedFrame` 那帧的**权威快照**哈希上报，服务端 `TryCompareReportedHash` (`BattleLogic.cs:257`) 与自己的历史比。注意哈希对账验的是「proto 往返 + 增量重建是否无损」，**不是**「预测准不准」——后者看 `consistencyMisses`。

## 五个关键洞察

1. **回滚重放是常态，不是异常。** 每次收到快照都倒带重演，一致与否只影响日志。S6（一致时跳过重放）要省的就是这里的 CPU，但不能整体 `return` —— 开头那三行有 S1/S3 在依赖。
2. **帧号是唯一坐标系。** 输入带帧号、快照带帧号、哈希带帧号、预测缓存以帧号为键。客户端本地帧 = `_lastAppliedFrame + _leadFrames`，不是独立时钟。
3. **`_leadFrames` 是双环控制。** 前馈项从 RTT 算下限（`RefreshBaselineLeadFrames`），反馈项盯服务端输入缓冲深度（`UpdateLeadFramesFromAcceptedInput`）把它抬到 8。**前馈用的 RTT 是客户端自算的**（`_rttEmaMs`，客户端时钟，服务端无从校验）—— 这正是 S5 要换掉的数据源，不是遗漏。
4. **客户端只预测自己。** 远端玩家冻在上次权威位置。所有涉及他人的交互（撞击击退）都是权威裁决 + 平滑吸收，这是刻意选择，因为对手位置在本地是过去时。
5. **确定性靠三件事撑住**：`Fixed64` 全定点无浮点、`dt` 逐位断言、遍历顺序显式排序。少任何一条双端就会分叉。

## 数据形态变换链

```
Unity Input (float 1.0)
  → (Fixed64)dx                      客户端边界唯一一次 float→定点
  → dx.m_rawValue = 4294967296       int64
  → C2B_PlayerInput.DxRaw            proto int64，无损
  → Fixed64.FromRaw(dxRaw)           服务端还原，逐位相同
  → 物理积分（全定点）
  → player.X.m_rawValue              int64
  → S2C_FrameSnapshot.XRaw           proto int64，无损
  → Fixed64.FromRaw(XRaw)            客户端还原，逐位相同
  → (float)player.X                  仅渲染时降精度，不回流逻辑
```
