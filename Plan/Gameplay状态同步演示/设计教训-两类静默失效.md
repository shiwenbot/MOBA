# 设计教训：两类静默失效

> 两个真实案例，共同的失效模式是**「全绿但系统没在做事」**。
> 面试讲料，也是新增校验层与新增测试前的检查清单。

「静默失效」指：系统完整、自洽、有测试、测试全通过，**但它实际不产生任何作用**，而且没有任何信号会提示这件事。

它比崩溃危险，因为崩溃会被发现。

## 第一类：判据绕过了真实区间

**新增一层校验，但它的判定区间与既有约束的交集为空，于是永不触发。**

### 案例

服务端对输入帧号有两道既有硬闸：

```
frameIndex <= LastFrameIndex                    → 丢弃
frameIndex >  LastFrameIndex + MaxFutureInputFrames(24)  → 拒收
```

即**既有接受区间是 `observedLead ∈ [1, 24]`**。

要在其之上加一层「用服务端实测 RTT 反推合理超前区间」的校验。上界锚在 `MaxLeadFrames(20)`，算出可疑区间：

```
判可疑：lead < −3  或  lead > 27
可接受：lead ∈ [1, 24]
交集：  空
```

**任何被判可疑的输入都已经被既有闸拒掉了。** 后果是告警模式与拒收模式对 gameplay 完全等价，整层校验是装饰品。

### 根因是量纲混淆

`MaxLeadFrames` 是 `clientLead` 的顶 —— 客户端**发出时**的超前量。
`observedLead` 是输入**到达服务端时**的超前量。

两者相差约 `rtt/2`。闭环控制真正调节的是后者，稳态目标是 `[4, 6]`，与 RTT 无关。拿前者当后者的上界锚点，量纲就错了。

### 验证步骤也是空的

原计划想用「把 `MaxLeadFrames` 从 20 调到 40」来验证检出能力。但那样 `observedLead` 会冲出 24，**直接被既有的 `FutureInputReject` 拦掉，根本不进新校验的可疑分支**。

**用一个空的验证去验证一个空的机制，两层都会显示通过。**

### 教训

1. **新增一层校验前，先把既有约束的接受区间算出来**，确认新判据与它有非空交集。
2. **判据的锚点必须与被判据的量同量纲。** 「发出时」与「到达时」是两个量。
3. **把非空性做成构造期断言**，而不是靠人记住。参数被调宽到让检出区归零时，构造应该抛异常，不该静默退化成装饰。
4. **验证手段本身也要验证。** 问一句：如果被测机制完全没实现，我这个验证步骤会不会照样通过？

## 第二类：测试绕过了真实路径

**修复是对的，但测试从未执行过被修复的那条路径，所以「全绿」不构成任何证据。**

### 案例

快照原来用 `float` 传 `Fixed64`，往返丢约 13 位精度，严格相等的哈希对账几乎恒失配。修法是 proto 全传 `m_rawValue`（`int64`）。**修复本身正确且已核实。**

但无头测试完全绕过序列化：

```
生产路径：
  BattleLogic.Tick → OnBroadcast → BattleComponent.BroadcastSnapshot
    → 逐字段填 S2C_FrameSnapshot（含 m_rawValue 转换）→ session.Send → KCP 序列化
    → 客户端 ConvertSnapshot → FromRaw → RestoreSnapshot

无头路径（TestRunner.cs:1057-1063）：
  BattleLogic.Tick → OnBroadcast → SimulatedClient.ApplySnapshot
    → WorldState.RestoreSnapshot(snapshot.ToBattleWorldSnapshot())
```

无头路径推的是**内存里的结构体**，`ToBattleWorldSnapshot()` 是纯内存转换。**全程零序列化、零 proto、零 `m_rawValue` 转换。**

于是「37 条用例全绿」证明的是**进程内确定性自洽**，不能证明**proto 往返位精确**。而后者才是「确定性 + 位精确和解」这条叙事的根基。

### 修法：改通路，不是加用例

直觉是「补一条走真 proto 的用例」。**这个修法本身就是同一个失效模式的实例** —— 它只守住今天这几个字段。下次给快照加字段（击退要加速度/状态位），盲区立刻回来，而且照样全绿。

正确修法是让测试通路**默认过序列化**：序列化 → 反序列化 → 走与客户端同一份转换逻辑。改完之后**所有**用例都在验证 proto 往返，新增字段自动被覆盖。

**这是把测试有效性做进结构里，而不是再加一条会过期的断言。**

关键约束：转换代码必须与生产共用。**如果在测试 harness 里重写一份转换逻辑，这件事就白做了** —— 那验证的是 harness 自己写的那份。

### 教训

1. **「测试全绿」只在测试真的执行了目标路径时才是证据。** 先问：这条路径上的代码，有哪一行是我的测试从未执行过的？
2. **修盲区要修结构，不要修实例。** 加一条用例守的是当前字段集合，改通路守的是所有将来的字段。
3. **生产与测试必须调同一份代码。** 接线层不在覆盖里，就把可判断的逻辑挪到覆盖得到的地方，让接线层只剩调用顺序。
4. **基线不变本身可以是断言。** 改通路后哈希基线一字未变，这才是「往返位精确」的机械证明。反之若基线变了，那是抓到真 bug，不要改基线去迁就。

## 共同点

| | 第一类 | 第二类 |
|---|---|---|
| 表现 | 机制完整、有测试、全绿 | 修复正确、有测试、全绿 |
| 实际 | 判定分支永不进入 | 被修复的代码路径从未执行 |
| 信号 | 无 | 无 |
| 检查方法 | 算出既有约束区间，验证交集非空 | 列出目标路径，验证测试真的走过 |
| 结构性防线 | 构造期断言检出区非空 | 测试通路默认过真实路径 |

**两类都是「缺少一个会失败的场景」**：第一类缺一个能同时被既有闸接受、又被新判据拒绝的输入；第二类缺一条真的经过序列化的快照。

**通用检查**：如果我要防的东西现在就发生，我的系统会不会出声？出声的是哪一行代码？我的测试执行过那一行吗？

## 讲解版本

面试可用。两个案例成对讲比单讲强，因为它们证明的是同一种判断力用在两个不同层面。

> 我修过一个精度 bug：快照用 float 传定点数，往返丢 13 位，哈希对账恒失配。但更值得说的是修完之后我发现的事——我的 37 条用例全绿，而它们根本没走过 proto 那条路，无头测试里客户端和服务端同进程，快照是内存结构体直传的。所以「全绿」证明的是进程内自洽，不是端到端位精确。
>
> 我的处理不是加一条走 proto 的用例，那只守住当时那几个字段。我改的是测试通路本身，让所有用例默认过一遍序列化。改完基线哈希一字未变，这才是机械证明。
>
> 同一个失效模式我还在另一处踩到过：给输入帧号加一层 RTT 反推的反作弊校验，设计到一半发现我算出的可疑区间和既有硬闸的接受区间交集是空的——任何被判可疑的输入都已经被既有闸拒了。那套机制会完整、自洽、有测试，而且永不触发。根因是量纲混淆，我拿「发出时超前量」的上限去当「到达时超前量」的锚点。
>
> 两件事的共同点是「全绿但系统没在做事」，而且都没有任何信号。所以我现在加校验层会先算既有约束的接受区间、把非空性写成构造期断言；加测试会先问这条路径上有哪一行是测试从未执行过的。
