# Gameplay 状态同步演示 Timeline

## Context

本分支面向 Gameplay 岗求职展示，不再以“弹珠技术演示”或“完整技能系统”为主线。当前目标是制作一个极简俯视角 Gameplay 状态同步沙盒：用小球角色、小房间、Dash、体力、Recover 和占点交互，展示弱网条件下的按帧输入、客户端预测、服务端权威校验、不一致诊断与回滚重播。

本 demo 的价值不在于美术复杂度，而在于面试官能清晰看见：

1. 输入如何绑定到 `FrameIndex`。
2. 客户端预测了哪些 Gameplay 状态。
3. 服务端如何在同一帧语义下消费命令并下发权威快照。
4. 客户端如何对比差异、回滚到权威帧并重播到当前预测帧。
5. 弱网下系统如何保持操作手感和最终状态一致。

## 产品定位

- **目标受众**：Gameplay / Unity 战斗 / 网络同步相关岗位面试官。
- **展示形态**：本地 client/server + 弱网工具；优先可解释，不优先公网部署。
- **场景形态**：俯视角小房间 + 小球角色 + 目标区 + 调试可视化。
- **核心卖点**：Gameplay 状态帧语义、预测、权威修正、rollback replay 和诊断能力。

## 非目标

- 不实现完整技能系统。
- 不实现复杂 Buff、伤害、命中、目标选择或战斗结算。
- 不追求完整商业玩法循环。
- 不优先接入复杂动画、角色模型或大量美术资源。
- 不把不可控 Unity 物理结果作为核心一致性来源。

## 技术约束

1. 所有客户端可预测状态变化都必须是按帧命令，命令携带 `FrameIndex`。
2. 客户端预测和服务端权威必须共享同一全局逻辑帧语义。
3. 进入预测链路的状态必须纳入快照、哈希、一致性检查、历史缓存和回滚重播。
4. 不适合预测的结果走服务端权威快照，不能伪装成预测命令。
5. mismatch 日志必须打印真实差异域，例如位置、速度、体力、状态机、占点进度。

### P1：俯视小球移动最小闭环

- **目标**：建立最小可玩的俯视角房间和小球移动同步链路。
- **范围**：
  - 小房间边界。
  - 小球位置、速度、朝向或移动方向。
  - WASD 输入按帧上行。
  - 服务端 30Hz 权威推进。
  - 客户端本地预测移动。
  - 服务端定期下发权威快照。
- **非目标**：
  - 不做 Dash。
  - 不做占点。
  - 不做复杂 UI。
- **验证方式**：
  - 无弱网时客户端预测与服务端权威稳定一致。
  - 小球不能穿出房间边界。
  - 状态 hash 覆盖位置和基础运动状态。
- **完成标准**：
  - 单客户端能在房间内移动。
  - 服务端快照能校正客户端状态。
  - 日志能显示当前帧、权威帧、预测帧和状态 hash。

### P2：Dash / 体力 / Recover 可预测行为

- **目标**：让 demo 从“同步 Transform”升级为“同步 Gameplay 行为状态”。
- **范围**：
  - Shift Dash 输入，作为 `PredictableAction`，不命名为技能。
  - Dash 消耗体力。
  - Dash 后进入 Recover 状态，Recover 期间禁止再次 Dash。
  - 体力恢复按逻辑帧推进。
  - 体力、Dash 状态、Recover 剩余帧进入快照、哈希、diff 和回滚。
- **非目标**：
  - 不做 SkillGraph。
  - 不做技能表现资源。
  - 不做伤害、命中或 Buff。
- **验证方式**：
  - 客户端在输入帧预测 Dash 和体力消耗。
  - 服务端在同一 `FrameIndex` 执行 Dash。
  - 故意制造错帧扣体力时，mismatch 能打印体力和状态机差异。
- **完成标准**：
  - Dash 手感在弱网下不等待服务端确认。
  - 回滚后位置、体力、状态机一致。
  - 日志能明确区分 `PositionMismatch`、`StaminaMismatch`、`StateMismatch`。

### P3：占点交互权威结算

- **目标**：加入一个服务端权威的轻量 Gameplay 目标，让 demo 有可展示的玩法闭环。
- **范围**：
  - 房间内放置一个目标区。
  - 小球进入目标区后开始占点。
  - 占点进度由服务端权威推进。
  - 客户端可以显示预测进入区域的即时反馈，但最终进度以权威快照为准。
  - 占点进度进入快照、哈希和 diff。
- **非目标**：
  - 不做多人争夺规则。
  - 不做复杂胜负流程。
  - 不做 UI 大屏结算。
- **验证方式**：
  - 弱网下进出目标区，最终占点进度与服务端一致。
  - 当客户端预测位置与权威位置跨越区域边界不一致时，diff 能打印 `CaptureProgressMismatch` 或区域状态差异。
- **完成标准**：
  - 玩家能通过移动和 Dash 快速进入目标区。
  - 占点进度能在回滚后正确重播。
  - demo 有明确的“操作目标”，不只是空房间移动。

### P4：弱网与回滚可视化

- **目标**：把同步系统的技术价值可视化，降低面试讲解成本。
- **范围**：
  - 调试面板：
    - `ServerFrame`
    - `ClientFrame`
    - `AuthoritativeFrame`
    - `RTT`
    - `TargetLeadFrames`
    - `RollbackCount`
    - `LastRollbackFrame`
    - `StateHash`
    - `LastMismatchField`
  - Ghost 显示：
    - 实心小球表示客户端预测位置。
    - 半透明 ghost 表示最近服务端权威位置。
  - 轨迹显示：
    - 最近若干帧预测轨迹。
    - 最近一次权威修正轨迹。
  - 弱网演示参数说明：
    - 延迟。
    - 抖动。
    - 丢包。
- **非目标**：
  - 不做复杂性能监控平台。
  - 不做生产级网络诊断系统。
- **验证方式**：
  - 使用本地弱网工具施加延迟/抖动/丢包。
  - 录制一次预测偏差、mismatch、rollback、replay、状态收敛的完整过程。
- **完成标准**：
  - 不看日志也能从画面理解预测位置和权威位置差异。
  - 看日志能定位真实不一致字段。
  - 回滚次数和回滚帧范围可见。

### P5：求职展示打磨

- **目标**：把技术 demo 包装成可投递、可讲解、可复现的作品。
- **范围**：
  - README 增加运行方式和演示脚本。
  - 增加 60-90 秒录屏脚本。
  - 整理关键代码入口说明。
  - 保留一组无头测试命令。
  - 准备面试讲解要点。
- **非目标**：
  - 不追求完整安装器。
  - 不做大量关卡内容。
- **验证方式**：
  - 新环境能按 README 跑起服务端和客户端。
  - 演示视频能覆盖移动、Dash、占点、弱网、rollback 可视化。
  - 自动化测试能覆盖核心状态一致性。
- **完成标准**：
  - 项目首页能在 1 分钟内说明 demo 价值。
  - 代码入口、架构边界和运行方式清楚。
  - 面试时能围绕 Gameplay 状态同步讲解，而不是被追问“为什么只是小球移动”。

## 推荐开发顺序

1. 先跑通 P1：小球移动和服务端权威快照。
2. 再做 P2：Dash、体力、Recover 进入预测与回滚链路。
3. 接着做 P3：占点交互，让 demo 有 Gameplay 目标。
4. 然后做 P4：弱网、ghost、轨迹、调试面板。
5. 最后做 P5：README、录屏脚本、验收命令和求职讲解。

## 面试讲解主线

1. 为什么选择极简俯视小球：降低表现噪声，突出 Gameplay 状态同步。
2. 哪些状态允许预测：移动、Dash、体力消耗、Recover。
3. 哪些状态保持权威：占点进度、最终位置校正、跨区域判定结果。
4. 如何避免伪 mismatch：客户端和服务端共享同一 `FrameIndex` 语义。
5. 如何定位问题：状态 hash + 字段级 diff + rollback 可视化。
6. 如何扩展到技能：Dash 已经是 `PredictableAction` 模型，后续可扩展为技能输入，但当前 demo 不把完整技能系统作为范围。
