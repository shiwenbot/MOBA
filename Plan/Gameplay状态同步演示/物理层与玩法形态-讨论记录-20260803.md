# 物理层与玩法形态 讨论记录

- 日期：2026-08-03
- 分支：`feature/gameplay-sync-sandbox`
- 基线提交：`12efa583`
- 状态：**决策已确认**（2026-08-03），见第四节

## 讨论起因

P1 完成后出现两个悬空问题，且互相纠缠：

1. 物理层定位不清：Box2D 内部是 float，逻辑层是 Fixed64，混合架构是否合理。
2. Demo 玩法形态未定：不清楚该展示什么才能证明 Gameplay 同步能力。

结论：**物理是玩法的下游**，玩法未定时讨论物理选型没有答案。故先定玩法形态，再回推物理需求。

## 一、核实发现：Box2D 实际只承担浮点积分

逐行读 `GameShared/FrameSync/Battle/FrameSyncPhysicsWorld.cs`（687 行，全项目唯一引用 Box2DSharp 的文件）后核实：

### 证据链

- `:91` 是全文唯一 `CreateBody`，只创建玩家圆形 body；World 内无墙体、无障碍、无关节
- `:107` 所有 fixture 设 `Filter.GroupIndex = -1`；按 Box2D 过滤规则，两 fixture 的 GroupIndex 相同且为负则不碰撞
- 全场只有玩家 → **任何 pair 都不产生 Contact** → `_contactListener`（`:614`）永不触发 → `_physicsContacts` 恒为空字典
- `BuildMergedContacts`（`:298`）每帧在拿一个空 dict 与手写的 `_occupancyContacts` 做合并
- 墙体边界靠手写 `ClampPlayersToRoom()`（`:178`）
- 玩家互推靠手写 `ResolvePlayerOccupancy()`（`:332`）
- 接触点靠手写 `RebuildOccupancyContacts()`（`:404`）

结论：`_world.Step(dt, 12, 8)`（`:171`）的实际效果等价于 `pos += vel * dt`。求解器完全空转。

### 已承担的代价

| 代价 | 位置 | 说明 |
|------|------|------|
| 定点链路中间是浮点 | `CaptureBodySnapshot :288` | 位置每帧 `Fixed64 → float → Fixed64` 往返，积分本身由 float 完成 |
| 回滚重建整个物理世界 | `RestoreSnapshot :258` | 先 `ClearBodies()` 再逐个重建 body |
| 反射写私有属性 | `:571` `:576` | `Body.LinearVelocity` / `AngularVelocity` setter 不可公开访问，Box2DSharp 升级即可能断 |
| pair 顺序隐患潜伏 | — | 一旦加入真实墙体 body 即激活 |
| WarmStarting 关闭无实效 | `:47` | 注释推理正确，但因无 Contact 而未产生作用 |

### 问题重构

- 现有文档（本目录两份 `*-2026-08-02.html`）描述为「接了 Box2D，但只用了一半」——**低估**，实际只用了一行
- 当前不是「逻辑定点 + 物理浮点」的合理分层，而是**浮点占据最核心的积分步骤、定点在外围做装饰**
- 这是两者最差的组合：拿不到定点的 bit-exact 保证，又背着物理引擎的全部复杂度

## 二、玩法形态

### 核心判断

- 移动预测是入场券，不是加分项——做过同步的人都实现过 WASD 预测
- 可讲解的价值集中在**预测失败的那一刻**：预测行为被服务端否决怎么办、回滚时画面怎么不跳、怎么区分真失同步与浮点噪声
- Demo 的价值不在玩法数量，在于**能否制造一个清晰可见的预测失败并优雅恢复**

### 三个候选

| 方案 | 内容 | 评价 |
|------|------|------|
| ① Timeline 原样 | Dash + 体力 + Recover + 占点 | Dash 适合（离散、消耗资源、有状态机）；**占点建议砍掉**，本质是进度条，画面上看不出同步难点 |
| ② 移动 + Dash + 撞击击退 | 击退为服务端权威、故意不预测 | 击退是玩家**之间**的交互，同步真正变难处；可复用现有 occupancy 代码 |
| ③ 极简玩法 + 满配诊断 | 只保留移动，全力做可观测性 | 最快拿到「可观测性」卖点，但玩法单薄，易被追问 |

### 已采纳：① 去掉占点 + ②

| 元素 | 定位 | 讲解价值 |
|------|------|----------|
| 移动 | 预测 | 基础链路 |
| Dash + 体力 / Recover | 预测 | 离散行为 + 资源门禁，用于制造 mismatch |
| **撞击击退** | **故意不预测** | 说清「什么该预测、什么不该」，价值高于多做一个功能；与 Source 系通行做法一致（§4） |
| ghost / 轨迹 / 回滚计数 / hash / 字段 diff | 可观测 | 不看日志即可理解 |
| 延迟 / 抖动 / 丢包滑杆 | 可施压 | 允许他人当场把系统搞坏 |

目标演示场景：两客户端对撞，各自预测自身 Dash、**均不预测击退**，服务端裁决后两端同时被修正；左侧硬跳变、右侧平滑恢复，并排对比。

优点：无需新增美术资源，全部复用既有系统。

## 三、物理层选型

推荐方案的物理需求展开后只有三件事：

1. 圆在矩形房间内的边界约束
2. 圆与圆的分离
3. 一次瞬时冲量（击退）

三者均可在 `Fixed64` 内手写，代码量约 200 行，少于现有 occupancy 逻辑。

### 三个候选

| 方案 | 说明 | 风险 |
|------|------|------|
| **拿掉 Box2D，手写定点物理**（推荐） | 换来「逻辑层完全定点、跨端 bit-exact」这一当前说不出的主张 | 需一次性重写物理层与相关自测用例 |
| 暂不动，等玩法定了再说 | 当前架构能跑，P1 已验收通过 | 越晚拆越贵；期间无法主张定点确定性 |
| 保留 Box2D 但用满它 | 加真墙体 body、放开 GroupIndex、走求解器 | 激活 pair 顺序隐患；需先解决 `Contact.Manifold` 存不进快照的问题；工作量最大且方向不确定 |

### 对外表述的差异

- 弱：「我用了 Box2D」
- 强：「读完 Box2D 求解器与碰撞流程后发现，warm starting 的累积冲量存在 `Contact.Manifold` 的 internal 字段里，快照存不下、回滚恢复不了；pair 顺序也未规范化。对需要回滚的确定性系统，通用浮点求解器是负债。因此按需求手写定点的圆-矩形与圆-圆，只做需要的部分。」

后者只有真读过源码才说得出，且使分支内 14 个 Box2D 教材提交由「学习开销」转为「决策依据」。

**外部支撑**：Rocket League 面对同类问题时也弃用了引擎自带物理——Psyonix 为确定性网络物理把 Bullet 集成进 UE3，放弃 UE3 的 PhysX（见 §4.3）。「为了确定性去控制物理内核」是这条路线上的通行动作，区别只在于 Rocket League 需要完整刚体求解器故换成可控的 Bullet，而本项目的需求（圆-矩形 + 圆-圆 + 冲量）简单到可以直接手写定点。

### 保留 Box2D 的成立条件

仅当玩法需要堆叠、关节、复杂形状碰撞或 ragdoll 时成立。此时须同步放弃「定点保证确定性」的表述，改为「状态同步容忍非确定性，靠权威快照收敛」。弹珠方向已否决，该条件目前不成立。

## 四、同类游戏对照：玩家间物理同步怎么做

本节为决策 1「击退不预测」提供外部支撑。**结论：该选择与 Source 系游戏的通行做法一致，不是妥协。**

### 4.1 三条路线

| 路线 | 代表 | 玩家间碰撞处理 | 代价 |
|------|------|----------------|------|
| **回避** | LOL / Dota 2 | 纯服务端裁决，客户端不预测 | 靠点击式操作藏延迟；WASD 连续输入会粘滞 |
| **全预测** | Rocket League | 预测所有车（含他人），全部回滚 | 需严格确定性，为此换掉引擎自带物理 |
| **只预测自己** | Source / CS-GO 系 | 本地预测自己，远端插值到过去；玩家间交互走权威 | 交互双方处于两个时间线，是公认难点 |

**本项目属第三格**，与决策 1 的选择一致。

### 4.2 LOL 不能作为参考

Dota 2 官方表述（Valve 在 7.38 讨论输入延迟时）：**Dota 不做客户端预测，只做输入确认**——点击时立刻出现的绿色箭头就是那个「确认」，不是预测。

LOL 同理：点地面 → 请求上行 → 服务端算寻路与碰撞 → 下发结果。英雄间碰撞（`Unit collision` 及 ghosting 免疫）**完全在服务端裁决**，客户端只显示。

它能这么做的前提是 **MOBA 的输入粒度**：点击到抵达之间有数百毫秒的移动过程，80ms 往返延迟藏在里面看不出来。WASD 是每帧连续输入，同样延迟直接变成操作粘滞。

LOL 客户端设置里的 "Movement Prediction" **不是** Source 那种 rollback 预测，只是对远端单位做外插——玩家反馈「网络稳定时关掉更准」印证了这点，它是弱网补丁而非架构核心。

### 4.3 Rocket League 是真正对标的案例

「玩家之间有真实物理碰撞且必须预测」的公开案例——车会撞车，撞击结果直接决定胜负，且必须零延迟手感。

Jared Cone 在 GDC 2018《It IS Rocket Science! The Physics of Rocket League》讲的做法：

- **把 Bullet Physics 集成进 UE3**，专门为了确定性网络物理（同样输入必须产生同样结果）
- 弃用 UE3 自带的 PhysX，因为拿不到需要的确定性与控制权
- 客户端**预测整个物理世界，包括其他玩家的车**，不区分「我的物体」与「别人的物体」

第三条是它与本项目最大的差异。第一、二条与决策 2 同向：**为了确定性去控制物理内核**——Psyonix 换成可控的 Bullet，本项目场景简单到可以直接手写定点。

### 4.4 为什么第三格里"玩家互撞"最难

Unity Netcode 文档对这个难点的表述：

> 客户端拿到的不是"实时"信息，而是一段时间前（比如 200ms 前）的信息。这意味着本地玩家和远端玩家碰撞时，两边看到的位置根本不是同一时刻的。

即：**要预测的那个对手，本地只有他 100ms 前的位置**。预测几乎必错，错了就回滚，回滚就跳变。这是这类游戏普遍不预测玩家间推挤的根本原因。

### 4.5 反向印证：Overwatch 的"opting out"

Overwatch 走的是**默认预测一切（含投射物），只在必要时才不预测**（原文措辞 opting out only when necessary）。

这说明「**哪些不预测」本身是需要专门决策的设计工作**，不是遗漏。demo 里有一个明确标注"故意不预测"的元素，是加分项。

### 4.6 可直接用于讲解的表述

主线：

> 本地玩家的移动和 Dash 走预测，因为输入源在本地、可信。玩家间的击退不预测，因为对手的位置在我这里是过去时——预测一个我只知道 100ms 前状态的对象，期望值是负的。所以它走服务端权威，客户端只做误差平滑。这和 Source 引擎的取舍一致；Rocket League 选了另一条路——全量预测所有车，代价是把 Bullet 集成进引擎来换确定性。

被追问「为什么不像 Rocket League 全预测」时：

> Rocket League 能全预测，是因为它的物理是刚体驱动、输入到结果的映射相对连续，预测偏一点表现上还能接受。而本 demo 的击退是离散冲量，预测错了就是"该被撞开却没撞开"，回滚时的位置差远大于连续移动的误差——硬跳变会很明显。所以放在权威侧，用平滑吸收误差。

三个层次：**自己的选择 + 为什么 + 知道另一条路存在及其代价**。

### 4.7 本节的证据强度

| 结论 | 强度 | 依据 |
|------|------|------|
| Dota 2 不做客户端预测，只做输入确认 | 强 | Valve 7.38 输入延迟说明的转述 |
| LOL 单位碰撞存在 ghosting 免疫机制 | 强 | LOL Wiki `Unit collision` |
| Rocket League 为确定性网络物理把 Bullet 集成进 UE3 | 强 | Bullet 官网 + GDC 2018 讲座 + 多处二手报道一致 |
| Overwatch 默认预测一切、必要时才 opt out | 中 | GDC 2016 讲座的二手总结 |
| **LOL 服务端裁决碰撞、无 rollback 预测** | **弱（推断）** | **Riot 未公开网络架构技术文章**；由 Dota 2 官方表述 + LOL 可观测行为推断，非 Riot 一手声明 |
| Rocket League "预测所有车"的细节与 tick 率 | 弱 | 需看 GDC Vault 原视频确认 |

对外讲解时，弱强度项应表述为「据我了解 / 从行为推断」，不要说成厂商声明。

## 五、已确认决策

2026-08-03 确认，三项均采纳推荐方案：

- [x] **决策 1｜玩法形态**：采纳「移动 + Dash（体力/Recover）+ 撞击击退」，**砍掉占点**
- [x] **决策 2｜物理层**：**拿掉 Box2D**，改为手写定点物理（圆-矩形边界 + 圆-圆分离 + 冲量）
- [x] **决策 3｜文档修正**：修正两份 8-02 HTML 概览中的过时描述（见第六节）

### 决策 1 的连带影响

- Timeline 的 **P3（占点交互权威结算）取消**，不再作为阶段目标
- P2 范围调整为「Dash + 体力 + Recover + 撞击击退」，其中击退为**服务端权威、客户端不预测**（该选择与 Source 系通行做法一致，见 §4）
- `README.md` 第一阶段玩法闭环第 4 条（占点）需同步删除

### 决策 2 的连带影响

- `FrameSyncPhysicsWorld.cs` 整体重写，移除 `Box2DSharp` 依赖与全部反射 hack
- `PhysicsBodySnapshot` 字段可由 float 中转改为原生 `Fixed64` 存储
- `RestoreSnapshot` 不再需要销毁重建 body，退化为直接写回定点状态
- `PhysicsContactSnapshot` / `_physicsContacts` 空字典合并逻辑可删除
- `BattlePredictionSelfTestSuite` 中依赖物理层的用例需复核（成文时 19 个用例，含 `room-boundary-clamps-player`）
- 可新增跨端 bit-exact 验证用例，补上分析报告 §5.4「跨平台确定性证据不足」这一项

> **以上六项已于 2026-08-04 全部落地**（`9be6e989`）。`FrameSyncPhysicsWorld.cs` 687 → 102 行，bit-exact 用例为 `fixed-physics-bit-exact`，用例总数 19 → 25。

## 六、独立于上述决策的结论

**预测误差平滑排在第一个做**，无论玩法与物理如何选择：

- 当前回滚时位置硬跳变，无任何表现层平滑（对应分析报告 §5.2）
- 是唯一能立刻在画面上看见效果的改动（P1 完成后才具备此条件）
- 与 P4 的 ghost 可视化**共享同一份数据**，一次实现产出两个成果
- 落地要点：偏移量只作用于渲染层，不得写入 `BattleWorldState`，避免污染哈希与确定性
