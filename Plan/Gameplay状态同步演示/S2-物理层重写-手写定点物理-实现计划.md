## Context

决策依据是 [物理层与玩法形态-讨论记录-20260803.md](物理层与玩法形态-讨论记录-20260803.md) 决策 2（2026-08-03 确认）。核心事实：

`FrameSyncPhysicsWorld.cs`（687 行，全项目**唯一**引用 Box2DSharp 的文件）里，Box2D 求解器**完全空转**：

- `:107` 所有 fixture `Filter.GroupIndex = -1`。Box2D 规则是「GroupIndex 相同且为负 → 无条件不碰撞」
- 全场只有玩家 body，无墙体、无障碍、无关节 → **任何 pair 都不产生 Contact**
- 于是 `_contactListener`（`:614`）永不触发，`_physicsContacts`（`:34`）恒为空字典
- `BuildMergedContacts()`（`:298`）每帧拿这个空 dict 与手写的 `_occupancyContacts` 做合并

`_world.Step(dt, 12, 8)`（`:171`）的实际效果等价于 `pos += vel * dt`。真正干活的三处全是手写的：`ClampPlayersToRoom()`（`:178`）、`ResolvePlayerOccupancy()`（`:332`）、`RebuildOccupancyContacts()`（`:404`）。

**为此付出的代价**：

| 代价 | 位置 |
|------|------|
| 定点链路中间夹一段浮点 | `CaptureBodySnapshot`（`:282`）位置每帧 `Fixed64 → float → Fixed64` 往返，积分由 float 完成 |
| 回滚要销毁重建整个物理世界 | `RestoreSnapshot`（`:251`）先 `ClearBodies()` 再逐个 `EnsureBody` |
| 反射写私有属性 | `:569` `:574` —— `Body.LinearVelocity` / `AngularVelocity` 的 setter 不可公开访问，Box2DSharp 升级即可能断 |
| pair 顺序隐患潜伏 | 一旦加入真实墙体 body 即激活（见 `Box2D确定性分析/README.md`） |
| WarmStarting 关闭无实效 | `:47` 推理正确，但因无 Contact 而未产生作用 |

这是两者最差的组合：**拿不到定点的 bit-exact 保证，又背着物理引擎的全部复杂度**。

## 目标

1. 逻辑层**完全定点**，去掉积分路径上的 `Fixed64 → float → Fixed64` 往返。
2. 移除 `Box2DSharp` 依赖与全部反射 hack。
3. 获得当前说不出的对外主张：**跨端 bit-exact**。
4. 为 S7 的撞击击退准备好冲量入口。

## 非目标

- 不改玩法。本阶段是等价替换 + 精度提升，不加击退（那是 S7）。
- 不改快照结构的**语义**，只把 float 中转字段改为原生 `Fixed64`。
- 不改网络协议、不改哈希算法本身。
- 不做通用物理引擎。只做本 demo 需要的三件事。
- 不动 `PredictionErrorSmoother`（S1 的产物）。

## 物理需求只有三件事

讨论记录 §3 展开后确认，整个 demo 的物理需求是：

1. **圆在矩形房间内的边界约束** —— 现有 `ClampPlayersToRoom()` 已是纯手写，逻辑照搬
2. **圆与圆的分离** —— 现有 `ResolvePlayerOccupancy()` 已是纯手写，逻辑照搬
3. **一次瞬时冲量**（击退，S7 用） —— 本阶段只预留入口

三者都能在 `Fixed64` 内手写。

**规模预期（2026-08-03 review 修正）**：`687 行 → 400~500 行`，不是最初估的 250 行。原因是保留的核心逻辑本身就有约 265 行（occupancy 71 + 分离份额 46 + clamp 44 + contacts 30 + normal 24 + intent 18 + transform/input/normalize 32），这些是**换类型不是删除**，行数不缩水。确定能删的约 140 行：`ContactListener` 嵌套类 51、两个反射 `PropertyInfo` 及其存取方法约 20、`EnsureBody` 里 Box2D 的 `BodyDef`/`FixtureDef`/`CircleShape` 仪式约 35、`BuildMergedContacts` 合并逻辑约 15、`CaptureBodySnapshot` 的 float 转换约 10、usings 约 8。

**这个数字不作为验收标准**，只用于排期心理预期，别因行数落差误判进度。

## 核心设计

### 关键洞察：这不是「重写」，是「删掉中间层」

现有代码的三个手写函数已经是完整实现，只不过它们把位置读进 `Vector2`(float)、算完写回 Box2D body。改造方式是**把状态容器从 Box2D `Body` 换成自己的定点结构**，三个函数的算法逻辑几乎不变，只是类型从 `float`/`Vector2` 换成 `Fixed64`。

风险因此比「重写物理引擎」低得多。真正的新代码只有速度积分那一行。

### 状态容器

用一个 `struct` 存 body 状态，字段与 `PhysicsBodySnapshot` 一一对应（位置、旋转、线速度、角速度、IsAwake、IsEnabled），全部 `Fixed64`。用 `Dictionary<int, FixedPhysicsBody>` 替掉 `Dictionary<int, Body>`。

`RotationRadians` / `AngularVelocity` 保留但恒为零 —— 现有代码 `FixedRotation = true` 且从不施加扭矩，保留是为了**不改快照结构和哈希输入**。

### 接口完全不变

两个接口共 **9 个**方法签名一个都不动：`IPhysicsSnapshotProvider`（`IPhysicsSnapshotProvider.cs:7-9`）的 `TakeSnapshot` / `RestoreSnapshot`，加 `IPhysicsMovementWorld`（`:14-26`）的 `ClearBodies` / `EnsureBody` / `RemoveBody` / `SetBodyTransform` / `SetBodyMovementInput` / `Step` / `TryGetBodySnapshot`。

9 个方法的参数类型全是 `Fixed64` / `int` / `bool`，**不暴露任何 Box2D 类型**——这是本方案能安全落地的关键。调用方（`BattleWorldState`、`BattleSimulation:654`、`BattleLogic`）零改动。

### Step 的新流程

```
AssertFixedDt(dt)                    ← 保留
BuildSortedBodyBuffer()              ← 保留，确定性来源
逐 body：vel = pendingInput，pos += vel * dt   ← 新代码，替掉 _world.Step
ResolvePlayerOccupancy()             ← 算法照搬，类型换 Fixed64
ClampPlayersToRoom()                 ← 算法照搬，类型换 Fixed64
RebuildOccupancyContacts()           ← 算法照搬，类型换 Fixed64
```

积分顺序按 `_sortedBodyIdsBuffer`（已排序）遍历，与现有一致。

### 定点开方要用 FixedMath

occupancy 里三处用了 `MathF.Sqrt`（`:357` `:455` `:464`）。全部换成 `FixedMath.Sqrt`。项目里已有先例：`NormalizeInput()`（`:564`）就在用 `FixedMath.Sqrt`。

**这是本方案唯一可能改变数值结果的地方** —— 定点开方与 float 开方结果不同，所以哈希基线会变（见风险表）。

### RestoreSnapshot 大幅简化

现在的流程是「销毁全部 body → 逐个重建 → 写位置速度」。改造后退化为**直接写回定点状态**，无需销毁重建：

```
清空 body 字典与 contact 字典
逐 snapshot：字典[bodyId] = 定点状态（直接赋值，无类型转换）
逐 contact：写回 _occupancyContacts
```

这同时消除了「回滚重建物理世界」这项代价。

### 空 Contact 字典的合并逻辑可删

`_physicsContacts`（`:34`）、`ContactListener`（`:614`）、`BuildMergedContacts()`（`:298`）整套都可以删 —— 前者恒为空，后者每帧在与空字典做无意义合并。`TakeSnapshot()` 直接用 `_occupancyContacts` 排序输出即可。

删除后 `RemoveContactsForBody` 的双字典版本也简化为单字典。

### GameplayRoomSettings 的 float 量化要保留

`GameplayRoomSettings.cs:16-19` 的边界值是**故意**经过 float 量化的：

```csharp
public static readonly Fixed64 PlayerMaxX = (Fixed64)((float)RoomHalfWidth - (float)PlayerRadius);
```

注释写明「Quantize bounds from the same float geometry used by Box2D before entering Fixed64」。

**本阶段不要"顺手"把它改成纯定点减法**。理由：改了会让 `room-boundary-clamps-player` 的期望值变化，与物理重写的效果混在一起，排查时分不清是哪一处引起的。等 S2 验收通过、哈希基线重新记录后，可作为独立小改动处理。

### 击退入口预留

给接口加一个方法用于施加瞬时冲量（改变 body 线速度），本阶段**只加空实现或直接改速度的最简版本，不接玩法**。S7 再接。

之所以现在预留：S7 要做的击退需要这个入口，而那时物理层已定型，加接口方法比改结构便宜。

## 实现步骤

### Step 1：定点 body 结构

在 `GameShared/FrameSync/Battle/` 新建定点 body 的 `struct`。字段与 `PhysicsBodySnapshot` 对齐，全 `Fixed64`。

`GameShared/` 是**通配符链接**（`Entity.csproj:31`），新文件自动纳入服务端编译，**不需要改 csproj**。这点与 S1 相反（S1 新文件在 `GameLogic/` 下，是逐文件列举，必须手动加行）。

### Step 2：重写 FrameSyncPhysicsWorld 内核

按上面「Step 的新流程」改造。要点：

- 删掉 `using Box2DSharp.*`、`using System.Numerics`、`using System.Reflection`
- 删掉 `_world`、`_contactListener`、`_physicsContacts`、两个反射 `PropertyInfo`
- `Vector2` 换成一对 `Fixed64`，或项目里已有的定点向量类型（先确认 `FixedMathSharp` 提供什么）
- `MathF.Sqrt` → `FixedMath.Sqrt`（三处）
- `Clamp(float, Fixed64, Fixed64)`（`:216`）改为纯定点比较，删掉 float 转换

### Step 3：快照字段改原生定点

`PhysicsBodySnapshot.cs` 现有两个构造器：float 版（`:7-29`）和 `Fixed64` 版（`:31`）。float 版只为 Box2D 中转存在。

**先改调用方，再删构造器。顺序反了会编译失败。**

float 构造器**有两个真实调用点**（2026-08-03 review 核实，此前误判为「无调用方」）：

| 位置 | 现状 | 处理 |
|------|------|------|
| `BattlePredictionSelfTestSuite.cs:366` | `new PhysicsBodySnapshot(1, 0.0f, 0.0f, ...)` 裸 float 字面量 | 改为 `(Fixed64)` 显式转型 |
| `BattlePredictionSelfTestSuite.cs:367` | `new PhysicsBodySnapshot(2, 5.0f, 0.0f, ...)` 同上 | 同上 |

**已确认不受影响的调用点**（勿动）：

- `BattleClientController.cs:496` —— 参数已带显式 `(Fixed64)` 转型，走 Fixed64 构造器
- `SnapshotSelfTestSuite.cs:167` `:204` `:216` —— 用 `F(...)` 辅助函数，其定义是 `F(float value) => (Fixed64)value`，产出 `Fixed64`
- `SnapshotSelfTestSuite.cs:186` —— 直接传 `Fixed64.Zero`
- `FrameSyncPhysicsWorld.cs:286` —— 本阶段整体重写

改完两处调用方后再删 float 构造器。**建议直接删而非标 `[Obsolete]`** —— 留着会让人以为 float 入口仍是合法路径。

> **范围外但值得知道**：`PlayerStateSnapshot.cs` 也有三个 float 构造器重载（`:9` `:14` `:19`），`BattlePredictionSelfTestSuite.cs:360-361` 在用。那是 gameplay 快照不是物理快照，**本阶段不动**。如果将来要一并清理，那是独立改动。

### Step 4：清理依赖声明

从这几处移除 Box2D 引用（已核实全部命中位置）：

- `GameServer/Server/Entity/Entity.csproj`
- `GameServer/Server/Main/Main.csproj`
- `GameServer/Tools/FrameSyncMvpAValidator/FrameSyncMvpAValidator.csproj`
- Unity 侧 asmdef / csproj（`Assembly-CSharp.csproj` 等由 Unity 自动生成，删 dll 后会自动更新）

Unity 侧的 `Box2DSharp.dll` 本体**先别删**，等无头 + 真机都验收通过再删，方便回退。

因此当前静态验收的「零命中」范围是 `UnityProject/Assets/GameScripts` 业务源码与三个手工维护的服务端项目文件。仓库根目录的 Unity 自动生成 `.csproj` 会在 DLL 本体仍保留时继续列出全局引用，**不手改**；最终删除 DLL 后由 Unity 重生成。

### Step 4.5：Box2D 求解器旁路的一个边角事实

重写后有一处行为**理论上会变，实践中不会**，记录下来免得后续排查时困惑。

Box2DSharp 的位置积分带安全钳制（`Settings.cs`：`MaxTranslation = 2.0f`、`MaxRotation = π/2`），单帧位移超过 2.0 会被截断。本项目 `MoveSpeed = 5`、`dt ≈ 0.0333`，单帧位移 `≈0.167`，**远低于阈值，永不触发**。手写定点版不需要复刻这个钳制。

但 S7 的击退是**瞬时冲量**。如果将来某次击退让单帧位移超过 2.0，Box2D 时期会被悄悄截断、手写版不会。S7 定击退强度时值得知道这条差异 —— 手写版的行为才是符合直觉的那个。

### Step 5：复核既有自测用例

**只有一个用例直接依赖 `FrameSyncPhysicsWorld` 的数值：**

| 用例 | 位置 | 影响 |
|------|------|------|
| `room-boundary-clamps-player` | `BattlePredictionSelfTestSuite.cs:124-133` | **必须复核**。直接 `new FrameSyncPhysicsWorld()`，断言具体 `m_rawValue`。去掉 float 往返后该值会变 |
| `authoritative-snapshot-restores-physics-world` | 同文件 `:339-386` | 走 `BattleSimulation` 对账链路，断言的是「恢复后与恢复前一致」的相对关系，**大概率无需改** |

**`physics-roundtrip` 与 `physics-affects-hash` 不在这个文件里** —— 它们在 `GameShared/FrameSync/Snapshot/SnapshotSelfTestSuite.cs`（`:17-18`），且用的是 `TestPhysicsSnapshotProvider` **假 provider**，完全不碰 `FrameSyncPhysicsWorld`。所以它们**不受本次改动影响**。

> S1 的验收指南 §4.1 把这四条并列为「重点确认的既有物理用例」，容易让人以为都在同一个文件、都会被物理重写波及。实际只有前两条与 `FrameSyncPhysicsWorld` 有关，后两条测的是快照机制。

`TestRunner.cs` 的 `Scenario 3 PlayerCollision`（MOBA 卡位）会跑 occupancy 真实路径，是本阶段**最有价值的回归信号**。

### Step 6：新增跨端 bit-exact 用例

补上分析报告 §5.4「跨平台确定性证据不足」这一项 —— 这是本阶段附带的最大收益。

用例思路：固定输入序列跑 N 帧，断言最终哈希等于硬编码的期望值。全定点后该值**跨平台可复现**，这是 Box2D 时期做不到的。

注册照 S1 的先例：`AllCaseNames` 数组 + `RunCase()` switch 两处，`TestRunner.cs` 不用改。

## 对外表述收益

本阶段完成后，下面这段话才成立（讨论记录 §3 的原话）：

> 读完 Box2D 求解器与碰撞流程后发现，warm starting 的累积冲量存在 `Contact.Manifold` 的 internal 字段里，快照存不下、回滚恢复不了；pair 顺序也未规范化。对需要回滚的确定性系统，通用浮点求解器是负债。因此按需求手写定点的圆-矩形与圆-圆，只做需要的部分。

外部支撑：Rocket League 为确定性网络物理把 Bullet 集成进 UE3、弃用 UE3 自带的 PhysX（讨论记录 §4.3）。「为了确定性去控制物理内核」是这条路线上的通行动作。

**连带影响**：`对外表述禁区` 里「不要说用定点数保证确定性」这条会**反转**为可主动讲的强项。同时 HTML §7 的 `#6`（float 字段加 epsilon 容差）整体作废 —— 没有浮点噪声，任何差异都是真失同步。
