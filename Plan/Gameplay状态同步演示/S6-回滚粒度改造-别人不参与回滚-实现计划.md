## Context

### 现状：重放粒度是自己，回滚粒度是全世界

已核实的三处代码：

```
BattleSimulation.cs:482  ReconcileAuthoritativeSnapshot(snapshot, replayTargetFrame, fixedDt, logRollback, reason)
                  :490    ApplyAuthoritativeSnapshot(snapshot)   → :459 _worldState.RestoreSnapshot(snapshot)
                  :491    DiscardPredictionsAtOrAfter(snapshot.FrameIndex)
                  :503    AdvancePredictionTo(replayTargetFrame, fixedDt)
```

`ApplyPendingServerSnapshot`（`:361`）先算出 `mismatch = CheckConsistency(snapshot)`，然后**无条件**调 `ReconcileAuthoritativeSnapshot`（`:374`）。`mismatch` 只作为 `logRollback` 传入，控制日志、计时与 `_rollbackCount++`，**不控制是否回滚**。

而 `BattleWorldState.RestoreSnapshot`（`BattleWorldState.cs:74-105`）第一件事就是 `_players.Clear()`（`:81`），随后为快照里每个玩家 `new PlayerState(...)` 重建。也就是说：

- 拨回过去的是**整个世界**，包含所有其他玩家
- 重放（`ApplyLocalPrediction`，`:751-763`）只推进**自己**

第一步把世界拨回了帧 N，第三步只能把自己走回现在。**别人被留在了过去，直到下一个快照到来才被再次覆盖。** 一致时之所以也必须重放，正是因为第一步已经破坏了「现在」这个状态。

**差异不在「要不要重放」，在「别人参不参与回滚」。** NKGMoba 能条件回滚，靠的是它压根没有「全量世界快照 + 客户端全量恢复」这个约束。

### 本阶段不抄的部分

NKGMoba 的完整形态还包含「服务端只发脏 Cmd」（`MoveComponentTicker.cs:84`）。本阶段**不做**，理由：

- 要动 `BattleComponent.cs` 发送逻辑 + 服务端侧历史快照容器
- 与 B1 刚落地的「属性与 Buff 每 60 帧按玩家错峰发送全量」有交互，需一并重新设计
- 带宽收益需实测才知道（S3 已有教训：`int64` 负数 10 字节，raw value 可能比 float 更费）

拆客户端就能拿到「一致时零回滚零重放」这个主要收益，协议零改动。服务端脏字段过滤若将来要做，另开号。

### 一个反直觉的前提：容差问题已经不存在了

我在讨论中曾建议「先修 proto 传 Fixed64 raw long」，**这条已过期**。已核实 `OuterMessage.proto` 现为 `int64 XRaw/YRaw/LinearVelocityXRaw/LinearVelocityYRaw`，全文件 `float` 零命中 —— S3（`4e294d55`）已修完。

所以本阶段**不需要**任何前置的精度修复，也**不引入容差**。NKGMoba 用的是 float 阈值 0.001（`参考仓库分析-NKGMobaBasedOnET.md:90`），那是它浮点物理的无奈；本项目 S2 后全定点，bit-exact 可达，`#6`（误差判定加 epsilon）已正式作废。**照抄它的容差是退步。**

## 关键决策

### 决策一：拆容器，不是加开关

不在 `ReconcileAuthoritativeSnapshot` 里加 `if (!mismatch) return;`。原因是那样只是把「一致时的浪费」藏起来，`_worldState` 里仍然混着别人，任何将来读 `_worldState.Players` 的代码都还得自己分辨谁是谁。

改法是让 `_worldState` **只装自己**，别人进独立的 `RemotePlayerBuffer`。这样：

- 「一致时不回滚」变成结构性的结果，不是一个可能被绕过的分支
- `RestoreSnapshot` 的 `_players.Clear()` 不再牵连别人
- 表现层读别人有明确来源，不再依赖「碰巧 `_worldState` 里有」

### 决策二：`RestoreSnapshot` 保持全量语义，新增一个只恢复自己的入口

不改 `BattleWorldState.RestoreSnapshot` 的行为。它有 11 处调用方（写计划时为 8 处，随 Buff/Numeric 往返用例增至 11：`SnapshotSelfTestSuite` 7 处 + `SnapshotManager.RollBack` + `SnapshotManager` 内嵌自检 + `SimulatedClient` 测试桩 + 客户端回滚本处），改语义会波及一片。

新增 `RestoreSelfOnly(BattleWorldSnapshot snapshot, long selfPlayerId)`：只取快照里 `PlayerId == selfPlayerId` 那一项重建，物理体只保留自己的。`ReconcileAuthoritativeSnapshot` 改调这个。

> **已核实无冲突**：`SnapshotManager.RollBack`（`SnapshotManager.cs:51-58`）虽然也调全量 `RestoreSnapshot`，但**全仓零调用方** —— `ClientTickDriver.cs:34` 暴露的 `SnapshotManager` 属性无任何消费者，grep `_snapshotManager.` 零命中。同文件 `CheckConsistency`（`:60-62`）是空方法体。它作为 tickable 注册（`ClientTickDriver.cs:140`）后实际只跑 `Tick`，算一个无人消费的 `LatestHash`。
>
> 所以本阶段不会与它冲突。决策七已定 A（摘掉 `SnapshotManager` 注册），此类不再实例化，`RollBack`/`CheckConsistency` 随之不可达、一并清理——无需再加注释标注。
>
> **定性更正（2026-08-06 代码核实）**：它不是「活跃预留」，是 **v0.3-arch 逻辑/渲染分离重构留下的孤儿**——v0.3a 原「为 v0.3c 预留」此钩子，但 v0.3-arch 把回滚搬进 `BattleSimulation.RollBack`（`BattleSimulation.cs:314`），v0.3c 完成时即走该路，此钩子从未被认领（`ITickable.RollBack`/`CheckConsistency` 为 default interface method，`ITickable.cs:11-17` 带默认空体，删除此覆盖零技术成本）。由决策七 A 在 S6 Step 5 一并清理（摘注册后此类不再实例化，孤儿方法随之不可达）。

### 决策三：别人的位置不做预测，只做插值

别人进 `RemotePlayerBuffer` 后，**不参与 `AdvancePredictionTo`**，也就是不预测。表现层从 buffer 取「快照帧 - 插值延迟」处的插值位置。

这是守望模型的核心（客户端只预测自己），也是 NKGMoba 的做法（`MoveComponentTicker.cs:129` 的 lerp）。代价是别人的显示位置比权威帧再落后一个插值延迟，收益是抖动消失、延迟量变成可控常数。

**本阶段只做「拆出去 + 单点直取」，插值曲线本身留给 S10**（远端插值 + 轨迹线）。即本阶段结束时别人的显示位置 = 最新权威快照里的位置，不做时间轴插值。这样本阶段的验收标准不依赖插值参数调优。

### 决策四：三处必须保留执行（继承 S3 接口约定）

`S3 计划:351-359` 的约定仍然生效，行号已按当前文件核实更新：

```
BattleSimulation.cs:489  _authoritativeSnapshots.Save(...)          ← S3 的哈希上报依赖它
              :491  DiscardPredictionsAtOrAfter(...)
              :508-511  if (logRollback) CapturePredictionErrorAfterReconciliation()   ← S1 守卫
```

第三处：一致快照**不得**重设平滑基线，否则每个快照都会重启 `SmoothingDurationSeconds = 0.12f` 计时器。现有代码已用 `if (logRollback)` 守住，拆分时别把这条守卫连带吞掉。

### 决策五：哈希口径不变，但两处诊断点的含义会变

**S3 的哈希上报不受影响** —— 已核实 `SendHashReportIfNeeded`（`BattleSimulation.cs:567-573`）取的是 `_authoritativeSnapshots.TryGet(_lastAppliedFrame, ...)`，即**服务端权威快照**，不是 `_worldState.TakeSnapshot()`。所以 S3 的哈希基线与告警逻辑全部不动。

但另有两处调 `_worldState.TakeSnapshot()`，拆分后它们的**覆盖范围会从「全世界」缩成「只有自己」**：

| 位置 | 用途 | 拆分后 |
|------|------|--------|
| `SnapshotManager.cs:40-42` | `LatestHash`，S3 已确认全仓无消费方 | 值会变，无消费方所以无影响 |
| `BattleClientController.cs:968-972` | `[Battle][P1]` 日志里的 `stateHash` | 值会变，仅诊断日志 |

两处都不进验收断言。**但必须在计划里写明，否则将来有人拿 P1 日志的 stateHash 跨版本对比会被静默误导。** 这正是 `设计教训-两类静默失效.md` 描述的失效模式。

### 决策六：物理体也跟着拆

`BattleWorldState.AddOrUpdatePlayer`（`:38`）会给每个玩家 `EnsureBody`。拆分后别人不进 `_worldState`，**别人的物理体也就不在物理世界里**。

当前无影响：S2 拆掉 Box2D 后 `FrameSyncPhysicsWorld` 只做定点积分，玩家之间无碰撞。

**这是 S8（Dash/体力/撞击击退）的前置约束，已拍板**：击退走服务端权威、客户端不预测。碰撞服务端判、位移用 Buff、位置走快照下发——客户端零碰撞代码、不维护远端物理体。**S8 继承此约束：击退 = 服务端碰撞判定 + Buff 位移 + 快照下发；客户端手感用 VFX 即时播放补，不用物理预测。** 参考仓库同样不在客户端做预测的玩家间碰撞（NKGMoba 击退走 Buff 状态非物理冲量；Source 玩家移动互相穿透、命中走服务端延迟补偿）。

### 决策七：`SnapshotManager` 这个死 tickable 的每帧成本要显式取舍

`ClientTickDriver:140` 注册了 `SnapshotManager`，其 `Tick`（`SnapshotManager.cs:32-44`）每帧 `_worldState.TakeSnapshot()`（分配 `PlayerStateSnapshot[]` + 物理快照）+ `_buffer.Save` + `StateHasher.Hash`。而 `LatestHash` / `TryGetSnapshot` / `RollBack` **全仓零消费方**（`BattleClientController:239` 调的是 `_simulation.RollBack` 即 `BattleSimulation.RollBack:314`，不是 `SnapshotManager.RollBack`）。拆分后 `_worldState` 只剩自己，这个 tickable 继续每帧分配、产出没人看的 self-only hash。

本阶段以「省每帧耗时」为第一完成标准，留着它与目标相悖。**已定：摘掉注册**——删 `ClientTickDriver:135-140` 的 `SnapshotManager` 构造与 `Register`，把 `RunSelfTest`（`SnapshotManager.cs:64-76`）迁移到启动期一次性调用（如 `ClientTickDriver.EnsureInitialized` 内一次性触发）。**零行为变化**（产出本就零消费方），省每帧分配与 GC 压力。摘掉后此类不再实例化，`RollBack`/`CheckConsistency`/`LatestHash`/`TryGetSnapshot` 全部不可达，可一并清理（决策二已定性为 v0.3-arch 孤儿，`ITickable.RollBack`/`CheckConsistency` 为 default interface method，删除零成本）。

## 实现步骤

### Step 1：新增 `RemotePlayerBuffer`

新建 `GameShared/FrameSync/Battle/RemotePlayerBuffer.cs`。

- 持有 `Dictionary<long, PlayerStateSnapshot>`，键为 `PlayerId`
- `ApplyAuthoritative(BattleWorldSnapshot snapshot, long selfPlayerId)`：遍历 `snapshot.Players`，跳过 `selfPlayerId`，其余覆盖写入；快照里已消失的玩家从字典移除
- `TryGet(long playerId, out PlayerStateSnapshot state)`
- `IReadOnlyCollection` 形式暴露枚举，供表现层遍历
- `Clear()`
- 记录 `LastAppliedFrame`，供诊断与将来 S10 插值取时间轴用

不含任何预测、回滚、物理体逻辑。这是个纯粹的「最新权威态」容器。

> 放 `GameShared` 而非 `GameLogic`，与 `BattleWorldState` 同级 —— 无头测试要能直接构造它。

### Step 2：`BattleWorldState` 新增 `RestoreSelfOnly`

不动现有 `RestoreSnapshot`（`BattleWorldState.cs:74`）。新增：

```csharp
/// <summary>
/// 只恢复指定玩家，其余玩家与其物理体一并清除。
/// 用于客户端预测回滚——客户端只预测自己，别人由 RemotePlayerBuffer 承载。
/// </summary>
public void RestoreSelfOnly(BattleWorldSnapshot snapshot, long selfPlayerId)
```

要点：

- 同样 `_players.Clear()`，但只重建 `PlayerId == selfPlayerId` 那一项
- 快照里找不到自己时**返回 `void`、什么都不做**（不抛、不静默留空 `_worldState`）。`ApplyAuthoritativeSnapshot` 现有逻辑在 `TryGetAuthoritativeSelf` 失败时本就走 `_hasLatestAuthoritativeSelfPosition = false`（`:470-473`），无需 `RestoreSelfOnly` 再回传状态；别人那路 `_remotePlayers.ApplyAuthoritative` 仍无条件执行，照常更新
- 物理体：**忽略 `snapshot.PhysicsSnapshot`，恒走 `ClearBodies()` + `EnsureBody(self)` + `SetBodyTransform(self, X, Y, resetVelocity:true)`**，只从 `PlayerStateSnapshot.X/Y` 重建自己。理由：`IPhysicsMovementWorld`（`IPhysicsSnapshotProvider.cs:12-23`）与 `FrameSyncPhysicsWorld` **没有**按 bodyId 过滤或单 body 恢复的 API——`RestoreSnapshot(PhysicsWorldSnapshot)` 内部 `ClearBodies()` 后遍历 `snapshot.Bodies` 全量重建（`FrameSyncPhysicsWorld.cs:168-178`），整份恢复会把别人的物理体带回来。而服务端快照的 `PhysicsSnapshot` 恒非空（`BattleWorldState.TakeSnapshot:70` 必带），必然落到这条分支，必须绕开整份恢复。自体物理每帧由输入驱动（`ApplyLocalPrediction:765-766`），位置足够、速度下帧重算——与现有 `RestoreSnapshot` 的 null 分支（`:97-104`，只设位置不恢复速度）行为一致
- `ToBodyId`（`:107`）是 `checked((int)playerId)`，重建自己时复用 `ToBodyId(selfPlayerId)`

### Step 3：改造 `ApplyAuthoritativeSnapshot` 与调用点

`BattleSimulation.ApplyAuthoritativeSnapshot`（`:462-480`）当前六件事，改造后：

| 原行为 | 改造后 |
|--------|--------|
| `:464-473` 取权威自己位置存 `_latestAuthoritativeSelfX/Y` | 不变 |
| `:475` `_lastAppliedFrame = snapshot.FrameIndex` | 不变 |
| `:476` `ApplySnapshotToWorldState(snapshot)` → 全量 `RestoreSnapshot` | **改**：`_remotePlayers.ApplyAuthoritative(snapshot, _selfPlayerId)` 无条件执行；`RestoreSelfOnly` 仅在 `mismatch` 时执行 |
| `:477` `_lastPredictedFrame = snapshot.FrameIndex` | **改**：仅 `mismatch` 时才回退。一致时自己没被拨回，`_lastPredictedFrame` 必须保持在现在，否则 `AdvancePredictionTo` 会重放已跑过的帧 |
| `:478` `RemoveConfirmedInputHistory(snapshot.FrameIndex)` | 不变（已确认的输入无论一致与否都可清） |
| `:479` `_skillGraphRuntime.Clear()` | **改**：仅 `mismatch` 时清。一致时自己没动过，清了会丢进行中技能状态 |

**这是本阶段最容易出错的一步。** `_lastPredictedFrame` 与 `_skillGraphRuntime.Clear()` 两处若漏改条件，一致路径会分别产生「重复重放」与「技能状态凭空消失」。

`ApplyAuthoritativeSnapshot` 需新增 `bool mismatch` 参数，由 `ReconcileAuthoritativeSnapshot` 透传。

### Step 4：`ReconcileAuthoritativeSnapshot` 引入条件分支

`BattleSimulation.cs:482`。现有签名已有 `bool logRollback`，它的实参就是 `mismatch`（`:378`）。**不新增参数，复用它**，但把语义在注释里写清：它现在既控日志也控回滚。

改造后结构：

```
_authoritativeSnapshots.Save(...)                    ← 保留，S3 依赖（决策四）
ApplyAuthoritativeSnapshot(snapshot, mismatch)       ← Step 3
DiscardPredictionsAtOrAfter(snapshot.FrameIndex)     ← 保留

if (mismatch)
{
    replayFrames = ...;  AdvancePredictionTo(replayTargetFrame, fixedDt);
    CapturePredictionErrorAfterReconciliation();     ← S1 守卫，位置不变
    // 计时、_rollbackCount++、日志
}
```

一致路径下 `AdvancePredictionTo` 不再被调 —— 但**注意 `BattleSimulation.Tick:228` 那次 `AdvancePredictionTo(frameIndex, fixedDt)` 仍照跑**，它是正常向前推进，不是重放。一致时自己就靠这一次推进到当前帧。

> `RollBack(uint targetFrame)`（`:314`）手动入口传 `logRollback: true`、reason `"manual"`，语义变成「强制回滚」，符合它的用途。加注释说明。

### Step 5：表现层改读 `RemotePlayerBuffer`

`BattleClientController.SyncRendering`（`:523-569`）现在遍历 `worldState.Players` 建 `_renderTargetsByPlayerId`（`:535`）。改为两路：

- 自己：仍从 `worldState.TryGetPlayer(_simulation.SelfPlayerId, ...)` 取，走现有 `PredictionErrorSmoother` 平滑路径
- 别人：从 `_remotePlayers` 枚举取，直接用权威位置建 `RenderTarget`

`_activePlayers` 的构成 = 自己 + buffer 里的全部。`GetOrCreateSphere` / `SetActive` / 陈旧目标清理逻辑（`:541-566`）不变。

`UpdateRendering`（`:571`）遍历 `_renderTargetsByPlayerId` 的部分不动 —— 它已经是「按 playerId 找球、插值到目标」的间接结构，换数据源不影响它。

`SyncAuthoritativeGhost()`（`SyncRendering:568` 末尾调用）不受影响——它读的是 `_simulation` 的权威自己位置（`_latestAuthoritativeSelfX/Y`，决策三/四保持不变），拆两路后仍在 self 路径之后调用即可。

同时执行决策七 A：摘掉 `ClientTickDriver` 对 `SnapshotManager` 的构造与 `Register`（`:135-140`），把 `RunSelfTest`（`SnapshotManager.cs:64-76`）迁移到启动期一次性调用；`SnapshotManager` 不再实例化，`RollBack`/`CheckConsistency` 随之不可达，一并清理（决策二已定性为 v0.3-arch 孤儿）。

### Step 6：`ClearWorldState` 与 `SetJoined` 补 buffer 清理

在 `ClearWorldState()` 方法体（`BattleSimulation.cs:812-826`）末尾加 `_remotePlayers.Clear()`。注意别加错位置：`:280` 的 `_selfPredictions.Clear()` 在 `SetJoined` 里，不在 `ClearWorldState` 里——`ClearWorldState` 方法体只做 `_stalePlayerIds.Clear()` + 逐个 `_worldState.RemovePlayer(...)`。`SetJoined`（`:253`）在 `:255` 调 `ClearWorldState()`，故自动覆盖；且 `ClearWorldState` 全仓唯一调用方就是 `SetJoined`，加在方法体里才能守住「将来新增调用方也清 buffer」的不变量。

**漏这步的后果**：重连或重开一局后，上一局的别人会以幽灵球残留。

### Step 7：新增用例

加到 `BattlePredictionSelfTestSuite.cs`，同时**必须加进 `AllCaseNames`**（`:18-19`）—— 漏加会静默不跑而 `--scenario=all` 仍报 PASS（S3 风险表已记录过这个坑）。

| 用例名 | 断言 |

| `consistent-snapshot-skips-rollback` | 构造一致快照，断言 `RollbackCount` 不增、`_lastPredictedFrame` 未回退。**不要**断言 `LastRollbackReplayFrames == 0`——该字段仅 `logRollback=true` 分支（`:521`）写，一致快照下是「保留旧值」而非「被清零」，隔离用例从 0 起始恰好成立但语义会误导实现者 |

## 风险与对策

| 风险 | 对策 |
|------|------|
| **`_lastPredictedFrame` 一致时也回退** | Step 3 最易错处。会导致每个一致快照都重放 `_leadFrames` 帧，性能反而更差且难察觉（结果仍正确）。`consistent-snapshot-preserves-predicted-frame` 专守此项 |
| **`_skillGraphRuntime.Clear()` 漏加条件** | 一致时清掉进行中技能，表现为技能突然中断。`consistent-snapshot-preserves-skill-graph` 专守 |
| **`RestoreSelfOnly` 整份恢复物理快照** | `_physicsWorld.RestoreSnapshot(snapshot.PhysicsSnapshot)` 会把别人的 body 带回来，`_players` 里没有但物理世界里有，后续 `Step` 会积分幽灵体。物理 API 无按 bodyId 过滤能力，对策是**忽略 PhysicsSnapshot、ClearBodies 后只重建自己**（Step 2），`restore-self-only-keeps-single-body` 专守此项 |
| **S1 平滑守卫被吞** | `CapturePredictionErrorAfterReconciliation` 必须留在 `if (mismatch)` 内。若挪到外面，每个一致快照都会重设平滑基线 |
| **`_authoritativeSnapshots.Save` 被短路吞掉** | S3 的哈希上报依赖它，且它在 `if` 之前。整体 `return` 是错的（S3 接口约定明文禁止） |
| **表现层漏了自己** | Step 5 拆两路后，若只改了别人那路，自己的球会消失。`_activePlayers` 必须含自己 |
| **重开局幽灵球** | Step 6，`ClearWorldState` 补 `_remotePlayers.Clear()` |
| **P1 日志 stateHash 跨版本对比** | 决策五。拆分后该值覆盖范围缩小，与本阶段之前的日志不可比。需在 `报告/` 或验收指南里标注 |
| **拿 NKGMoba 的 0.001 容差一起抄来** | 本项目全定点，`#6` 已作废。抄容差是退步，见 Context 末节 |
| **别人的物理体缺失影响 S8 击退** | 决策六已拍板走服务端权威：击退 = 服务端碰撞 + Buff 位移 + 快照下发，客户端不维护远端物理体（见决策六） |
| **现有用例隐含「一致也重放」假设** | Step 7 末注。改用例可以，静默改绿不可以 |
