## 本阶段做什么

让一个已在战斗中的客户端断线后重新接回**同一个玩家实体**，而不是变成一个新玩家。四件事：

1. **服务端宽限期** —— session 断开后玩家状态不立即销毁，保留可配置的一段帧数等待认领。
2. **真实账号登录 + 身份凭据** —— 进战斗必须先登录，Authentication 签发 token、Battle 校验，战斗槽位绑 `accountId`；重连凭同一枚 token 认领原实体。**自动化也走真实登录，不开后门**（决策八）。
3. **断线期间的世界行为** —— 明确定义断线玩家在宽限期内怎么动（决策二：冻结，不复用旧输入）。
4. **重连后的状态恢复** —— 客户端本地状态清空并从服务端权威全量重建，帧号重新对齐。

**这不是「保存进度/存档」**，宽限期内玩家实体一直活在服务端仿真里，重连只是把一条新连接接回既有实体。世界不为断线玩家停下。

## Context

以下事实均已在当前工作区核对。分三组：

- **前两节 + 「`C2B_JoinBattle` 是空消息」** —— 当前代码完全不支持重连
- **「进战斗完全绕过登录」起四节** —— 登录链路的现状与跨服校验的选型依据
- **「属性基线与 Buff 基线的索引粒度不一致」** —— 一处「靠巧合能跑」的隐式耦合，决定了决策三的修法

### 断线玩家状态被立即销毁 —— 没有可重连的东西

`BattleComponent.CleanupDisconnectedPlayers()` 在 `Tick` 开头**每帧**执行：扫 `_sessionsByPlayerId`，凡 `session == null || session.IsDisposed` 就立刻走完整清理 —— 移除 session 映射、RTT tracker、属性基线、Buff 基线，并调 `_battleLogic.RemovePlayer(playerId)`。

玩家实体在断开后的第一个逻辑帧就没了。**S9 的第一个必改点**：把「检测到断开」与「销毁实体」拆成两步，中间插入宽限期。

### `Join` 的复用分支只认 session.Id，重连必然走新建分支

`BattleComponent.Join(Session)` 有一条复用分支，条件是 `_playerIdBySessionId.TryGetValue(session.Id, ...)`。重连是一条新连接、新 `session.Id`，查不到 → 落到 `long playerId = _nextPlayerId++` 发新 playerId、新出生点。

更麻烦的是 `Join` 开头第一句就是 `CleanupDisconnectedPlayers()` —— **重连请求会先把自己要认领的那个实体删掉**。宽限期实现后这句必须改成「只清理宽限期已满的」。

### 进战斗完全绕过登录，登录 UI 从不弹出

这条决定了「做真实账号登录」的工作量，与重连本身同等重要。

实际跑的入口是 `GameApp.StartGameLogic()`（`GameApp.cs:36-49`）：`await GameClient.Instance.InitAsync()` 之后**无条件** `GameplaySandboxView.Create()`，不弹登录界面。

`CommonUIController.cs:12-15` **确实有**「`OnLoginSuccess` → `GameplaySandboxView.Create()`」的挂钩，但它是**死代码** —— `CommonUIController` 在全项目只有自身定义与 `IUIController` 接口两处命中，从未被实例化或调用 `RegUIMessage`；`ShowLoginUI()` 也无人调用。

`DataCenterSys.Login`（`DataCenterSys.cs:60-80`）本身是完整的：连 20001 → 发 `C2A_LoginRequest` → 查错误码 → 置 `StatusEnter` → 触发 `OnLoginSuccess`。**但它从不读响应里的 Token**，且整条路径没人走。

**有一处现成便利**：`DataCenterSys.Login` 与 `ConnectBattle` 共用同一个 `GameClient.Scene.Session`，而 `ConnectBattle` 第一句就是 `GameClient.Instance.Disconnect()`。所以「连 Auth → 登录 → 断开 → 连 Battle」正是现有形态，**不需要改连接管理**。

**接线时的坑**：`GameplaySandboxView.Create()` 开头有 `FindObjectOfType` 幂等守卫（`GameplaySandboxView.cs:26`）。若只加登录跳转而忘了删 `GameApp` 那条无条件路径，**画面完全正常、登录形同虚设**，且因为守卫存在连重复创建都看不出来。Step 10 必须显式删除该路径。

### 登录服不签发 token，`A2C_LoginResponse.Token` 恒为空

proto 里 `A2C_LoginResponse.Token`（string）字段存在（`OuterMessage.proto:36-39`），但 `C2A_LoginRequestHandler` 校验账号密码后直接返回空串，代码注释明说 MVP 阶段不做签发。`Account` 实体只有 `Username / Password / CreateTime / LoginTime`，**没有 token 字段、没有会话表**。

`AuthenticationComponent` 挂在 Authentication scene，其 System（`AuthenticationComponentSystem.cs:26`、`:92`）走 `scene.World.Database` 读写 MongoDB 处理注册与登录 —— **这套 DB 访问范式可直接复用**（决策一的会话表照它写）。

**顺带记录一处既有状态**：密码是**明文**存储，无哈希无盐。这是既有设计，S9 不修（见非目标），但演示被问到要直说。

### 相关 scene 共享同一个 World 与 MongoDB —— 这决定了跨服校验怎么做

`Program.cs` → `Fantasy.Platform.Net.Entry.Start` 按 `Fantasy.config` 启动场景。当前相关入口是 Authentication(20001) 与 Battle(20101)；Authentication 的 `ProcessConfigId=1`，Battle/Gate 的 `ProcessConfigId=2001`，但它们的 `WorldConfigId` 都是 1，World 1 指向同一个 MongoDB 数据库 **`fantasy_main`**（`mongodb://127.0.0.1`）。跨服校验依赖的是共享数据库与 World 配置，不依赖错误的“ProcessConfigId 相同”假设。

**Auth 与 Battle 共享数据库** → 跨服 token 校验最省的做法是共享会话表，不必引入 Fantasy 内部消息（决策一）。

`OnSceneCreate_Init.cs` 里只给 Authentication 挂 `AuthenticationComponent`、给 Battle 挂 `BattleComponent` + `ServerTickDriver`，**Gate scene 是空的**（没有 Gate 分支）。所以 Gate 跳转等于从零做，本阶段不做（非目标）。

`InnerMessage.proto` 里有一对 route 样板（`ChatRouteType` + `G2Chat_SendMessage`），但 Auth 与 Battle 之间没有任何内部消息。若将来改走内部 RPC，照这对样板抄即可，不用从零学 Fantasy 的 route 机制。

### 服务端启动硬依赖 Mongo（Step 0 已实测确认）

`MongoDataBase.Initialize` 里 `new MongoClient` 与 `GetDatabase` 都是惰性的，但紧随其后的 `ListCollectionNames().ToList()` 是**急切网络调用**。`World` 构造在 scene 创建时发生，因此**没跑 mongod 时服务端会卡约 30 秒后超时启动失败**，报的是 Mongo 选主超时，与战斗逻辑无关。

**已实际启动服务端验证过，不是静态推断。**

两个后果：

1. **决策八的代价比预想小** —— Mongo 本来就是必需的，自动化改走真实登录只新增 Authentication scene 与测试账号两项前置
2. **发现一处既有文档缺陷** —— 五份含 `two-client-*` 场景的验收指南（`Dash与击退`、`回滚粒度改造`、`服务端RTT测量`、`弱网自动化测试`、`哈希上报与服务端告警`）**全都漏写 Mongo 前置**。在没跑 mongod 的机器上这些场景会在服务端启动阶段全灭，且错误信息把人往网络/握手方向带。一直没暴露是因为 S8 那轮只跑了无头用例与服务端编译，从未触发服务端启动。Step 13 顺手补齐

### `C2B_JoinBattle` 是空消息，服务端无从认领

proto 里 `C2B_JoinBattle` 消息体为空（`OuterMessage.proto:47-49`）。没有任何身份信息，服务端只能按「新玩家」处理。`C2B_JoinBattleResponse` 只有 `PlayerId / XRaw / YRaw / ServerFrameIndex` 四个字段。

**这是本阶段唯一必须的协议改动**（决策一）。

### 输入缺失时服务端复用上一帧输入

`BattleLogic.Tick` 在当帧无输入时走 `else if (hadLastConsumedInput)` 分支，取 `_lastConsumedInputByPlayerId` 的值并 `ReusedInputCount++`。这个设计是给**丢包补偿**用的，正确。

但断线玩家没有任何输入到达，会**一直命中这条分支**：断线瞬间若正按住方向键，宽限期内这个球会沿该方向持续移动，撞墙、撞人，甚至满足 S8 的 Dash 撞击条件触发击退。**不能直接改这条分支**（会破坏丢包补偿），必须用 per-player 的抑制标记（决策二）。

### 属性基线与 Buff 基线的索引粒度不一致 —— 属性的正确性搭在 Buff 基线的缺失上

两张基线表的键**不同粒度**：

| 表 | 键 | 计算位置 |
|---|---|---|
| `_lastBroadcastAttributesByPlayerId` | **playerId** | `BuildAttributeSyncPlans`，每次广播算**一次**，在 per-session 循环**之外** |
| `_buffBaselinesByObserverTarget` | **(observerSessionId, targetPlayerId)** | `BuildBuffSyncPayload`，在 per-session 循环**之内** |

也就是说**属性的脏掩码对全房间所有观察者是同一个**，Buff 的是每个观察者各自一份。

重连（新 sessionId、同 playerId）时属性基线仍在 → 服务端本该继续发增量，而客户端 `SetJoined` 已 `ClearWorldState()` 清空一切、没有基线可叠。B1 加的 baseline 帧号校验会拒收错位增量（`MergeAttributes` 返回 `Diverged`），要等最多 60 帧的周期性全量才恢复。

**但当前它恰好不出问题** —— `BuildAttributeSyncPlans` 里的 `HasObserverWithoutBuffBaseline(playerId)`（`BattleComponent.cs:472`，全项目**仅此一处调用**）会因为「新 session 没有 Buff 基线」把属性掩码强制成 `All`。**属性的正确性搭在 Buff 基线的缺失上。**

这是 [设计教训](设计教训-两类静默失效.md) 那类失效的反面形态：机制是错的，但被另一处副作用盖住。一旦 Buff 基线改成按 playerId 缓存（一个看起来纯粹省内存的优化），属性会立刻静默错乱且没有任何用例会红。

**这条决定了修法**（决策三）：因为属性掩码是全房间共享的，「重连时清 `_lastBroadcastAttributesByPlayerId[playerId]`」既**不足**（不能保证其他玩家对新 session 全量），又**过头**（会把该玩家属性全量推给所有无关观察者）。真正的修法是把属性基线的粒度对齐到 Buff。

### Buff 基线的粒度是对的，是属性该学的样板

`_buffBaselinesByObserverTarget` 的键含 observerSessionId。重连是新 sessionId，`BuildBuffSyncPayload` 查不到基线 → 走 `CreateInitialFullSync` 全量，且**只对这一个观察者全量**。行为正确，**S9 不改它**，但要补用例锁住（防止将来优化缓存时无声回归）。

### 属性基线的尾部更新是条件式的 —— 这否掉了「per-observer 覆盖掩码」这个更小的改法

`BroadcastSnapshot` 末尾更新属性基线时有一句 `if (DirtyMask == None) continue;`（`BattleComponent.cs:333`）—— **属性无变化的那些帧，基线帧号不推进。**

于是「在 per-session 循环里把重连 session 的掩码覆盖成 `All`、其余不动」这个看起来改动更小的方案有一个必踩的坑：重连帧上若该玩家属性恰好无变化（属性变化本就稀疏，这是**常见情况**），全局基线停在旧帧号 B，而重连客户端收到的是 `baselineFrameIndex = F` 的全量并把本地基线置为 F。下一帧全局按 B 算增量下发，重连客户端持 F，`MergeAttributes` 判定 `Diverged` 拒收 —— **本来要修的 bug 换了个触发条件又回来了。**

这就是决策三选「改索引粒度」而不选「覆盖掩码」的原因。

### RTT tracker 按 sessionId 索引，重连后从零开始

`_rttTrackersBySessionId` 键为 sessionId。新 session → 新 tracker、无样本 → `ResolveTargetLeadFrames` 返回 `0u` → 客户端退回自算 RTT。这条路径已有用例 `zero-target-lead-falls-back-to-client-rtt` 覆盖。

**S9 不改 RTT 通路**，但重连后前若干帧的超前量会退化到 `MinLeadFrames` 再重新收敛，验收时会看到一段 lead 爬升，属预期。

### `SetJoined` 已经是完整的「清空 + 从权威态重建」入口

`BattleSimulation.SetJoined(playerId, serverFrame, x, y)` 开头 `ClearWorldState()`，随后重置 30 余项状态（`_lastAppliedFrame`、`_lastPredictedFrame`、`_localFrame`、lead、预测缓冲、输入历史、SkillGraph、平滑器…）并 `_isJoined = true`。

**重连可以直接复用它**，客户端侧改动量因此很小。但它同时把 `_rollbackCount`、`StateMismatchCount`、`HashReportsSent` 等诊断计数清零 —— 验收要看「重连后是否稳定收敛」，清零会丢掉对照信号（决策五）。

### 客户端连接入口已具备重连形态

`DataCenterSys.ConnectBattle` 的实现就是「`Disconnect()` → `ConnectAsync()` → `Status = StatusEnter`」。战斗侧重连可直接复用，**不需要动通用的 `ClientConnectWatcher`**（那是登录/大厅链路的自动重连与弹窗确认，语义不同，混用会把战斗重连拖进版本检查流程）。

### 服务端没有 idle checker，「拔网线」不会被及时发现

`GameServer/Server` 全域 grep `SessionIdleCheckerComponent` 零命中，只有 Fantasy 框架 dll 与客户端侧有。服务端感知断线**完全依赖 KCP 层断开或客户端主动 `Dispose`**。

客户端拔网线/进程被杀的场景下，服务端可能长时间认为 session 仍然有效，宽限期根本不会开始计时。**S7 的 RTT 探测正好可以复用为第二个判据**（决策四）。

### 无头 harness 无法真正 dispose session

无头测试客户端与服务端同进程，没有真实 Fantasy Session。现有 `two-client-disconnect` 场景（`Run-BattleAcceptance.ps1` 默认场景之一）验的是「observer 看到 activePlayerCount 下降」，断开靠**客户端进程跑完退出**触发，controller 里没有任何主动断开调用。

S9 要测的是服务端认领逻辑与客户端状态重建，需要一个可控的断连注入入口（决策六）。`BattleNetworkGate` 的丢包注入**不够用** —— 它只让消息不可见，服务端 session 不会 dispose，测不到宽限期与认领。

## 目标

1. **重连拿回同一 playerId、同一世界状态** —— 位置、体力、Buff、Dash/Recover 剩余帧逐位恢复。
2. **凭据不可冒领** —— 无法用他人 playerId 认领他人实体（决策一）。
3. **断线期间行为有定义且可验收** —— 断线玩家冻结不移动，但 Buff/体力继续按帧演化（决策二）。
4. **重连后收敛速度可观测** —— 重连后 mismatch/rollback 在有界帧数内回到基线水平（决策五保留累计计数使其可比较）。
5. **两条断线判据都生效** —— session dispose 与 RTT 探测连续超时（决策四）。
6. **画面产出** —— 断线状态提示、宽限期倒计时、重连成功后的收敛过程（S11 素材）。

## 非目标

- **不做跨进程/跨服的会话迁移**，宽限期状态只在 `BattleComponent` 内存里。
- **不做断线期间的输入补偿或 AI 托管** —— 冻结就是冻结（决策二）。
- **不做匹配/大厅流程** —— 登录成功后仍直连战斗服（20101），不经 Gate。**Gate scene 目前是空的**（`OnSceneCreate_Init.cs` 无 Gate 分支），Gate 跳转等于从零做，不在本阶段。
- **不做密码哈希/加盐/传输加密** —— `Account` 实体的密码是**明文**存储，这是既有状态，S9 不修。演示被问到就直说，别把演示级登录讲成安全的。
- **不做多设备登录互踢** —— 会话表结构支持将来扩展（一个 accountId 多枚 token），本阶段不做。
- **不改 S3 哈希口径、不改 S6 回滚粒度、不改 S7 的 RTT 控制算法与已验收参数**（`ProbeTimeoutMs = 5000` 等；不动它意味着接受探测判据约 5.7 秒的判定延迟，见决策四）。
- **属性基线索引粒度会改**（决策三）—— 这是 S9 唯一触碰既有同步机制的地方，但脏同步的**算法与协议不变**，只改基线表的键与计算位置。
- **不做客户端自动重连的 UI 交互打磨**（弹窗/重试次数策略留给 S11）。
- 不做重连风暴的服务端限流（单机 demo 无此压力，但要在风险表里记一笔）。

## 决策一：凭据由 Authentication 签发、Battle 校验，战斗槽位绑 `accountId`

进战斗必须先登录。`C2B_JoinBattle` 新增 `Token` 字段（登录时拿到的那枚），`C2B_JoinBattleResponse` 新增 `IsReconnect` 标记。

完整链路：

```
登录  client ──C2A_LoginRequest{账号,密码}──> Auth(20001)
      Auth: 校验 → 生成 token → 写会话表{token → accountId, 过期时刻}
           ──A2C_LoginResponse{Token}──> client 缓存

进战斗 client ──C2B_JoinBattle{Token}──> Battle(20101)
      Battle: 读会话表校验 token → 得 accountId
            → 该 accountId 有宽限期条目? 是 → 重连认领
                                        否 → 建新玩家，槽位绑 accountId
```

**槽位绑 `accountId`，不绑 playerId** —— playerId 是自增小整数（`_nextPlayerId++`，从 1 开始）且随快照广播给房间内所有客户端。任何客户端都知道别人的 playerId，若凭它认领等于**任何人都能踢掉并接管任意玩家**。`accountId` 由 token 换出、无法伪造。绑账号还顺带保证「一个账号在同一场战斗里只有一个槽位」。

### 重连凭据整套机制消失

**槽位绑 accountId 之后，重连只需把登录时那枚 token 原样再发一次。** token 本身就证明「我是这个账号」，而槽位本来就绑在账号上 —— 服务端按 accountId 查宽限期条目即可完成认领。

**因此战斗服不生成、不轮换、不作废任何凭据，也不需要 per-player 凭据容器。** token 存在 Auth 的会话表里，寿命与战斗服的连接生命周期无关。

登录 token 的三条性质，实现时按这个理解：

- **可重复出示** —— 重连要再发同一枚，**不是一次性凭据**
- **寿命独立于战斗** —— 由 Auth 的过期时刻决定，与宽限期无关
- **由 Auth 单点签发与吊销** —— 战斗服只读不写

> **不要在战斗服里另造一套自签凭据。** 那样只能证明「你持有这个串」，不能证明「你是谁」，做不了踢下线、防一个账号多开这类事，等于重新发明一个残缺的认证系统。

### Battle 怎么信任这枚 token：选共享会话表

| 方案 | 取舍 |
|---|---|
| **A. 共享会话表（选它）** | Auth 登录时写 MongoDB `{token → accountId, 过期时刻}`，Battle 直接读。**零新协议**，只多一次异步 DB 查询；支持吊销；复用 `AuthenticationComponentSystem` 已有的 `scene.World.Database` 范式 |
| B. Fantasy 内部 RPC | 可行，`ChatRouteType` 有样板可抄，但为一次校验引入新 RouteType 与内部消息不值 |
| C. 自签 HMAC / JWT | 无需共享存储，但**过期前无法吊销**，且要引入签名密钥管理 |

选 A 的前提是 Context 已核实的「Authentication 与 Battle 共享 World 1 的同一个 MongoDB」。

**token 生成复用 `CryptoProbeNonceSource`**（S7 已有，密码学随机 64 位）。不要用 `Random`、时间戳或 accountId 派生值。token 不进任何广播消息、不进快照、不进哈希。

**必须有过期时刻** —— 否则一枚泄露的 token 永久有效。过期时长**独立于宽限期配置**，且应远大于宽限期，否则会出现「宽限期还没满但 token 已过期、重连必失败」的自相矛盾。用例 `expired-login-token-cannot-join-or-claim` 锁住。

> **口径**：这是**演示级**鉴权。生产通常用 JWT 或独立会话服务 + 缓存（每次进战斗读一次 DB 会成为瓶颈），还要密码哈希加盐与传输层加密（本项目密码明文存储，见 Context）。讲解按这个口径说，别说大了。

### 失败语义（定稿）

登录强制后每个 Join 都带 token，按 **token 有效性 × accountId 是否有宽限期条目 / 现有槽位**分流：

| 请求形态 | 服务端行为 |
|---|---|
| token 有效，accountId 无条目无槽位 | 建新玩家，槽位绑 accountId |
| token 有效，accountId 有宽限期条目 | **重连认领**，复用原 playerId 与世界状态 |
| token 有效，accountId 有在线槽位，**且请求来自同一 session** | 幂等成功，返回现有 playerId |
| token 有效，accountId 有在线槽位，**但请求来自不同 session** | **返回「账号已在线」错误**，不建玩家、不改绑（见下） |
| token 无效 / 过期 / 会话表无记录 | **统一错误码拒绝**，不建任何玩家 |

**「有在线槽位」必须按 session 再分一次，不能一律返回幂等响应。** 若对**新** session 返回现有 playerId，那个 session 从未写进 `_playerIdBySessionId` —— 于是它收不到快照，输入也会被 `BattleComponent.SubmitInput`（`:107-110`：查不到映射就 `return`）静默丢弃。客户端拿着一个合法 playerId、界面正常，但**完全不通信**。这类症状最难查，因为握手是成功的。

这条不只在「一个账号两处登录」时触发 —— **主动断开后快速重连也会撞上**：新 Join 可能先于服务端观察到旧 session dispose，此时旧槽位在服务端看来还在线。所以「账号已在线」错误必须是**可退避重试**的（客户端收到后短暂等待再试，等旧 session 被清理或宽限期条目建立）。用例 `fast-reconnect-before-dispose-observed-retries-then-succeeds` 锁住这条时序。

**为什么不做原子接管** —— 「不做多设备登录互踢」是本阶段非目标（见非目标）。原子接管等于实现了互踢的一半（能踢但没有通知与确认），语义半成品比明确拒绝更糟。拒绝 + 退避重试在本阶段范围内足够。

**首次进入与重连在协议上是同一个请求** —— 客户端不需要判断自己是不是重连，服务端按 accountId 有无条目自动分流。客户端侧因此没有「先试认领、失败再建新」的两步流程，别去实现它。

**失败必须统一错误码** —— 分别返回不同码等于给出一个「这个账号是否在线 / 宽限期是否还在」的探测接口。

**失败不能静默建新玩家** —— 一次 token 问题就凭空多出一个玩家，而客户端以为接回了原实体。演示中表现为「重连后自己的球位置和属性全变了」，排查会先怀疑状态恢复通路，方向完全跑偏。

**风险点转移到了宽限期边界** —— 过期与「仍可重连」的分界必须帧级确定，否则同一操作时有时无。用例 `reconnect-at-grace-boundary-is-deterministic` 锁住。

## 决策二：断线期间输入冻结为零，不复用上一帧

在 `BattleLogic` 上加一个 per-player 的输入抑制标记（如 `SetInputSuppressed(playerId, bool)`）。被抑制时，当帧输入直接取零，**不进入 `_lastConsumedInputByPlayerId` 的复用分支**；重连解除抑制后从新到达的输入继续。

### 进入抑制时必须清掉 last-consumed input

**只在抑制期短路复用是不够的** —— `_lastConsumedInputByPlayerId` 只在 `RemovePlayer` 里被清（`BattleLogic.cs:85`），而宽限期**故意不删玩家**，所以断线前那一帧的方向会**完整保留到重连之后**。解除抑制的那一帧若新输入还没到（重连后必然有几帧空窗），复用分支会立刻拿这个旧方向驱动移动 —— **玩家一接回就朝断线时的方向自己走一步**。

两种做法任选，但必须做其一：

- **进入抑制时 `_lastConsumedInputByPlayerId.Remove(playerId)`**（推荐，最直接）
- 或保留一个「等待新 session 首个有效输入」的门闩，门闩未开时复用分支不生效

用例 `no-stale-input-reuse-on-first-frame-after-unsuppress` 专门锁恢复边界 —— **既有的 `disconnected-player-input-is-frozen-not-reused` 锁不住它**，那条只验抑制期内为零，恢复边界是另一个时点。

**为什么不改复用分支本身** —— 那条分支是丢包补偿，正常玩家弱网时要靠它维持手感（S4 的 `netsim-uplink-loss-causes-server-reuse-input` 用例正是在验它）。改它会同时破坏一个已验收的机制。抑制标记是正交的开关，两者互不干扰。

**为什么不是「完全冻结整个实体」** —— 断线玩家的 Buff 剩余帧、体力恢复、被他人施加的击退位移都应继续演化。世界不为他停下，否则一个人断线就能把自己变成无敌的静止障碍物。**只冻结主动输入，其余照常 tick。**

**与 S8 的交互**：冻结后残留输入不再驱动移动，所以断线玩家不会因为「按住方向键时断线」而撞进别人触发击退。用例 `disconnected-player-does-not-trigger-knockback` 锁住这条。

但断线玩家**仍可被别人撞**（他是合法的碰撞体与击退目标），这是正确行为，不要一起冻掉。

**已在执行中的 Dash 怎么办**：Dash 是 SkillGraph + Buff 驱动的，起手帧已锁方向，不读后续输入 —— 它会自然跑完，不需要特殊处理。这是 S8 决策一「方向在起手帧锁定」带来的意外好处，**但要补用例确认**，别假设。

## 决策三：属性基线改成 per-observer，与 Buff 对齐；不扩 Join 响应

重连响应里**不**塞完整世界快照 —— 全量快照的序列化通路已经存在且被 106 条用例覆盖（`BattleSnapshotProtocolMapper`）。在 Join 响应里另写一份「完整状态」等于新增第二条状态传输路径，两条会分叉且新路径无既有用例守护。这与 S5「改测试通路而非加一条用例」同源。

恢复靠**下一个 `S2C_FrameSnapshot` 自然走全量**。但要让它真的全量，必须先修属性基线的索引粒度。

**把 `_lastBroadcastAttributesByPlayerId` 改成按 `(observerSessionId, targetPlayerId)` 索引**，与 `_buffBaselinesByObserverTarget` 一致；`BuildAttributeSyncPlans` 从「每次广播算一次」移进 per-session 循环。

有两个看起来更省事的改法，**都是错的，不要选**：

**❌ 「重连时清该 playerId 的属性基线」** —— 属性掩码是全房间共享的，清一个 playerId 的条目既不足又过头：

- **不足** —— 重连客户端需要的是**房间内所有玩家**的属性全量，不只是自己的。清自己那条对别人的属性无效，正确性仍然落回「新 session 没有 Buff 基线」这条巧合，等于没修
- **过头** —— 会把该玩家的属性全量推给所有无关观察者，白费带宽

**❌ 「per-session 覆盖掩码」** —— 见 Context「属性基线的尾部更新是条件式的」一节：属性基线尾部更新是条件式的（`DirtyMask == None` 时不推进帧号），重连帧属性恰好无变化时（属性变化稀疏，这是常见情况）全局基线与重连客户端基线会错开，下一帧增量被 `MergeAttributes` 判 `Diverged` 拒收。改动小，但把 bug 换了个触发条件留在原地。

**顺带删掉 `HasObserverWithoutBuffBaseline`** —— 它是这个粒度错配的补丁，全项目仅一处调用。属性改成 per-observer 后，新观察者天然查不到属性基线 → 自然全量，不再需要借 Buff 的缺失来判断。

**这不是顺手重构，是 S9 的必需项**：不改粒度就没有任何办法在不误伤其他观察者的前提下给重连 session 补全量。

**代价与验证**：

- 内存从 `O(玩家数)` 变成 `O(观察者数 × 玩家数)`。demo 量级（个位数玩家）可忽略，但要在风险表记一笔
- **删掉 crutch 会带来一处合法的行为变化**：新观察者加入时，改造前是「所有玩家的属性对**所有人**强制全量」，改造后是「只对新观察者全量」。带宽统计里的全量尖峰会变小 —— 这是改进，但要写进验收指南，否则会被误判为脏同步失效
- 旧 sessionId 的两张基线条目、`_playerIdBySessionId` / `_rttTrackersBySessionId` 映射都必须在认领成功时清掉，否则随重连次数单调增长

**重连后第一帧下行包会明显大于稳态**（全量属性 + 全量 Buff）。单玩家量级可忽略，但要能在带宽统计里看出这个尖峰。

## 决策四：断线判据双源 —— session dispose 与 RTT 探测连续超时

只看 `session.IsDisposed` 在「拔网线」场景下可能长时间不触发（见 Context「服务端没有 idle checker」一节）。第二个判据复用 S7 已在跑的 RTT 探测。

**但判据所需的数据现在并不存在，必须新增。** `ServerRttTracker.TimedOutProbeCount`（`ServerRttTracker.cs:86`，在 `:189` 递增）是**累计值**，成功 Ack 走 `ApplySample`（`:207`）**不会重置它**。一个跑了十分钟的正常连接照样会攒出一堆超时 —— **直接拿它当判据 = 稳定误杀所有长连接**。

新增一个**连续**计数器与明确状态机：

| 元素 | 定义 |
|---|---|
| `ConsecutiveTimedOutProbeCount` | 探测在 `CleanupStale` 中过期时 `++` |
| 归零条件 | 有效 Ack（`TryRecordAck` 返回 true）**或**任何有效业务包到达 |
| 判定阈值 | 连续 N 次（N 可配，默认 3） |
| 首次判定耗时 | `ProbeTimeoutMs + (N-1) × ProbeIntervalFrames × 33.333ms` |

**判定耗时按实际参数算，约 5.7 秒** —— `BattleRttConfig.DefaultProbeTimeoutMs = 5000`、`DefaultProbeIntervalFrames = 10`（约 333ms），取 N=3 得 `5000 + 2×333 ≈ 5.67` 秒。想压到 3 秒必须**同时**下调 `ProbeTimeoutMs`，而它是 S7 已验收参数，动它要重跑 S7 那 19 条用例。

**本阶段不动 S7 参数，接受约 5.7 秒判定，宽限期从判定时刻起算。** 后果是「拔网线」到「界面显示断线」有约 6 秒延迟；录屏用主动断开（走 dispose 判据，即时）作为主素材，探测判据作补充说明。这个取舍必须写进验收指南，否则会被当成「判据失效」。

**两个判据语义不同，不要混**：

- **dispose** = 确定性断开 → 立即进宽限期，**不可撤销**
- **探测连续超时** = 推定断开 → 进宽限期，**必须可撤销**（session 可能还活着）

**撤销入口必须落到具体 handler，不能只写抽象规则** —— 「任何包到达即撤销」在实现时会变成「谁都以为别人做了」。明确列出：`SubmitInput`、`SubmitRttProbeAck`、`SubmitStateHashReport`（`BattleComponent` 现有的三个入口），每个都要归零连续计数并撤销推定断开。将来新增任何客户端上行入口都必须加进这个列表。

**已 dispose 的确定性断开不得被迟到包撤销** —— session 已销毁却因一个迟到包退出宽限期，玩家会卡在「服务端认为在线、实际无连接」的状态，直到宽限期外的某个时刻才被发现。

**这条是本阶段最容易做错的地方**。用例三条：`probe-timeout-disconnect-is-revoked-on-late-packet`（可撤销）、`successful-ack-resets-consecutive-probe-timeouts`（连续语义，直接抓「误用累计值」）、`disposed-disconnect-is-not-revoked-by-late-packet`（确定性断开不可撤销）。S4 的注入设施能构造出误伤场景。

## 决策五：重连不清零累计诊断计数

`SetJoined` 现在会把 `_rollbackCount` / `StateMismatchCount` / `PositionMismatchCount` / `StaminaMismatchCount` / `HashReportsSent` 等清零。重连场景下需要**跨重连累计**的口径，否则报告里看不出「重连后是否收敛」。

做法：把这批诊断计数从 `SetJoined` 的重置清单里拆出来，改由一个显式的「新战斗」入口重置；重连走的 rejoin 路径保留累计值，并额外记录重连发生时的帧号与当时的计数快照，报告里给出「重连后新增的 mismatch/rollback」。

**为什么重要** —— 完成标准里有一条「重连后 mismatch/rollback 在有界帧数内回到基线水平」。若计数从零开始，这条判据无法与重连前对照，等于空转（[设计教训](设计教训-两类静默失效.md) 第一节那类「判据绕过真实区间」）。

新增 report 字段：`reconnectCount`、`lastReconnectFrame`、`rollbackCountAtReconnect`、`stateMismatchCountAtReconnect`、`framesToConvergeAfterReconnect`。

## 决策六：无头断连注入走生产同一函数

在 `BattleComponent` 上把「进入宽限期」抽成一个显式方法（如 `MarkDisconnected(long sessionId, DisconnectCause cause)`）。生产路径由 `CleanupDisconnectedPlayers` 检测到 dispose 后调它，RTT 超时判据也调它；**无头测试直接调同一个方法**。

**为什么不给测试单独开一条模拟路径** —— S5 的教训就是「测试绕过真实路径」：精度 bug 已修但无头测试从不走 proto，于是全绿却什么都没证明。断连注入若走独立实现，测的就是那份实现，不是生产行为。

同理，重连认领也必须走真实的 `C2B_JoinBattle` 处理逻辑（含 proto 往返，S5 已铺好通路），不能在 harness 里直接改字典。

## 决策七：宽限期条目带 sessionId 与状态，`MarkDisconnected` 必须幂等

决策四的「任何包到达即撤销推定断开」若不限定来源与时机，会与决策一的认领产生两处竞态。

**竞态一：新 session 已认领后，旧 session 的迟到包仍在撤销** —— 旧连接的残留包（弱网下可能延迟数百毫秒）会去解除一个已经被新 session 接管的状态，可能错误解除输入抑制或搅乱映射。

对策：宽限期条目携带 `DisconnectedSessionId` 与显式状态（`SuspectedDisconnected` / `ConfirmedDisconnected` / `Claimed`）。**撤销只在两个条件同时成立时生效**：条目仍处于 `SuspectedDisconnected`，且包来自 `DisconnectedSessionId` 那条 session。

认领成功的顺序：**先把旧条目置为 `Claimed`（终结态），再删旧映射** —— 顺序颠倒会留下一个「条目还在 Suspected、映射已没了」的窗口。此后旧 session 的任何包一律忽略。

**竞态二：`MarkDisconnected` 每帧重复调用会不断重置宽限期倒计时** —— `CleanupDisconnectedPlayers` 每帧扫一遍，一个 disposed 的 session 会被反复命中；探测判据同理。若每次调用都新建条目或重置剩余帧数，**宽限期永不到期**，玩家实体永久驻留。这个 bug 的症状是「宽限期功能看起来正常，只是从来不过期」，很容易在只测重连成功路径时漏掉。

对策：`MarkDisconnected` 幂等 —— 条目已存在时只做状态提升（`Suspected` → `Confirmed`，如 dispose 判据后至），**不重置剩余帧数**。用例 `mark-disconnected-is-idempotent-and-grace-still-expires` 锁住。

## 决策八：自动化也走真实登录，不开跳过鉴权的后门

**这是本阶段最大的风险点，也是工作量最集中的一处。**

现状：`BattleAutomationConfig` 只有战斗服地址与端口（默认 20101），整个 `BattleAutomationRuntime` 搜不到登录/账号/20001 相关代码。8 个既有 `two-client-*` 场景全部直连战斗服、发空 `C2B_JoinBattle`。**登录强制后它们会在握手阶段全灭。**

三个选项，选第一个：

| 选项 | 取舍 |
|---|---|
| **A. 自动化走真实登录（选它）** | 场景启动前预置测试账号，客户端先连 Auth 取 token 再连 Battle。改动集中在自动化配置与握手段 |
| B. 给自动化开「跳过鉴权」开关 | 改动最小，但**鉴权链路永远没有自动化覆盖** |
| C. 自动化直接注入伪造 token | 同样绕过真实签发路径 |

**拒绝 B/C 的理由是 S5 的教训**：精度 bug 已修但无头测试从不走 proto，于是全绿却什么都没证明。鉴权若开后门，测的就是后门，不是生产行为。这会完整重复 [设计教训](设计教训-两类静默失效.md) 第二节那类失效。

代价（必须写进验收指南）：

- 自动化新增两项前置：Authentication scene 可用、测试账号已预置。Mongo 本来就是硬依赖（Context 已实测），**不算新增**
- **双客户端场景必须用两个不同账号** —— 决策一「一个账号一个槽位」意味着共用账号会让第二个客户端拿到幂等响应、看不到自己的球。这个坑的症状是「client-b 一直等不到 joined」
- 8 个既有场景逐个回归，这是 Step 12 的主要工作量

**共享层用例不受影响** —— 它们是进程内客户端仿真，不走真实 Fantasy Session 与 Join RPC。新增的鉴权用例也在进程内验证会话表逻辑。

## 决策九：重连后到首个全量快照之前，不预测、不发玩法输入

**Join 响应只带位置，属性/Buff/体力要等下一帧快照** —— 而现在 `SetJoined` 会在 `ClearWorldState()` 后**立刻**把玩家按默认属性建出来并放行仿真（`BattleSimulation.cs:309` 起）。`_isJoined` 一旦为真，`Tick`（`:262`）就开始跑预测与输入。

后果：**首个全量快照到达前，客户端拿默认体力/Buff/速度做预测**，可能发出一个自己其实没体力的 Dash，也可能按错误的移速预测位置。首包若被弱网延迟或丢弃，这段错误预测会持续多帧，然后在快照到达时表现为一次大回滚 —— 排查时会先怀疑回滚逻辑，而根因在这里。

新增 `RejoiningAwaitingFullSnapshot` 阶段：

| 时点 | 允许 | 禁止 |
|---|---|---|
| 收到 Join 响应 | 对齐 `selfPlayerId` 与帧号、建本体、渲染占位 | **预测、发玩法输入、回滚** |
| 收到并成功合并首个全量快照 | 全部恢复 | —— |

**实现约束：不要靠「让 `_isJoined` 保持 false」来实现这个门禁。** `AlignLocalFrame`（`:369`）在 `!_isJoined` 时**直接抛异常**，而重连流程必须对齐帧号 —— 这么做会让重连一进来就崩。

正确做法是**加一个正交标记**（如 `_awaitingFullSnapshot`）：`_isJoined` 照常置真让帧对齐可用，`Tick` 在该标记为真时短路返回 `default`，合并首个全量快照后清标记。这与决策二「输入抑制用正交标记、不动复用分支」是同一手法。

**「成功合并」的判定要明确**：`MergeAttributes` 返回 `Diverged` 不算成功（说明基线错位），不能清标记。否则会在错位状态下放行预测，比不设门禁更糟。

**首包迟迟不来时不能把客户端永久卡死** —— 需要超时兜底：超过 N 帧未收到可合并的全量快照就回到重连流程重试（与 Step 8 的 token 失效降级同一入口）。用例 `no-gameplay-input-while-awaiting-full-snapshot` 与 `awaiting-full-snapshot-times-out-into-retry` 各锁一头。

## 架构

一次完整的登录-断线-重连时序：

```
[登录]  client ──C2A_LoginRequest──> Auth(20001)
        Auth: 校验账号密码 → 生成 token → 写会话表{token→accountId,过期}
             ──A2C_LoginResponse{Token}──> client 缓存 token

[进战斗] client: Disconnect() → 连 Battle(20101)
        ──C2B_JoinBattle{Token}──> Battle
        Battle: 读会话表校验 → 得 accountId → 无条目 → 建新玩家，槽位绑 accountId
             ──Response{PlayerId, 出生点, ServerFrameIndex, IsReconnect=false}──>

[稳态]  client A ──输入──> server ──快照──> client A

[断开]  client A ×
        server: session dispose（确定性）或 探测连续 N 次超时（推定）
             → MarkDisconnected(sessionId, cause)      ← 幂等，不重置倒计时（决策七）
             → 宽限期条目（按 accountId 索引）
                { accountId, playerId, 剩余帧数,
                  DisconnectedSessionId, 状态 }
               ↑ 不存 token —— token 在 Auth 会话表里（决策一）
             → SetInputSuppressed(playerId, true)      ← 决策二
             → 实体留在仿真里，Buff/体力继续 tick

[宽限期内] 其他客户端照常收到该玩家快照（不因输入移动，但可被撞）
           每帧递减剩余帧数
           推定断开 + 包来自同一 session → 撤销，退出宽限期（决策四/七）
           确定性断开 → 不可撤销

[重连]  client A ──C2B_JoinBattle{Token}──> server   ← 同一枚登录 token，原样再发
        server: 读会话表校验 token → 得 accountId（与首次进入同一请求形态）
             → accountId 有宽限期条目: 复用 playerId，重绑 session
                     旧条目置 Claimed → 再删旧映射（决策七顺序）
                     清旧 sessionId 的属性/Buff 基线残留（决策三）
                     SetInputSuppressed(false)
                     ──Response{IsReconnect=true}──>
             → token 无效/过期: 统一错误码拒绝，不建玩家（决策一）
        client A: SetJoined(权威态) → AlignLocalFrame → 累计计数保留（决策五）

[恢复]  下一帧 S2C_FrameSnapshot 全量 → 客户端逐位重建
        lead 从 MinLeadFrames 重新收敛（RTT tracker 是新的）

[宽限期满未重连]  → 走既有的完整清理路径 RemovePlayer(playerId)
```

**关键顺序约束**（写错则症状与未实现一致）：

1. **`Join` 开头的 `CleanupDisconnectedPlayers()` 必须先改成「只清宽限期已满的」** —— 不改则重连请求先删掉自己要认领的实体，认领必定失败，且症状看起来像 token 不匹配。
2. **同一 accountId 的认领必须串行** —— token 可重复出示（决策一），两个并发 Join 携带同一枚 token 都会通过校验。防双重接管靠的不再是「token 一次性」，而是**条目状态机**：`Claimed` 是终结态，第二个请求看到它就走「已有在线槽位」的幂等分支。用例 `concurrent-claims-are-serialized` 锁住。**这条是登录方案与自签方案的关键差异，容易照抄旧逻辑写错。**
3. **旧条目置 `Claimed` 必须在删旧映射之前**（决策七）—— 顺序颠倒会留下可被旧 session 迟到包撤销的窗口。
4. **清旧 sessionId 的基线条目必须在重绑之后、下一次 `BroadcastSnapshot` 之前** —— 属性改 per-observer 后，新 sessionId 天然无基线即全量，此处清的是**旧 sessionId 的残留条目**（防内存增长），别把两件事搞混。
5. **解除输入抑制必须在重绑 session 之后** —— 提前解除会让宽限期末尾的残留输入生效。

## 用例分层：为什么不能全放一个文件

**`BattlePredictionSelfTestSuite` 是双端共享源码，不是客户端专属。** `Entity.csproj` 用 `<Compile Include>` 把它逐文件链进服务端程序集（`Entity.csproj:32-38`），所以它**同时在 Unity 与服务端两个程序集里编译**，并且两端都有执行入口：

| 入口 | 位置 |
|---|---|
| Unity | `BattleSimulation.cs:402` → `BattlePredictionSelfTestSuite.Run` |
| 服务端 | `TestRunner.cs:492` → `BattlePredictionSelfTestSuite.RunCase` |

**由此得到硬约束：写进 `.S9.cs` 的代码只能引用两端都可见的类型**（`GameShared/**` 全部 + `Entity.csproj:33-38` 显式列举的那几个 GameLogic 文件）。

`BattleComponent` 在 `GameServer/Server/Entity/Battle/`，**不在共享集里**；`Session`、Fantasy 实体、Mongo API 同理。把它们写进 `.S9.cs` → **Unity 侧编译失败**，而且失败点在测试文件里，看起来像用例写错，实际是分层错。

因此按可见性分两层：

| 层 | 放哪 | 能测什么 | 计数 |
|---|---|---|---|
| **共享层（19 条）** | `.S9.cs`（Unity 目录，链进服务端） | 纯逻辑：输入抑制语义、属性基线粒度、Buff/体力恢复、客户端重连重建、RTT 连续计数 | 进 Unity 套件，**106 + 19 = 125** |
| **服务端层（19 条）** | `GameServer/Server/Entity/TestHarness/` 新建文件，`TestRunner` 分发 | `BattleComponent` 宽限期与认领、并发串行、session 语义、Auth 会话表与 token 校验 | 只在服务端 harness 跑 |

**不要用一个总数汇报**，两层各报各的：**Unity 套件 125 条** + **服务端 harness 19 条**。验证方式与完成标准都按这两个数字写 —— 合成一个数会掩盖「服务端层根本没跑」这种情况。

**服务端层不是「不受 Mongo 影响的进程内仿真」** —— 涉及会话表的用例要真连 Mongo（服务端启动本就硬依赖它，见 Context）。这几条属于集成测试，跑之前确认 mongod 在跑。

## 验证方式

1. **无头自测** —— Unity 套件 125 条全绿（既有 106 + 共享层 19）**且**服务端 harness 19 条全绿。**Step 3 完成时先单独跑一次既有 106 条**，属性基线粒度改造必须在引入任何重连逻辑之前自证无回归。
2. **`fixed-physics-bit-exact` 基线必须不变** —— S9 不改仿真内核，哈希基线变化即为真 bug，**不要改基线迁就**（与 S8 相反，S8 是刻意改内核）。
3. **连续两跑输出一致** —— 排除 token 随机源污染确定性（token 不进快照/哈希，若基线抖动说明它漏进了仿真状态）。
4. **8 个既有 `two-client-*` 场景改走真实登录后逐个回归** —— 决策八的代价，也是鉴权链路真被覆盖的证据。**任何场景为了通过而绕过登录即本阶段失败。**
5. **`two-client-reconnect` 场景** —— client B 断开、宽限期内重连，两端 report 满足机械断言。
6. **弱网叠加** —— 在 S4 注入下跑重连场景，确认推定断开不误伤。

> **执行边界**：第 1~3 项的 `.NET` 无头部分与服务端 harness 由实现 agent 执行；第 4~6 项依赖真实 Unity 双客户端，归项目负责人。共享套件还需负责人在 Unity Editor 侧复核一次，agent 的 `.NET` 结果不能替代 Unity 实际编译与运行结果。

### 定量判据

绑定 `two-client-reconnect` 固定场景与固定种子：

- `reconnectCount == 1`，重连后 `selfPlayerId` 与断开前**相同**
- 重连后 `framesToConvergeAfterReconnect` 有界（阈值实现期实测后写死，不留「观察即可」）
- 重连后新增 `stateMismatchCount` 有界且不持续增长
- **断线后由主动输入产生的速度/位移为零；在无在途 Dash、无击退的隔离场景中位置保持不变**（决策二）
- 宽限期满未重连时 observer 侧 `activePlayerCount` 下降

> **不要把位置判据写成「宽限期内位置变化量为零」** —— **输入冻结 ≠ 位置冻结**。决策二明确「已起手的 Dash 自然跑完」（用例 `dash-in-flight-completes-during-disconnect`）且「断线玩家仍可被别人撞」（用例 `disconnected-player-remains-knockback-target`），两者都会让位置变化。总位置零的判据会与这两条用例互相打脸。位置零只在隔离场景成立；Dash 完成与外部击退由那两条专项用例各自验证，不用一条总判据覆盖所有情形。

3. 重连凭同一枚登录 token 拿回同一 playerId，位置/体力/Buff/Dash 剩余帧逐位恢复。（**负责人**）
4. 无效/过期 token 均不能进战斗也不能认领实体，失败统一错误码且不建玩家；拿别人 playerId 无法接管他人实体。（**agent 跑无头 / 负责人跑 Unity 集成**）
5. 断线玩家不因主动输入移动，但仍被 Buff/体力/他人击退/在途 Dash 影响。（**agent 跑无头 / 负责人跑 Unity 集成**）
6. 属性全量不再依赖 Buff 基线缺失（决策三），**Step 3 阶段由 agent 单独跑 `.NET` 回归验绿**，最终由负责人复核 Unity。（**agent + 负责人**）
7. 推定断开可被同源迟到包撤销、确定性断开不可撤销，弱网注入下无误伤。（**agent 跑无头 / 负责人跑 Unity 弱网**）
8. 重连后 mismatch/rollback 在有界帧数内回到基线水平（累计计数可对照）。（**agent 跑 report 断言 / 负责人跑 Unity 集成**）
9. **8 个既有 `two-client-*` 场景改走真实登录后全部通过**，且自动化路径无跳过鉴权的开关或伪造 token。（**负责人**跑场景 / **agent** 自检 grep 无后门）
10. **画面上能看出断线、宽限期倒计时、重连成功与收敛过程**（**负责人**，真机观测须回填）。
11. 服务端编译通过 + 各 Step 静态检查全过。（**agent**，交付硬门槛）

## 风险与对策

| 风险 | 后果 | 对策 |
|---|---|---|
| `Join` 开头的清理未改 | 认领必定失败，症状伪装成 token 不匹配 | Step 1 必须先改；用例 `reconnect-token-claims-same-player-id` 直接暴露 |
| 属性基线粒度不改，只清 playerId 条目 | 既不足（别人属性对新 session 仍是增量）又过头（推给无关观察者），bug 原地保留 | 决策三改索引粒度；Step 3 独立跑绿；5 条专项用例 |
| 属性改 per-observer 后内存增长 | `O(观察者 × 玩家)`，demo 量级可忽略 | 记录不做上限，多人场景需复评 |
| 照抄自签方案的「token 一次性 + 失效后再动状态」 | 登录 token 可重复出示，一次性逻辑会让重连必失败 | 决策一；并发防护改走条目状态机；用例 `concurrent-claims-are-serialized` |
| token 过期时长配得小于宽限期 | 宽限期未满但 token 已过期，重连必失败且看起来像宽限期失效 | 决策一要求两者独立配置且过期远大于宽限期；用例 `expired-login-token-cannot-join-or-claim` |
| 自动化开鉴权后门 | 鉴权链路永无自动化覆盖，重复 S5 教训 | 决策八；Step 11 自检 grep 无跳过开关/伪造 token |
| 双客户端场景共用一个账号 | 第二个客户端拿幂等响应、看不到自己的球（症状是「client-b 等不到 joined」） | 决策八；Step 11 自检 grep 两账号不同 |
| 忘删 `GameApp` 无条件建沙盒路径 | **登录形同虚设但画面完全正常**（`Create()` 有幂等守卫，看不出来） | Step 5 显式删除 + 自检 grep |
| 把服务端类型写进共享层用例文件 | Unity 侧编译失败，且失败点在测试文件里、看起来像用例写错 | 「用例分层」一节；Step 10 自检 grep |
| 漏加 `Entity.csproj` 的 `<Compile Include>` 行 | 共享层用例在服务端**静默不编译**，少跑一批却不报错 | Step 10 自检；GameLogic 是逐文件列举不是通配 |
| 在线槽位一律返回幂等响应 | 新 session 无 `_playerIdBySessionId` 映射 → 收不到快照、输入被静默丢弃，但握手成功、界面正常 | 决策一按 session 分流；用例 `online-slot-rejects-different-session` |
| 快速重连撞上「旧 session 未观察到 dispose」 | 被判「账号已在线」而永久失败 | 该错误必须可退避重试；用例 `fast-reconnect-before-dispose-observed-retries-then-succeeds` |
| 首个全量快照前就放行预测 | 用默认体力/Buff 预测，发出无体力的 Dash，首包到达时一次大回滚（会被误查成回滚 bug） | 决策九 `_awaitingFullSnapshot` 门禁 |
| 用「`_isJoined` 保持 false」实现等待门禁 | `AlignLocalFrame` 抛异常，重连一进来就崩 | 决策九明确用正交标记 |
| 解除抑制首帧复用断线前输入 | 玩家一接回就朝断线时方向自己走一步 | 决策二要求进入抑制时清 `_lastConsumedInputByPlayerId`；用例 `no-stale-input-reuse-on-first-frame-after-unsuppress` |
| 照抄不存在的 timeout 组件范式 | `AccountTimeOutComponent` 等只是空数据实体、零引用，抄不到东西 | Step 4 列明五条待定项，清理策略自己定 |
| token 过期后客户端无限重试 | 画面卡在「重连中」永不结束的静默死循环 | Step 8 要求降级回登录流程 + 重试次数上限 |
| 新增 Auth/测试账号前置未写进指南 | 验收在「连不上」上白耗时间（Mongo 本就是硬依赖，Step 0 已实测） | Step 13 写前置清单，排查第一项是 mongod |
| 误用累计 `TimedOutProbeCount` 当判据 | 正常长连接攒够超时被误判断线 | 决策四新增连续计数器；用例 `successful-ack-resets-consecutive-probe-timeouts` |
| `MarkDisconnected` 非幂等 | 每帧重置倒计时，宽限期永不到期（症状是「功能正常只是不过期」） | 决策七；用例 `mark-disconnected-is-idempotent-and-grace-still-expires` |
| 抑制标记漏进快照/哈希 | 两端必然失配，全场回滚 | Step 2 明确不进；连续两跑一致可暴露 |
| 推定断开不可撤销 / 撤销不限来源 | 前者弱网误踢，后者旧 session 迟到包搅乱新状态 | 决策四 + 决策七；三条专项用例 + S4 注入验证 |
| 认领失败静默建新玩家 | 客户端以为接回原实体，实际是新球，排查方向跑偏 | 决策一失败语义定稿：统一拒绝、不建玩家 |
| 重连后第一次修正超过平滑阈值 | 走硬跳，画面突兀 | Step 7 显式处理重连帧，不靠调大阈值（会毁掉 S8 击退的平滑演示） |
| token 随机源污染确定性 | 哈希基线抖动 | token 不进快照/哈希；连续两跑一致作为守卫 |
| 宽限期内重复 Join 请求 | 状态机竞态、双重接管 | 认领分支幂等 + 条目 `Claimed` 终结态（决策一/七） |
| 重连风暴 | 单机 demo 无压力，但服务端无限流 | 本阶段记录不做，写进非目标 |

## 验收指南

实现完成后产出 `Tools/AutomationAcceptance/断线重连-验收测试指南-20260808.md`，**写成给项目负责人的真实 Unity 逐步操作手册，同时记录 agent 已执行的自动化命令与结果**（形态与内容要求见「职责边界与交付门槛」末节）。

前置条件一节必须完整列出：**mongod 在跑**（Step 0 已实测：不跑则服务端 30 秒超时失败）、Authentication scene 可用、端口 20001 与 20101、测试账号预置方式（双客户端要两个不同账号）、Unity 版本、dotnet SDK 选择（`dotnet --list-sdks` 先确认，选错报 `NETSDK1045`）。

**指南里必须写明三条容易被误判为缺陷的预期行为**：

1. **探测判据约 5.7 秒才判定**（决策四，不动 S7 参数的结果）。验收「拔网线」时若 6 秒内没看到断线提示，**不是判据失效**。主动断开走 dispose 判据是即时的 —— 录屏用主动断开作主素材。
2. **新观察者加入时的带宽全量尖峰会比 S9 之前小**（删掉 crutch 后只对新观察者全量，不再波及所有人）。这是改进，不是脏同步失效。
3. **重连后前若干帧 lead 会从 `MinLeadFrames` 重新爬升**（RTT tracker 按 sessionId 索引，新 session 无样本 → 退回客户端自算，见 Context）。这是预期，不是超前量控制失效。

**须同步更新的既有指南**：本阶段不改哈希基线，故三份含基线的指南（`哈希上报`、`物理层重写`、`预测误差平滑`）**不需要改动** —— 但要在验收时确认基线确实没变。`属性与Buff增量恢复-验收测试指南-20260805.md`（B1）**需要复核**：属性基线改 per-observer 后其描述的机制粒度已变，判据本身应仍成立，但措辞要跟上。
