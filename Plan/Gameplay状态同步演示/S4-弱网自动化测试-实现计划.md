## Context

### 弱网设施完全不存在

全仓 `latency` / 丢包相关标识零命中；`jitter` 唯一命中是 `InputBufferTuning.cs:15` 的 `JitterBufferFrames = 2`，那是抖动**缓冲**参数，不是抖动**注入**。Fantasy 网络库自身也不带模拟功能（`Fantasy.Unity` 全目录搜 `simulat` / `packetLoss` 零命中）。

而 Timeline 的 P4 完成标准明确写了「使用本地弱网工具施加延迟/抖动/丢包」。这个工具从来没有被实现过，P4 的验证方式因此一直无法执行。

| 阶段 | 悬空的判据 | 为什么零延迟下无意义 |
|------|-----------|---------------------|

| S3 | 「`rollbackCount` 是否显著低于修复前」 | 「修复前每个权威快照都触发一次回滚」**至今仍是推论**，未实测 |

### 输入没有冗余，丢一个包就产生真实分歧

客户端每帧发一次输入，**无重发、无冗余窗口**（`BattleSimulation.cs:216`，`_onSendInput(frameIndex, ++_inputSeq, dx, dy, skillId)`）。服务端 `Tick` 消费输入时，若该帧输入缺失，**复用上一帧已消费的输入**（`BattleLogic.cs:227`，`ReusedInputCount++`），两端都无输入历史则回落零输入（`:231`，`ZeroInputFallbackCount++`）。

于是丢一个输入包，那一帧客户端按真实输入预测、服务端按旧输入推进，**两端预测态真实分歧**，直到权威快照到达才被修正。

**副产品**：`ReusedInputCount` / `ZeroInputFallbackCount` 两个计数器已存在，上行丢包在服务端天然可观测，不需要新增计数器去证明注入生效。

**注意**：这产生的是**预测态**分歧，不是哈希对账会报的那种分歧。两者的区别是本计划决策三的全部内容，动手前必读。

### 无头测试有两类客户端载体，只有一类能注入

| 载体 | 出现在 | 驱动 `BattleSimulation` | 能否注入弱网 |
|------|--------|------------------------|-------------|
| `SimulatedClient` | 5 个 scenario（Determinism / Consistency / PlayerCollision / Convergence / PlayerLeave） | ❌ 否 | ❌ 不能 |
| 真正的 `BattleSimulation` | `BattlePredictionSelfTestSuite` 的 29 条 case | ✅ 是 | ✅ 能 |

`SimulatedClient` 全文 41 行，是个被动壳子：`ApplySnapshot` 直接 `RestoreSnapshot`，无预测、无回滚、无 lead frame；输入经构造注入的委托**同步直呼** `battleLogic.SubmitInput`，快照经 `OnBroadcast` 同步推给所有客户端（`TestRunner.cs:1037`）。链路上没有任何可延迟的缝。

**因此本阶段的无头用例走 `BattlePredictionSelfTestSuite` 风格（`BattleSimulation` 直驱），不改造那 5 个 scenario 的 harness。**

### 关键前提：客户端上报的哈希是什么

这一节是本计划的地基，上一版在这里判断错了，导致整节决策作废。

`SendHashReportIfNeeded`（`BattleSimulation.cs:550-570`）：

```
if (!_authoritativeSnapshots.TryGet(_lastAppliedFrame, out BattleWorldSnapshot snapshot)) return;
_onSendHashReport(_lastAppliedFrame, StateHasher.Hash(snapshot));
```

`_authoritativeSnapshots` 全文唯一写入点是 `:485`（`ReconcileAuthoritativeSnapshot` 内），存的是**服务端发来的权威快照**。所以：

- 哈希的对象是**服务端自己的快照**，不是客户端预测态
- 帧号是 `_lastAppliedFrame`（最后应用的权威帧），不是当前预测帧
- 调用位置在 `AdvancePredictionTo` 之后，但那只影响**何时算**，不影响**算什么**

**这个对账实际回答的是：服务端权威快照经过 proto 序列化、网络传输、客户端重建之后，是否还与服务端原始状态逐位相同。** 即「往返无损 + 两端 hasher 口径一致」。它不回答「客户端预测对不对」，也不回答「两端模拟是否发散」。

服务端侧对照：`BattleLogic.cs:248` 在每帧 Tick 末尾 `_authoritativeHashHistory.Save(frameIndex, StateHasher.Hash(snapshot.ToBattleWorldSnapshot()))`，`TryCompareReportedHash`（`:257`）按帧号取出比对。

### `ConvertSnapshot` 是有状态增量合并，不是纯转换

这是决定注入位置的关键事实。`ConvertSnapshot`（`BattleClientController.cs:582-644`）内部：

| 行 | 副作用 |
|----|--------|
| `:590` | `_authoritativePlayersInSnapshot.Add(player.PlayerId)` |
| `:591-603` | 取客户端缓存基线 → `PlayerAttributeSync.Merge(baseline, dirtyMask, ...)` |
| **`:605`** | **`_authoritativeAttributesByPlayerId[player.PlayerId] = mergedAttributes`** ← 属性基线更新 |
| `:604` → `:732-787` | `ResolveAuthoritativeBuffSnapshot`，其中 **`:742`** / **`:782`** 更新 Buff 基线 |
| `:630` | `CleanupStaleAuthoritativeState()` |

服务端只发脏字段（`BattleComponent.cs:190-192`，`ComputeDirtyMask`），客户端靠自己缓存的基线补齐未变字段。**所以「快照可见性」和「基线更新」是两件事，注入位置决定动到哪一件。**

## 决策一：注入在逻辑层，且丢包与延迟分处不同位置

**选定：在 `BattleClientController` 内包装收发回调，不动 `GameClient`、不动 Fantasy、不动服务端。**

上行有现成的注入缝——`BattleSimulation` 构造时注入三个回调，覆盖全部战斗上行消息：

```
BattleSimulation.cs:28-30
  _onSendInput       // BattleInputSender(uint frameIndex, uint inputSeq, Fixed64 dx, Fixed64 dy, int skillId)
  _onSendPing        // Action<ulong> sendTimestampMs
  _onSendHashReport  // Action<uint, ulong>? (frameIndex, stateHash)
```

生产实参在 `BattleClientController.cs:318-323`，三个都是同文件的 private static 方法（`:849`、`:861`、`:869`），各自只做「构造消息 + `GameClient.Instance.Send()`」。`BattlePredictionSelfTestSuite` 已在 `:895`、`:1017`、`:1202` 三处把它们换成 recorder，**证明这三个回调是可自由替换的纯函数式接缝**。

选这一层而非 `GameClient.Send` 或 KCP Channel，理由是**生命周期安全**：回调签名是已解包的强类型标量，延迟队列可以安全持有 `(frameIndex, inputSeq, dx, dy, skillId)` 到未来某刻再真正发送。而 `GameClient.Send` 与 Channel 层拿到的是**池化消息对象**，`MessageDispatcherComponent.cs:193` 在回调返回后立即 `Dispose()`，缓存引用会读到被复用的垃圾数据。

### 下行：丢包在转换前，延迟在转换后

**这是本版最重要的修正。上一版把两者合成一条「先转换再交给模拟器」，会导致 S4 测不到它声称要暴露的缺陷。**

因为 `ConvertSnapshot` 会更新属性与 Buff 基线（`:605`、`:742`、`:782`），**转换后再丢弃，等于客户端已经吸收了这份增量**。基线与服务端广播基线仍然同步，下一份快照照样正确合并，脏同步的丢包缺陷被完全掩盖。丢弃只让 `BattleSimulation` 少收一份权威快照——而那是它本来就会正常处理的情况（`EnqueueServerSnapshot` 本就允许跳帧）。

两者对「需要保留什么」的要求不同，因此分开处理：

| 方向 | 位置 | 保留成本 | 语义 |
|------|------|---------|------|
| **丢包判定** | `ConvertSnapshot` **之前** | **零**。判定命中直接 `return`，不转换不入队，池化对象立刻被上层 `Dispose()`，我们什么都没持有 | 「这条消息从未到达」。基线不更新，下一份增量合到过期基线上 → 真实缺陷暴露 |
| **延迟** | `ConvertSnapshot` **之后** | 持有 `BattleWorldSnapshot`（纯值类型，安全） | 只推后 `EnqueueServerSnapshot`。基线仍按到达顺序更新——纯延迟无丢包时增量链本就完整，不该人为打断 |

这样丢包路径**零分配、零保留**，而丢包正是要暴露缺陷的那条路径。同时天然避开了「转换发生在释放时刻」带来的乱序合并风险（见下）。

### 若改成「延迟也前置」，必须补一道单调帧闸

本计划**不选**这条路线，但记录代价，因为 S10 可能需要更严格的语义（「延迟到达的快照在到达前对客户端完全不可见」）。

那需要把池化 `IMessage` 深拷贝成普通 DTO，延迟后在释放时刻才转换。此时转换顺序不再等于到达顺序，而**转换是顺序敏感的有状态操作**：

- 帧 103 先转换 → 基线变成 103 的状态
- 帧 100 后转换 → 在 103 的基线上合并 100 的增量 → **属性静默错**

Buff 侧能拦住（`:762-777` 校验 `baseline.FrameIndex != player.BuffSnapshotFrameIndex`，不匹配则拒绝合并并置 `_playersAwaitingBuffFullSync`），**属性侧没有任何等价保护**——`PlayerAttributeSync.Merge`（`PlayerAttributeSync.cs:44`）签名里没有帧号或基线概念，全文 `FrameIndex` 零命中。

所以走那条路线必须在转换前加单调帧闸：帧号低于已转换最高帧的直接丢弃。**本版不走，故不实现。**

### 代价必须写清楚，这是要能对外讲的

本方案模拟的是**消息可见时刻**，不是真实 KCP 行为。丢包不会触发 KCP 的 ARQ 重传，因为包根本没进协议栈。这意味着：

- **注入的「丢包」等价于「该消息永久丢失」**，而真实 KCP 下丢包会被重传、表现为额外延迟而非丢失
- 所以本设施模拟的是**比真实 KCP 更严酷的条件**（永久丢失），这对暴露同步 bug 是好事，但不能对外宣称「模拟了真实网络」

要做真实 KCP 行为模拟，得改 `Fantasy.Unity/Runtime/Core/Network/Protocol/KCP/` 的 Channel（客户端有完整源码），但**服务端 Fantasy 是 NuGet 包无源码**（`Entity.csproj:13` 的 `<PackageReference Include="Fantasy-Net" Version="2026.0.1007" />`），只能做单向。收益不足，本阶段不做，**但要在验收指南与讲解要点里写明这个边界**。

## 决策二：乱序注入做不了，不要写进范围

`EnqueueServerSnapshot`（`BattleSimulation.cs:158-178`）会**静默丢弃**帧号 ≤ `_lastAppliedFrame`（`:165`）或 ≤ `_latestQueuedSnapshotFrame`（`:170`）的快照。所以在这一层重排快照顺序，旧的那个会被直接吞掉，观测不到任何「乱序」行为，只会表现为丢包。

**本阶段范围因此限定为「延迟 + 抖动 + 丢包」三项，不含乱序。** 抖动会让消息的**释放时刻**分散，但队列仍按帧号单调释放。

这不是缺陷，是分层的正常结果：可靠有序交付本就是传输层的职责，KCP 已经保证了，逻辑层看不到乱序才是对的。**讲解时这是个加分点，不是要藏的短板。**

## 决策三（已整节重写）：弱网下的 `HashMismatch` 是缺陷信号，不是预期结果

**上一版在这里判断错了。它以为客户端上报预测态哈希，于是推论「上行丢包会让客户端预测错 → HashMismatch 合法大量触发 → 需要按输入 reuse 分级告警」，并给出方案 A / B。这三步全部作废。**

### 为什么原推论不成立

见 Context「关键前提」一节：客户端哈希的是**服务端权威快照**（`_authoritativeSnapshots`，`:485` 唯一写入点），不是预测态。

于是上行输入丢包时：
- 服务端复用旧输入、客户端用真实输入 → **预测态**确实不同
- 但双方哈希的**都是同一份服务端权威快照** → 仍应逐位相等

**结论：上行输入丢包本身不会产生 `HashMismatch`。** 原方案 A（按 reuse 分级）压制的是不存在的误报，还会顺手把真实信号一起静音；原方案 B（对账后上报）**已经是现状**，是空操作。两者均删除。

### 弱网下真正会变化的是什么

| 指标 | 弱网下的变化 | 定性 |
|------|------------|------|
| `HashNoRecord` | 下行延迟让 `_lastAppliedFrame` 落后服务端 `LastFrameIndex` 更多；上行延迟让上报再迟到一截。超出 `_authoritativeHashHistory` 容量 64（`BattleLogic.cs:36`，30Hz 下约 2.13 秒）才会 noRecord | 预期。但按当量估算：200ms 下行 ≈ 6 帧 + 200ms 上行 ≈ 6 帧，共约 12 帧，**远未触及 64**。所以 noRecord 若真的大量出现，说明延迟远超预期或另有问题，值得查 |
| 上行哈希上报丢包 | 该帧不参与对账，样本变少 | 预期。不影响正确性判据 |
| **`HashMismatch`** | **见下** | **缺陷信号** |

### `HashMismatch` 在弱网下确实会响，原因是脏同步无丢包恢复

**下行快照丢包会真实触发 `HashMismatch`，而这是真缺陷，不是误报。**

机理（承接决策一）：丢包判定在 `ConvertSnapshot` 之前，所以被丢的那份快照，客户端的属性基线**没有吸收**它携带的脏字段。下一份快照到达时，客户端在过期基线上合并新增量 → 重建出的 `BattleWorldSnapshot` 与服务端原始状态不同 → 哈希不等 → `HashMismatch`。

而客户端**无从察觉**：`AttributeDirtyMask` 只说哪些字段变了，不说相对哪一帧。协议里没有属性基线版本信息，`PlayerAttributeSync.Merge` 也没有帧号参数。错位一旦发生就**永久保持**，直到该字段再次变更并被成功接收，或收到一次全量。

Buff 侧反而做对了——`:762-777` 校验基线帧不匹配就拒绝合并并置 `_playersAwaitingBuffFullSync`。但**这个等待态没有任何协议路径能告知服务端**：服务端 `BuildBuffSyncPayload`（`BattleComponent.cs:481-494`）只依据自己的 `_buffBaselinesByObserverTarget` 是否缺 key 决定发不发全量，两边永不交汇。所以客户端进入等待态后只是本地挂着，服务端不会补发。

### 因此本阶段的哈希判据

1. **正常路径（零丢包，可含延迟与抖动）：`HashMismatch` 必须为零。** 这是强判据，直接守 S2 买到的 bit-exact 与 S3 的往返无损。
2. **下行丢包场景：`HashMismatch > 0` 记录为待查缺陷，不写成「预期结果」。** 它是本阶段第一个真实产出。
3. **上行输入丢包场景：`HashMismatch` 仍应为零**（若不为零，说明还有别的问题）。同时 `ReusedInputCount > 0` 证明注入生效。

**验收指南必须区分这三条**，不能笼统写「弱网下 mismatch 属预期」——那会把最有价值的信号第一次跑就静音掉。

### 修复不在本阶段范围，但要写清修复面

暴露即达标，修复是独立决策。**已由 B1 落地**（2026-08-05，见 [缺陷修复/B1](缺陷修复/B1-属性与Buff增量丢包恢复-实现计划.md)）。**不能只给 `Merge` 加个校验就算完**，协议里根本没有属性基线信息。完整修复至少要：

1. 协议加属性基线帧号或状态版本号（对齐 Buff 的 `BuffSnapshotFrameIndex`）
2. 服务端按**观察者**维护属性基线——当前 `_lastBroadcastAttributesByPlayerId`（`BattleComponent.cs:187`）只按 `playerId` 键，与 Buff 的 `(observerSessionId, TargetPlayerId)` 不对称
3. 客户端检测到基线错位后的恢复通路：请求全量、或服务端周期性全量、或 ack 机制

**顺带记录一处待查项**（静态阅读所得，未跑验证）：属性全量当前搭在 Buff 全量上——`dirtyMask = buffPayload.IsFullSync || !hasPreviousAttributes ? All : ComputeDirtyMask(...)`（`BattleComponent.cs:190-192`）。新观察者接入时 Buff 侧缺 key → `IsFullSync = true` → 属性 mask 强制 `All`，于是新客户端拿到全量属性。能工作，但属性全量是 Buff 全量的**副作用**，改 Buff 逻辑会波及属性。

## 决策四：时间源必须外部注入，且收发两侧共用同一个

模拟器**自己绝不读时钟**。时间由调用方传入：

- **无头用例**：喂由帧号推导的合成毫秒，完全可复现
- **真实客户端**：喂 `DateTimeOffset.UtcNow.ToUnixTimeMilliseconds()`

### 但当前有两处硬编码墙钟，只改一处不够

| 位置 | 现状 | 影响 |
|------|------|------|
| `BattleSimulation.cs:548` | `_onSendPing((ulong)DateTimeOffset.UtcNow.ToUnixTimeMilliseconds())` —— **在 `BattleSimulation` 内部**读时钟 | ping 发出时间戳不可注入 |
| `BattleClientController.cs:432` | `long nowMs = DateTimeOffset.UtcNow...` 然后 `:433` 算 `rttMs` | pong 到达时间不可注入 |

RTT = 到达时刻 − 发出时刻，**两个时刻分处两个文件**。只改一处，RTT 里就混着真实墙钟与合成时钟，确定性无从谈起。所以本阶段必须让两侧共用同一个可注入时间源（见 Step 3.5）。

否则 `netsim-downlink-delay-raises-lead-frames` 只能绕过 ping 通路直调 `ProcessPong(200)`——那退化成测 `ProcessPong` 本身，证明不了注入生效。

### 合成时钟用 `FixedDeltaMilliseconds`，不要用 33

上一版写「喂 `frameIndex * 33`」。真实每帧是 `FixedDeltaMilliseconds = DeterminismRules.FixedFrameTime * 1000f`（`BattleSimulation.cs:25`），30Hz 下 ≈ 33.333ms。用 33 会每帧漂 −0.333ms，900 帧累计 −300ms。虽然可复现，但与仿真时间不一致，且与 `RefreshBaselineLeadFrames` 里的 `_rttEmaMs / 2.0f / FixedDeltaMilliseconds`（`:587-589`）口径冲突。

**用 `frameIndex * FixedDeltaMilliseconds` 并取整，或直接把延迟表达成帧数。**

### 随机源

抖动与丢包的随机源用 **`DeterministicRandom`**（`GameShared/ThirdParty/FixedMathSharp/Random/DeterministicRandom.cs`，xoroshiro128++ + splitmix64 播种，无分配，已通过 `Entity.csproj:24` 的 `GameShared/**` 通配链进服务端）。可用 API：`Next(int maxExclusive)`、`NextU64()`、`Next(int minInclusive, int maxExclusive)`。

**禁止用 `System.Random`** ——无种子则不可复现，用例会间歇性红。种子必须可配、必须记进 report.json。**失败时没有种子就无法复现。**

## 决策五：接线层必须可测，否则三个已知坑全无覆盖

`Entity.csproj` 只逐个链接了三个 GameLogic 文件：

```
Entity.csproj:25  BattleSimulation.cs
Entity.csproj:26  PredictionErrorSmoother.cs
Entity.csproj:27  BattlePredictionSelfTestSuite.cs
```

**`BattleClientController.cs` 不在其中**（它依赖 Unity 与 Fantasy 客户端，链不进服务端）。

而本计划预判的三个坑——Pump 位置、Pong 拆分、丢包/延迟的前后位置——**全部在 `BattleClientController` 里**。若只把模拟器原语做成可测，无头用例守的是原语，不是接线。上一版的完成标准 #2 说 `netsim-disabled-is-passthrough` 守直通路径，它守的是**模拟器的**直通，不是**接线的**直通。

**选定：把收发调度逻辑抽成 GameShared 里不依赖 Unity/Fantasy 的可测类。**

```
GameShared/FrameSync/Network/BattleNetworkGate.cs   ← 收发调度，可测
  - 持有 NetworkConditionSimulator
  - 上行：WrapSendInput / WrapSendPing / WrapSendHashReport（接受委托，返回委托）
  - 下行：TryAcceptSnapshotMessage(nowMs) → bool   ← 丢包判定，转换前调用
          EnqueueConvertedSnapshot(nowMs, snapshot, action)   ← 延迟，转换后调用
          TryAcceptPong(nowMs, sendTimestampMs, action)
  - PumpDownlink(nowMs) / PumpUplink(nowMs)
```

`BattleClientController` 退化为：DTO 转换 + 调用 gate + 真正 `Send`。它仍不被无头覆盖，但里面只剩「调用顺序」这一件事，而顺序约束由 gate 的 API 形状强制（丢包判定返回 `bool` 且必须在转换前调用，延迟接受已转换的值类型）。

## 为什么自建而不用现成弱网工具

**这不是替代关系，是两层不同的东西。** 需要先说清，否则会被问到（面试也会问）。

### 无头用例里外部工具物理上用不了

`Entity.csproj:25-27` 把客户端的 `BattleSimulation.cs` 链进服务端一起编译，所以端到端用例是：

```
new BattleSimulation(worldState, 输入回调 → battleLogic.SubmitInput, ...)
```

输入回调**直接函数调用**服务端的 `SubmitInput`，快照经 `OnBroadcast` 同步推回。**没有序列化、没有 socket、没有 UDP 包**。`tc netem` / Clumsy / Toxiproxy 都工作在 IP 或 TCP 层——这里根本没有包可拦。

8 条用例里 5 条测模拟器自身（本质是单元测试），3 条端到端也在同进程。所以对本阶段主体来说，「网络工具」这个类别不是不好用，是**不适用**。

### 其余约束各自单独否掉外部工具

| 约束 | 为什么外部工具不行 |
|------|-------------------|
| **确定性是硬需求** | 验收要求「同种子两次跑，report.json 弱网计数逐字段相等」，agent 靠退出码判 PASS/FAIL。系统级工具是概率性的，写不成断言，也无法凭种子复现失败 |
| **消息粒度** | 上行输入丢包 → `ReusedInputCount++`；下行快照丢包 → 属性基线永久错位。两者暴露完全不同的缺陷，必须分别注入。外部工具在 IP 包层面工作，不知道哪个包是输入哪个是快照；且 KCP 会把多条逻辑消息打包进一个 UDP 包，包级丢包无法对应到消息级 |
| **平台与协议** | 项目在 Windows，`tc netem` 是 Linux 的；Clumsy 要 WinDivert 驱动 + 管理员权限，塞进 CI 很重。Toxiproxy 只支持 TCP，而 Fantasy 走 KCP over UDP |
| **库自带模拟也没有** | Fantasy 全目录搜 `simulat` / `packetLoss` 零命中，且服务端是 NuGet 包无源码（`Entity.csproj:13`） |
| **可观测性** | 验收要 report.json 里有 `UplinkDropped` / `DownlinkDropped` 供机械断言。外部工具的统计在工具进程里，拿不进 report |

至于「找个现成 .NET 库嵌进来」——约束是零 `UnityEngine` 引用、能编进服务端、随机源必须用项目的 `DeterministicRandom`。满足这些的现成库难找，而延迟队列本身约 150-200 行，引依赖收益不足。

### 但外部工具有一件事做得更好，应分层并用

真实性。本方案模拟**消息可见时刻**，丢包等价于「永久丢失」，不触发 KCP 的 ARQ 重传（见决策一「代价」一节）。真实网络下丢包多半表现为额外延迟而非丢失。

| 层 | 手段 | 验证什么 | 频率 |
|---|------|---------|------|
| 无头 CI | 本阶段自建注入器 | 确定性回归、缺陷定位、精确到消息类型 | 每次提交 |
| 真机验收 | Clumsy 之类外部工具 | 真实 KCP ARQ 兜住之后，上层看到延迟抖动而非丢失，预测层能否扛住 | 阶段性人工 |

第二层有真实 socket（`Run-BattleAcceptance.ps1` 起真实客户端进程），外部工具在那里可用且更合适。

**但它不是本阶段的交付物，不写进 Step** —— 它需要装驱动、要管理员权限、结果不可复现，无法纳入 agent 自动验收。定位是 S11 对外展示前的一次性人工确认，或 S9 断线重连时的辅助手段。**验收 agent 不应因为缺这一项而判 FAIL。**

## 架构

```
新增：GameShared/FrameSync/Network/NetworkConditionSimulator.cs  ← 纯逻辑，双端可用
      GameShared/FrameSync/Network/NetworkConditionConfig.cs     ← 参数（readonly struct）
      GameShared/FrameSync/Network/BattleNetworkGate.cs          ← 收发调度，可测（决策五）
      GameShared/FrameSync/Core/IBattleClock.cs                  ← 可注入时间源（决策四）

客户端接线（BattleClientController）：
  上行  SendInputCommand ──┐
        SendPingCommand ───┼─→ gate.WrapXxx(...) ─→ 模拟器判定丢包/排延迟 ─→ 真正 Send
        SendHashReport ────┘
  下行  OnSnapshotMessage ─→ gate.TryAcceptSnapshotMessage(nowMs)   ← 丢包判定（转换前！）
                          │    false → return，不转换、不持有池化对象
                          └─→ true → ConvertSnapshot（立即，逃离池化对象）
                               └─→ gate.EnqueueConvertedSnapshot(...) ─→ EnqueueServerSnapshot
        OnPongMessage ────→ 只取 pong.SendTimestampMs（ulong 标量）
                          └─→ gate.TryAcceptPong(...) ─→ 释放时才取 nowMs 并算 rttMs ─→ ProcessPong
  泵    每帧 gate.PumpDownlink(nowMs) 在 Tick 之前
        每帧 gate.PumpUplink(nowMs)   在 Tick 之后（见 Step 3）
```

### 一个会自动生效的连锁效应，要留意

下行 Pong 延迟会被 `_rttEmaMs` 自动观测到 —— RTT 是客户端自算的，注入的延迟落在这个差值里，于是 `RefreshBaselineLeadFrames()`（`BattleSimulation.cs:585-600`）会自动抬升 `_leadFrames`。

公式是 `JitterBufferFrames(2) + InputSendSafetyFrames(1) + ceil(rttEma / 2 / 33.333)`，clamp 到 `[MinLeadFrames=3, MaxLeadFrames=20]`（`InputBufferTuning.cs`）。**200ms RTT → lead = 3 + 3 = 6，余量充足，不会撞 20 的顶。** 撞顶要 RTT > 1133ms。

**这给了一条现成的验收信号：注入 200ms 延迟后 `leadFrames` 必须上升。**

但因此**必须把延迟也施加在 Pong 路径上**，且**必须在释放时刻才算 RTT**（见 Step 3）。漏了这条会让整个弱网测试的结果失真：RTT 观测不到注入延迟 → `leadFrames` 不动 → 客户端以为网络很好而 lead 不足 → 产生一堆与弱网无关的 `LateInputDrop`。

## 实现步骤

### Step 1：`NetworkConditionConfig`

`readonly struct`，字段：

| 字段 | 类型 | 说明 |
|------|------|------|
| `UplinkDelayMs` / `DownlinkDelayMs` | `int` | 基础单向延迟 |
| `UplinkJitterMs` / `DownlinkJitterMs` | `int` | 抖动幅度，实际延迟 = 基础 + `[0, jitter)` |
| `UplinkLossPercent` / `DownlinkLossPercent` | `int` | 丢包率 `[0, 100]` |
| `Seed` | `ulong` | 抖动与丢包的随机种子 |
| `IsEnabled` | `bool` | 全关时模拟器必须走零开销直通路径 |

参数校验：延迟/抖动非负、丢包率在 `[0, 100]`。**校验失败抛异常，不要静默 clamp 后继续** —— 弱网参数配错会让整轮测试结果无意义，而静默修正会让人以为跑的是自己配的条件。

按 `BattleBandwidthConfig.cs` 的范本写（`:48` 的 `GetEnvBool` / `:76` 的 `GetEnvUInt`，支持 `1/true/yes/on`、无法识别回落默认值）。**但不要照抄它的饿汉式静态 `Current`**（`:15`，`public static BattleBandwidthConfig Current { get; } = CreateCurrent();`）—— 那是进程内单次求值、无法运行时切换。S10 调试面板要做运行时切换，做成可变实例能省一次返工。

### Step 2：`NetworkConditionSimulator`

纯逻辑类，**零 `UnityEngine` 引用**（要能编进服务端参与无头测试）。

核心结构：上行、下行各一个按释放时刻排序的队列，元素是 `(releaseAtMs, Action)`。

必须实现的行为：

- `bool TryEnqueueUplink(long nowMs, Action send)` —— 掷丢包判定，命中丢包则返回 `false` 且不入队；否则算 `releaseAtMs = nowMs + delay + jitter` 入队，返回 `true`
- `bool TryEnqueueDownlink(long nowMs, Action deliver)` —— 同上，用下行参数
- `bool ShouldDropDownlink(long nowMs)` —— **只掷丢包判定，不入队**。供决策一的「转换前丢包判定」使用，此时还没有可保留的值类型
- `void PumpUplink(long nowMs)` / `void PumpDownlink(long nowMs)` —— 释放全部 `releaseAtMs <= nowMs` 的项，按 `releaseAtMs` 升序。**上下行分开泵**（见 Step 3）
- 计数器：`UplinkSent` / `UplinkDropped` / `DownlinkDelivered` / `DownlinkDropped` / `MaxQueueDepth` / `OverflowDropped`

**`IsEnabled == false` 时必须同步直呼，不入队。** 不是「延迟 0 入队再立刻释放」——那会把发送时机从「调用点当帧」挪到「下次 Pump」，即使延迟为 0 也改变了时序，让关闭弱网的回归测试与弱网代码引入前不等价。**这是本方案最隐蔽的一个坑**：它会让所有既有用例的行为发生微妙变化而不报错。

**队列必须有深度上限**（建议 1024）。超限时丢弃最旧项并计数 `OverflowDropped`。无上限的话，高延迟 + 长时间运行会无界增长；更要紧的是无头用例若忘记调 Pump，会静默堆积到 OOM 而不是快速失败。

`Pump` 的释放顺序按 `releaseAtMs` 升序 —— 抖动会让后发的消息先到期，这是抖动的正常语义。但因决策二，快照到 `EnqueueServerSnapshot` 后旧帧仍会被吞掉。

### Step 3：`BattleNetworkGate` 与客户端接线

先建 gate（决策五），再让 `BattleClientController` 调它。

改 `BattleClientController`：

**上行**（`:318-323` 的三个实参）：包一层 gate。**注意 `_onSendInput` 等是 `readonly` 字段（`BattleSimulation.cs:28-30`），构造后不可换**，所以 wrapper 必须常驻，靠内部 config 决定是否延迟 —— 不能靠「运行时替换回调」实现开关。

**下行快照**（`:412-422`）拆成三段，顺序不可换：

```
1. gate.TryAcceptSnapshotMessage(nowMs) == false → return    ← 丢包判定，转换前
2. ConvertSnapshot(...)                                       ← 立即，逃离池化对象
3. gate.EnqueueConvertedSnapshot(nowMs, snapshot, () => _simulation?.EnqueueServerSnapshot(...))
```

第 1 步在第 2 步之前是**本计划的核心修正**，理由见决策一。`_snapshotMessageCount++`（`:419`）应留在第 1 步之后——它统计的是「实际处理的快照数」，被丢的不该计入。

**下行 Pong**（`:424-440`）：

```
1. ulong sendTimestampMs = pong.SendTimestampMs;   ← 只取标量，安全
2. gate.TryAcceptPong(nowMs, sendTimestampMs, ts => {
       long rttMs = clock.NowMs - (long)ts;        ← 释放时才取当前时间
       if (rttMs < 0) return;
       _simulation?.ProcessPong(rttMs);
   });
```

**不要在到达时刻算 `rttMs`。** 现状 `:432-433` 是到达即算，若照上一版「立即算 rttMs、延迟 ProcessPong」，注入的下行延迟就被排除在 RTT 之外，`leadFrames` 不动，`netsim-downlink-delay-raises-lead-frames` 直接失败。

**Pump 位置：上下行分开。**

| 方向 | 位置 | 理由 |
|------|------|------|
| `PumpDownlink` | `BattleSimulation.Tick` **之前** | 到期的快照与 pong 应当在本帧被看见，晚一帧释放会凭空多出一帧延迟 |
| `PumpUplink` | `Tick` **之后** | 上行入队发生在 `Tick` **内部**（`:216` 的 `_onSendInput`）。若只在 Tick 前泵，帧 N 入队的输入最早在帧 N+1 释放 → **只要 `IsEnabled`，上行就凭空多一帧延迟，哪怕 delay=0** → 配不出「纯丢包不带延迟」，丢包用例带混淆变量 |

`C2B_JoinBattle` 走 RPC（`:360`），**不注入**。join 阶段施加弱网只会让测试在建连阶段随机失败，与要观测的东西无关。

### Step 3.5：可注入时间源

新增 `IBattleClock`（`GameShared/FrameSync/Core/`），实现两个：

- `SystemBattleClock` —— 返回 `DateTimeOffset.UtcNow.ToUnixTimeMilliseconds()`
- `FrameBattleClock` —— 返回 `(long)Math.Round(frameIndex * FixedDeltaMilliseconds)`，帧号由外部推进

改两处硬编码墙钟（决策四）：

| 位置 | 改法 |
|------|------|
| `BattleSimulation.cs:548` | `SendPingIfNeeded` 改用注入的 clock。`BattleSimulation` 构造函数需加 clock 参数（可选，默认 `SystemBattleClock` 保持既有调用点不破） |
| `BattleClientController.cs:432` | 走 gate 的 clock |

**两侧必须是同一个 clock 实例**，否则 RTT 混算。无头用例注入 `FrameBattleClock`，真实客户端注入 `SystemBattleClock`。

改 `BattleSimulation` 构造签名会波及 `BattlePredictionSelfTestSuite` 的三处 `new BattleSimulation`（`:895`、`:1017`、`:1202`）。**给 clock 参数默认值可避免改这三处**，但新增的弱网用例要显式传 `FrameBattleClock`。

### Step 4：无头用例（`BattlePredictionSelfTestSuite`）

**Suite 内注册两处，漏任何一处用例都会静默漏测或直接失败**：`AllCaseNames` 数组 + `RunCase` 的 switch。`TestRunner` 同时登记 8 个单用例名与 3 个 `two-client-weaknet-*` 无头别名，便于按验收命令单独定位；`prediction-self` 仍包含在 `--scenario=all` 内。
