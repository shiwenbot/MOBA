## Context

### 弱网设施完全不存在

全仓 `latency` / `jitter` / 丢包相关标识零命中（唯一命中是 `BattleSimulation.cs:596` 的 `JitterBufferFrames`，那是抖动**缓冲**参数，不是抖动**注入**）。Fantasy 网络库自身也不带模拟功能（`Fantasy.Unity` 全目录搜 `simulat` / `packetLoss` 零命中）。

而 Timeline 的 P4 完成标准明确写了「使用本地弱网工具施加延迟/抖动/丢包」。这个工具从来没有被实现过，P4 的验证方式因此一直无法执行。

### 三个已落地阶段的判据当前是空转的

| 阶段 | 悬空的判据 | 为什么零延迟下无意义 |
|------|-----------|---------------------|
| S1 | `SmoothingDurationSeconds = 0.12f`、`MaxSmoothingDistance = 6.0f` | 本地零延迟预测几乎不偏，平滑层没有真实误差可吸收，两个阈值是照经验定的，无观测支撑 |
| S3 | 「真实网络下告警是否为零」「noRecord 占比不构成多数」 | 无头测试客户端与服务端同进程，`noRecord` 恒为 0，两条判据空转 |
| S3 | 「`rollbackCount` 是否显著低于修复前」 | 「修复前每个权威快照都触发一次回滚」**至今仍是推论**，未实测 |

### 输入没有冗余，丢一个包就产生真实分歧

这是本阶段最重要的一条现状，它决定了会观测到什么。

客户端每帧发一次输入，**无重发、无冗余窗口**（`BattleSimulation.cs:232`，`_onSendInput(frameIndex, ++_inputSeq, dx, dy, skillId)`）。服务端 `Tick` 消费输入时，若该帧输入缺失，**复用上一帧已消费的输入**（`BattleLogic.cs:211-215`，`ReusedInputCount++`），两端都无输入历史则回落零输入（`:217-219`，`ZeroInputFallbackCount++`）。

于是丢一个输入包，那一帧客户端按真实输入预测、服务端按旧输入推进，**两端状态真实分歧**，直到权威快照到达才被修正。这正是本阶段要生产的、目前完全拿不到的东西——真实的 mismatch。

**副产品**：`ReusedInputCount` / `ZeroInputFallbackCount` 两个计数器已存在，上行丢包在服务端天然可观测，不需要新增计数器去证明注入生效。

### 无头测试有两类客户端载体，只有一类能注入

| 载体 | 出现在 | 驱动 `BattleSimulation` | 能否注入弱网 |
|------|--------|------------------------|-------------|
| `SimulatedClient` | 5 个 scenario（Determinism / Consistency / PlayerCollision / Convergence / PlayerLeave） | ❌ 否 | ❌ 不能 |
| 真正的 `BattleSimulation` | `BattlePredictionSelfTestSuite` 的 18 个 case | ✅ 是 | ✅ 能 |

`SimulatedClient` 全文 41 行，是个被动壳子：`ApplySnapshot` 直接 `RestoreSnapshot`，无预测、无回滚、无 lead frame；输入经构造注入的委托**同步直呼** `battleLogic.SubmitInput`（`TestRunner.cs:1048-1050`），快照经 `OnBroadcast` 同步推给所有客户端（`:1037-1043`）。链路上没有任何可延迟的缝。

**因此本阶段的无头用例走 `BattlePredictionSelfTestSuite` 风格（`BattleSimulation` 直驱），不改造那 5 个 scenario 的 harness。** 后者要从被动壳子改造成带预测的客户端，成本远超本阶段范围，且 `BattleSimulation` 直驱已经复用了全部现成基础设施。

## 决策一：注入在逻辑层，不在字节层

**选定：在 `BattleClientController` 内包装收发回调，不动 `GameClient`、不动 Fantasy、不动服务端。**

上行有现成的注入缝——`BattleSimulation` 构造时注入三个回调，覆盖全部战斗上行消息：

```
BattleSimulation.cs:28-30
  _onSendInput       // BattleInputSender(uint frameIndex, uint inputSeq, Fixed64 dx, Fixed64 dy, int skillId)
  _onSendPing        // Action<ulong> sendTimestampMs
  _onSendHashReport  // Action<uint, ulong>? (frameIndex, stateHash)
```

生产实参在 `BattleClientController.cs:318-323`，三个都是同文件的 private static 方法，各自只做「构造消息 + `GameClient.Instance.Send()`」。`BattlePredictionSelfTestSuite` 已在 `:869`、`:975`、`:1157` 三处把它们换成 recorder，**证明这三个回调是可自由替换的纯函数式接缝**。

选这一层而非 `GameClient.Send` 或 KCP Channel，理由是**生命周期安全**：回调签名是已解包的强类型标量，延迟队列可以安全持有 `(frameIndex, inputSeq, dx, dy, skillId)` 到未来某刻再真正发送。而 `GameClient.Send` 与 Channel 层拿到的是**池化消息对象**，`MessageDispatcherComponent.cs:193` 在回调返回后立即 `Dispose()`，缓存引用会读到被复用的垃圾数据。

下行没有等价的构造缝，但 `RegisterMsgHandler` 接受任意 `Action<IMessage>`（`BattleClientController.cs:401-406`），可以包一层。**关键约束**：延迟必须发生在 `ConvertSnapshot`（`:582-644`，产出纯值类型 `BattleWorldSnapshot`）**之后**、`EnqueueServerSnapshot`（`:421`）之前。即把 `OnSnapshotMessage` 拆成「立即转换」+「延迟入队」两半，绝不能缓存 `IMessage` 本身。

### 代价必须写清楚，这是要能对外讲的

本方案模拟的是**消息可见时刻**，不是真实 KCP 行为。丢包不会触发 KCP 的 ARQ 重传，因为包根本没进协议栈。这意味着：

- **注入的「丢包」等价于「该消息永久丢失」**，而真实 KCP 下丢包会被重传、表现为额外延迟而非丢失
- 所以本设施模拟的是**比真实 KCP 更严酷的条件**（永久丢失），这对暴露同步 bug 是好事，但不能对外宣称「模拟了真实网络」

要做真实 KCP 行为模拟，得改 `Fantasy.Unity/Runtime/Core/Network/Protocol/KCP/` 的 Channel（客户端有完整源码 443 个 .cs），但**服务端 Fantasy 是 NuGet 包无源码**（`Entity.csproj` 的 `<PackageReference Include="Fantasy-Net" Version="2026.0.1007" />`），只能做单向。收益不足，本阶段不做，**但要在验收指南与讲解要点里写明这个边界**。

## 决策二：乱序注入做不了，不要写进范围

`EnqueueServerSnapshot`（`BattleSimulation.cs:173-190`）会**静默丢弃**帧号 ≤ `_lastAppliedFrame` 或 ≤ `_latestQueuedSnapshotFrame` 的快照。所以在这一层重排快照顺序，旧的那个会被直接吞掉，观测不到任何「乱序」行为，只会表现为丢包。

**本阶段范围因此限定为「延迟 + 抖动 + 丢包」三项，不含乱序。** 抖动会让消息的**释放时刻**分散，但队列仍按帧号单调释放。

这不是缺陷，是分层的正常结果：可靠有序交付本就是传输层的职责，KCP 已经保证了，逻辑层看不到乱序才是对的。**讲解时这是个加分点，不是要藏的短板。**

## 决策三（重要）：S3 的哈希判据在弱网下需要收窄口径

**这不是 S3 实现有 bug，是弱网暴露出判据口径过宽。动手前必须定，否则 S4 验收会与 S3 完成标准直接冲突。**

S3 完成标准第 6 条写的是「无头场景下 `[Battle][HashMismatch]` 零告警」。但上行丢包必然让客户端预测错——服务端复用旧输入，客户端用真实输入，那一帧两端状态**真实不同**。客户端上报的是**预测态**哈希（`SendHashReportIfNeeded` 在 `AdvancePredictionTo` 之后当场算），所以：

**弱网下 `HashMismatch` 会合法地大量触发，这是正确行为，不是 bug。**

问题在于当前哈希对账实际回答的是「**我的预测对不对**」，而不是「**两端模拟是否发散**」。这两件事的价值差别很大：

- 「预测对不对」—— 丢包时必然不对，信息量低，且它已经被 `consistencyMisses` / `rollbackCount` 覆盖了
- 「模拟是否发散」—— 这才是哈希对账不可替代的价值：**同样的输入、同样的起始状态，两端算出的结果是否逐位相同**。它守的是 S2 买到的 bit-exact 确定性

建议按下面两条之一处理，**二选一，在实现前定**：

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| **A. 分级告警**（推荐） | 保留现有上报不变，但 `HashMismatch` 告警按「该帧是否发生过输入丢失/回滚」分级：正常路径 mismatch 打 `Warning`，丢包窗口内 mismatch 只计数不告警 | 改动小；仍保留「正常路径必须零告警」这个强判据 | 需要服务端知道该帧是否 reuse 过输入——`ReusedInputCount` 已有，但需按帧记录 |
| B. 改上报时机 | 客户端改为在**对账并重放完成后**上报该帧哈希 | 判据变成纯粹的确定性校验，语义最干净 | 与 S3 刻意选定的「当场算当场发」采样点冲突，且上报帧号会滞后，noRecord 上升 |

**推荐 A**，因为它不动 S3 的采样点（那个设计是为规避帧号错位专门定的，见 S3 计划「采样点」一节），只在服务端比对侧加上下文。

无论选哪个，**S4 验收指南必须显式声明弱网场景下 `HashMismatch > 0` 是预期结果**，并把「正常路径（零丢包）零告警」单列为一条独立判据。否则验收 agent 会照 S3 标准判 FAIL。

## 决策四：时间源必须外部注入

模拟器**自己绝不读时钟**。时间由调用方传入：

- **无头用例**：喂由帧号推导的合成毫秒（`frameIndex * 33`），完全可复现
- **真实客户端**：喂 `DateTimeOffset.UtcNow.ToUnixTimeMilliseconds()`

这条与项目既有纪律一致——`PingIntervalFrames` / `HashReportIntervalFrames` 都按帧计数而非 wall-clock，正是为了无头可复现（S3 计划 Step 2 明确写了这个理由）。

抖动的随机源用 **`DeterministicRandom`**（`GameShared/ThirdParty/FixedMathSharp/Random/DeterministicRandom.cs`，xoroshiro128++ + splitmix64 播种，无分配，已通过 `Entity.csproj:24` 的 `GameShared/**` 通配链进服务端）。**禁止用 `System.Random`** ——无种子则不可复现，用例会间歇性红。

种子必须可配、必须记进 report.json。**失败时没有种子就无法复现，这类 bug 只能靠复现定位。**

## 目标

1. **建一个纯逻辑、可确定性复现的弱网注入器** —— 延迟、抖动、丢包三项可独立配置，上下行可分别配置，无引擎依赖、无时钟依赖。
2. **无头用例覆盖注入器本身与端到端行为** —— 注入器的队列/丢弃逻辑单测可判，加上 `BattleSimulation` 直驱的端到端弱网场景。
3. **真实客户端可施加弱网** —— 经 `-CustomArgs:` 传参，`Run-BattleAcceptance.ps1` 支持弱网场景。
4. **回填 S1 / S3 的悬空判据** —— 平滑阈值有观测支撑、`rollbackCount` 修复前后实测对比、`noRecord` 在真实延迟下的占比。

## 非目标

- 不做乱序注入（决策二，做不到且不该做）。
- 不做真实 KCP 层模拟（决策一，服务端无源码）。
- 不改造 5 个 scenario 的 `SimulatedClient` harness。
- 不做服务端侧注入 —— 客户端单侧包装收发即可覆盖双向（发送侧丢弃 = 上行丢包，接收侧丢弃 = 下行丢包），服务端零改动。
- 不做输入冗余/重发来「修好」丢包。**那是 S8 或独立阶段的事**，本阶段要的是暴露问题，不是掩盖它。
- 不做 UI 上的弱网开关（属 S9 调试面板）。

## 架构

```
新增：GameShared/FrameSync/Network/NetworkConditionSimulator.cs   ← 纯逻辑，双端可用
      GameShared/FrameSync/Network/NetworkConditionConfig.cs      ← 参数（readonly struct）

客户端接线（BattleClientController）：
  上行  SendInputCommand ──┐
        SendPingCommand ───┼─→ simulator.EnqueueUplink(releaseAtMs, action) ─→ 真正 Send
        SendHashReport ────┘
  下行  OnSnapshotMessage ─→ ConvertSnapshot（立即，避免池化对象失效）
                          └─→ simulator.EnqueueDownlink(...) ─→ EnqueueServerSnapshot
        OnPongMessage ────→ 算 rttMs（立即）
                          └─→ simulator.EnqueueDownlink(...) ─→ ProcessPong
  泵    每帧 Update/Tick 调 simulator.Pump(nowMs) 释放到期项
```

### 一个会自动生效的连锁效应，要留意

下行 Pong 延迟会被 `_rttEmaMs` 自动观测到 —— RTT 是客户端自算的（`BattleClientController.cs:432-433`，`nowMs - pong.SendTimestampMs`），注入的延迟落在这个差值里，于是 `RefreshBaselineLeadFrames()`（`BattleSimulation.cs:594-608`）会自动抬升 `_leadFrames`。

**这是想要的效果**，而且给了一条现成的验收信号：注入 200ms 延迟后 `leadFrames` 必须上升。它同时验证了注入生效与 lead 自适应逻辑正确。

但因此**必须把延迟也施加在 Pong 路径上**，否则 RTT 观测不到注入的延迟，`leadFrames` 不动，客户端会以为网络很好而 lead 不足，产生一堆与弱网无关的 `LateInputDrop`。**漏了这条会让整个弱网测试的结果失真。**

## 实现步骤

### Step 1：`NetworkConditionConfig`

`readonly struct`，字段：

| 字段 | 类型 | 说明 |
|------|------|------|
| `UplinkDelayMs` / `DownlinkDelayMs` | `int` | 基础单向延迟 |
| `UplinkJitterMs` / `DownlinkJitterMs` | `int` | 抖动幅度，实际延迟 = 基础 + `[0, jitter)` |
| `UplinkLossPercent` / `DownlinkLossPercent` | `int` | 丢包率 `[0, 100]` |
| `Seed` | `ulong` | 抖动与丢包的随机种子 |
| `IsEnabled` | `bool` | 全关时模拟器必须走零开销直通路径 |

参数校验：延迟/抖动非负、丢包率 clamp 到 `[0, 100]`。**校验失败抛异常，不要静默 clamp 后继续** —— 弱网参数配错会让整轮测试结果无意义，而静默修正会让人以为跑的是自己配的条件。

按 `BattleBandwidthConfig.cs` 的范本写（`:48-80` 的 `GetEnvBool` / `GetEnvUInt` 支持 `1/true/yes/on`、无法识别回落默认值）。**但不要照抄它的饿汉式静态 `Current`**（`:15`）—— 那是进程内单次求值、无法运行时切换。本阶段虽然只需启动时配一次，但 S9 调试面板要做运行时切换，做成可变实例能省一次返工。

### Step 2：`NetworkConditionSimulator`

纯逻辑类，**零 UnityEngine 引用**（要能编进服务端参与无头测试）。

核心结构：上行、下行各一个按释放时刻排序的队列，元素是 `(releaseAtMs, Action)`。

必须实现的行为：

- `bool TryEnqueueUplink(long nowMs, Action send)` —— 掷丢包判定，命中丢包则返回 `false` 且不入队；否则算 `releaseAtMs = nowMs + delay + jitter` 入队，返回 `true`
- `TryEnqueueDownlink(...)` —— 同上，用下行参数
- `void Pump(long nowMs)` —— 释放全部 `releaseAtMs <= nowMs` 的项，按 `releaseAtMs` 升序
- 计数器：`UplinkSent` / `UplinkDropped` / `DownlinkDelivered` / `DownlinkDropped` / `MaxQueueDepth`

**`IsEnabled == false` 时必须同步直呼，不入队。** 不是「延迟 0 入队再立刻释放」——那会把发送时机从「调用点当帧」挪到「下次 Pump」，即使延迟为 0 也改变了时序，让关闭弱网的回归测试与弱网代码引入前不等价。**这是本方案最隐蔽的一个坑**：它会让所有既有用例的行为发生微妙变化而不报错。

**队列必须有深度上限**（建议 1024）。超限时丢弃最旧项并计数 `OverflowDropped`。无上限的话，高延迟 + 长时间运行会无界增长；更要紧的是无头用例若忘记调 `Pump`，会静默堆积到 OOM 而不是快速失败。

`Pump` 的释放顺序按 `releaseAtMs` 升序 —— 抖动会让后发的消息先到期，这是抖动的正常语义。但因决策二，快照到 `EnqueueServerSnapshot` 后旧帧仍会被吞掉。

### Step 3：客户端接线

改 `BattleClientController`：

- `EnsureSimulation()`（`:318-323`）把三个上行实参包一层。**注意 `_onSendInput` 等是 `readonly` 字段（`BattleSimulation.cs:28`），构造后不可换**，所以 wrapper 必须常驻，靠内部 config 决定是否延迟 —— 不能靠「运行时替换回调」实现开关
- `OnSnapshotMessage`（`:412-421`）拆两半：立即 `ConvertSnapshot`，延迟 `EnqueueServerSnapshot`
- `OnPongMessage`（`:424-433`）拆两半：立即算 `rttMs`，延迟 `ProcessPong`
- 每帧调 `Pump()`。位置须在 `BattleSimulation.Tick` **之前** —— 到期的输入与快照应当在本帧被看见，晚一帧释放会凭空多出一帧延迟

`C2B_JoinBattle` 走 RPC（`:360`），**不注入**。join 阶段施加弱网只会让测试在建连阶段随机失败，与要观测的东西无关。

### Step 4：无头用例（`BattlePredictionSelfTestSuite`）

**注册三处，漏任何一处用例静默不跑**（`AllCaseNames` 数组 + `RunCase` switch；`TestRunner` 侧不需要改，`prediction-self` 已在 `--scenario=all` 内）。

新增用例（**只追加，不改既有 29 条**）：

| 用例 | 断言什么 |
|------|---------|
| `netsim-disabled-is-passthrough` | `IsEnabled = false` 时发送**同步立即**发生（不需 `Pump`）。**这条守 Step 2 那个隐蔽坑** |
| `netsim-delay-releases-on-schedule` | 延迟 100ms 的项在 `nowMs + 99` 不释放、`+100` 释放 |
| `netsim-loss-rate-is-deterministic` | 同种子两次运行的丢弃序列完全一致；不同种子不同 |
| `netsim-queue-overflow-drops-oldest` | 超限后 `OverflowDropped > 0` 且不抛异常 |

## 风险与对策

| 风险 | 对策 |
|------|------|
| **关闭时做成「延迟 0 入队」** | **本方案第一大坑。**会微妙改变全部既有用例时序而不报错。`netsim-disabled-is-passthrough` 专门守这条 |
| **漏了 Pong 路径的延迟** | RTT 观测不到注入延迟 → `leadFrames` 不动 → 一堆与弱网无关的 `LateInputDrop`，结果失真 |
| **弱网参数没传进去导致假通过** | 必须有一条断言是「注入确实发生了」，不能只断言「系统仍然一致」 |
| **缓存 `IMessage` 引用** | 池化对象在回调返回后 `Dispose()`（`MessageDispatcherComponent.cs:193`），必须先 `ConvertSnapshot` 再延迟 |
| **用 `System.Random`** | 不可复现，用例间歇性红。用 `DeterministicRandom` 并把种子写进 report |
| **S4 验收与 S3 完成标准冲突** | 决策三必须在实现前定，验收指南显式声明弱网下 `HashMismatch > 0` 属预期 |
| **Pump 位置在 Tick 之后** | 凭空多出一帧延迟。必须在 Tick 之前 |
| 队列无上限 | 忘调 `Pump` 会静默堆到 OOM。给 1024 上限 + `OverflowDropped` 计数，快速失败 |
| 新场景名只登记一处 | `--scenario=all` 假 PASS。三处都要登记 |
| 试图注入乱序 | 做不到，`EnqueueServerSnapshot` 会吞掉旧帧。范围内不含乱序 |
| 对 join RPC 注入 | 建连阶段随机失败，与观测目标无关。不注入 |
| 参数校验静默 clamp | 配错参数会让整轮测试无意义。校验失败抛异常 |
| 沿用饿汉式静态 `Current` | S9 要运行时切换，做成可变实例省一次返工 |
| 服务端运行中报 `MSB3027` | 先停服务端，或只 build `Entity.csproj` |
