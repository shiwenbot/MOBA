# T2：延迟补偿（服务端倒带命中判定）

> **状态**：待讨论（2026-08-06 立项）。负责人态度：虽然是 demo，也要做到成熟游戏做到的机制。本项定下「要做」，但**范围/时机/与 S8 的关系**未拍板，回来谈。

## 一句话

联网游戏里玩家看到的永远是敌人「过去」的位置（≈ RTT/2 + 插值缓冲 前）。**延迟补偿 = 服务端判命中时，不判敌人「现在」在哪，而是把敌人倒带回「开火者看到的那一刻」，在过去的时间点判命中**。效果：你瞄到哪打到哪，「所见即所中」。没有它，你瞄准过去的位置、服务端却判现在，明明点在身上也打空。

## 两种命中判定哲学（这是理解本项的钥匙）

| | 无延迟补偿（本项目现在） | 有延迟补偿（Source/CS/Valorant/Overwatch） |
|--|--|--|
| 玩家瞄的 | 敌人过去的位置（屏幕所见） | 同左 |
| 服务端判的 | 敌人**现在**的权威位置 | 敌人**过去**的位置（倒带到开火者所见） |
| 结果 | 瞄过去、判现在 → 可能打空 | 所见即所中 |
| 谁吃亏 | 开火方（要预判走位） | 被击方（转角杀） |

**两者都躲不开「玩家看到的是过去」这个物理事实。区别只在服务端迁就谁的时间。**

## 为什么要做（负责人的原话）

> 「虽然是一个 demo，但我的项目也要做到人家做到的东西。」

没有延迟补偿，demo 的命中手感就和真实射击游戏有明显差距（「我打中了他但没伤害」）。要做扎实 demo，这关得过。

## 参考实现：Source SDK（已核实）

`D:\Unity\source-sdk-2013` 的 `src/game/server/player_lagcompensation.cpp`：

- `StartLagCompensation`（约 `:337-427`）：开火时算倒带目标帧 `targettick = cmd->tick_count - lerpTicks`，其中 `lerpTicks = TIME_TO_TICKS(player->m_fLerpTime)`（约 `:374-379`）——倒带到的就是**开火者屏幕上的那一帧**
- `BacktrackPlayer`（约 `:428-622`）：把**其他玩家**同时插值回退**碰撞体**（`SetLocalOrigin/SetLocalAngles/SetSize`）与 **hitbox**（`SetSequence/SetCycle/pose/overlay` → `InvalidateBoneCache`）
- 在回退后的世界判命中，判完 `FinishLagCompensation`（约 `:742-876`）还原
- 每帧 `FrameUpdatePostEntityThink`（约 `:280-310`）为每个玩家记录 origin/angles/bbox/动画 —— **这是倒带的数据源：服务端按 tick 存的位置历史**

**核心三件套**：① 服务端按 tick 存每个玩家的位置历史 ② 开火时按 (RTT/2 + 插值) 算倒带帧数 ③ 把目标倒带到那一帧判命中、判完还原。

## 本项目现状：未实现，S7 在铺路

- 总索引 `:107` 明写：「lag compensation（按 RTT/2 回退命中判定）—— **未实现**，本阶段（S7）为其铺路」
- S7（服务端权威 RTT 测量）产出的 RTT 值，是延迟补偿算倒带帧数的**必要输入**
- S10（远端插值）产出的插值延迟（lerp time），是倒带帧数的**另一必要输入**（`targettick = now - RTT/2 - lerp`）

**所以本项的前置是 S7 + S10 都落地。** 在那之前做不了完整的延迟补偿。

## 要实现它，大致要加什么

1. **服务端位置历史缓冲**：按 tick 存每个玩家的 origin/bbox（可能还有动画状态）。Source 是每帧 `FrameUpdatePostEntityThink` 记录。本项目服务端 `BattleLogic` 已有按帧推进，可加一个 `Dictionary<frameIndex, PlayerPositions>` 之类的历史容器（容量按最大倒带窗口算）。
2. **倒带帧数计算**：`倒带帧数 = TICKS(RTT/2) + TICKS(插值延迟)`。RTT 来自 S7，插值延迟来自 S10。
3. **命中判定时倒带 + 还原**：判命中前后包一层「把目标回退 → 判 → 还原」。注意只倒带**被判定的一方**，本地世界其他状态不动。
4. **协议**：命中结果照常走权威态下发，倒带本身**不进协议**（纯服务端内存操作，和 S7 的「时间戳不进协议」同理）。

## 已知代价（必须知道的取舍）

**转角杀 / Peeker's Advantage**：被击方躲进掩体后**才**死——因为开火方在「过去」看到他还露着，服务端倒带判过去命中。延迟越高越严重。这是「迁就开火方、委屈被击方」的固有取舍，所有用延迟补偿的游戏都有这个问题（CS/Valorant 玩家常骂的「我都进墙了」）。

**demo 里要不要展示这个副作用**：要。它是延迟补偿的固有代价，藏起来就不诚实。可以让弱网场景刻意触发一次转角杀，作为讲解点。

## 与现有阶段的关系

| 阶段 | 关系 |
|------|------|
| S7（服务端 RTT 测量） | **前置依赖**。提供倒带帧数里的 RTT 项 |
| S10（远端插值） | **前置依赖**。提供倒带帧数里的插值延迟项；且延迟补偿的「所见即所中」依赖客户端插值延迟稳定 |
| S8（撞击击退） | **独立**。S8 是近战碰撞、服务端判现在、无延迟补偿（A 预判 B 走位）。延迟补偿主要服务于**远程/即时命中**，S8 的碰撞不是它的主战场。两者可并行规划 |
| S6（回滚粒度） | 无直接关系。S6 是客户端预测回滚，延迟补偿是服务端命中判定，两个不同的「回退」 |

## 相关但不同的「藏延迟」手段（不在本项范围，记录以免混淆）

- **VFX/音效即时播放**：开火瞬间客户端立刻播命中特效/音效，盖住逻辑延迟。这是表现层手段，不动逻辑，和延迟补偿正交。S8 击退也可用（撞击瞬间客户端立刻播特效）。
- **客户端自预测**：自己动作无延迟（本项目已有，预测自己）。
- **实体插值（S10）**：平滑远端位置抖动，不改命中判定。

**延迟补偿专指「服务端倒带迁就开火者看到的过去」，是命中判定层的事，和上面三者不是一回事。**
