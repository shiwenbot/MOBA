## 一、为什么必须先做平滑，而不是把占位分离搬到输入端

这个顺序曾经反过来，核实 Source SDK 源码后改了。理由要理解，否则会想「不如先改占位分离」。

TF2 能把玩家间分离量做成纯客户端输入（`c_tf_player.cpp:6315` 的 `AvoidPlayers()` 把推力写进 `pCmd->forwardmove/sidemove`，服务端照收到的输入执行、从不重算），前提是 `tf_avoidteammates=1` 时**队友之间根本不 solid**——`c_tf_player.cpp:7707` 的 `ShouldCollide()` 直接返回 false。推力只是「软避让」，算错的后果仅是推多推少，不违反任何约束。

本项目的 `ResolvePlayerOccupancy()` 是**硬约束**：玩家不允许重叠。硬约束下客户端拿旧的远端位置去算必然偶尔算错，且错了不能放任（会出现重叠）。Source 对 solid 实体的处理是**服务端权威 + 客户端预测 + 误差平滑掩盖残差**，不是把约束挪进输入。

所以平滑层是前提。没有它，占位分离无论选哪条路都表现为硬跳。

## 二、为什么平滑量绝对不能进 GameShared

`GameShared/` 是双端共享的确定性逻辑层，服务端通过**通配符全量链接**（`Entity.csproj:31`）。把一个 float 平滑器放进去，风险不是「现在会坏」，而是「后续有人把它纳入快照或哈希，然后确定性静默失效」。

参照 Source 的分层：`prediction.cpp` 的 `CheckError()` 只比位置一个字段，算出来的是**视觉平滑量**，仿真本身已经被修正到权威值。平滑和仿真是两条互不干涉的路。

所以 `PredictionErrorSmoother.cs` 放 `GameLogic/Battle/`，与 `BattleSimulation.cs` 同级。

## 三、为什么新文件必须手动改 csproj

`Entity.csproj` 对两个目录的处理方式**不同**：

```xml
<!-- :31  GameShared 是通配符，新增文件自动纳入 -->
<Compile Include="...GameShared\**\*.cs" Exclude="..." Link="Shared\..." />
<!-- :32-33  GameLogic 是逐文件显式列举 -->
<Compile Include="...GameLogic\Battle\BattleSimulation.cs" Link="..." />
<Compile Include="...GameLogic\Battle\BattlePredictionSelfTestSuite.cs" Link="..." />
```

新增的 `PredictionErrorSmoother.cs` 在 `GameLogic/` 下，**不会**被自动纳入。不加 `Compile Include` 行，服务端无头测试会报「找不到类型」。

这是本方案第一大坑，因为 Unity 侧编译正常，只有跑无头测试时才炸。

## 四、为什么采样点必须在重放完成之后

`ReconcileAuthoritativeSnapshot()`（`BattleSimulation.cs:415-451`）的**真实**结构（含一个容易漏掉的提前返回）：

```
:422  _authoritativeSnapshots.Save(...)
:423  ApplyAuthoritativeSnapshot(snapshot)   ← 状态被拉回权威帧（较旧的帧）
:424  DiscardPredictionsAtOrAfter(...)
:433  if (replayTargetFrame > snapshot.FrameIndex)
:436  {   AdvancePredictionTo(...)   }       ← 重放，推进回当前预测帧
:437  ← ★ 采样插这里
:439  if (!logRollback) { return; }          ← 提前返回，绝大多数帧走这里
:451  }                                      ← 函数真正的尾部
```

**两件事都要做对：**

**① 不能在 `ApplyAuthoritativeSnapshot` 之后立刻采样。** 那样拿到的是「当前渲染位置 → 权威帧位置」之差。但玩家实际会看到的是**重放完成后**的位置。权威帧比当前预测帧旧若干帧，所以这个差值方向和量级都不对，表现是球先往后跳再往前追。

**② 不能放在函数真正的尾部（`:442` 之后）。** `logRollback` 实参就是 `mismatch`（`:322`），一致时为 `false`，会在 `:439` 提前返回——采样代码永远不执行。

②这条是 2026-08-03 review 抓出来的，本文原先的示意代码漏画了 `if (!logRollback) return;` 这一步。**更坑的是：计划推荐的测试模板 `AuthoritativeSnapshotRestoresPhysicsWorld()` 自己就落在这条提前返回上**——它 `SetJoined` 后直接 `EnqueueServerSnapshot(...,11)` 而没先 `Tick(11,...)`，第 11 帧无预测记录，`CheckConsistency` 走 `_skippedNoRecord` 返回 `false`。所以照字面理解插在尾部，新用例断言「偏移非零」会必然失败，而且失败原因看起来像平滑器坏了。

**正确位置：`:437` 之后、`:439` 之前**，即两个出口的公共路径上。

## 五、为什么 transform 写入必须搬到 Update()

`SyncRendering()` 现在由 `Tick()` 调用（`BattleClientController.cs:192`）。而 `Tick()` 的驱动链是：

```
ClientTickDriver.Update()          ← MonoBehaviour，渲染帧率
  → _dispatcher.Update(Time.deltaTime)   ← 累积时间
    → TickOnce() 仅在累积够一个逻辑帧时触发   ← 30Hz
      → BattleClientController.Tick()
        → SyncRendering()
```

所以 `SyncRendering()` **跑在 30Hz**。把平滑衰减和 transform 写入留在这里，平滑会被切成 33ms 一跳——你想消除硬跳，结果换成了一串小跳。

拆法见计划 Step 3：`Tick()` 只更新逻辑目标缓存和注入误差，`Update()` 负责衰减推进 + 写 transform。

**追帧会让一次渲染帧内跑多次 Tick。** `ClientTickDriver.Update()`（`:77-98`）在时间累积之外还有一段追帧循环，上限 `MaxCatchUpTicksPerFrame = 8`，所以一次渲染帧最多 9 次 Tick。追帧只在客户端落后时触发，即弱网场景。

同帧多次对账时，每次注入都读到同一个「上一帧绘制位置」缓存（渲染层还没刷新它）。**这是正确的，不要在 `Tick()` 里更新该缓存**——它的语义是「玩家上一次实际看到的位置」，一个渲染帧玩家只看到一次画面。最终偏移由最后一次对账决定，中间几次被覆盖，正是期望结果。

## 五点五、为什么偏移要「重设基准」而不是累加或覆盖

这是方案里唯一一处真正的设计决策，别改。

前提事实：权威快照 **30Hz** 到达（每 33ms 一个），平滑窗口 **100~150ms**。所以上一次平滑远没走完，下 3~5 次修正就到了。**修正重叠是每帧都在发生的主路径，不是边界情况。**

三种写法的后果：

| 写法 | 后果 |
|------|------|
| 累加（新旧偏移相加） | 偏移越滚越大，球永远追不上，甚至发散 |
| 覆盖（直接丢弃旧偏移） | 残余偏移被瞬间抹掉 → 二次跳变，等于没解决原问题 |
| **重设基准**（本方案） | 正确 |

重设基准的公式：

```
新偏移 = 上一帧实际绘制的位置 − 本次修正后的逻辑位置
```

之所以成立：「上一帧实际绘制的位置」本身已经含有旧的残余偏移，所以旧偏移被自然吸收，不需要单独记账。首次修正（残余为 0）和重叠修正走的是同一套公式，实现上**不需要任何分支判断**。

因此渲染层每帧写完 transform 后，必须把「本帧实际绘制的自身位置」缓存下来。这个缓存纯视觉用途，不进快照、不进哈希。

对应用例 `error-smoothing-overlapping-corrections-rebaseline`。

## 六、既有代码的可复用模式

**对外暴露只读状态**：`BattleSimulation` 已有一批 `public X => _x` 属性（`:102-117`，含 `RollbackCount`、`LastRollbackReplayFrames`、`LastRollbackElapsedMs`、`SelfPlayerId`），新增误差相关属性照这个模式加。

**调试面板**：`BandwidthStatsUI` 那套已跑通的模式是——controller 上放 `public XxxSnapshot LatestXxx { get; private set; }` + `public bool HasXxx { get; private set; }`（`BattleClientController.cs:61-64`），数据到达时 `GameEvent.Get<IBattleUI>().OnXxxUpdated()`，UI 侧订阅刷新。`IBattleUI`（`GameLogic/IEvent/IBattleUI.cs`）加一个方法即可。

**坐标转换**：`ToWorldPosition(Fixed64 x, Fixed64 y)` 已存在（`:796`），逻辑坐标 → Unity 世界坐标用它。

**球体创建**：`GetOrCreateSphere(long playerId, bool isSelf)`（`:772`）。ghost 球照这个思路新建一个方法，材质改半透明，只对自身玩家创建。

**自测注册**：**只需两处，但不是你以为的那两处。** 照 P1 新增 `room-boundary-clamps-player` 的先例走：

1. `BattlePredictionSelfTestSuite.cs` 的 `AllCaseNames` 数组（`:10-30`）—— 加用例名字符串
2. 同文件 `RunCase()` 的 switch（`:47-73`）—— 加分支

**`AllCaseNames` 漏加是本方案最危险的失误**：编译正常、`--scenario=all` 正常报 PASS，但新用例**根本没跑**。这是静默跳过，比编译错误难发现得多。

`TestRunner.cs` **不用改**。核实过：`room-boundary-clamps-player` 在 `TestRunner.cs` 里 grep 零命中，它只随 `--scenario=all` 或 `--scenario=prediction-self` 跑，不能单独调用。新用例照此办理即可。

如果非要支持 `--scenario=<单个用例名>` 单独调用，那才需要另外三处：`TestScenario` 常量定义（`:1331` 起）、`NormalizeScenario()` 映射（`:1257-1321`）、`Execute()` 的 fall-through case 列表（`:127-146`）。共五处，漏 `Execute()` 那处会报 `Unknown test scenario`（注意和 `Unknown --scenario value` 是**不同**的报错，来自不同位置）。**本方案不需要，别做。**

**断言写法参照**：`m_rawValue` 逐位比较的技巧看 `room-boundary-clamps-player`（`:122-133`）。但**场景构造别照抄它**——那个用例直接 new 一个 `FrameSyncPhysicsWorld` 就测，不涉及 `BattleSimulation`。新用例要走 `EnqueueServerSnapshot` → `Tick` → 对账链路，场景构造参照 `AuthoritativeSnapshotRestoresPhysicsWorld()`（`:339-386`）或 `AuthoritativeSnapshotRestoresPlayerAttributes()`（`:388` 起）。
