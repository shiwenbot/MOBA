1项目速览

一句话定位：这不是一个商业游戏，而是一个面试用的 Gameplay 状态同步技术演示。它用一个小球角色 + 极简房间，集中展示弱网条件下的按帧输入、客户端预测、服务端权威校验、不一致诊断与回滚重播能力。

演示玩法

  1. WASD 控制小球移动
  2. Shift Dash，消耗体力并进入 Recover
  3. 体力 / 冷却 / Recover 都按逻辑帧推进
  4. 两球相撞产生击退（服务端权威裁决，客户端故意不预测）

核心设计哲学：FrameIndex 是唯一的逻辑帧语义——输入和状态变化都绑定到具体帧。服务端权威推进，客户端可预测本地移动 / Dash / 体力，收到权威快照后做逐字段 bit-exact 校验，不一致就回滚到权威帧再用本地缓冲输入重放。

2同步架构总览

本项目采用服务端权威的状态帧同步（Server-Authoritative State Sync），而非传统 lockstep。核心特征：服务端跑唯一权威仿真，每帧广播完整状态快照；客户端本地预测自己的玩家，收到权威快照后对账并回滚。

3服务端权威推进

3.1 帧驱动链路（从挂钟时间到逻辑帧）

服务端的固定步长推进通过一条清晰的调用链实现，把真实的 wall-clock 时间转换成整数个 1/30s 的逻辑帧：

ServerTickDriverUpdateSystem.Update()          // 每个 Unity/主循环 tick
    └─ ServerTickDriver.TickOnce()              // 用 Stopwatch 测真实 dt
        └─ TickDispatcher.Update(realDt)        // 喂给累加器
            └─ TickAccumulator.Accumulate(dt)   // 累积，输出本帧要跑几个逻辑帧
                └─ ExecuteTick(frame, fixedDt)  // 按优先级调用每个 ITickable
                    └─ BattleComponent.Tick()
                        └─ BattleLogic.Tick()   // 权威推进 + 广播

TickAccumulator

核心常量

FixedDeltaTime
1/30 s
MaxDeltaTime
0.5s（防死亡螺旋，单次最多补 ~15 帧）

所有数学运算用 Fixed64 定点数，保持确定性。

TickDispatcher

一个 Update 可能触发多个 fixed tick（追帧）。ITickable 按优先级 + 注册顺序调用。

迭代期间注册/注销会延迟到 tick 批次结束后，避免边迭代边改集合。

DeterminismRules

AssertFixedDt（DEBUG）按位模式比较 dt，不是近似相等。

BitConverter.SingleToInt32Bits(dt)
  != FixedDeltaBits → throw

3.2 BattleLogic.Tick —— 权威推进的每一步

这是权威仿真每帧执行的动作序列（BattleLogic.cs:159-233）：

#动作说明
1断言 fixedDtDEBUG 下按位校验 dt 必须精确等于 1/30

7PhysicsWorld.Step定点物理积分（移动 + body blocking）

3.3 输入解析的三态机

服务端为每个玩家、每一帧查找输入时，存在三种情况（BattleLogic.cs:170-222）：

命中

有输入

从 _pendingInputsByPlayerId[player][frame] 取出，消费后删除该帧条目。记录为 lastConsumed。

缺帧

复用上一帧

本帧没收到输入但之前有 → 复用 lastConsumed 输入。ReusedInputCount++。这是"按住方向键不松手"的容错。

冷启动

零输入兜底

从未收到过任何输入 → 用零向量。ZeroInputFallbackCount++。

3.4 输入校验四道防线

BattleLogic.SubmitInput（:99-157）对每个进来的输入做四层校验：

防线条件动作计数器
① 未知玩家playerId 不存在直接丢弃—
② 迟到输入frame ≤ LastFrameIndex（已跑过的帧）丢弃，输入边沿时告警LateInputDropCount
③ 过远未来帧frame > LastFrameIndex + 24拒绝（防恶意囤积）FutureInputRejectCount
④ 序列号去重同帧已有更新的 inputSeq丢弃旧序号—
序列号回绕处理：用模运算比较 IsInputNewerOrEqual——a - b < 0x80000000 判断 a 是否更新，正确处理 uint 回绕。MaxFutureInputFrames = 24 帧 ≈ 800ms 的未来输入缓冲窗口。

3.5 状态哈希

BattleLogic.GetStateHash() 构建完整的 BattleWorldSnapshot 后交给 StateHasher。哈希用于测试框架对比服务端与客户端是否收敛到同一状态。

4客户端预测与回滚

这是整个系统最精巧的部分。客户端不是被动接收服务端状态，而是乐观地本地预测自己的玩家，跑在服务端前面，收到权威快照后再对账。

4.1 核心数据结构

结构类型容量用途
_selfPredictionsDict<uint, SelfPrediction>32每帧的本地预测结果，用于对账
_inputHistoryDict<uint, BufferedInput>128本地输入历史，回滚后重放用
_authoritativeSnapshotsSnapshotBuffer<BattleWorldSnapshot>32收到的权威快照历史，手动回滚目标
_pendingServerSnapshotsQueue<PendingAuthoritativeSnapshot>4抖动缓冲——解耦网络线程与 tick 线程

4.2 客户端每个 Tick 做什么

BattleSimulation.Tick(frameIndex, fixedDt, dx, dy, skillId)
  ├─ 归一化输入（|dx,dy| ≤ 1）
  ├─ SaveInputHistory(frame, dx, dy, skillId)     // 存入输入历史，供回滚重放
  ├─ SendPingIfNeeded()                            // 每 30 帧测一次 RTT
  ├─ _onSendInput(frame, ++seq, dx, dy, skillId)   // ★ 每帧发一条 C2B_PlayerInput
  ├─ ApplyPendingServerSnapshot()                  // ★ 处理收到的权威快照（对账）
  └─ AdvancePredictionTo(frame, ...)               // ★ 本地推进 1 帧预测
注意：输入是逐帧、不批量发送的——每个逻辑帧发一条 C2B_PlayerInput。这是为了简化设计、保证每帧输入语义清晰，代价是上行消息频率高（30 msg/s）。

4.3 一致性校验（CheckConsistency）

收到权威快照后，客户端从 _selfPredictions 里取出该帧的本地预测，和权威结果做逐字段 bit-exact 比较（BattleSimulation.cs:389-427）：

比较内容

逐字段精确比对

  • 位置：比较 Fixed64.m_rawValue（原始定点值），不是浮点近似
  • 属性：HP / MaxHP / MP / MaxMP / Attack
  • NextRuntimeBuffId
  • 每个 Buff：RuntimeId / BuffId / Caster / Target / Stack / Remaining / AppliedFrame / Flags
  • 每个数值修饰：SourceBuffId / ValueType / AttributeKind / Value
统计

计数器

_checked
总校验次数
_hits
预测命中（一致）
_misses
预测偏差（触发回滚）
_skippedNoRecord
无预测记录（刚加入/被驱逐）
_skippedEvicted
预测缓冲溢出
关键：比较是bit-exact的，没有任何 epsilon 容差。任何 1 ULP 的差异都会触发回滚。这正是"全定点物理"决策的动机——只要物理是 bit-exact 的，真正的不一致就一定是逻辑分叉，而非浮点噪声。

4.4 回滚重放流程（ReconcileAuthoritativeSnapshot）

当检测到不一致时，执行回滚 + 重放（BattleSimulation.cs:471-510）：

ReconcileAuthoritativeSnapshot(snapshot, replayTargetFrame)
  │
  ├─ 1. _authoritativeSnapshots.Save(frame, snapshot)      // 存入权威历史
  │
  ├─ 2. ApplyAuthoritativeSnapshot(snapshot)               // ★ 回滚到权威帧
  │     ├─ _worldState.RestoreSnapshot(snapshot)           //   整个世界状态恢复
  │     ├─ _lastAppliedFrame = snapshot.FrameIndex
  │     ├─ 移除已确认的输入历史
  │     └─ 清空技能图
  │
  ├─ 3. DiscardPredictionsAtOrAfter(snapshot.FrameIndex)   // 丢弃该帧之后的预测
  │
  ├─ 4. if (replayTargetFrame > snapshot.FrameIndex):      // ★ 重放
  │     └─ AdvancePredictionTo(replayTargetFrame, fixedDt) //   用 _inputHistory 重新跑
  │                                                           //   (move + physics + buff + numerics)
  │
  ├─ 5. CapturePredictionErrorAfterReconciliation()        // 喂给表现层平滑器
  │
  └─ 6. _rollbackCount++; 记录帧号/重放帧数/耗时
重放的本质：回滚到权威帧 N 后，客户端从 N+1 重新跑到当前帧 M，每一步都从 _inputHistory 取本地输入。这就是为什么 InputHistoryCapacity = 128 必须大于最大可能回滚深度——回滚深度受 MaxLeadFrames = 20 限制，128 足够安全。

4.5 表现层平滑（PredictionErrorSmoother）

回滚会让逻辑状态"硬跳"到权威位置，看起来很扎眼。解法：逻辑状态立刻采用权威值，但表现层保留误差偏移并逐帧衰减。

PredictionErrorSmoother

  • 记录"渲染位置 − 权威位置"的误差偏移
  • 每帧按衰减系数收敛到零
  • 误差超过阈值 6.0 → 走硬跳（太大收不回来）
  • 绝不进入逻辑状态或哈希——纯表现层

Authoritative Ghost 球

  • 一个半透明黄色球，显示最近权威位置
  • 和玩家球并排，直观对比"预测 vs 权威"
  • 演示用的核心可视化——面试官一眼能看懂误差

4.6 远端玩家不预测

客户端只预测自己的玩家。其他玩家的状态直接从权威快照取，不做本地预测。这让回滚成本只与自己的领先深度成正比（通常 3-20 帧），而非全场玩家数。

6确定性保证

确定性是这个系统的命脉。任何非确定性都会被 bit-exact 校验放大成"持续回滚"，让游戏不可玩。项目从多个层面封锁不确定性来源。

6.1 定点数学（Fixed64）

Fixed64 定点数

  • 来源：FixedMathSharp 第三方库
  • 所有仿真数学（位置、速度、物理）都用 Fixed64
  • 跨平台 bit-exact——同样的输入一定产生同样的二进制结果
  • 哈希时直接取 m_rawValue（原始整数），不是转成 float

为什么放弃 Box2D

原方案用 Box2D/Box2DSharp，但：

  • 所有 fixture GroupIndex = -1 → 全场不产生 Contact
  • 求解器实际空转，却背负全部代价
  • 边界和分离本来就是手写的
  • 浮点积分无法保证跨端 bit-exact

→ 2026-08-03 决策：拿掉 Box2D，手写定点物理

6.2 手写定点物理

FrameSyncPhysicsWorld（GameShared/FrameSync/Battle/FrameSyncPhysicsWorld.cs）实现了：

  • 圆-圆分离：玩家间 body blocking，最小分离距离 = 2 × 玩家半径
  • 圆-矩形边界：房间边界 clamp
  • 占用解析迭代：OccupancyResolveIterations = 4
  • 所有 epsilon 都用定点常量：OccupancyEpsilon = 1/10000 等

6.3 确定性扫描（静态检查）

FrameSyncValidator 会对 GameShared/FrameSync/*.cs 做静态扫描，禁止以下出现在确定性路径中：

禁止项原因
UnityEngine 命名空间引擎相关，非确定性
Fantasy 命名空间网络框架，非确定性
DateTime / Stopwatch挂钟时间非确定
System.Random随机数非确定
async / await调度顺序非确定
Dictionary<> / HashSet<>建议避免——迭代顺序在某些平台不一致
关于 Dictionary 的处理：扫描只是"建议避免"而非硬禁止。实际代码里仍用了 Dictionary，但关键迭代路径都先 Sort()（如 BattleLogic.Tick 里 BuildSortedPlayerBuffer()）。这是一种务实的折中。

6.4 FNV-1a 状态哈希

StateHasher（GameShared/FrameSync/Snapshot/StateHasher.cs）用 FNV-1a 64 位哈希整个世界状态：

FNV-1a 64-bit
  offset = 14695981039346656037
  prime  = 1099511628211

混合顺序（确定性）：
  每个玩家（按 ID 排序）:
    PlayerId (hi+lo), X.m_rawValue, Y.m_rawValue,
    Health, MaxHealth, Mana, MaxMana, Attack,
    buff count + 每个 buff 的全部字段,
    NextRuntimeBuffId (hi+lo), 基础属性,
    modifier count + 每个 modifier 全字段
  物理体: count + 每个体的 raw 值 + IsAwake/IsEnabled
  接触: count + 每对接触
帧号不参与哈希：故意设计——两帧的世界状态如果完全相同，哈希应该相同。这样才能对比"服务端第 N 帧"和"客户端第 N 帧"是否收敛。

7带宽优化

30Hz 广播完整快照给所有玩家，带宽会很大。项目实现了脏同步（dirty sync）+ 增量编码来压缩下行流量，并做实时测量和反事实对比。

7.1 两条优化轴

属性脏同步

PlayerAttributeSync

每个观察者维护一个 _lastBroadcastAttributesByPlayerId 基线。每帧计算 AttributeDirtyMask——只有变化的属性位被置 1。

序列化时只有 dirty 字段携带有效值，客户端用 PlayerAttributeSync.Merge 合并回完整状态。

Buff 增量同步

BuffSync

每个 (观察者, 目标玩家) 维护一个 BuffBroadcastBaseline。首次全量同步，之后 BuffSync.ComputeChanges 只发变化的 Buff。

带 BuffSnapshotFrameIndex（基线帧）+ IsBuffFullSync 标志。客户端基线不匹配时丢弃增量，请求全量。

7.2 带宽测量与反事实对比

BattleBandwidthStats 不只是统计实际发送量，还会做反事实计算——"如果不做脏同步，全量同步要多少字节"：

指标含义
ActualPayloadBytes实际发送的字节数（含脏同步）
FullSyncPayloadBytes反事实：假设全量同步的字节数（强制 DirtyMask=All 重序列化）
DirtySyncSavedBytes节省量 = FullSync − Actual
DirtySyncSavedRatio节省比例 = Saved / FullSync × 100%
测量方法：MeasureFullSyncBytes 克隆快照，强制 AttributeDirtyMask = All、BuffDirtyMask = uint.MaxValue、IsBuffFullSync = true，重新序列化得到全量字节数。用真实的 protobuf 序列化（SerializerManager.ProtoBufHelper.Serialize）进复用的 MemoryStreamBuffer，零每帧分配。

7.3 报告节奏

  • 每 ReportIntervalFrames = 300 帧（= 10s @ 30Hz）生成一次报告
  • 通过 S2C_BandwidthStats 推送给所有客户端
  • 客户端 UI 实时显示节省量（带宽节省量调试面板）
  • 每包外层头 OuterPacketHeadBytes = 20 字节（PacketLength 4 + ProtocolCode 4 + RpcId 4 + Address 8）
配置项（环境变量，默认全开）：
  • BATTLE_BANDWIDTH_STATS=true —— 开启统计
  • BATTLE_BANDWIDTH_FULLSYNC_BASELINE=true —— 开启反事实基线测量
  • BATTLE_BANDWIDTH_REPORT_FRAMES=300 —— 报告间隔

8闭环反馈控制

这是一个容易被忽略但非常精妙的设计：客户端不是固定领先服务端 N 帧，而是通过闭环反馈动态调整领先量，确保服务端的输入队列始终健康。

8.1 问题：为什么要动态调整领先量？

客户端领先服务端越多，预测越远 → 回滚越深 → 体验越差。领先太少 → 服务端缺帧 → 输入迟到被丢弃 → 玩家操作"丢失"。需要找到一个平衡点，并随网络波动自适应。

8.2 反馈信号：LatestAcceptedInputFrame

服务端在每条 S2C_FrameSnapshot 里，每个玩家都回显一个 LatestAcceptedInputFrame——"我已经接受到你的第几帧输入了"。

8.3 闭环控制算法（UpdateLeadFramesFromAcceptedInput）

// 客户端收到快照后
serverBufferedFrames = latestAcceptedInputFrame - snapshotFrame

if (serverBufferedFrames < MinAcceptedInputBufferFrames=4):
    // 服务端队列快空了！危险，要掉帧了
    _leadFrames += deficit            // ★ 加大领先量

else if (serverBufferedFrames > MaxAcceptedInputBufferFrames=6):
    // 服务端队列太满，可以收敛
    if (冷却结束):  _leadFrames--     // ★ 减小领先量（限速）

// 钳制到 [MinLeadFrames=3, MaxLeadFrames=20]

8.4 RTT 驱动的基线

除了服务端反馈，客户端还根据 RTT 设定领先量基线（RefreshBaselineLeadFrames）：

baseline = JitterBufferFrames(2) 
         + InputSendSafetyFrames(1) 
         + ceil(rttEmaMs / 2 / fixedDtMs)
// 钳制到 [3, 20]

JitterBufferFrames = 2

吸收网络抖动的缓冲帧

InputSendSafetyFrames = 1

输入发送安全余量

RTT 项

半 RTT 对应的帧数（信号单程时间）

8.5 RTT 测量

  • 客户端每 30 帧（1s）发一次 C2B_Ping，带 SendTimestampMs
  • 服务端 C2B_PingHandler 原样回显时间戳到 S2C_Pong
  • 客户端 OnPongMessage：rttMs = nowMs - pong.SendTimestampMs
  • EMA 平滑：_rttEmaMs = α·rtt + (1-α)·_rttEmaMs，α = 0.2
待补缺口（S7）：目前 C2B_PingHandler 只回显时间戳，服务端不记录不计算 RTT。"服务端用 RTT 反推应然帧号"的能力尚不存在。注意不能让客户端上报自算的 RTT——那会变成"用客户端声称的 RTT 验证客户端"，反外挂价值归零。必须服务端独立测量。
