1为什么不用 Box2D

在讲实现之前，先理解 S2（commit 9be6e989）为什么要移除 Box2D。这不是"换一个更好的物理引擎"，而是"承认物理引擎是个累赘，把一直在干活的代码扶正"。

❌ 之前：两套物理并存
Box2DSharp
  ├─ 挂在项目里，占 DLL
  ├─ 所有 fixture GroupIndex = -1
  ├─ → 全场不产生 Contact
  ├─ → 求解器空转
  └─ 但背着 WarmStarting 等
     跨帧隐藏状态（确定性隐患）

FrameSyncPhysicsWorld  ← 真正干活的
  ├─ 圆-圆分离（手写）
  ├─ 圆-矩形边界（手写）
  └─ 从一开始就在跑
✅ 现在：单一物理方案
FrameSyncPhysicsWorld  ← 唯一
  ├─ 全定点（Fixed64）
  ├─ 跨端 bit-exact
  ├─ 无浮点噪声
  ├─ 无隐藏跨帧状态
  └─ 555 行，可完全掌控

Box2DSharp
  └─ DLL 引用已从 csproj 删除
     （grep box2d 源码零命中）
Box2D 的致命问题不是性能，是确定性。Box2D 的 WarmStarting 会把上一帧的冲量缓存到这一帧复用——这是浮点值，跨端/跨平台无法保证 bit-exact。一旦开启，任何 1 ULP 的差异都会被客户端的 bit-exact 校验放大成"永久回滚"。所以项目在 0bb9a468 先关闭了它，S2 直接连根拔除。

一句话：物理层追求的不是"物理真实"，而是"可快照、可哈希、可回滚、跨端一致"。Box2D 太重、太黑盒，手写定点反而更可控。

2数据结构

FrameSyncPhysicsWorld 内部用 4 个字典 + 1 个有序列表管理所有状态：

字段类型作用
_bodiesDictionary<int, FixedPhysicsBody>所有物理体。key 是 bodyId（= playerId），value 是位置/速度/状态
_pendingLinearVelocitiesDictionary<int, FixedPhysicsVector>本帧待应用的移动输入（玩家移动意图）
_pendingImpulsesDictionary<int, FixedPhysicsVector>本帧待应用的冲量（撞击击退）
_occupancyContactsDictionary<ContactKey, PhysicsContactSnapshot>当前正在接触的玩家对（用于快照/哈希）
_sortedBodyIdsBufferList<int>排序后的 bodyId 缓冲——所有迭代都基于它

FixedPhysicsBody —— 单个物理体

internal struct FixedPhysicsBody
{
    public Fixed64 PositionX, PositionY;      // 位置
    public Fixed64 RotationRadians;           // 旋转（目前恒为 0，俯视角不需要）
    public Fixed64 LinearVelocityX, Y;        // 线速度
    public Fixed64 AngularVelocity;           // 角速度（目前恒为 0）
    public bool IsAwake;                       // 是否活跃
    public bool IsEnabled;                     // 是否启用
}
注意：RotationRadians 和 AngularVelocity 字段虽然存在，但代码里永远被设为 0（Step 里 body.AngularVelocity = Fixed64.Zero）。这是俯视角小球的设定——只有平移，没有旋转。保留字段是为了快照结构兼容和未来扩展。

ContactKey —— 接触对的规范化

private readonly struct ContactKey
{
    public ContactKey(int bodyAId, int bodyBId)
    {
        // ★ 永远把较小的 ID 放前面——规范化
        if (bodyAId <= bodyBId) { BodyAId = bodyAId; BodyBId = bodyBId; }
        else                    { BodyAId = bodyBId; BodyBId = bodyAId; }
    }
}

这样 (玩家1, 玩家2) 和 (玩家2, 玩家1) 会被当作同一个接触，避免重复。这是确定性的基础——同一对接触在不同端必须生成相同的 key。

3Step 三段式流程

Step(Fixed64 dt)（:92-132）是物理层的入口，每帧由 BattleLogic.Tick 调用一次。它做三件事，顺序不能变：

① 移动积分（Movement Integration）

遍历所有 body，把 _pendingLinearVelocities（移动输入）+ _pendingImpulses（冲量）合并成请求速度，写入 body 速度，然后 position += velocity * dt。此时玩家可能已经穿进墙里、穿进别人身体里。

② 占用分离（Occupancy Resolution）

检测所有玩家两两之间的穿透，把互相重叠的玩家沿法线推开。迭代 4 次保证收敛。这一步处理后，玩家之间不再重叠。

③ 房间边界 Clamp

把所有玩家的位置钳制到房间边界内。如果撞墙，清零往墙里钻的速度分量。放在最后，因为占用分离可能把人推过墙。

④ 收尾

RebuildOccupancyContacts 重建当前接触列表（供快照/哈希用），清空 _pendingLinearVelocities 和 _pendingImpulses（一帧一清）。

为什么是这个顺序？

积分在前

必须先让玩家"移动到新位置"，分离和 clamp 才有东西可以处理。先算出"想去哪"，再修正"能不能去"。

分离在中

分离可能把玩家推到墙外（比如被另一个玩家挤过去）。所以分离必须在 clamp 之前。

Clamp 在后

作为最终防线——不管前面怎么动，最后一定能把人拉回房间内。这是硬保证。

4移动积分

第一步积分（:96-125）的细节：

4.1 先排序再迭代

BuildSortedBodyBuffer();   // _sortedBodyIdsBuffer.Clear() → 加全部 key → Sort()

每次 Step 开头都重新排序。因为 _bodies 是 Dictionary，迭代顺序在 .NET 不同版本/平台间不保证一致。排序后用确定性的 bodyId 顺序迭代，是跨端 bit-exact 的前提。

4.2 速度合成

// 每个 body 的请求速度 = 移动输入 + 冲量
FixedPhysicsVector inputVelocity = GetRequestedVelocity(bodyId, _pendingLinearVelocities);
FixedPhysicsVector impulse = GetPendingImpulse(bodyId);
FixedPhysicsVector requestedVelocity = inputVelocity + impulse;

body.LinearVelocityX = requestedVelocity.X;
body.LinearVelocityY = requestedVelocity.Y;

移动输入（LinearVelocity）

来自 SetBodyMovementInput(bodyId, dx, dy)，由 MoveSystem.Apply 调用。值 = 归一化的(dx,dy) × MoveSpeed(5)。这是玩家"WASD 想往哪走"。

冲量（Impulse）

来自 ApplyBodyImpulse(bodyId, ix, iy)，用于撞击击退。可以叠加（currentImpulse + newImpulse）。这是"被别人撞飞"。

4.3 位置更新

if (body.IsEnabled && body.IsAwake)
{
    body.PositionX += body.LinearVelocityX * dt;   // dt = 1/30 Fixed64
    body.PositionY += body.LinearVelocityY * dt;
}
IsAwake 的作用：如果请求速度非零，置 IsAwake = true（:113-116）。静止的 body（IsAwake = false 或 IsEnabled = false）不更新位置。这是一种简单的"休眠"优化，但更重要的是——它影响状态哈希，所以必须确定性维护。

4.4 输入归一化

SetBodyMovementInput 会先调用 NormalizeInput（:484-495）：

private static void NormalizeInput(ref Fixed64 dx, ref Fixed64 dy)
{
    Fixed64 lengthSquared = (dx * dx) + (dy * dy);
    if (lengthSquared <= Fixed64.One) return;   // 向量长度 ≤ 1，不归一化
    Fixed64 inverseLength = Fixed64.One / FixedMath.Sqrt(lengthSquared);
    dx *= inverseLength;
    dy *= inverseLength;
}

只有当输入向量长度超过 1才归一化。这保证了斜向移动（如 dx=1, dy=1）不会比直线快——对角线的长度 √2 会被压回 1。

5占用分离（核心）

ResolvePlayerOccupancy（:228-306）是物理层最精巧的部分。它处理"两个玩家挤在一起"的情况——不是弹开，而是谁在推就推谁，都不推就对半分。

5.1 算法骨架

for (iteration = 0; iteration < 4; iteration++)        // ★ 外层：最多迭代 4 次
{
    bool resolvedAnyPair = false;
    for (i = 0; i < N-1; i++)                            // 两两组合
        for (j = i+1; j < N; j++)
        {
            // 1. 算两球距离
            // 2. 算穿透量 = 最小分离距离(2R) - 距离
            // 3. 如果没穿透 → continue
            // 4. 算分离法线方向
            // 5. 算各自要推多少份额
            // 6. 推开两个 body
            resolvedAnyPair = true;
        }

    if (!resolvedAnyPair) break;                         // 本轮没发现任何穿透 → 提前退出
}

5.2 为什么需要多次迭代？

单次不够的场景

三个玩家 A、B、C 排成一条线，A 撞 B。单次迭代：把 A 和 B 分开。但分开 B 时，B 可能又穿进 C。需要第二轮把 B 和 C 分开。

4 次为什么够？

这是经验值。玩家数量少（演示场景 2-4 人），穿透链不会太长。加上有 if (!resolvedAnyPair) break 提前退出——一旦收敛就停，不浪费。对于小球演示场景，4 次绰绰有余。

5.3 穿透检测

Fixed64 deltaX = bodyB.PositionX - positionAX;
Fixed64 deltaY = bodyB.PositionY - positionAY;
Fixed64 distanceSquared = (deltaX * deltaX) + (deltaY * deltaY);
Fixed64 distance = distanceSquared > OccupancyEpsilon
    ? FixedMath.Sqrt(distanceSquared) : Fixed64.Zero;
Fixed64 penetration = MinimumPlayerSeparation - distance;  // 2R - dist
if (penetration <= OccupancyEpsilon) continue;             // 没穿透，跳过
玩家分离示意（俯视）： bodyA ● ● bodyB ←── dist ──→ MinimumPlayerSeparation = 2 × PlayerRadius = 2 × 0.45 = 0.9 如果 dist < 0.9 → penetration = 0.9 - dist > 0 → 需要分离 如果 dist ≥ 0.9 → penetration ≤ 0 → 不干涉，跳过
为什么先算 distanceSquared 再开方？开方是定点运算里较贵的操作。先用平方比较（distanceSquared > OccupancyEpsilon）做粗筛，只在确实需要距离值时才开方。这是定点数学的常见优化。

6"谁推谁"份额分配

CalculateSeparationShares（:387-433）决定了分离时两个玩家各被推多少。这不是简单对半分，而是基于移动意图的三态决策。

6.1 移动意图（TowardIntent）

先算每个玩家"是否在朝对方推"（GetTowardIntent，:435-444）：

// 玩家的请求速度在法线方向上的投影
Fixed64 towardIntent = (velocity.X * normalX) + (velocity.Y * normalY);
return towardIntent > 0 ? towardIntent : 0;   // 负值（在远离）记为 0

直观理解：如果玩家 A 的移动方向和"指向 B 的法线"同向，说明 A 在往 B 身上挤——A 是"推的人"。

6.2 三种情况

A 推 B 不动

A 单向推

A 朝 B 移动，B 没动。

moveBodyA = penetration  // A 全责，被推回
moveBodyB = 0             // B 不动
双向互推

都在推

A 和 B 都朝对方移动。

// 按意图强度比例分摊
moveBodyA = penetration × (intentA / (intentA + intentB))
moveBodyB = penetration - moveBodyA
都不推

无人移动

两人静止但重叠（如刚 Spawn）。

// 对半分
moveBodyA = penetration / 2
moveBodyB = penetration / 2
这个设计对应演示玩法：README 提到"两球相撞产生击退，客户端故意不预测，由服务端权威裁决"。撞击的冲量通过 ApplyBodyImpulse 施加，而占用分离处理的是持续挤压（推墙、推人卡位）。两者的区别：冲量是瞬时的（飞出去），占用是持续的（贴着推）。

6.3 为什么用意图比例而不是质量？

这套物理没有质量概念——所有玩家等价。份额分配靠"谁更用力推谁就多被反推"，这比模拟质量/动量简单得多，而且对 MOBA 风格的"有卡位、无真实互推"语义更合适。这也对应总目录里提到的设计决策："MOBA 式有卡位、无普通移动真实互推"。

7完全重叠兜底

一个必须处理的边界情况：两个玩家完全重合（距离 ≈ 0）。这时无法算法线方向（除零），DetermineSeparationNormal（:351-385）有三级兜底：

第一优先：用位置差算法线

distanceSquared > OccupancyEpsilon → 正常情况，法线 = 归一化的位置差向量。

第二兜底：用相对速度方向

位置重合但两人有相对速度 → 法线 = 归一化的相对速度方向。物理意义："两人迎面撞上，沿撞击方向分开"。

最终兜底：用 ID 比较定方向

位置重合 + 速度也相同/为零 → normalX = bodyAId ≤ bodyBId ? 1 : -1。用 ID 大小决定谁往左谁往右。

为什么最终兜底用 ID 比较？因为必须确定性。如果用随机方向或时间戳，两端会算出不同的法线 → 分离后位置不同 → 哈希不一致 → 永久回滚。用 bodyAId ≤ bodyBId 这种纯 ID 比较，保证两端做出完全相同的选择。这是确定性工程的典型手法：当没有物理依据时，用稳定的序关系兜底。

8房间边界 Clamp

ClampPlayersToRoom（:192-226）是 Step 的最后一步，把所有玩家拉回房间内。

8.1 房间尺寸

// GameplayRoomSettings.cs
RoomHalfWidth  = 12.0    // 房间半宽
RoomHalfHeight = 8.0     // 房间半高
PlayerRadius   = 0.45    // 玩家半径

// 玩家可达边界（留出半径，防止半身出墙）
PlayerMaxX = RoomHalfWidth  - PlayerRadius = 11.55
PlayerMinX = -11.55
PlayerMaxY = RoomHalfHeight - PlayerRadius = 7.55
PlayerMinY = -7.55
房间边界示意： ┌─────────────────────────────┐ Y = +8.0 │ │ │ ● ← 玩家中心 │ 玩家可达 Y = +7.55 │ ↑ PlayerRadius = 0.45 │ │ │ │ │ └─────────────────────────────┘ Y = -8.0 X=-12.0 X=+12.0

8.2 智能速度清零

撞墙时不是粗暴地把速度全清零，而是只清掉往墙里钻的那个分量：

// 撞左墙且正在往左钻 → 清零 X 速度
if (clampedX <= PlayerMinX && body.LinearVelocityX < 0)
    body.LinearVelocityX = 0;

// 撞右墙且正在往右钻 → 清零 X 速度
if (clampedX >= PlayerMaxX && body.LinearVelocityX > 0)
    body.LinearVelocityX = 0;
❌ 简单做法（清零全部速度）

贴着墙往斜方向走时，速度全清零 → 贴墙滑动失效，玩家感觉"卡住"。

✅ 本项目（只清法向分量）

撞左墙时只清 X，保留 Y → 玩家可以沿墙滑动，手感自然。

8.3 一个有趣的注释

// Quantize bounds from the same float geometry used by Box2D before entering Fixed64.
public static readonly Fixed64 PlayerMaxX = (Fixed64)((float)RoomHalfWidth - (float)PlayerRadius);

这个注释说明边界值先转 float 做减法，再转 Fixed64——刻意复刻 Box2D 时代的几何值，保证 S2 前后的房间边界完全一致，让哈希基线变化最小化。这是一个"迁移时保持兼容"的细节。

9定点 epsilon

物理层定义了 4 个定点 epsilon 常量，每个都有具体用途：

常量值用途
OccupancyEpsilon1/10000 = 0.0001占用分离的穿透判定阈值。穿透量 ≤ 此值视为不干涉。也用于距离平方的比较（避免除零）。
ContactTolerance1/1000 = 0.001接触判定的容差。距离 ≤ (2R + tolerance) 视为"正在接触"，记入 _occupancyContacts。
MovementIntentEpsilon1/10000移动意图判定阈值。意图投影 ≤ 此值视为"没在推"。
MinimumPlayerSeparation2R = 0.9不是 epsilon，是最小分离距离——两球圆心间的最小允许距离。
为什么用这么小的值？因为是定点数。Fixed64 的精度是确定的（不像浮点会随数值大小波动），0.0001 在定点域里是一个稳定的小量。用这么小的阈值意味着——任何超过 0.0001 的穿透都会被处理，几乎没有"漏网之鱼"。这与浮点物理需要较大容差（如 0.01）形成对比。

10确定性保障

这套物理的每个设计都服务于一个目标：给定相同输入，两端产出 bit-exact 相同的结果。具体手段：

① 全定点运算

无浮点

  • 所有位置、速度、距离用 Fixed64
  • 开方用 FixedMath.Sqrt（定点实现）
  • 没有 float / double 参与计算
② 排序迭代

顺序确定

  • BuildSortedBodyBuffer 每帧重排
  • 所有循环基于排序后的列表
  • 不依赖 Dictionary 迭代顺序
③ 接触规范化

ContactKey 归一

  • 小 ID 在前，大 ID 在后
  • (A,B) 和 (B,A) 生成相同 key
  • 快照/哈希时接触列表也排序
④ 兜底可复现

无随机/无时间

  • 完全重叠时用 ID 比较定方向
  • 没有 Random、DateTime
  • 没有 async（调度顺序不定）

黄金哈希验证

BattlePredictionSelfTestSuite 里有一个 fixed-physics-bit-exact 用例，跑固定物理场景后断言哈希等于 0xD2120B5F0F5A5FE5。这个哈希是全定点物理跨端一致性的硬保证——只要任何平台的计算结果偏离这个值，测试就会报错并打印实际哈希。

对比 Box2D 的根本差异：Box2D 的 WarmStarting 把上一帧的冲量缓存（浮点）复用到这一帧，跨端无法保证 bit 一致。而这套手写物理每帧独立计算，无跨帧隐藏状态——给定 (位置, 速度, 输入) 就能算出确定的 (新位置, 新速度)。这是"可快照、可哈希、可回滚"的根本前提。

11快照与回滚

物理世界必须支持 TakeSnapshot / RestoreSnapshot，这是客户端回滚的基础。

TakeSnapshot（:146-166）

public PhysicsWorldSnapshot TakeSnapshot()
{
    // 1. 收集所有 body，转成 PhysicsBodySnapshot[]
    // 2. Array.Sort(bodies, BodyId 比较)        ★ 排序保证哈希确定
    // 3. 收集所有 contact，转成 PhysicsContactSnapshot[]
    // 4. Array.Sort(contacts, BodyAId→BodyBId 比较)  ★ 排序
    // 5. 返回 new PhysicsWorldSnapshot(bodies, contacts)
}

RestoreSnapshot（:168-190）

public void RestoreSnapshot(PhysicsWorldSnapshot snapshot)
{
    ClearBodies();                    // 清空所有状态
    foreach (body in snapshot.Bodies)
        _bodies[body.BodyId] = new FixedPhysicsBody(body);   // 逐个恢复
    foreach (contact in snapshot.Contacts)
        _occupancyContacts[key] = contact;                   // 恢复接触
}
注意：RestoreSnapshot 不恢复 _pendingLinearVelocities 和 _pendingImpulses——这两个是"本帧待处理输入"，回滚后会由上层（BattleLogic.Tick / BattleSimulation）根据输入历史重新填充。物理世界只负责"状态"，不负责"输入意图"。

在回滚链路中的位置

客户端收到权威快照（不一致时）
  └─ BattleSimulation.ReconcileAuthoritativeSnapshot
      └─ ApplyAuthoritativeSnapshot
          └─ _worldState.RestoreSnapshot(snapshot)
              └─ PhysicsWorld.RestoreSnapshot    ← 物理世界被重置到权威帧
      └─ AdvancePredictionTo(replayTarget)            ← 用本地输入重新跑
          └─ BattleLogic/BattleSimulation.Tick
              └─ SetBodyMovementInput(...)             ← 重新填输入
              └─ PhysicsWorld.Step                  ← 物理重新积分

12设计权衡总结

这套物理做了什么 / 没做什么

维度做了没做（刻意取舍）
运动平移积分、输入归一化、冲量叠加旋转、角动量（俯视角不需要）
碰撞圆-圆占用分离、圆-矩形边界 clamp真实弹性碰撞、摩擦、 restitution
互推基于移动意图的份额分配（三态）质量、动量守恒（MOBA 卡位语义）
求解4 次迭代 + 提前退出连续碰撞检测（CCD）、亚步进
休眠IsAwake 标志（静止不积分）完整的 Broadphase/Narrowphase 分层

核心设计哲学

简单优先

555 行解决战斗

没有 Broadphase 树、没有约束求解器、没有 manifold。玩家数少（2-4），两两暴力检测完全够用。简单 = 可控 = 可验证。

确定性优先

一切为了 bit-exact

排序迭代、定点 epsilon、ID 兜底、无跨帧状态——每个决策都是为了"两端算出相同结果"。物理真实可以妥协，一致性不能。

演示导向

够用就好

这是求职演示，不是商业引擎。撞击击退 + body blocking 足够展示同步难点，不需要 ragdoll、布料、关节。

可解释

每行代码能讲清"为什么"

面试场景下，能讲清楚 4 次迭代为什么够、份额分配为什么用意图、clamp 为什么放最后——这比物理精度更重要。

一句话总结：这套物理不是"强大的物理引擎"，而是"恰到好处的确定性物理"。它用最小的复杂度，换来了完全可控、跨端一致、可快照可回滚——这三点正是帧同步游戏的命脉。S2 移除 Box2D 不是降级，是卸下了一个看起来强大实则不适合的包袱。
