## Context

### 快照通路正在丢精度

`Fixed64` 有 32 位小数（`FixedMath.cs:17` `SHIFT_AMOUNT_I = 32`）。而 proto 的快照坐标是 **float**：

```proto
message PlayerSnapshot {
    float X = 2;
    float Y = 3;
    float LinearVelocityX = 6;
    float LinearVelocityY = 7;
}
```

服务端发送时 `X = (float)player.X`（`BattleComponent.cs:191`），客户端收到后 `(Fixed64)player.X` 转回定点（`BattleClientController.cs:602`）。float 只有 24 位有效位，坐标在 ±20 量级时可分辨增量为 2⁻¹⁹，而定点精度是 2⁻³²——**往返一趟 raw value 低约 13 位被抹掉，误差量级 ~8000 raw units**。

后果落在 `CheckConsistency`（`BattleSimulation.cs:406-408`）上，它比的是严格相等：

```csharp
bool matched = prediction.X.m_rawValue == authoritativeSelf.X.m_rawValue &&
               prediction.Y.m_rawValue == authoritativeSelf.Y.m_rawValue && ...
```

物理积分产出的坐标不可能恰好落在 float 可精确表示的点上，因此真实网络路径下该判断**几乎必然为 false**。推论：当前 `_rollbackCount` 虚高，每个权威快照都在触发一次失配与一次回滚，而 S1 的平滑层把 0.000002 单位的误差吸收得看不出来。

25 条自测用例全绿不矛盾——它们用 `new BattleWorldSnapshot(...)` 手工构造权威快照（`BattlePredictionSelfTestSuite.cs:258-268`），**不走 proto 序列化**，碰不到这个损失。测试与生产走的是两条路，这是本阶段要一并补上的缺口。

### 输入通路是安全的

`ReadKeyboardDirection`（`BattleClientController.cs:817-841`）只产出 `-1/0/1`，float 与 Fixed64 都能精确表示；归一化在两端各自用定点做（`FrameSyncPhysicsWorld.cs:484-495`）。`C2B_PlayerInput` 的 `float Dx/Dy` 无需改动。

### 两端都在算哈希，链路是断的

客户端 `SnapshotManager.cs:40-42` 每帧算 `LatestHash`，**全仓无消费方**，算完即被下一帧覆盖。服务端 `BattleLogic.GetStateHash()`（`BattleLogic.cs:235-238`）只能算当前帧——客户端上报天然晚一个 RTT，等服务端收到第 N 帧的报告时自己已跑到 N+3，而它没保存 N 帧的值。

### 四个字段已是恒定值

查全仓写入点，物理体这四个字段从未被真正改变：

| 字段 | 实际取值 | 唯一写入点 |
|------|---------|-----------|
| `RotationRadians` | 恒 `Zero` | 仅构造（`FixedPhysicsBody.cs:11`）与快照转录（`:23`），物理代码从未触碰 |
| `AngularVelocity` | 恒 `Zero` | `FrameSyncPhysicsWorld.cs:66`、`:112`，两处都是赋 `Zero`，每 Step 重置 |
| `IsAwake` | 恒 `true` | 初始 `true`（`FixedPhysicsBody.cs:15`），`FrameSyncPhysicsWorld.cs:115` 再赋 `true`。**全仓无一处设 false** |
| `IsEnabled` | 恒 `true` | 初始 `true`（`:16`），此后无人写 |

俯视角小球不旋转、无休眠机制，这是必然结果。这些字段是 Box2D 时代的结构遗留，S2 重写时照搬了形状但语义已空。它们每帧仍在 proto 里序列化，服务端 `BattleComponent.cs:194-199` 老实地填。

## 关键约束：不引入任何容差

Source 引擎用「每字段容差」做对账（`predictioncopy.cpp:725`，`fieldTolerance` 按字段声明），因为它是浮点物理，跨平台 bit-exact 不可达，只能靠容差兜底。

**本项目不能照搬。** S2 已把物理层全部重写为定点，买到的正是 bit-exact 确定性——一位不差是可达成的，任何差异都是真 bug。在这个位置引入容差等于把 S2 的成果扔掉，且代价具体：**容差会吃掉小误差，而失同步几乎总是从小误差开始的**。一个定点运算顺序写错导致的 1 raw unit 偏差，容差会判成通过，直到被后续帧放大成肉眼可见——那时已丢失定位能力，而定位能力正是 S3 存在的理由。

正确方向是反的：**让网络层不丢精度**，而不是让判据容忍丢精度。

## 目标

1. **快照定点字段无损传输** —— proto 改传 `m_rawValue`，往返逐位一致，`CheckConsistency` 的严格相等从「几乎必然失败」变为「该成立就成立」。
2. **客户端上报逐帧哈希** —— 新增 `C2B_StateHashReport`，携带帧号与**该帧预测完成后**的世界哈希。帧号与哈希必须在同一函数内同时取得，见「采样点」。
3. **服务端建历史哈希索引并告警** —— 可查任意近期帧的权威哈希，与上报值比对，不一致打 `[Battle][HashMismatch]` 警告。
4. **补上「走完整序列化往返」的测试路径** —— 现有 25 条用例全部绕开了 proto，本阶段补第一条覆盖它的用例。

## 哈希口径：不改 StateHasher

`StateHasher.cs:11-95` 现有覆盖面**原样保留**。逐类说明理由，这张表要防的是后续有人加字段时塞错东西：

| 类别 | 字段 | 进哈希 | 理由 |
|------|------|--------|------|
| 核心世界态 | 坐标、Health/MaxHealth/Mana/MaxMana/Attack、Buff 全字段、Numeric 修饰器 | ✅ | 两端独立推算，该一致就必须一致 |
| 推导冗余 | contacts | ✅ | 位置的纯函数，`RebuildOccupancyContacts()`（`FrameSyncPhysicsWorld.cs:308-338`）每 Step 先清空再从位置重算，输出经排序（`:164`）且 `ContactKey` 归一化 A/B（`:499-511`）。位置一致则 contacts 必然一致，无害 |
| 恒定遗留 | RotationRadians、AngularVelocity、IsAwake、IsEnabled | ✅ | 恒定值，两端混入同一常量，不影响判据。字段本身从 proto 删除（Step 1），但哈希侧不动 |
| 传输元数据 | LatestAcceptedInputFrame、AttributeDirtyMask、BuffDirtyMask、BuffSnapshotFrameIndex、IsBuffFullSync、BuffSnapshot.DirtyFlags | ❌ | **语义不可比**：服务端知道自己这帧标脏了什么，客户端重建出的状态里没有「曾经脏过」这个概念。拿它对账必然恒不匹配，且不匹配不代表任何问题 |

最后一类当前**已经剔干净了**，`StateHasher` 一个都没混。但这是手写字段列表，没有机制保护——Source 用 `FTYPEDESC_NOERRORCHECK` 标志位把它做成了机制（`datamap.h:221`），本项目只能靠文档与 review。**因此写成显式约束防回归。**

要紧的一点：客户端属性是 `PlayerAttributeSync.Merge()` 把增量合到基线上**重建**出来的（`BattleClientController.cs:590-597`）。哈希覆盖的必须是**合并的结果**，绝不能是合并的记账。脏同步是上个阶段刚做的（`4c1104cb`），其正确性目前没有任何自动化判据在守——S3 的哈希对账正好补上这个缺口。

## 数据流

```
客户端 BattleSimulation.Tick 第 N 帧
  → AdvancePredictionTo(N) 完成，世界态已是 N 帧预测结果
  → 同一函数内：算 N 帧哈希，每 30 帧发 C2B_StateHashReport(N, hash)
                    ↓ 网络（约 1 RTT）
服务端收到「客户端说第 N 帧是 0xABCD」
  → 查历史哈希索引第 N 帧
  → 查不到（太旧/太新）→ 计入 noRecord，不告警
  → 查到且相等 → 计入 matched
  → 查到且不等 → 计入 mismatch + Log.Warning
```

## 采样点

**这一步是方案里最容易做错的地方。**

采样点必须满足一个条件：**帧号与该帧的哈希在同一个函数作用域内同时可得**。否则会出现「发送 `FrameIndex = N` 却携带 N-1 帧哈希」，服务端系统性 mismatch，而这类 bug 极难查——`StateHasher.Hash` 不混入 `snapshot.FrameIndex`（`StateHasher.cs:11-95` 通读可确认），哈希不自证帧号，帧号记账错了产生的是**假匹配或系统性失配**，不是可定位的错误。

选 `BattleSimulation.Tick`，紧接 `AdvancePredictionTo` 之后：

```
BattleSimulation.cs:215  _onSendInput(frameIndex, ++_inputSeq, dx, dy, skillId)
              :217-222   ApplyPendingServerSnapshot(...)        ← 对账 + 回滚重放
              :223       AdvancePredictionTo(frameIndex, fixedDt)  ← 本帧预测完成
                         ★ 采样点：此处 frameIndex 与世界态严格对应
              :225       return new TickResult(...)
```

**为什么不用 `SnapshotManager.Tick`（`GameLogic/FrameSync/SnapshotManager.cs:40-42`）**——那里虽然已经在算哈希，但存在致命时序问题：

```
TickDispatcher.ExecuteTick 按 Priority 升序：
  BattleClientController (Priority => 0)
    └─ BattleSimulation.Tick(N)  ← 若在此发送，此刻 SnapshotManager 还没跑
  SnapshotManager (Priority => int.MaxValue)
    └─ 才保存 N 帧哈希           ← 晚了一个环节
```

在 `BattleSimulation` 里发送、却去读 `SnapshotManager` 的历史，读到的必然是 N-1 帧的值，或者读不到。**两者必须在同一处，不能跨 tickable 拆开。**

**因此本方案不改 `SnapshotManager`，也不需要客户端历史哈希索引。** 客户端在采样点当场算、当场发，不留历史——历史只有服务端需要（用来匹配迟到的上报）。这比原设计少一个数据结构。

代价是每 30 帧多一次 `TakeSnapshot()` + `Hash()`。`SnapshotManager` 每帧都在做同样的事，所以增量是 1/30 的既有开销，可忽略。

服务端采样点在 `BattleLogic.Tick` 末尾、`OnBroadcast` 之前（`BattleLogic.cs:227-229` 之间），即 `ApplyBuffTicks` 之后。**必须在这个位置**，才能保证存下的哈希与同帧广播给客户端的快照描述同一个世界。

## 实现步骤

### Step 1：proto 快照字段改传 raw，删除死字段

改 `GameServer/Tools/NetworkProtocol/Outer/OuterMessage.proto` 的 `PlayerSnapshot`：

| 字段号 | 原 | 改为 | 说明 |
|--------|-----|------|------|
| 2 | `float X` | `int64 XRaw` | 传 `m_rawValue` |
| 3 | `float Y` | `int64 YRaw` | 传 `m_rawValue` |
| 5 | `float Angle` | **删除** | 恒 `Zero` 死字段 |
| 6 | `float LinearVelocityX` | `int64 LinearVelocityXRaw` | 传 `m_rawValue` |
| 7 | `float LinearVelocityY` | `int64 LinearVelocityYRaw` | 传 `m_rawValue` |
| 8 | `float AngularVelocity` | **删除** | 恒 `Zero` 死字段 |
| 9 | `bool IsAwake` | **删除** | 恒 `true` 死字段 |
| 10 | `bool IsEnabled` | **删除** | 恒 `true` 死字段 |

**字段号一律保留原值，删掉的号不复用。** protobuf 里留空号是正常的，它标记「这里曾有字段」；复用会让缓存的旧生成代码静默读错字段。

同时改 `C2B_JoinBattleResponse`（`:47-53`）：`float X = 2` / `float Y = 3` → `int64 XRaw` / `int64 YRaw`。

**这条别漏。** 客户端用它初始化位置（`(Fixed64)response.X`），服务端 `JoinPlayer` 也是 `(Fixed64)x`（`BattleLogic.cs:50-52`）。当前 `GetSpawnPosition`（`BattleComponent.cs:642-648`）产出 ±3.0 及其倍数，float 可精确表示，所以**暂时**没有损失。但只要将来出生点改成非 float 可精确表示的值（随机散布、从配置读定点值），客户端初始状态就与服务端不同，**哈希告警会从加入战斗那一刻就开始**。留着它，「网络层不丢精度」这个目标就是不完整的。

`GetSpawnPosition` 的返回类型也应从 `(float, float)` 改为 `(Fixed64, Fixed64)`，否则 raw 转换只是把损失点往前挪了一格。注意 `TestRunner.cs:714`、`:812`、`:1008` 三处调用要同步改。

**`Contacts` 保留传输，不要顺手删。** 虽然客户端每 Step 都会重算，但 `RestoreSnapshot`（`FrameSyncPhysicsWorld.cs:184-189`）会先把网络值填进 `_occupancyContacts`，而权威帧恢复后若在下一个 `Step` 之前发生 `TakeSnapshot()`，读到的就是这份转录值。停传会让该帧客户端 contacts 为空而服务端非空，凭空造出一次哈希失配。

改完跑 `GameServer/Tools/ProtocolExportTool/Run.bat`，一次同时刷新服务端与客户端四个生成文件。**新增消息（Step 3）与本步的字段改动应在同一次生成里完成**，避免两侧生成代码错位。

同步改三处调用：

- 服务端 `BattleComponent.cs:188-199`：`XRaw = player.X.m_rawValue`，删掉 Angle/AngularVelocity/IsAwake/IsEnabled 四行；`:300-315` 的 `BuildFullSyncSnapshot` 同样处理
- 服务端 `BattleComponent.cs:69` 附近的 Join 响应填充
- 客户端 `BattleClientController.cs:602-616`：`Fixed64.FromRaw(player.XRaw)`；`PhysicsBodySnapshot` 构造里 `RotationRadians`/`AngularVelocity` 传 `Fixed64.Zero`、`IsAwake`/`IsEnabled` 传 `true`——与 `FixedPhysicsBody` 全新构造时的值一致（`FixedPhysicsBody.cs:11-16`），保证转录路径与本地路径产出同一份状态

`Fixed64.FromRaw(long)` 已存在且在用（`TickAccumulator.cs:12`、`FixedMath.cs:167`），无需新增。

### wire type 变更的发布约束

字段 2/3/6/7 从 `float`（wire type 5，fixed32）改为 `int64`（wire type 0，varint）**不是改名，是改 wire type**。因此：

- **客户端与服务端必须同步发布**，不支持滚动升级
- 旧生成代码连新协议会静默解析错误，不是报错而是读出垃圾值
- 若将来需要滚动升级能力，必须**改用新字段号**而非复用 2/3/6/7

本项目是本地 demo，客户端与服务端总是一起编译，所以直接改字段号可接受。**这个前提要是变了（比如发布到公网、需要灰度），必须回头重新评估。**

### 带宽影响：必须实测，可能变大

`int64` 在 protobuf 里用 varint 编码，**负数会符号扩展成 10 字节**。坐标和速度都可能为负（房间坐标以原点为中心），所以最坏情况下每个字段从 4 字节涨到 10 字节。

正数侧也不便宜：raw value 是真实值 × 2³²，坐标 3.0 的 raw 是约 1.29e10，需要 5 字节 varint。

所以「int64 比 float 多 4 字节但 varint 友好」这个说法是错的——**实际大小取决于数值符号与绝对值，必须实测**（Step 8 的 4.7）。

`sint64`（zigzag 编码，负数不再是 10 字节）理论上更合适，但**本 proto 从未用过该类型，导出工具的类型映射未经验证**。不要在本阶段引入，先用 `int64` 跑通并实测；若带宽确实成为问题，再单独验证 `sint64` 是否被工具链支持。

### Step 2：上报消息与发送节奏

proto 末尾**追加**（不要插在中间，opcode 按声明顺序分配，插中间会让后续消息全部改号）：

```proto
// 客户端逐帧状态哈希上报（单向消息）
message C2B_StateHashReport // IMessage
{
	uint32 FrameIndex = 1;
	uint64 StateHash = 2;
}
```

当前一次性消息最大 opcode 是 `S2C_BandwidthStats = 134227734`（`OuterOpcode.cs:20`），新消息将得 `134227735`。

发送节奏照抄 Ping 的写法（`BattleSimulation.cs:531-541`）——帧计数而非 wall-clock，这样无头测试可复现：

- 新增 `HashReportIntervalFrames = 30` 常量（与 `PingIntervalFrames` 并列，`:18`）
- 新增 `_hashReportCount` 字段，`SetJoined` 里归零（`:258` 那一串旁）
- 构造函数注入 `Action<uint, ulong>` 回调（`:95-108`），与 `_onSendPing` 同样处理

**新增 `SendHashReportIfNeeded(uint frameIndex)`，调用点在 `AdvancePredictionTo` 之后、`return` 之前（`:223` 与 `:225` 之间）。** 与 `SendPingIfNeeded()`（`:214`）的位置不同，后者在预测之前——**别照位置抄，只照结构抄**。

函数体内当场算哈希，不读任何历史：

```
BattleWorldSnapshot snapshot = _worldState.TakeSnapshot().WithFrameIndex(frameIndex);
_onSendHashReport(frameIndex, StateHasher.Hash(snapshot));
```

`frameIndex` 是入参，与快照严格同帧，**不存在跨 tickable 的错位可能**。`StateHasher` 已在 using 列表内（`:8` `GameShared.FrameSync.Snapshot`），无需新增引用。

发送实现放 `BattleClientController.cs`，照 `SendPingCommand`（`:855-861`）的 `new` + `GameClient.Instance.Send()` 写法。生成类虽提供池化 `Create()`，但客户端现有代码一处都没用，**保持一致，不要在同一文件引入第二种风格**。

**帧号必须显式携带在消息里。** `StateHasher.Hash` 不混入 `snapshot.FrameIndex`，哈希不自证帧号。这也是为什么采样点必须让帧号与哈希同源——见「采样点」一节。

### Step 3：服务端历史哈希索引与告警

`BattleLogic.cs` 新增 `SnapshotBuffer<ulong> _authoritativeHashHistory`，**容量 64**。取值理由：需覆盖「上报间隔 30 帧 + 单程网络延迟」。30Hz 下 64 帧约 2.1 秒，弱网 500ms 单程仍有余量。**这个数字不作为验收标准**，弱网测试若观察到 noRecord 偏高再上调。

`SnapshotBuffer<T>` 已 link 编译进服务端（`Entity.csproj:24` 通配 `GameShared/**/*.cs`），无需新依赖。

**前提声明：`SnapshotBuffer` 按插入顺序淘汰，不是按最小帧号淘汰**（`SnapshotBuffer.cs:26-41`，`Dictionary` + `Queue` FIFO）。服务端侧这个前提成立——`TickDispatcher` 的 `_currentFrame++` 单调递增（`TickDispatcher.cs:133`），永不回退，所以插入顺序恒等于帧号顺序，容量 64 就等于「最近 64 帧」。

**若将来服务端引入回滚或非单调保存，这个等价关系失效**，届时必须改成按帧号维护，或为哈希历史单独实现淘汰逻辑。客户端侧不受影响——本方案不在客户端存历史。

在 `Tick` 末尾、`OnBroadcast` 之前存入。注意 `GetStateHash()` 每次调用都会重新 `BuildBattleWorldSnapshot` + `Hash`，而 `:229` 的 `BuildTestSnapshot(frameIndex)` 已经构了一份快照——**复用它算哈希，不要多构一次**。

新增 `TryCompareReportedHash(long playerId, uint frameIndex, ulong reportedHash)`，返回三态（matched / mismatch / noRecord）。

**计数器生命周期（必须按此实现，否则跨测试污染）**：

- **三个计数器是整场战斗累计，不按玩家分**。日志里带 playerId 用于定位，计数不分玩家
- **`BattleLogic` 没有 `SetJoined`**——那是客户端 `BattleSimulation` 的概念。服务端只有 `JoinPlayer`（`BattleLogic.cs:50-55`）
- **清零依赖实例生命周期，不写显式 reset**。`TestRunner` 每个场景 `new BattleLogic()`（`TestRunner.cs:454`、`:474`、`:486`、`:508`、`:523` 等），字段自然从 0 开始，天然无跨测试污染
- **`JoinPlayer` 里不要清零**。新玩家加入或重连不应抹掉已有的失配记录——那是真实发生过的事实
- report.json 输出**全局值**，字段名用 `hashReportsSent`（客户端侧）与 `hashMismatchCount` / `hashNoRecordCount`（服务端侧），不加 playerId 后缀

告警走 `_logWarning`（`BattleLogic.cs:28`，`BattleComponent.cs:14` 已注入 `Log.Warning`），标签 `[Battle][HashMismatch]`，与现有 `[Battle][LateInputDrop]`（`:116`）风格一致。日志须含 playerId、frameIndex、双方哈希值。

**noRecord 不告警。** 帧太旧被逐出或太新还没算到，都是正常现象，告警只会训练出忽略告警的习惯。

但**noRecord 应该是少数**。如果它占了上报总数的大头，说明采样点或帧号记账有问题——验收时把它当信号看，不是当噪音看。

Handler 新建 `GameServer/Server/Hotfix/Battle/Handler/C2B_StateHashReportHandler.cs`，照 `C2B_PlayerInputHandler.cs` 的结构：取 `session.Scene.GetComponent<BattleComponent>()`、null 守卫、委托给组件、`await FTask.CompletedTask`。**Fantasy 靠反射发现 handler，无需注册表改动。** session → playerId 映射用 `_playerIdBySessionId`（`BattleComponent.cs:85`）。

### Step 5：自测用例

`BattlePredictionSelfTestSuite.cs` 注册两处：`AllCaseNames` 数组（`:13-40`，当前 25 条）末尾**追加**，以及 `RunCase()` switch（`:56-99`）加分支。`TestRunner.cs` 不用改。

**漏加 `AllCaseNames` 会导致用例静默不跑，而 `--scenario=all` 仍报 PASS。** 这是本方案第一大坑。

**只追加，不修改任何既有用例。** 断言用同一次运行内的前后比较，不硬编码绝对坐标——既有的 `room-boundary-clamps-player` 断言了具体 `m_rawValue`，**别学它**。

四条新用例：

- `snapshot-raw-roundtrip-bit-exact` —— **本阶段最关键的一条**。构造非平凡定点坐标（让 `Step` 跑若干帧自然产出，不要手填整数——整数在 float 里可精确表示，会让用例假通过），走完整 proto 序列化往返，断言 `m_rawValue` 逐位相等
- `hash-report-matches-reported-frame` —— **必须断言帧号与哈希的对应关系，不能只断言次数。** `HashReportRecorder` 记下每次回调的 `(frameIndex, hash)`；用例在同一帧独立算一次哈希，断言 `recordedHash == 独立算出的哈希` 且 `recordedFrame == 当时的 frameIndex`。**只断言次数的用例抓不到错位 bug**——这是本阶段最需要防的一类错误
- `server-hash-history-detects-mismatch` —— 服务端存若干帧后，喂一个正确哈希断言 matched、一个篡改哈希断言 mismatch、一个远期帧号断言 noRecord
- `hash-report-interval-is-30-frames` —— 断言 100 帧内回调次数为 3，防止节奏被误改。**这条是次要的**，前一条才是真判据

失败时**抛异常把实际值带出来**，照 `FixedPhysicsBitExact`（`:764-800`）的写法，别静默 `return false`——哈希类断言失败时看不到实际值，排查成本极高。

新增 `HashReportRecorder` 测试桩，形状照 `PingRecorder`（`:918-926`），但**必须同时记录帧号与哈希**（`PingRecorder` 只存单个值，不够用）。建议存 `List<(uint, ulong)>` 以便断言最后一次之外的历史。

## 与 S5 / S6 的接口约定

现在钉死，避免将来互相踩。

**与 S5（RTT 交叉校验）**：`C2B_StateHashReport` **只带 `FrameIndex` 与 `StateHash`，不带任何时间戳或客户端自算 RTT**。S5 要做服务端独立测量，从 `C2B_PingHandler.cs` 那条通路自己建，不要往本消息上挂字段。混进来会让 S3 的判据被客户端声称的数据污染。

**与 S6（一致时跳过重放）**：S6 的短路判断**必须放在 `ReconcileAuthoritativeSnapshot` 中段，不能在函数最前面整体 return**。以下三处必须保留执行：

```
BattleSimulation.cs:478  _authoritativeSnapshots.Save(...)              ← S3 依赖
              :480  DiscardPredictionsAtOrAfter(...)
              :497-500  if (logRollback) CapturePredictionErrorAfterReconciliation()   ← S1 守卫
```

第三处是 S1 落地的守卫：一致快照不重设平滑基线，否则每个快照都重启 `SmoothingDurationSeconds` 计时器。S6 若整体短路会一并吞掉。

## 风险与对策

| 风险 | 对策 |
|------|------|
