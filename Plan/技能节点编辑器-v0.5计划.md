# 技能节点编辑器 v0.5 开发计划

## Context

当前 `v0.4` 已经打通了一个重要闭环：

- 编辑器可以创建并保存 `ActionNode`
- 导出器可以把编辑器图转换为运行时 JSON
- 运行时可以加载并顺序执行 `Entry / Debug / Delay / Action`
- `ActionNode` 已经验证了“编辑器节点 -> 运行时节点 -> 资源执行”这条主链路

这说明当前系统已经不再是“一个能画图的小工具”，而是已经具备了**图编辑、图导出、图执行**三层结构。

但从节点图系统本身来看，当前版本依然停留在“单链路顺序执行”的阶段：

- 只能表达线性流程
- 没有统一的数据上下文
- 没有条件判断与分支能力
- 执行结果模型仍然偏 MVP
- 导出契约和图校验仍然偏弱

因此，`v0.5` 的重点不应该继续扩展业务节点，而应该回到节点图系统本身，补齐它作为后续战斗系统、网络同步系统、调试系统基础设施所必须具备的能力。

---

## 版本目标

`v0.5` 的核心目标定义为：

**把当前顺序执行图升级为“具备基础逻辑表达能力的运行时图”。**

一句话说：

**让图不仅能顺序跑，还能读写上下文、做条件判断，并根据结果走不同分支。**

本版本完成后，节点图系统应具备以下基础能力：

1. 有统一的运行时参数容器
2. 节点可以读取和写入参数
3. 图可以根据条件选择不同出口
4. 运行时执行不再只依赖单一顺序流
5. 导出和校验规则能覆盖这些新能力

---

## 为什么先做这个版本

### 1. 这是节点图系统真正的“语言能力”补全

当前图的本质仍然是：

`NodeA -> NodeB -> NodeC`

它能证明执行器存在，但还不能证明这套系统能够描述“逻辑”。

一旦补上：

- `Blackboard`
- `Condition`
- `Branch`

图才真正拥有最基本的逻辑表达能力。

### 2. 这一步仍然不需要引入战斗系统设计

本版本不定义：

- 伤害公式
- 技能目标选择规则
- Buff 机制
- 网络同步细节

它只定义图系统如何：

- 保存上下文
- 读取参数
- 判断条件
- 决定执行路径

这完全属于节点图系统基础设施，而不是玩法设计。

### 3. 后续所有复杂系统都会依赖这层能力

无论以后做：

- 战斗技能
- AI 行为树式逻辑
- 客户端表现图
- 服务端技能执行图
- 回放 / 预测 / 同步

几乎都离不开：

- 上下文数据
- 条件判断
- 分支流转

所以这一步越早定型，后面越稳。

---

## 本轮范围

### 本轮要做

- 新增统一 `Blackboard` 数据容器
- 新增 `SetVariable` / `GetVariable` 相关能力
- 新增 `ConditionNode`
- 新增 `BranchNode`
- 运行时支持多出口流转
- 导出器支持条件与分支节点
- 增强图校验规则

### 本轮不做

- 具体战斗节点设计
- 网络同步协议设计
- 回滚 / 预测执行
- 图可视化调试器
- Undo / Redo
- Copy / Paste / Duplicate
- 并行执行
- 子图 / 嵌套图
- 完整类型系统

### 本轮只解决一件事

**让图从“线性执行”升级为“能表达基础逻辑”。**

---

## 核心方案

## 一、引入 Blackboard 作为统一运行时上下文

当前 `SkillContext` 只有少量固定字段：

- `CasterId`
- `TargetId`
- `SkillId`
- `IsCancelled`

这不足以支撑图中的可扩展逻辑。

因此 `v0.5` 需要新增一个统一参数容器，例如：

- `SkillBlackboard`

职责只做一件事：

**以统一接口存取运行时变量。**

建议最小能力：

- `SetString`
- `SetFloat`
- `SetInt`
- `SetBool`
- `TryGetString`
- `TryGetFloat`
- `TryGetInt`
- `TryGetBool`
- `Contains`

本轮不追求复杂泛型与反射式系统，只做稳定、明确、可序列化、可校验的最小实现。

### 为什么现在就要 Blackboard

因为如果没有统一变量容器，后续每加一个节点，都只能：

- 往 `SkillContext` 持续塞字段
- 或把参数直接做成节点私有属性

这两种方式都会让系统快速失控。

Blackboard 的价值在于：

- 节点之间可以通过约定变量名协作
- 运行时状态有统一入口
- 后续做调试、回放、同步时有明确承载点

---

## 二、引入 ConditionNode

`ConditionNode` 的职责是：

**读取 Blackboard 中的变量，并做一次布尔判断。**

建议 `v0.5` 先支持最小条件集合：

- `Exists`
- `Equal`
- `NotEqual`
- `Greater`
- `GreaterOrEqual`
- `Less`
- `LessOrEqual`
- `IsTrue`
- `IsFalse`

建议最小属性结构：

- `key`
- `operator`
- `value`
- `valueType`

其中：

- `key` 表示要读取的 Blackboard 变量名
- `operator` 表示比较方式
- `value` 表示比较目标
- `valueType` 用于解析 `value`

### ConditionNode 的出口建议

- `True`
- `False`

这样它天然就是一个分流节点。

### 为什么先做 Condition 而不是更多 Action

因为没有条件判断，图无法表达：

- “如果有目标就继续”
- “如果怒气足够就进入下一段”
- “如果变量已初始化就走快捷路径”

这类逻辑全部都无法落图。

---

## 三、引入 BranchNode

`ConditionNode` 解决的是“判断”，`BranchNode` 解决的是“根据一个输入值分发到不同出口”。

建议 `v0.5` 的 `BranchNode` 先做成最小版：

- 读取一个布尔值或枚举样式字符串
- 根据结果选择不同输出端口

第一阶段甚至可以只支持：

- `True`
- `False`

如果实现成本可控，也可以直接支持：

- `CaseA`
- `CaseB`
- `Default`

但建议本轮不要做成任意动态端口系统，避免把编辑器复杂度一下抬得太高。

### 为什么 ConditionNode 和 BranchNode 要分开

因为两者职责不同：

- `ConditionNode` 负责产生判断结果
- `BranchNode` 负责根据输入结果做流转

如果一开始就把两者揉成一个“万能判断分支节点”，后面节点职责会越来越模糊。

---

## 四、运行时支持多出口流转

当前运行时的核心模型是：

- 节点执行
- 返回 `NextPort`
- 执行器根据 `NextPort` 找到下一条连接

这个方向本身是对的，`v0.5` 不需要推翻，只需要正式把它从“顺序执行实现细节”提升为“标准流转协议”。

### 运行时建议保持的抽象

节点执行结果继续保留：

- `Completed`
- `NextPort`

但语义需要更明确：

- `Completed = true` 表示流程结束
- `NextPort = "Out"` 表示继续到对应出口
- `NextPort = "True"` / `"False"` 表示进入分支

### 本轮不急着升级为复杂状态机

`Running / Success / Failure / Cancelled` 这类状态很重要，但建议放到 `v0.6`。

原因是 `v0.5` 的首要目标是先把图语言能力补齐。

---

## 五、导出契约增强

当前导出器已经能把编辑器图转成运行时 JSON，但下一步需要把契约明确化。

建议新增以下约束：

- 运行时图包含 `version`
- 节点类型必须在运行时白名单内
- 节点属性必须满足该类型的 schema
- 条件节点必须具备合法的比较参数
- 分支节点的出口定义必须合法

建议运行时 JSON 形态扩展为：

```json
{
  "version": "0.5",
  "skillName": "TestSkill",
  "nodes": [],
  "connections": []
}
```

后续版本如果有格式调整，可以基于 `version` 做兼容处理。

---

## 六、图校验增强

当前校验主要聚焦“是否能导出”和“是否存在基础节点错误”，但如果图要成为基础设施，校验强度必须提升。

`v0.5` 建议至少新增：

- 必须存在且只存在 1 个 `Entry`
- 所有边引用的节点必须存在
- 端口名必须匹配节点定义
- 非多出口节点不能从同一出口连出多条边
- `ConditionNode` 的比较参数必须合法
- `BranchNode` 的出口必须完整
- 不允许出现明显死路节点
- 不允许出现运行时不支持的节点类型

### 关于循环

本轮建议：

- 可以先不支持循环
- 或者仅检测并报错

因为一旦允许循环，就会牵涉：

- 执行步数限制
- 死循环诊断
- 中断语义

这些更适合放到 `v0.6` 再统一处理。

---

## 数据设计建议

### 一、SkillContext

建议新增：

- `SkillBlackboard Blackboard`

从而让 `SkillContext` 变成：

- 固定系统字段
- 统一运行时服务
- 可扩展运行时变量

### 二、SkillBlackboard

建议本轮使用简单字典实现，例如：

- `Dictionary<string, string>`
- `Dictionary<string, float>`
- `Dictionary<string, int>`
- `Dictionary<string, bool>`

优点是：

- 清晰
- 易校验
- 不依赖反射
- 不依赖 Unity 类型

### 三、ConditionNode 的运行时属性

建议导出示意：

```json
{
  "nodeType": "Condition",
  "properties": [
    { "key": "key", "value": "HasTarget" },
    { "key": "operator", "value": "IsTrue" },
    { "key": "valueType", "value": "Bool" }
  ]
}
```

### 四、BranchNode 的运行时属性

布尔分支最小形态可以是：

```json
{
  "nodeType": "Branch",
  "properties": [
    { "key": "key", "value": "HasTarget" },
    { "key": "valueType", "value": "Bool" }
  ]
}
```

然后运行时根据读取结果走：

- `True`
- `False`

## 编辑器侧建议

## 一、节点类型扩展

建议在编辑器中新增：

- `ConditionNode`
- `BranchNode`
- `SetVariableNode`

如果想控制本轮复杂度，也可以先不上独立 `GetVariableNode`，而是让读取变量只发生在 `ConditionNode` / `BranchNode` 内部。

### 为什么要先有 SetVariableNode

因为如果图里永远没有节点能写 Blackboard，那么：

- 条件判断只能依赖初始化上下文
- 节点之间无法形成数据协作

这样图系统依然偏弱。

因此建议 `v0.5` 最小闭环为：

`SetVariable -> Condition -> Branch`

---

## 二、属性编辑 UI

### ConditionNode

建议属性包括：

- `Key`
- `Operator`
- `ValueType`
- `Value`

UI 约束：

- `IsTrue / IsFalse / Exists` 时可隐藏 `Value`
- 数值类型时使用数值输入框
- 字符串类型时使用文本输入框

### BranchNode

最小实现建议：

- `Key`
- `ValueType`

出口固定：

- `True`
- `False`

这样编辑器改动最小，也便于导出和校验。

### SetVariableNode

建议属性包括：

- `Key`
- `ValueType`
- `Value`

出口：

- `Out`

---

## 实施步骤

### Phase 1：Blackboard 运行时数据层

目标：建立统一变量容器

工作项：

- 新增 `SkillBlackboard`
- 在 `SkillContext` 中挂入 `Blackboard`
- 提供基础类型读写接口
- 确保 `GameShared` 侧无 Unity 依赖

完成标准：

- 运行时可稳定读写 `bool / int / float / string`

### Phase 2：运行时节点类型扩展

目标：让运行时支持基础逻辑节点

工作项：

- 新增 `RuntimeNodeTypes.Condition`
- 新增 `RuntimeNodeTypes.Branch`
- 新增 `RuntimeNodeTypes.SetVariable`
- 实现对应 handler

完成标准：

- 执行器可识别并执行这些节点
- `NextPort` 可稳定驱动多出口流转

### Phase 3：编辑器节点实现

目标：在图编辑器中可配置这些新节点

工作项：

- 新增 `ConditionNode`
- 新增 `BranchNode`
- 新增 `SetVariableNode`
- 接入 NodeFactory / SearchWindow / SaveLoad

完成标准：

- 节点可创建、保存、加载
- 属性不会在 Save / Load 后丢失

### Phase 4：导出器与校验器升级

目标：让运行时 JSON 合法且稳定

工作项：

- 扩展导出器对白名单节点的支持
- 新增节点属性 schema 校验
- 新增端口合法性校验
- 新增图结构校验
- 新增 `version`

完成标准：

- 非法图在导出时会被明确拦截
- 合法图导出的 JSON 可直接运行

### Phase 5：最小闭环验证

目标：证明图已具备基础逻辑表达能力

推荐验证图：

1. `Entry -> SetVariable(HasTarget=true) -> Condition(HasTarget IsTrue) -> Debug("TruePath")`
2. `Condition.False -> Debug("FalsePath")`

或：

1. `Entry -> SetVariable(State="Ready") -> Branch(State) -> Debug(...)`

完成标准：

- 不同变量值会走不同路径
- 日志顺序与图逻辑一致
- 导出 JSON 可反复执行

---

## 验收标准

以下条件全部满足，即视为 `v0.5` 完成：

1. 图中可创建并保存 `ConditionNode`
2. 图中可创建并保存 `BranchNode`
3. 图中可创建并保存 `SetVariableNode`
4. `SkillContext` 具备统一 `Blackboard`
5. 运行时可根据 Blackboard 数据进行条件判断
6. 运行时可根据不同出口流转到不同节点
7. 导出器可正确导出这些节点
8. 非法节点配置会在导出时被拦截
9. `Entry -> SetVariable -> Condition -> Debug` 链路可稳定运行

---

## 风险与注意点

### 1. 不要把 Blackboard 做成过度设计的通用对象系统

本轮只需要：

- 基础类型
- 明确接口
- 稳定行为

不要过早引入：

- 反射式对象访问
- 任意 UnityEngine.Object 引用
- 复杂嵌套结构

### 2. ConditionNode 不要一开始做成完整表达式语言

本轮不要支持：

- `A && B`
- `A || B`
- 嵌套表达式
- 自定义函数

这些会快速抬高解析复杂度。

### 3. BranchNode 不要一开始做成动态任意端口编辑器

动态端口不是不能做，而是不应该在当前阶段做。

先固定少量端口，优先把：

- 节点模型
- 导出契约
- 执行语义

做扎实。

### 4. 图系统与业务系统边界要保持清晰

`v0.5` 的目标是：

- 让图能表达逻辑

不是：

- 让图开始直接承载复杂战斗规则

只要边界不乱，后续集成任何业务系统都会更容易。

---

## 后续版本顺序建议

## v0.6：执行状态与中断语义

在 `v0.5` 具备基本逻辑能力后，下一步建议处理执行语义问题。

核心目标：

- 把当前偏简单的执行结果模型升级为更明确的运行时状态模型

建议内容：

- 引入 `Running / Success / Failure / Cancelled`
- 明确节点中断语义
- 明确取消传播规则
- 统一异步节点完成时机
- 增强循环与步数保护

这一版解决的是“图怎么更稳地执行”。

## v0.7：导出版本化、静态校验、执行 Trace

当图能力和执行语义都基本稳定后，应开始加强工程化能力。

核心目标：

- 让图可诊断、可校验、可演进

建议内容：

- 完整版本化导出格式
- 更系统的 schema 校验
- 死路 / 孤立节点 / 非法端口检测
- 运行时执行 Trace
- 节点执行日志与路径记录

这一版解决的是“图怎么更可维护、更可调试”。

## v0.8：面向同步与回放的确定性约束

当前阶段先不要直接做网络同步实现，但可以在图系统层面提前建立约束。

核心目标：

- 让图执行模型具备未来接入同步系统的基础条件

建议内容：

- 区分确定性节点与非确定性节点
- 规范随机数来源
- 规范时间来源
- 规范事件记录点
- 为回放 / 校验预留执行事件流

这一版解决的是“图怎么成为网络同步和回放系统的可靠底座”。

## 长线方向

在 `v0.8` 之后，再自然进入：

- 图调试器
- 子图 / 复用模板
- 更完整的类型系统
- 面向业务系统的节点扩展

到那个阶段，节点图系统才适合承接更复杂的战斗和网络业务逻辑。

---

## 一句话结论

`v0.5` 的正确方向不是继续堆业务节点，而是：

**先把 Blackboard、Condition、Branch、多出口执行和导出校验补齐，让节点图系统真正具备表达逻辑的基础能力。**
