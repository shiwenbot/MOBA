# 技能节点编辑器 v0.6 开发计划

## Context

当前 `v0.5` 已经让技能图从“只能顺序串起来跑”的形态，升级成了“能表达基础逻辑”的形态：

- 编辑器可以创建并保存 `ConditionNode`
- 编辑器可以创建并保存 `BranchNode`
- 编辑器可以创建并保存 `SetVariableNode`
- `SkillContext` 已经有统一 `Blackboard`
- 导出器能够把这些逻辑节点导出为运行时 JSON
- 运行时已经能根据 Blackboard 进行条件判断和分支流转

这意味着当前系统已经具备三层基础闭环：

- 图编辑
- 图导出
- 图执行

但 `v0.5` 解决的重点仍然是“图能表达逻辑”，还没有真正解决“图怎么稳定执行”。

从当前运行时实现看，仍然存在几个明显短板：

- 执行结果模型仍然过于简单，基本只有 `Completed + NextPort`
- 节点完成、失败、取消之间的语义还没有清晰分层
- 异步节点的结束时机没有统一约定
- 取消逻辑分散在 `SkillContext.IsCancelled` 和 `CancellationToken` 两处
- 循环保护只有简单步数上限，仍属于 MVP 级防护

因此，`v0.6` 不应该继续优先扩充业务节点，而应该回到执行器本身，补齐运行时语义。

---

## 版本目标

`v0.6` 的核心目标定义为：

**把当前“能执行”的技能图，升级为“执行语义明确、异步行为一致、可安全中断”的运行时系统。**

一句话说：

**让图不仅能跑，而且能清楚地定义正在执行、成功结束、失败结束、取消结束。**

本版本完成后，技能图运行时应具备以下能力：

1. 节点执行结果具有明确状态语义
2. Runner 对成功、失败、取消有统一处理规则
3. 异步节点的完成与中断行为一致
4. 取消可以沿执行链路传播
5. 循环与异常执行路径有更明确的防护

---

## 为什么先做这个版本

### 1. 当前主矛盾已经不是“图不会表达逻辑”

`v0.5` 已经补上了：

- Blackboard
- 条件判断
- 分支流转

也就是说，图语言能力已经从“线性”进入“基础逻辑”阶段。

这时再继续加更多业务节点，收益会迅速下降，因为执行内核本身还不够稳定。

### 2. 没有执行语义，后续异步节点会快速失控

当前只有少量节点时，`Completed / Continue` 还能勉强支撑。

但一旦继续增加：

- 播放表现
- 等待事件
- 等待动画完成
- 等待网络响应
- 持续施法
- 可中断行为

就一定会遇到：

- 节点什么时候算结束
- 被打断时返回什么
- 取消后后继节点是否还应继续
- 失败与取消是否需要区分

如果不在 `v0.6` 先把这套语义定下来，后面每新增一个异步节点都要各写一套规则。

### 3. 执行状态模型是后续工程化能力的前提

后面如果要做：

- 执行 Trace
- 路径回放
- 运行时日志
- 静态校验增强
- 网络同步约束

都必须先回答一个基础问题：

**每个节点执行后，到底产生了什么状态。**

所以 `v0.6` 本质上是在给 `v0.7+` 铺底，而不是孤立的小修补。

---

## 本轮范围

### 本轮要做

- 升级 `SkillExecuteResult` 为明确状态模型
- 明确 `SkillGraphRunner` 的状态流转规则
- 明确节点取消与中断语义
- 统一异步节点的完成时机
- 增强循环与步数保护
- 补充必要的运行时测试样例

### 本轮不做

- 新增大量业务节点
- 图编辑器交互增强
- 执行 Trace 可视化
- 完整导出 schema 版本治理
- 静态死路 / 孤立节点全量分析
- 并行执行
- 子图 / 嵌套图
- 网络同步与回放实现

### 本轮只解决一件事

**让技能图从“逻辑能表达”升级为“运行时语义清晰且稳定”。**

---

## 核心方案

## 一、把执行结果升级为状态模型

当前执行结果更像一个“下一步跳哪”的轻量返回值，而不是完整的运行时状态。

`v0.6` 应把它升级为显式状态模型，例如：

- `Running`
- `Success`
- `Failure`
- `Cancelled`

同时保留用于流转的附加信息，例如：

- `NextPort`
- `Message` 或错误说明
- 是否允许继续推进

### 建议的最小设计原则

1. `Success`
表示当前节点完成，且执行器可以根据 `NextPort` 继续流转。

2. `Failure`
表示当前节点执行失败，图应终止，且该结果要与取消区分开。

3. `Cancelled`
表示执行是被外部取消或中断，不应被当作普通失败。

4. `Running`
表示节点进入挂起中的执行态，供后续更复杂的调度模型演进。

本轮不一定要求完整实现“挂起后恢复”，但结果模型里应预留这个正式状态。

### 为什么这一步最重要

因为只要结果模型仍停留在：

- 完成
- 未完成

那所有复杂行为最终都会被压扁成模糊语义，后续只能靠约定和特判继续堆。

---

## 二、明确 Runner 的状态流转规则

`SkillGraphRunner` 需要从“顺着线跑到结束”升级成“按状态驱动的执行器”。

建议明确以下规则：

### 1. 节点返回 `Success`

- 读取 `NextPort`
- 查找该端口的唯一后继连接
- 若存在唯一后继，则进入下一个节点
- 若不存在后继，则视为图正常结束

### 2. 节点返回 `Failure`

- 立即停止执行
- 向调用方返回失败结果
- 不继续查找后继节点

### 3. 节点返回 `Cancelled`

- 立即停止执行
- 标记整张图进入取消结束状态
- 不应继续流转到后继节点

### 4. 节点返回 `Running`

- 当前节点被视为仍在执行中
- Runner 不应错误地重复推进到后继节点
- 为未来“挂起恢复”预留正式语义入口

### 5. 图整体结果也应显式可见

建议 `Run` 不再只是“执行完就返回”，而是返回图级别结果，例如：

- 图成功结束
- 图失败结束
- 图取消结束

这样调用方才能在更高层统一处理技能执行结果。

---

## 三、明确节点中断语义

`v0.6` 需要规定哪些节点是天然可中断的，哪些节点是同步一步完成的。

建议先按两类划分：

### 1. 同步节点

例如：

- `Entry`
- `Debug`
- `SetVariable`
- `Condition`
- `Branch`

这类节点原则上：

- 不持有长期运行状态
- 一次执行立即返回结果
- 不需要额外中断流程

### 2. 异步节点

例如：

- `Delay`
- `Action`
- 后续的 Wait 类节点

这类节点必须明确：

- 开始执行的时刻
- 完成执行的时刻
- 收到取消时的行为
- 取消后返回 `Cancelled` 还是 `Failure`

### 中断语义建议

本轮统一约定：

- 外部主动停止执行，返回 `Cancelled`
- 节点内部执行出错，返回 `Failure`
- 正常完成后继续流转，返回 `Success`

不要再让“取消”通过写 `IsCancelled = true` 再 `Complete()` 的方式隐式表达。

---

## 四、统一取消传播规则

当前取消能力已经存在，但语义还不统一。

`v0.6` 建议把取消传播规则明确为：

1. 调用方触发取消
2. `SkillContext` 感知到取消状态
3. 当前异步节点尽快结束等待
4. 节点返回 `Cancelled`
5. Runner 终止整张图执行
6. 图级结果对外表现为 `Cancelled`

### 需要统一的点

- `IsCancelled` 是否仍保留
- `CancellationToken` 是否作为唯一取消来源
- 节点是否允许自行把运行时状态改成取消
- 取消后是否允许补做清理

### 建议方向

本轮优先收敛为：

- 外部取消来源统一
- 节点只消费取消状态，不随意发明新语义
- Runner 负责把节点取消提升为图级取消

这样职责更清晰：

- Context 提供状态
- Node Handler 响应状态
- Runner 解释状态

---

## 五、统一异步节点完成时机

如果没有统一规则，异步节点将成为后续维护成本最高的部分。

### DelayNode 的建议语义

- 开始等待时进入异步执行
- 等待自然结束，返回 `Success("Out")`
- 等待期间被取消，返回 `Cancelled`

### ActionNode 的建议语义

以当前 `PlayAnimation` 为例，需要明确：

- “开始播放动画”就算完成
- 还是“动画真正播放完”才算完成

`v0.6` 必须选定一种统一规则，而不是依赖每个节点各自决定。

建议本轮优先采用：

**节点对外暴露的完成时机，应与该节点语义真正结束的时刻一致。**

也就是说：

- 如果节点语义是“等待动画播放完成”，那完成应发生在播放结束时
- 如果节点语义只是“触发播放请求”，那应拆成另一种明确语义的节点

### 本轮目标

不是把所有异步节点都做复杂，而是先把“完成时机”这个原则钉死。

---

## 六、增强循环与步数保护

当前步数保护仍然是简单上限，属于必要但不充分的防御。

`v0.6` 至少要把这层能力正式化。

建议增强点：

- 把步数上限从临时经验值变成显式配置或明确常量
- 错误文案与当前版本保持一致
- 区分“正常重复执行”和“疑似死循环”
- 为未来循环节点保留更明确的保护接口

### 最小目标

即使本轮不实现复杂循环节点，也要保证：

- 配置错误导致的回路不会无限执行
- 错误能被稳定暴露
- 调试时能快速判断是哪个阶段触发保护

---

## 七、建议的最小实现顺序

为了降低重构风险，建议实现顺序如下：

1. 重构 `SkillExecuteResult`
2. 重构 `SkillGraphRunner.Run` 的返回结果
3. 统一同步节点返回 `Success`
4. 统一异步节点返回 `Success / Cancelled / Failure`
5. 收敛取消传播逻辑
6. 更新步数保护与报错信息
7. 补充最小测试样例

这个顺序的好处是：

- 先改数据契约
- 再改调度主干
- 最后逐个收敛节点行为

可以避免边改节点边猜 Runner 语义。

---

## 本轮建议验证样例

### 样例 1：同步直线链路

`Entry -> SetVariable -> Debug`

验证目标：

- 所有同步节点返回 `Success`
- 图能够正常结束

### 样例 2：条件分支链路

`Entry -> SetVariable -> Condition -> Debug(True/False)`

验证目标：

- 条件节点根据 Blackboard 正确选择出口
- 分支命中后图正常结束

### 样例 3：Delay 正常完成

`Entry -> Delay -> Debug`

验证目标：

- `Delay` 完成后返回 `Success`
- 后继节点继续执行

### 样例 4：Delay 被取消

`Entry -> Delay -> Debug`

验证目标：

- 等待期间触发取消
- `Debug` 不会继续执行
- 图级结果为 `Cancelled`

### 样例 5：Action 执行失败

`Entry -> Action`

验证目标：

- 当资源配置非法或执行失败时
- 节点返回 `Failure`
- 图终止且错误可见

### 样例 6：错误回路保护

构造一个简单循环图：

`Entry -> A -> B -> A`

验证目标：

- 执行不会无限循环
- 能稳定触发保护
- 错误信息可定位问题

---

## 验收标准

以下条件全部满足，即视为 `v0.6` 完成：

1. `SkillExecuteResult` 具备明确状态语义，而不再只有 `Completed + NextPort`
2. `SkillGraphRunner` 能区分 `Success / Failure / Cancelled`
3. 图执行的最终结果可以被调用方显式感知
4. `DelayNode` 在正常完成与取消时返回不同结果
5. `ActionNode` 的完成时机有明确且一致的定义
6. 取消后不会继续推进到后继节点
7. 节点内部异常不会被当作取消处理
8. 循环或异常回路能被稳定拦截
9. 至少覆盖一条同步链路、一条分支链路、一条异步取消链路

---

## 风险与注意点

### 1. 不要把 `Running` 提前做成完整协程框架

本轮的目标是先把状态语义定义清楚，而不是直接实现复杂调度器。

`Running` 可以先作为正式状态存在，但不应在 `v0.6` 顺手演变成一整套恢复系统。

### 2. 不要把取消和失败混在一起

取消是控制流语义，失败是错误语义。

如果两者混在一起：

- 调试会很痛苦
- 上层系统无法正确响应
- 后续同步与回放会缺少稳定边界

### 3. 不要在本轮继续扩张节点数量

`v0.6` 的核心价值来自执行器内核，而不是节点清单变长。

如果边修语义边加新节点，版本目标会被稀释。

### 4. 不要让每个异步节点各自定义完成规则

本轮必须统一原则，否则后面每多一个异步节点，执行语义都会再分叉一次。

---

## 后续版本顺序建议

## v0.7：导出版本化、静态校验、执行 Trace

当执行状态模型基本稳定后，应开始加强工程化能力。

核心目标：

- 让图可诊断、可校验、可演进

建议内容：

- 完整版本化导出格式
- 更系统的 schema 校验
- 死路 / 孤立节点 / 非法端口检测
- 运行时执行 Trace
- 节点执行日志与路径记录

这一版解决的是“图怎么更可维护、更可调试”。

## v0.8：面向同步与回放的确定性约束

当执行状态和工程化基础都稳定后，再考虑同步与回放约束。

核心目标：

- 让图具备更强的确定性边界

建议内容：

- 限制不确定输入来源
- 明确可同步状态与不可同步状态
- 约束时间与随机数来源
- 为回放与重演建立一致执行前提

这一版解决的是“图怎么更适合联网与回放场景”。
