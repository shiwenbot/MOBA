# 状态帧同步-阶段总目录

## Context

状态帧同步系统需要按多个 Session 分阶段推进，不在一个版本里一次性完成。本文档作为总目录，只定义阶段目标、阶段边界和每个阶段对应的计划文档。

> 版本线说明：`状态帧同步 v0.x` 与 `技能节点编辑器 v0.x` 为两条独立版本线。  
> 其中技能节点编辑器 `v0.8-A` 的 Step / Snapshot 内核产物，是状态帧同步 `v0.5b` 的前置依赖之一。

### 已锁定的技术决策

1. **确定性物理**：使用 Box2D / Box2DSharp 路线。
2. **网络框架**：Fantasy。
3. **异步模型**：FTask。
4. **网络消息序列化**：Fantasy 自带序列化 / Protobuf，Luban 仅用于配置表。
5. **逻辑帧率**：30Hz，固定 `dt = 33.333ms`。
6. **追帧不改仿真 dt**：追帧只改变单个渲染帧内执行多少次 Tick，不改变每次 Tick 的固定步长。

### 设计原则

1. **确定性验证贯穿始终**：每个阶段都要有确定性相关验收点。
2. **阶段聚焦**：每个子阶段只解决 1 个核心问题。
3. **日志与自动测试优先**：先保证可验证，再做更大规模功能推进。
4. **实验记录与主线决策解耦**：历史方案保留归档，但主线始终以最新架构决策为准。

### 当前主线架构（2026-05-17 更新）

详见 [状态帧同步-架构重构计划.md](/D:/unity/Tencent/TEngine/Plan/状态帧同步/状态帧同步-架构重构计划.md:1)。

- `FrameIndex` 的唯一语义是全局逻辑帧号。
- 服务端固定 30Hz 权威推进，缺帧时复用上一帧输入。
- 客户端 `leadFrames` 表示预测领先量，而非帧号偏移。
- 客户端预测、权威校正、回滚重播共享同一帧坐标系。
- 当前 `v0.4a` 已明确采用 **MOBA 式“有卡位、无普通移动真实互推”** 的移动语义。
- 当前自动测试、双端联调与手动体验验证均已通过。

## 阶段推进规则

1. 每个阶段文档必须包含：目标、范围、非目标、实现步骤、验证方式、完成标准。
2. 当前阶段完成标准全部满足后，才能进入下一阶段。
3. 阶段结束时同步更新本总目录中的状态标记。
4. 任何新增需求优先归类到现有阶段；若影响主路径，再新增子阶段文档。
5. **确定性验证是每个阶段的必修项**，不能跳过。
