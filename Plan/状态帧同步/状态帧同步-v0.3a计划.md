# 状态帧同步-v0.3a计划：状态快照/恢复机制

## Context

v0.2b 已完成 Ping/Pong RTT 测量、超前帧控制与追帧机制，`leadFrames` 稳定收敛，`RejectRate=0%`。

当前客户端没有本地仿真状态：`BattleClientController` 收到服务端 `S2C_FrameSnapshot` 后直接将位置写入 Unity GameObject，没有任何本地 `PlayerState` 对象。这意味着：

- 无法在本地预测执行输入（v0.3b 需要）
- 无法在检测到不一致时回退到历史状态（v0.3c 需要）
- 无法计算全局状态哈希用于一致性比对

v0.3a 的任务是补全这一基础设施：引入本地仿真状态容器 `BattleWorldState`，定义快照接口，实现滑动窗口存储，并实现全局状态哈希。

前置依赖：
- v0.2b（已完成）：`TickDispatcher.TickOnce()`、`ClientTickDriver.SetTargetFrame()`、`leadFrames` 基础设施

## 目标

- 定义 `ISnapshotable<TSnapshot>` 接口，规范快照/恢复契约。
- 引入 `BattleWorldState`，持有所有玩家的本地 `PlayerState`，实现 `ISnapshotable`。
- 实现 `SnapshotBuffer<T>`：固定容量滑动窗口，按帧号存取快照，超容量自动淘汰最旧帧。
- 实现 `StateHasher`：对 `BattleWorldState` 计算确定性全局哈希（`ulong`）。
- 实现 `SnapshotManager`：作为 `ITickable` 注册到 `TickDispatcher`，每帧末尾自动存快照。
- 验收：快照往返测试（Save → Modify → Restore → Hash 一致），内存无泄漏。

## 技术决策

### 1. ISnapshotable 接口

泛型接口，类型安全，避免装箱：

```
interface ISnapshotable<TSnapshot>
    TakeSnapshot() → TSnapshot
    RestoreSnapshot(TSnapshot snapshot)
```

`TSnapshot` 为不可变值对象（struct 或 sealed class with readonly fields），快照后不应被外部修改。

### 2. BattleWorldState 与 BattleWorldSnapshot

`BattleWorldState` 是客户端本地仿真状态的唯一容器：
- 持有 `Dictionary<long, PlayerState>`（PlayerId → PlayerState）
- 提供 `AddPlayer` / `RemovePlayer` / `TryGetPlayer` API
- 实现 `ISnapshotable<BattleWorldSnapshot>`

`BattleWorldSnapshot` 结构：
- `FrameIndex`（uint）：对应的帧号
- `Players`（`IReadOnlyList<PlayerStateSnapshot>`）：所有玩家快照，按 PlayerId 升序排列（确定性）
- `PhysicsSnapshot`（object，nullable）：Box2D 物理状态扩展槽，v0.3a 始终为 null，v0.4a 填充

`PlayerStateSnapshot` 为 readonly struct：`PlayerId`、`X`、`Y`。

### 3. SnapshotBuffer<T>

固定容量循环淘汰：
- 容量：可配置，默认 `MaxLeadFrames(8) + MaxCatchUpTicksPerFrame(8) + 冗余(4) = 20`，向上取整为 `SnapshotBufferCapacity = 24`
- 内部：`Dictionary<uint, T>` 存快照 + `Queue<uint>` 记录插入顺序
- `Save(frameIndex, snapshot)`：
  - 若 `frameIndex` 已存在 → **覆盖**（幂等，不重复入队）
  - 若已满且 `frameIndex` 不存在 → 先出队最旧帧并从 dict 删除，再插入
- `TryGet(frameIndex, out T snapshot)`：按帧号查找
- `Clear()`：清空所有

不使用数组循环缓冲，原因：帧号不连续（追帧时可能跳帧），dict 查找更安全。

### 4. StateHasher

确定性哈希要求：
- 使用 `BitConverter.SingleToInt32Bits(float)` 取位模式，不依赖 `float.GetHashCode()`
- **归一化规则**：写入哈希前，将 `-0f` 替换为 `+0f`（`bits == unchecked((int)0x80000000)` 时置零），`NaN` 统一替换为 `0`（`float.IsNaN(v)` 时置零）
- 计算流程：
  1. `BattleWorldSnapshot.Players` 已按 PlayerId 升序排列（TakeSnapshot 时保证）
  2. 对每个玩家：将 `PlayerId`（long，拆成两个 int）、归一化后的 `X` 位模式、`Y` 位模式依次混入 FNV-1a
  3. 返回 `ulong` 哈希值

### 5. SnapshotManager（ITickable）

- Priority = `int.MaxValue`（与 `FrameTimerService` 相同）
- 在 `ClientTickDriver.EnsureInitialized()` 中，`FrameTimerService` 注册之后再注册 `SnapshotManager`，利用 `TickDispatcher` 同优先级按注册顺序的 tie-breaking，确保 `SnapshotManager` 在 `FrameTimerService` 之后执行（即帧末）
- `Tick(frameIndex, fixedDt)`：先应用待处理的服务端快照队列（见下），再调用 `_worldState.TakeSnapshot()` 存入 buffer，更新 `LatestHash`
- 实现 `ITickable.RollBack(uint targetFrame)`：调用 `TryGetSnapshot(targetFrame)` 并 `RestoreSnapshot()`，为 v0.3c 预留
- 实现 `ITickable.CheckConsistency(uint frameIndex)`：取当前哈希与外部传入哈希比对，为 v0.3b 预留
- 暴露 `TryGetSnapshot(frameIndex, out BattleWorldSnapshot)` 供 v0.3b 使用
- 暴露 `LatestHash` 属性（每帧更新，供日志输出）

### 6. BattleClientController 修改（入队模型）

**网络回调不直接写状态**，改为入队：
- `OnSnapshotMessage()` 将收到的 `S2C_FrameSnapshot` 放入 `_pendingServerSnapshot`（单槽，新快照覆盖旧快照，因为只需要最新权威状态）
- `Tick()` 中检查 `_pendingServerSnapshot`，若非空则取出，应用到 `_tickDriver.WorldState`（AddPlayer/更新X/Y/RemovePlayer），同时更新 GameObject 位置，然后清空槽位

这样所有状态写入都发生在 Tick 阶段，快照边界清晰，不存在网络回调与 Tick 的时序竞争。

`BattleWorldState` 的引用由 `ClientTickDriver` 持有并暴露，`BattleClientController` 通过 `_tickDriver.WorldState` 访问。

### 7. 验收日志

每 300 帧（约 10 秒）输出一次：
- `[Snapshot]`：当前帧号、`LatestHash`、buffer 中快照数量
- `[SnapshotTest]`：启动时执行一次往返测试（Save → Modify → Restore → Hash 比对），输出 PASS/FAIL

## 实现步骤

### Step 0：定义状态写入所有权约束

在动手写代码前，先在计划中明确：
- **唯一写入口**：`BattleWorldState` 只在 `SnapshotManager.Tick()` 内被修改（通过消费 `_pendingServerSnapshot` 队列）
- **网络回调只入队**：`OnSnapshotMessage` 只写 `_pendingServerSnapshot`，不直接访问 `BattleWorldState`
- **渲染单向同步**：GameObject 位置由 `BattleWorldState` 驱动，不反向写入

### Step 1：定义快照接口与数据类

新建 `ISnapshotable.cs`、`PlayerStateSnapshot.cs`、`BattleWorldSnapshot.cs`。

`BattleWorldSnapshot` 的 `PhysicsSnapshot` 字段类型为 `object`（nullable），v0.3a 始终传 null，v0.4a 替换为具体 Box2D 快照类型。

### Step 2：实现 BattleWorldState

新建 `BattleWorldState.cs`，持有 `Dictionary<long, PlayerState>`，实现 `ISnapshotable<BattleWorldSnapshot>`。

`TakeSnapshot()`：遍历所有玩家，构造 `PlayerStateSnapshot` 列表（按 PlayerId 升序排序），返回 `BattleWorldSnapshot`。

`RestoreSnapshot(snapshot)`：清空当前 dict，按快照重建所有 `PlayerState`。

### Step 3：实现 SnapshotBuffer<T> 与 StateHasher

新建 `SnapshotBuffer.cs`（泛型，容量 16）和 `StateHasher.cs`（FNV-1a，输入 `BattleWorldSnapshot`）。

### Step 4：实现 SnapshotManager

新建 `SnapshotManager.cs`，实现 `ITickable`（Priority = `int.MaxValue - 1`）。

构造函数接收 `BattleWorldState` 和 `SnapshotBuffer<BattleWorldSnapshot>`。

`Tick()` 末尾：取快照 → 存 buffer → 更新 `LatestHash`。

### Step 5：修改 ClientTickDriver

新增 `BattleWorldState WorldState` 属性（只读）。

在 `EnsureInitialized()` 中：
1. 创建 `BattleWorldState`
2. 创建 `SnapshotBuffer<BattleWorldSnapshot>`（容量 24）
3. 注册 `_timerService`（Priority = `int.MaxValue`）
4. 创建 `SnapshotManager`（Priority = `int.MaxValue`），在 `_timerService` 之后注册，利用注册顺序 tie-breaking 确保最后执行

暴露 `SnapshotManager SnapshotManager` 属性供外部访问。

### Step 6：修改 BattleClientController（入队模型）

`OnSnapshotMessage()` 只将 `S2C_FrameSnapshot` 写入 `_pendingServerSnapshot`（单槽覆盖）。

`Tick()` 中：检查 `_pendingServerSnapshot` 是否非空 → 取出 → 应用到 `_tickDriver.WorldState` → 更新 GameObject 位置 → 清空槽位。

### Step 7：往返测试验收

在 `SnapshotManager` 初始化后，执行覆盖以下路径的测试（运行时日志输出，不依赖测试框架）：

1. **基础往返**：添加 2 个玩家 → TakeSnapshot A → 修改 X/Y → RestoreSnapshot A → TakeSnapshot B → 断言 `Hash(A) == Hash(B)`
2. **容量淘汰**：连续 Save 25 帧（超过容量 24）→ 断言第 1 帧已被淘汰，第 2 帧仍可 TryGet
3. **同帧覆盖**：Save 帧 10 两次（不同内容）→ 断言 buffer 中帧 10 只有 1 条，Queue 无重复
4. **哈希归一化**：构造含 `-0f` 和 `NaN` 的快照 → 断言哈希与对应 `+0f`/`0f` 版本相同

全部通过输出 `[SnapshotTest] ALL PASS`，任一失败输出 `[SnapshotTest] FAIL: <case>`。

## 确定性约束

- `TakeSnapshot()` 中玩家列表必须按 PlayerId 升序排列，保证哈希确定性。
- `StateHasher` 使用 `BitConverter.SingleToInt32Bits` 取位模式，并对 `-0f`/`NaN` 归一化，避免跨端哈希不一致。
- `RestoreSnapshot()` 完全重建状态，不做增量 patch，避免残留脏数据。
- `SnapshotManager.Tick()` 在 `FrameTimerService.Tick()` 之后执行（同 Priority，注册顺序靠后），确保快照是帧末完整状态。
- 所有 `BattleWorldState` 写入只发生在 `SnapshotManager.Tick()` 内，网络回调只入队，不直接写状态。

## 关键风险与应对

| 风险 | 影响 | 应对 |
|------|------|------|
| `SnapshotManager` 在 `FrameTimerService` 之前执行 | 快照是帧中间状态，哈希不稳定 | 同 Priority = `int.MaxValue`，在 `FrameTimerService` 之后注册，利用注册顺序 tie-breaking |
| 网络回调直接写 `BattleWorldState` | 时序不确定，快照边界不清 | 入队模型：回调只写 `_pendingServerSnapshot`，Tick 中统一消费 |
| `float` 哈希跨平台不一致（`-0f`/`NaN`） | 双端哈希不匹配，误报不一致 | `BitConverter.SingleToInt32Bits` + 归一化规则 |
| `SnapshotBuffer` 同帧重复 Save 导致 Queue 重复帧号 | 淘汰逻辑错删有效快照 | Save 时检查 dict，已存在则覆盖不入队 |
| `RestoreSnapshot` 后 `PlayerState` 引用失效 | v0.3b 预测时访问旧引用 | `RestoreSnapshot` 重建 dict，外部不缓存 `PlayerState` 引用 |
| `BattleWorldSnapshot.PhysicsSnapshot` 长期为 `object` | v0.4a 集成时需要强转，可变引用污染 | v0.4a 时替换为具体 Box2D 快照接口，届时修改 `BattleWorldSnapshot` |
