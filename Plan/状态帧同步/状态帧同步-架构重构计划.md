# 状态帧同步-架构重构计划

- 创建日期: `2026-05-06`
- 当前状态: `已评审；测试 MVP 当前未执行（按需求方要求跳过），允许直接进入 v0.3b 实施`
- 适用范围: 客户端 `BattleSimulation` / `BattleClientController` / `ClientTickDriver`，服务端 `BattleLogic` / `BattleComponent`，协议 `C2B_PlayerInput`

## Context

当前主线实现基于“客户端预测服务端帧号 + 服务端窗口校验”模型：

- 客户端通过 `_serverFrameOffset` 将本地帧映射到“预测服务端帧”
- 客户端用 `ToPredictedServerFrame()` 发送 `C2B_PlayerInput.FrameIndex`
- 服务端用 `LastFrameIndex` 和 `MaxFrameWindow` 做窗口拒绝
- 客户端再通过 `leadFrames`、追帧、RTT EMA 去维持这套映射

这套设计已经带来两个结构性问题：

1. 客户端和服务端的 `FrameIndex` 不在同一坐标系，协议语义不稳定。
2. `FrameIndex`、`InputSeq`、`_serverFrameOffset`、`MaxFrameWindow`、追帧逻辑彼此耦合，后续回滚与容错会越来越复杂。

本次重构的目标不是局部修补，而是把主线模型切换为更适合 MOBA 帧同步的“全局帧号 + 服务端权威推进”。

## 执行策略结论

从当前仓库状态看，主线重构并不是从零开始：

- 服务端 `BattleLogic` 已经具备“未来输入缓冲 + 缺帧复用上一帧输入”的基础形态
- 客户端 `JoinBattle -> ServerFrameIndex -> AlignToFrame` 链路也已有雏形
- `v0.3-test` 已经提供了 `dotnet run -- --mode=test` 的无头测试入口

因此，推荐顺序不是“先做完整独立 CLI，再开始改主线”，而是：

1. 先增强现有 `v0.3-test` 无头入口，形成 agent 可高频调用的测试 MVP
2. 再按本文第一至第四阶段推进主线重构
3. 完整独立 `GameLogicTester` 工具放到主线稳定后再产品化

这样做的好处是：

- agent 后续每次改动都可以直接回归
- `v0.3b` / `v0.3c` 能在无头环境下持续验证
- 避免完整 CLI 工具被主线重构反复推翻

## 核心结论

### 1. `FrameIndex` 统一为全局逻辑帧号

- 游戏开始后，客户端与服务端都使用同一套全局帧号语义：`0, 1, 2, 3...`
- 客户端发送的 `C2B_PlayerInput.FrameIndex` 就是“这份输入属于哪一个全局逻辑帧”
- 服务端广播的 `S2C_FrameSnapshot.FrameIndex` 也是同一语义
- 不再允许“本地帧 A 映射到预测服务端帧 B”的主线机制存在

### 2. 服务端固定 30Hz 权威推进

- 服务端继续按固定 `33.333ms` 推进
- 推进到 `Frame N` 时，读取每个玩家 `Frame N` 的输入
- 若该帧输入缺失，则使用该玩家上一帧已消费的输入兜底
- 服务端不等待单个玩家，不因缺帧暂停整局推进

### 3. 客户端的“领先量”改为执行进度领先，而不是帧号偏移

- `leadFrames` 保留，但语义改为：客户端本地预测执行相对服务端权威帧的目标领先量
- 公式保留 RTT 思路，但不再驱动 `_serverFrameOffset`
- 推荐口径：

```text
targetLeadFrames = jitterBufferFrames + ceil(rttEmaMs / 2 / fixedDtMs)
```

- `targetLeadFrames` 用于决定客户端应该预测到哪一帧，以及在收到快照后要不要追帧

### 4. RTT / Ping / EMA 保留，但用途收缩

- `C2B_Ping` / `S2C_Pong` 保留
- RTT EMA 保留
- `TickOnce()` / `MaxCatchUpTicksPerFrame` 保留
- 这些机制继续用于“本地预测窗口”和“追帧目标”控制
- 不再用于维护“预测服务端帧号”的偏移映射

### 5. `InputSeq` 不再作为主线帧语义的一部分

- 在全局帧号模型下，`FrameIndex` 本身就是天然序号
- `InputSeq` 可以暂时保留在协议里，用于同帧覆盖、调试观测或未来重传
- 但服务端核心逻辑不应再依赖“帧号不连续，所以必须靠 `InputSeq` 保序”这个前提

### 6. “时间膨胀”不作为第一阶段默认实现

原讨论中“单帧丢包后客户端加速 Tick，从而自然增大服务端缓冲区”的思路有启发性，但第一阶段不直接落地，原因是：

- 它会同时放大客户端预测领先量和回滚跨度
- 单次丢包不等于持续性缓冲不足
- 若没有 `bufferDepth` 指标约束，容易把恢复机制做成新的抖动源

当前建议：

- 第一阶段先完成全局帧号、输入缓冲、缺帧兜底、追帧对齐
- 后续若要做速率控制，必须以“服务端观察到的持续性缓冲深度不足”为触发条件，而不是“任意一次缺帧”

## 主线设计

### 服务端输入模型

服务端为每个玩家维护“未来输入缓冲”和“上一帧已消费输入”：

- `frameIndex <= LastFrameIndex`：视为过期输入，直接丢弃
- `frameIndex > LastFrameIndex + MaxFutureInputFrames`：视为过远未来输入，拒绝或裁剪
- `LastFrameIndex < frameIndex <= LastFrameIndex + MaxFutureInputFrames`：写入缓冲
- 服务端推进到 `Frame N` 时：
  - 有 `Frame N` 输入：消费该输入，并更新“上一帧已消费输入”
  - 没有 `Frame N` 输入：重复使用“上一帧已消费输入”

这会取代当前的 `MaxFrameWindow + HardReject` 主模型。

### 客户端执行模型

客户端保留本地预测和追帧，但执行目标改为：

- 本地当前逻辑帧本身就是全局帧号
- 客户端收到权威快照 `Frame S` 后，目标本地帧应为 `S + targetLeadFrames`
- 若当前本地帧落后于该目标，则通过 `TickOnce()` 追到目标附近
- 本地预测、输入历史、回滚重播都直接按全局帧号索引

### 客户端初始化与对齐

为真正实现“同一坐标系”，客户端加入战斗后需要对齐本地逻辑帧：

- `JoinBattle` 返回 `ServerFrameIndex`
- 客户端应把本地逻辑当前帧对齐到 `ServerFrameIndex + initialLeadFrames`
- 不再通过 `_serverFrameOffset = serverFrame - localFrame` 这类偏移来曲线救国

这意味着后续实现大概率需要给 `TickDispatcher` / `ClientTickDriver` 增加显式的帧对齐入口。

## 实施分阶段建议

### 前置阶段（推荐先做）：测试护栏收敛

- 复用现有 [状态帧同步-v0.3-test计划.md](/D:/unity/Tencent/TEngine/Plan/状态帧同步/状态帧同步-v0.3-test计划.md:1) 的 `--mode=test` 作为主回归入口
- 将 `FrameSyncMvpAValidator` 的静态规则与当前 `FrameSync` 实现收敛，避免历史规则误伤主线
- 为全局帧号改造提前补齐 `join-aligns-global-frame`、`frame-index-is-global`、`catchup-target-is-auth-plus-lead` 等自测
- 此阶段**不要求**先落地完整独立 `GameServer/Tools/GameLogicTester/`

### 第一阶段：语义切换

- 将 `FrameIndex` 语义正式切为全局逻辑帧号
- 移除客户端 `_serverFrameOffset`、`ToPredictedServerFrame()`、`GetSendFrame()` 主路径
- 客户端加入时显式对齐本地逻辑帧
- 服务端废弃 `MaxFrameWindow` 主校验链路

### 第二阶段：服务端输入缓冲与缺帧兜底

- 引入 `MaxFutureInputFrames`
- 为每个玩家维护上一帧已消费输入
- 缺帧时使用上一帧输入推进，并补充缺帧统计
- 这一步完成后，协议和推进模型就与全局帧号方案一致了

### 第三阶段：客户端预测与回滚对齐

- 客户端预测记录直接以全局帧号为 key
- 一致性检查和回滚重播全部基于全局帧号
- `leadFrames` 只决定预测窗口，不再参与帧号换算

### 第四阶段：缓冲深度反馈与恢复策略

- 引入服务端观测指标：`bufferDepth = maxReceivedFrame - currentServerFrame`
- 只有在持续性 buffer deficit 出现时，才考虑客户端速率控制
- 若未来实现“时间膨胀”，也只允许影响 Tick 触发频率，不允许改仿真 dt
