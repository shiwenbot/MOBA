## 背景：两种方案对比

### 方案 A：客户端预测帧号 + 服务端窗口校验（当前路线）

客户端发送本地 Tick 的 `frameIndex`，服务端校验帧差在 `[-W, +W]` 范围内才接受输入。

- 优点：客户端帧号有语义，是 v0.3b 预测回滚的基础（预测帧 = 本地帧号）。
- 缺点：需要维护窗口逻辑；客户端时钟漂移过大时会触发拒绝。

### 方案 B：服务端分配帧号

客户端只发输入，不带帧号；服务端在当前 Tick 执行时分配帧号。

- 优点：实现最简单，无需校验。
- 缺点：客户端无帧号语义，v0.3b 预测回滚需要额外机制来关联"我预测的是哪一帧"。

### 决策方向

v0.2a 通过日志数据验证方案 A 的可行性。若局域网环境下拒绝率 < 1% 且 `|delta|` P95 在窗口内，则锁定方案 A。

## 技术决策

### 1. 窗口大小

初始值 `MaxFrameWindow = 10`（对应 333ms，约覆盖 150ms RTT 的双向抖动）。

作为常量定义在 `BattleComponent` 中。v0.2a 阶段不对外暴露配置接口，但预留注释说明后续可改为启动参数。

### 2. 帧差计算

```
uint rawDelta = unchecked(input.FrameIndex - LastFrameIndex);
int frameDelta = unchecked((int)rawDelta);
```

先做无符号减法，再 `unchecked` 转有符号，避免大帧号或溢出场景下直接 `(int)a - (int)b` 的边界问题。

**校验基准帧**：使用 `LastFrameIndex`，即服务端 `Tick` 开始时已更新的权威模拟帧。`SubmitInput` 在 Tick 间隙被调用，此时 `LastFrameIndex` 是上一个已完成 Tick 的帧号，语义明确。

- `frameDelta > 0`：客户端帧号超前服务端（正常，客户端时钟略快）。
- `frameDelta < 0`：客户端帧号落后服务端（正常，网络延迟导致）。
- `Math.Abs(frameDelta) > MaxFrameWindow`：超窗，Shadow 模式下记录但不拒绝；硬拒绝模式下丢弃。

### 3. 拒绝后策略

v0.2a 阶段：超窗输入**直接丢弃**，不沿用上一帧输入（即该帧该玩家输入为零向量）。

理由：v0.2a 目标是观测帧差分布，沿用上一帧输入会掩盖拒绝事件对游戏体验的影响，不利于决策。v0.2b 引入输入缓冲后再考虑更优雅的降级策略。

### 4. Shadow 模式 → 硬拒绝两阶段

**Shadow 模式**（Step 1-2）：`SubmitInput` 计算 `wouldReject` 但不真正丢弃输入，只累加统计。跑一轮验收，确认帧差分布后再开启硬拒绝。

**硬拒绝模式**（Step 3）：在 Shadow 模式数据支撑下，开启真正的拒绝逻辑。

这样 Step 4 的验收数据不带"策略干预偏差"，决策更可靠。

### 5. 统计日志内容

每 300 帧（约 10 秒）输出一次，统计后重置计数器：

- 接受数 / 拒绝数（Shadow 模式下为 wouldReject 数）
- **接受样本**：帧差 min / max / avg / P95（`|delta|`）
- **拒绝样本**：帧差 min / max / avg（不能只统计接受样本，否则掩盖真实分布）
- 正超前（`frameDelta > 0`）占比 / 负落后（`frameDelta < 0`）占比
- 连续拒绝最大次数（per player）

P95 用简单排序近似：维护一个固定容量（300）的 `int[]` 环形缓冲，每次统计时排序取第 285 位。

### 6. 客户端 FrameDelta 日志

`OnSnapshotMessage` 中计算：

```
clientFrameDelta = (int)snapshot.FrameIndex - (int)_tickDriver.Dispatcher.CurrentFrame
```

`TickDispatcher.CurrentFrame` 已确认为只读属性，可直接访问。

每 300 次快照输出一次，用于观察客户端视角的帧差趋势。

## 实现步骤

### Step 1：服务端加 Shadow 统计

修改 `BattleComponent.SubmitInput`：

- 用 `unchecked` 方式计算 `frameDelta`。
- 计算 `wouldReject = Math.Abs(frameDelta) > MaxFrameWindow`。
- **不丢弃输入**，正常更新 `_pendingInputsByPlayerId`。
- 累加统计计数器（接受/wouldReject、帧差样本写入环形缓冲）。

### Step 2：服务端加统计日志

在 `BattleComponent` 中维护：
- `_acceptedCount`、`_wouldRejectCount`（int）
- `_acceptDeltaSamples`（int[300] 环形缓冲 + 写指针）
- `_rejectDeltaMin`、`_rejectDeltaMax`、`_rejectDeltaSum`、`_rejectCount`（int）
- `_maxConsecutiveRejectPerPlayer`（Dictionary<long, int> + 当前连续计数）

在 `Tick` 末尾判断 `frameIndex % 300 == 0` 时：
- 对 `_acceptDeltaSamples` 排序，取 P95。
- 输出完整统计日志。
- 重置所有计数器。

### Step 3：开启硬拒绝

Shadow 模式验收通过后，将 `wouldReject` 改为真正拒绝：超窗输入直接 return，不更新 `_pendingInputsByPlayerId`。统计字段名从 `_wouldRejectCount` 改为 `_rejectedCount`。

### Step 4：客户端加 FrameDelta 日志

修改 `BattleClientController.OnSnapshotMessage`：

- 维护 `_snapshotCount`（int）计数器，每次应用快照 +1。
- 每 300 次输出一次 `FrameDelta` 日志（快照帧号 vs 本地 Tick 帧号）。

### Step 5：验收运行

- 启动服务端（端口 20101）。
- ParrelSync 双 Editor 运行，各自连接服务端，持续运行至少 5 分钟（≥ 9000 帧，≥ 30 个统计周期）。
- 观察服务端日志：拒绝率 < 1%，`|delta|` P95 ≤ MaxFrameWindow，连续拒绝 ≤ 3 次。
- 观察客户端日志：`FrameDelta` 稳定，无异常跳变。

### Step 6：写决策文档

新建 `Plan/状态帧同步/帧号策略决策.md`，记录：
- 验收数据（帧差分布、拒绝率、P95、连续拒绝最大值）
- 方案 A vs 方案 B 对比结论
- 锁定方案 A，`MaxFrameWindow = 10`

## 关键风险与应对

| 风险 | 影响 | 应对 |
|------|------|------|
| 局域网帧差 P95 超出 10 帧 | 硬拒绝后拒绝率过高 | Shadow 模式先观测，必要时调大 `MaxFrameWindow` 再开硬拒绝 |
| 统计日志输出过于频繁 | 日志噪音 | 固定 300 帧周期，不在每次 SubmitInput 时输出 |
| 客户端时钟与服务端时钟漂移 | 帧差持续偏移 | v0.2b 的超前帧控制会修正，v0.2a 只观测不修正 |
| 连续拒绝导致操作卡顿 | 体验问题 | Shadow 模式先验证，硬拒绝后若连续拒绝 > 3 次则输出 Warning |
| P95 环形缓冲排序开销 | 每 300 帧一次排序，可忽略 | 固定 300 容量，排序耗时 < 0.1ms |
