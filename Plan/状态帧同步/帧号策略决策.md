# 状态帧同步-v0.2a 帧号策略决策（归档）

- 文档日期: 2026-04-16
- 当前状态: `已归档（旧方案）`
- 决策范围: `BattleComponent.SubmitInput` 帧号窗口校验策略

## 0. 归档说明（2026-05-06）

本文记录的是“客户端预测帧号 + 服务端窗口校验”旧主线的实验结果。

这些数据仍然有参考价值，但从 2026-05-06 起，主线架构已经切换为：

- `FrameIndex` 统一为全局逻辑帧号
- 服务端改为固定 30Hz 权威推进 + 缺帧兜底
- `_serverFrameOffset` / `PredictedServerFrame` / `MaxFrameWindow` 不再作为主线方案继续推进

当前主线请以 [状态帧同步-架构重构计划.md](/D:/unity/Tencent/TEngine/Plan/状态帧同步/状态帧同步-架构重构计划.md:1) 为准。

## 1. 候选方案

- 方案 A: 客户端携带 `FrameIndex`，服务端按 `LastFrameIndex` 做窗口校验（`|delta| <= MaxFrameWindow`）。
- 方案 B: 客户端不带帧号，服务端在执行 Tick 时分配帧号。

## 2. v0.2a 实现口径

- 已实现: 方案 A 的完整链路（Shadow 统计 + HardReject 开关）。
- 当前默认模式: `HardReject`（`BattleComponent.EnableHardReject = true`）。
- 窗口参数: `MaxFrameWindow = 10`。
- 统计周期: 每 `300` 帧输出一次。
- 服务端统计项:
  - `Accepted` / `WouldReject(or Rejected)` / `RejectRate`
  - 接受样本 `|delta|` 的 `min / max / avg / p95`
  - 拒绝样本 `delta` 的 `min / max / avg`
  - `delta > 0` 与 `delta < 0` 占比
  - 每玩家连续拒绝最大值（并在 `> 3` 时告警）
- 客户端统计项:
  - 每 300 次快照输出一次 `FrameDelta = SnapshotFrame - PredictedServerFrame`

## 3. 验收数据

> 建议在局域网双端联调场景持续运行 ≥ 5 分钟（约 9000 帧）

- Shadow 基线验收（局域网，双端联调）:
  - 结论: 通过
  - 服务端:
    - RejectRate: `0%`
    - `|delta|` 范围: `3 ~ 5`
    - `|delta|` P95: `4`
    - MaxConsecutiveReject: `0`
  - 客户端:
    - `PredictedServerFrame` vs `SnapshotFrame` 的 `FrameDelta` 稳定在 `0 ~ 1`
    - 无异常跳变
- HardReject 复验（轻度弱网，clumsy lag 档）:
  - 结论: 通过
  - 服务端:
    - SumAccepted: `12654`
    - SumRejected: `2`
    - RejectRate: `0.0158%`
    - `|delta|` 范围: `6 ~ 10`
    - `|delta|` P95: `8`
    - MaxConsecutiveReject: `2`
    - 仅观察到 1 个拒绝窗口，`RejectDelta = -11`
  - 客户端:
    - 两个客户端 `FrameOffset` 分别稳定在 `354` 与 `158`
    - `PredictedServerFrame` vs `SnapshotFrame` 的 `FrameDelta` 稳定在 `0 ~ 1`
    - 无异常跳变

## 4. 历史结论

- 决策建议:
  - 若 `RejectRate < 1%` 且 `|delta| P95 <= 10`，锁定方案 A。
  - Shadow 验收通过后，将 `EnableHardReject` 改为 `true` 并复验。
- 当前结论: `该结论仅对 2026-04 旧实现有效`
- 锁定参数:
  - `MaxFrameWindow = 10`
  - 客户端输入帧号采用 `PredictedServerFrame = LocalFrame + FrameOffset`
  - 服务端保持 `HardReject` 开启

## 5. 当前主线更新

上述锁定参数不再作为后续实现约束。

新的主线结论是：

- `FrameIndex` 使用全局逻辑帧号
- 服务端接受有限未来窗口内的输入，而不是对称 `±MaxFrameWindow` 校验
- 缺帧时服务端复用上一帧输入推进
- RTT / EMA 保留，但只用于决定客户端目标预测领先量
