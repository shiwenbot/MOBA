定点数全局迁移计划：帧同步系统全面 Fixed64 化

● 未开始 依赖: 定点数库实现计划 (已完成) 后续: 双端帧同步确定性验证
📚 Context

前序阶段「定点数库实现计划」已完成：羽毛球弹道全链路（ShuttlecockPhysics / ShuttlecockEntity / ShuttlecockState / ShuttlecockSnapshot / CourtConstants 等）迁移到 Fixed64 / Vector2d，TickAccumulator 内部使用 Fixed64 累积。

但当前帧同步系统的角色移动链路仍然使用 float：

  1. ITickable.Tick(uint, float)：所有仿真实体的帧驱动接口使用 float fixedDt
  2. PlayerState：玩家位置 float X, Y
  3. FrameSyncPhysicsWorld：封装 Box2D，全链路 System.Numerics.Vector2（float）
  4. MoveSystem：移动输入 float dx, dy, dt
  5. BattleSimulation：客户端预测逻辑全部 float
Key Issue 虽然羽毛球弹道已确定性，但角色移动在跨平台（Windows GameServer vs 多平台 Unity Client）下不保证位级一致。

已锁定的设计决策（来自前序计划和阶段总目录）

  1. 帧率：30Hz 逻辑帧（dt = 33.333ms）
  2. 坐标约定：2D 模型——X/Y 为平面坐标
  3. Box2D 范围：角色移动走 Box2D，羽毛球弹道不走 Box2D（已迁移到 Fixed64）
  4. 确定性工具链：Fixed64.m_rawValue 位比较 + DeterminismRules 约束
  5. 双端共享代码：GameShared/ 源码通过 Entity.csproj 的 <Compile Include> glob 被 GameServer 编译

⚙ 技术决策
TD-1

ITickable 接口 — fixedDt 从 float 改为 Fixed64

将 ITickable.Tick(uint frameIndex, float fixedDt) 改为 ITickable.Tick(uint frameIndex, Fixed64 fixedDt)。

为什么改接口而非保留 float + 入口转换：前序计划（TD-9）选择保留 float 接口以最小化影响面，但那只是羽毛球弹道的局部迁移。现在要做全局迁移，保留 float 接口意味着每个 ITickable 实现都要重复 Fixed64 dt = DeterminismRules.FixedDeltaTimeFixed64 的入口转换，违背 DRY 原则且容易遗漏。

级联影响：所有 ITickable 实现的 Tick 方法签名需同步更新：

  • ShuttlecockEntity（GameShared/Badminton/）— 内部已 Fixed64，仅改签名
  • BattleComponent（GameServer/Entity/Battle/）— 服务端入口
  • SnapshotManager（GameLogic/FrameSync/）— 快照管理
  • FrameTimerService（GameShared/FrameSync/Timer/）— 帧定时器，内部使用 float 计时需改为 Fixed64
  • BattleClientController（GameLogic/Battle/）— 渲染层入口
  • 测试 Mock 类（TickDispatcherTests 中的 MockTickable / CounterTickable / ThrowingTickable / CaptureDtTickable）
Note BattleWorldState 不直接实现 ITickable，它通过 BattleComponent.Tick 间接被调度。

落地：TickDispatcher 从 TickAccumulator.FixedDeltaTime 获取 float 后立即转为 Fixed64，传递给所有 ITickable。

TD-2

Box2D 边界策略 — Fixed64 API，float 内部

FrameSyncPhysicsWorld 实现 IPhysicsMovementWorld 接口。将接口和实现的所有 float 参数改为 Fixed64。FrameSyncPhysicsWorld 内部在调用 Box2D 前将 Fixed64 转为 float，Box2D 输出后将 float 转回 Fixed64。

转换安全性：Fixed64 ↔ float 转换是确定性的（相同的 Fixed64 raw 值总是产生相同的 float 值，反之亦然）。Box2D 在相同平台、相同输入、相同迭代次数下输出一致。因此 Fixed64 → float → Box2D → float → Fixed64 链路在同平台下是确定性的。

Box2D 常量：FrameSyncPhysicsWorld 内部的常量（PlayerBodyRadius、MinimumPlayerSeparation 等）改为 static readonly Fixed64，在传递给 Box2D 时转为 float。

物理快照：PhysicsBodySnapshot 的所有 float 字段改为 Fixed64。FrameSyncPhysicsWorld.TakeSnapshot() 将 Box2D 输出的 float 转为 Fixed64 填充快照。

TD-3

网络协议边界 — 保持 float，序列化层转换

OuterMessage 中的 PlayerSnapshot（float X, Y）、C2B_PlayerInput（float Dx, Dy）、PhysicsBodySnapshotProto（float PositionX/Y 等）保持 float 不变。

理由：

  • 网络协议的 float 字段是序列化格式，改动涉及 proto 定义 → 代码生成 → 双端同步升级，工作量大且风险高
  • 相同的 float 值在两端（都是 .NET 8+）序列化/反序列化结果一致
  • Fixed64 ↔ float 转换在序列化边界做，是确定性操作

落地：

  • 服务端 BattleComponent 发送快照时：Fixed64.ToFloat() 填充协议字段
  • 客户端 BattleSimulation 收到快照时：Fixed64.FromFloat() 或直接构造转换
  • 客户端发送输入时：float 保持不变（输入本身就是 float，来自摇杆/键盘）
TD-4

Luban 配置读取 — 保持 float 生成，读取时转换

ShuttlecockShot（Luban 生成的配置类）保持 float HorizontalSpeed / LaunchAngle / Drag 不变。ShuttlecockShotConfigProvider 在读取配置时将 float 转为 Fixed64 传给 ShuttlecockShotDefinition。

理由：改 Luban 定义需要修改 Excel/JSON 数据源 + Luban 模板 + 重新生成，属于配置系统工程，不在本迁移范围。

当前状态：ShuttlecockShotDefinition 已是 Fixed64 字段（前序计划完成），ShuttlecockShotConfigProvider 已做转换。无需额外工作。

TD-5

渲染层边界 — 保持 float

BattleClientController（GameLogic/）和 ShuttlecockDebugController / ShuttlecockTrajectoryDebug 保持 float 用于 Unity 渲染。

理由：Unity 引擎渲染管线使用 float（Vector3、transform.position 等），Fixed64 无法直接用于 UnityEngine API。在渲染层读取 GameShared 状态时做 Fixed64.ToFloat() 转换即可。

落地：BattleClientController.Tick 接收 Fixed64 fixedDt，但内部渲染计算可以转为 float 使用。读取 PlayerState.X/Y 时做一次 .ToFloat() 转换。

TD-6

BattleSimulation 迁移 — 全链路 Fixed64

BattleSimulation.cs 虽在 GameLogic/ 下，但通过 Entity.csproj 的 <Compile Include> 被 GameServer 编译。它不引用 UnityEngine（已验证），可以安全迁移到 Fixed64。

迁移范围：

  • 输入参数：float dx, dy → Fixed64 dx, dy（BattleInputSender delegate 签名同步更新）
  • 预测/回滚逻辑：状态比较使用 Fixed64.m_rawValue
  • NormalizeInput：使用 FixedMath.Sqrt + Vector2d 运算
TD-7

PlayerState 位置 — Fixed64，属性保持 int

PlayerState 的 float X, Y 改为 Fixed64 X, Y。属性（Health / MaxHealth / Mana / MaxMana / Attack）已经是 int，不需要迁移。

PlayerAttributeSnapshot 保持纯 int 字段，不需要迁移。

TD-8

TickDispatcher 策略 — Fixed64 传递

TickDispatcher 从 TickAccumulator 获取 tick 事件后，将 TickAccumulator.FixedDeltaTime（float）转为 Fixed64 传给 ITickable。由于所有 ITickable 现在接收 Fixed64，Dispatcher 不再需要关心 float fixedDt 的传递。

TickDispatcher 内部的 _fixedDt 字段改为 Fixed64，在构造时从 TickAccumulator 的 FixedDeltaTime 属性（float）转换一次。

TD-9

常量统一 — DeterminismRules.MoveSpeed 改为 Fixed64

DeterminismRules.MoveSpeed 当前为 const float MoveSpeed = 5.0f。FrameSyncPhysicsWorld 内部使用这个常量。改为 static readonly Fixed64 MoveSpeed。

TD-10

测试策略 — m_rawValue 位比较

沿用前序计划的测试策略：

  • 所有状态比较使用 Fixed64.m_rawValue 直接比较（整数值比较，天然位级一致）
  • 确定性自测：同输入两次仿真，所有中间状态 m_rawValue 完全相等
  • MoveSystem 自测：同输入同 Box2D 状态，输出位置位级一致

Important 由于本阶段 OuterMessage 保持 float，服务端和客户端的状态重建路径不同：
  • 服务端：直接在 Fixed64 游戏逻辑中运算 → 直接哈希 Fixed64 raw 值
  • 客户端：接收 float 协议 → 转为 Fixed64 → 重建状态 → 哈希
因此本阶段的 hash 比对仅限"同进程内自测"（不涉及网络传输）。跨进程（客户端 vs 服务端）的 hash 比对需要后续阶段完成协议 raw long 化后才能严格对齐。
