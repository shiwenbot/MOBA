# 状态帧同步-v0.3-test：自动化逻辑验收框架

## Context

当前测试流程需要手动操作三个进程（服务器 + 2 个 Unity 客户端），agent 无法自动驱动。v0.3-arch 完成后客户端逻辑已经是纯 C#，服务端的 `BattleComponent.Tick()` 主体也已经是纯逻辑（MoveSystem + 状态管理），只有 `BroadcastSnapshot()` 中的 `session.Send()` 和 `Join(Session session)` 依赖 Fantasy 网络。

两侧都做一次"网络剥离"后，可以在**单进程内**用函数调用代替网络，搭建一个完全脱离 Unity 和服务器进程的 TestHarness，agent 一条命令即可跑完整的帧同步逻辑验证。

**前置依赖**：v0.3-arch（已完成后客户端逻辑已具备纯 C# 基础；当前实现仍使用 BattleWorldState 轻量客户端，不直接依赖 BattleSimulation）

## 目标

- 从 `BattleComponent` 提取 `BattleLogic`（零 Fantasy 依赖的服务端仿真逻辑）
- `BattleComponent` 瘦身为 Fantasy 网络适配层
- 搭建 `TestHarness`：单进程运行 BattleLogic（虚拟服务端）+ N 个 SimulatedClient（虚拟客户端）
- agent 可用 `dotnet run -- --mode=test` 一条命令触发，输出 PASS / FAIL

---

## 非目标

- 不测试实际网络路径（网络测试是 v0.6a 的任务）
- 不测试 Unity 渲染层
- 不修改现有的服务端网络协议
- 不引入外部测试框架（xUnit/NUnit），使用运行时断言 + 日志输出

## 核心设计

### 整体架构

```
TestHarness（单进程，纯 C#，运行于 GameServer 内）

  ┌──────────────────────────────────────────┐
  │  BattleLogic（虚拟服务端）               │
  │  ├── JoinPlayer(playerId, x, y)          │
  │  ├── SubmitInput(playerId, frame, dx, dy)│
  │  ├── Tick(frameIndex, fixedDt)           │
  │  └── OnBroadcast: Action<TestSnapshot>  ─┼──┐
  └──────────────────────────────────────────┘  │
                      ↑ SubmitInput              │ 广播（函数调用）
  ┌─────────────────────────────────────┐        │
  │  SimulatedClient[0]                 │ ←──────┘
  │  SimulatedClient[1]                 │ ←──────┘
  │  （BattleWorldState）               │
  └─────────────────────────────────────┘

  TestRunner
  ├── 初始化：创建 BattleLogic + N 个 SimulatedClient
  ├── 连线：BattleLogic.OnBroadcast → 每个 client.ApplySnapshot()
  ├── 驱动：for frame in [0, TotalFrames): server.Tick() + client.SubmitInput()
  └── 验证：比对所有 client 的 StateHash → ALL MATCH = PASS
```

### BattleLogic（服务端纯逻辑提取）

从 `BattleComponent` 中分离出来的纯逻辑类，无任何 Fantasy 依赖：

```
BattleLogic
├── JoinPlayer(long playerId, float x, float y)      ← 不再接收 Session
├── RemovePlayer(long playerId)                      ← 只能在帧间调用（非 Tick 内）
├── HasPlayer(long playerId) → bool                  ← 防御性检查（移除后仍有输入时）
├── SubmitInput(long playerId, uint frameIndex,
│               uint inputSeq, float dx, float dy)   ← 直接用 playerId
├── Tick(uint frameIndex, float fixedDt)             ← MoveSystem + 广播回调
├── GetStateHash() → ulong                           ← 供场景 2 比对服务端内部哈希
└── OnBroadcast: Action<TestSnapshot>               ← 替代 session.Send()
```

**RemovePlayer 调用约束**：只能在两帧之间调用（即 `Tick()` 执行完毕后，下一次 `Tick()` 开始前）。BattleComponent 的 `CleanupDisconnectedPlayers()` 在 `Tick()` 之前调用，已满足此约束。TestHarness 同理。

**已迁移的内容**（BattleComponent → BattleLogic）：
- 状态字段：`_statesByPlayerId`、`_pendingInputsByPlayerId`、`_playerIdBuffer`、所有统计字段
- 方法：`Tick()`、`SubmitInput()` 逻辑部分（去掉 Session 查找）、`BuildSortedPlayerBuffer()`、`GetSpawnPosition()`、所有统计方法
- `PendingInput` struct

**保留在 BattleComponent 中的内容**（Fantasy 网络桥接）：
- `_sessionsByPlayerId`、`_playerIdBySessionId`（Session 管理）
- `Join(Session session)` → 转换后调用 `_battleLogic.JoinPlayer(playerId, x, y)`
- `SubmitInput(Session session, ...)` → 查 sessionId → `_battleLogic.SubmitInput(playerId, ...)`
- `CleanupDisconnectedPlayers()` → 检查 Session.IsDisposed → `_battleLogic.RemovePlayer()`
- `OnBroadcast` 绑定 → `foreach session: session.Send(snapshot)`

**TestSnapshot（TestHarness 用的轻量快照）**：
```
readonly struct TestSnapshot
  uint FrameIndex
  (long PlayerId, float X, float Y)[] Players   ← 数组而非接口（零 GC）
```

字段约束：
- `Players` 数组按 **PlayerId 升序**排列，与 `_playerIdBuffer.Sort()` 保持一致——这是哈希确定性的隐式依赖
- `Players` 字段集合 = 当前 `PlayerState` 所有参与哈希计算的字段（PlayerId、X、Y），两者必须同步扩展

不复用 Fantasy 协议类型（`S2C_FrameSnapshot`），避免 TestHarness 引入 Fantasy 依赖。BattleComponent 在将 TestSnapshot 转为 `S2C_FrameSnapshot` 广播时，需在转换代码旁注明映射关系，未来扩展字段时开发者知道要同步更新。

### SimulatedClient（客户端仿真）

TestHarness 内部的轻量客户端，**不依赖 BattleSimulation**：

```
SimulatedClient
├── PlayerId: long
├── WorldState: BattleWorldState   ← 来自 GameShared
├── ApplySnapshot(TestSnapshot)    ← 通过 ISnapshotable.RestoreSnapshot 路径更新 WorldState
├── GetStateHash() → ulong         ← StateHasher.Hash(WorldState.TakeSnapshot())
└── SubmitInput(float dx, float dy) → 调用 OnSendInput 回调
```

**ApplySnapshot 实现约束**：内部必须使用 `WorldState.RestoreSnapshot(snapshot)` 路径（即先构造 `BattleWorldSnapshot`，再调用 `ISnapshotable` 接口），而不是直接逐字段赋值。这保证当 v0.3-arch 完成后 `SimulatedClient` 升级为包装 `BattleSimulation` 时，快照恢复路径完全一致，不会出现"测试通过但真实路径不通"的情况。

当前实现保持该轻量路径，目的是让服务端测试入口不依赖 Unity 侧程序集。

### TestRunner

```
TestScenario
├── TotalFrames: uint
├── ClientCount: int
├── InputProvider: Func<int clientIndex, uint frame, (float dx, float dy)>
└── ExpectedBehavior: enum { AllHashMatch, PositionsConverge, ... }

TestRunner.Run(scenario) → TestResult(bool pass, string log)
```

### 驱动循环顺序（确定性关键）

TestRunner 每帧的执行顺序必须严格遵守：

```
for frame in [0, TotalFrames):
    // 1. 先提交输入（模拟网络到达）
    foreach client: battleLogic.SubmitInput(client.PlayerId, frame, seq++, dx, dy)

    // 2. 再 Tick（内部执行 MoveSystem + 触发 OnBroadcast）
    battleLogic.Tick(frame, DeterminismRules.FixedDeltaTime)

    // 3. ApplySnapshot 由 OnBroadcast 回调同步触发，不需要额外调用
```

顺序不对会破坏确定性：`Tick` 先于 `SubmitInput` 会导致输入延迟一帧。

TestHarness 模拟**零延迟**（输入当帧即到），不覆盖网络延迟/乱序场景（那是 v0.6a 的任务）。

### 运行方式

在 `GameServer/Server/Main/Program.cs` 以 `--mode` 路由不同入口，便于后续扩展：

```
args 包含 "--mode=test" → 跳过 Fantasy 服务器启动，直接运行 TestRunner，完成后退出
args 默认              → 正常启动 Fantasy 服务器
```

Agent 调用：
```bash
dotnet run --project 'GameServer/Server/Main/Main.csproj' -- --mode=test
```

退出码：0 = 全部通过，1 = 有失败（agent 可直接读取退出码判断结果）。

**输出格式**（规范化，便于 agent 解析）：
```
[TestSuite] Running 4 scenarios...
[Scenario 1] Determinism (2 clients, 300 frames) ... PASS  hash=0xABCD1234
[Scenario 2] Consistency (server-client, 300 frames) ... PASS
[Scenario 3] Convergence (no input after frame 50) ... PASS
[Scenario 4] PlayerLeave (player B leaves at frame 100) ... PASS
[TestSuite] 4/4 PASS
```

失败时输出详细信息：
```
[Scenario 1] FAIL  Client[0].hash=0xABCD1234  Client[1].hash=0xDEAD5678  frame=47
```

## 实现步骤

### Step 1：提取 BattleLogic

新建 `GameServer/Server/Entity/Battle/BattleLogic.cs`。

迁移 `BattleComponent` 的纯逻辑部分：
- 无 `using Fantasy.Network`
- `JoinPlayer(long playerId, float x, float y)` 替代 `Join(Session session)`
- `SubmitInput(long playerId, ...)` 替代 `SubmitInput(Session session, ...)`（去掉 session 查找层）
- 广播改为：`OnBroadcast?.Invoke(buildTestSnapshot())`
- `TryLogFrameStats` 中的 `Log.Debug` → 通过构造函数注入 `Action<string> log`

### Step 2：瘦身 BattleComponent

`BattleComponent` 变为 Fantasy 适配层，持有 `_battleLogic` 引用：

- 构造时：`_battleLogic = new BattleLogic(); _battleLogic.OnBroadcast = OnBattleLogicBroadcast;`
- `Join(Session session)` → 分配 playerId → `_battleLogic.JoinPlayer(playerId, x, y)`
- `SubmitInput(Session session, input)` → 查 sessionId → `_battleLogic.SubmitInput(playerId, ...)`
- `Tick()` → `_battleLogic.Tick(frameIndex, fixedDt)`
- `CleanupDisconnectedPlayers()` → 留在 BattleComponent，检查 Session 后调 `_battleLogic.RemovePlayer()`
- `OnBattleLogicBroadcast(TestSnapshot snapshot)` → 将 TestSnapshot 转为 `S2C_FrameSnapshot` → 广播

### Step 3：新建 TestSnapshot

新建 `GameServer/Server/Entity/TestHarness/TestSnapshot.cs`：

```
readonly struct TestSnapshot
  uint FrameIndex
  (long PlayerId, float X, float Y)[] Players
```

### Step 4：新建 SimulatedClient

新建 `GameServer/Server/Entity/TestHarness/SimulatedClient.cs`：

- 内部持有 `BattleWorldState`（来自 GameShared）
- `ApplySnapshot(TestSnapshot)`：通过 `BattleWorldState.RestoreSnapshot()` 应用快照
- `GetStateHash()`：调用 `StateHasher`，从 `WorldState.TakeSnapshot()` 计算哈希

### Step 5：新建 TestRunner

新建 `GameServer/Server/Entity/TestHarness/TestRunner.cs`，内置四个场景：

**场景 1：两客户端确定性验证**
- 2 个 SimulatedClient，各自跑 300 帧
- 每帧：双方提交相同的输入序列（预设脚本输入）
- 验证：300 帧后 Client[0].StateHash == Client[1].StateHash

**场景 2：服务端 - 客户端状态一致性**
- 1 个 SimulatedClient + BattleLogic
- 每帧：BattleLogic 广播快照 → Client 应用 → 比对 Client.StateHash 与 BattleLogic 内部 StateHash
- 验证：每 30 帧，双方哈希一致

**场景 3：无输入收敛**
- 2 个 SimulatedClient，初始位置不同，50 帧后停止输入
- 验证：停止输入后位置稳定（不漂移），双方哈希一致

**场景 4：玩家离开稳定性**
- 2 个 SimulatedClient（玩家 A、B），第 100 帧调 `BattleLogic.RemovePlayer(B)`
- 验证：第 101-150 帧玩家 A 的哈希不受影响，位置正常继续移动
- 覆盖 `RemovePlayer` 路径，防止提取 BattleLogic 时引入 bug

### Step 6：集成到 Program.cs

在 `GameServer/Server/Main/Program.cs` 入口处：

```
if (args 包含 "--test" 或 "--mode=test"):
    int exitCode = TestRunner.RunAll();
    Environment.Exit(exitCode);
```

退出码：0 = 全部通过，1 = 有失败。

### Step 7：验证

```bash
dotnet run --project 'GameServer/Server/Main/Main.csproj' -c Debug --framework net8.0 --no-build -- --mode=test
# 期望输出：[TestSuite] 4/4 PASS
```

**实际验收结果**：

```text

[Scenario 3] Convergence (no input after frame 50) ... PASS
```

## 确定性约束

- TestHarness 中每帧的 `fixedDt` 必须直接传入 `DeterminismRules.FixedDeltaTime` 常量，**不得在 TestHarness 内重新定义同值常量**，两处同源是确定性的硬约束
- 输入脚本（预设序列）保证两个客户端在同一帧收到相同输入
- `StateHasher` 使用已有的 FNV-1a 实现，与线上路径完全一致
- `BattleLogic.Tick()` 中的玩家排序逻辑（`_playerIdBuffer.Sort()`）不变，确保确定性
- 驱动循环中 `SubmitInput` 必须先于 `Tick` 执行，顺序反转会导致输入延迟一帧，破坏场景 1 的哈希一致性

## 关键风险与应对

| 风险 | 影响 | 应对 |
|------|------|------|
| TestSnapshot 与 S2C_FrameSnapshot 转换遗漏字段 | 快照应用不完整，哈希不一致 | 转换后立即做 Players.Count 断言 |
| BattleLogic 内的 CleanupDisconnectedPlayers 被破坏 | 玩家不能正确移除 | 将 CleanupDisconnectedPlayers 留在 BattleComponent，BattleLogic 只暴露 RemovePlayer(playerId) |
| TestHarness 中 dt 累积误差 | 浮点帧时间不稳定 | 直接传 DeterminismRules.FixedDeltaTime 常量，不通过 TickAccumulator |
| 场景 2 中 StateHasher 对服务端状态的路径与客户端不一致 | 误报哈希不匹配 | 两侧都通过 `BattleWorldState.TakeSnapshot()` → `StateHasher.Hash()` 路径计算 |
| 驱动循环中 Tick 先于 SubmitInput 执行 | 输入延迟一帧，场景 1 哈希不一致（误判非确定性 bug） | 代码 review 时检查 for 循环体顺序，TestRunner 的循环结构必须以 SubmitInput 开头 |
| `_playerIdBuffer.Sort()` 在提取 BattleLogic 时丢失 | 玩家处理顺序随机，哈希不确定 | 迁移时明确注释「排序是确定性约束，禁止删除」；场景 1 自动验证此路径 |
