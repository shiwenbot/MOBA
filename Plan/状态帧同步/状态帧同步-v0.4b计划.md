# 状态帧同步-v0.4b计划：属性脏同步

## Context

`v0.4a` 已把 Box2D 物理状态正式纳入统一快照、回滚与一致性校验链路，当前主线路径已经具备：

- 服务端 30Hz 权威推进
- 客户端只预测自己
- 物理状态与逻辑状态共用同一 `FrameIndex`
- 权威快照、状态哈希、正式回滚都已可验证

进入 `v0.4b` 后，下一条必须补齐的不是 Buff 或 Skill，而是**战斗属性本身**。原因很直接：

- 后续 Buff、技能、黑板最终都会落到属性变化
- 如果属性不进入统一快照，回滚时就只能“位置回去了，血量没回去”
- 如果属性不同步，客户端看到的受击、耗蓝、攻击力结算都会和服务端漂移

因此，`v0.4b` 的首要目标不是一次做完整数值系统，而是先把“属性状态进入快照/哈希/协议/客户端恢复”这条最小闭环做稳，再在此基础上逐步扩展更多属性与裁剪策略。

## 阶段状态

- 状态：`进行中（第一刀：属性快照 + 属性脏标记同步）`
- 更新日期：`2026-05-17`

## 目标

- 将玩家属性正式纳入 `BattleWorldSnapshot` / `BattleWorldState` / `StateHasher`。
- 在服务端建立最小战斗属性集：`HP / MaxHP / MP / MaxMP / Attack`。
- 扩展 `PlayerSnapshot`，支持“属性脏标记 + 属性字段”下发。
- 客户端收到局部属性字段后，能够合并为完整权威属性，再进入现有回滚/一致性链路。
- 保持“快照保存的是完整状态，协议只下发脏字段”的分层约束。

## 非目标

- 本阶段不做完整 Numeric 系统重构，不接入复杂公式、成长曲线或装备体系。
- 本阶段不实现 Buff、技能伤害、DOT/HOT、暴击、护盾等派生玩法。
- 本阶段不做属性 UI 展示与表现层动画。
- 本阶段不做细粒度带宽统计面板，只先把裁剪协议与正确性闭环建立起来。

---

## 设计约束

1. **快照始终保存完整属性状态**  
   无论网络层是否做脏同步，`BattleWorldSnapshot` 中必须始终保存完整属性，保证回滚、哈希和无头测试不依赖“上一包缓存”。

2. **脏同步只发生在传输层**  
   服务端广播给客户端时可以只下发脏字段；但服务端内部权威状态、测试快照、状态哈希全部继续基于完整状态。

3. **首包必须全量**  
   某玩家第一次被客户端观察到时，属性脏标记必须覆盖所有字段，确保客户端能建立完整基线。

4. **无脏位字段不得覆盖本地权威基线**  
   客户端收到 `dirtyMask = 0` 的属性包时，必须保留上一份权威属性，而不是把未下发字段误写为 `0`。

5. **属性变更与物理结果共享同一帧语义**  
   同一逻辑帧内，属性变化最终也要被视作该帧权威结果的一部分，和位置/物理状态一起进入快照。

6. **客户端可预测的属性变化必须走按帧命令模型**  
   如耗蓝、客户端主动触发的本地可确定消耗，必须携带 `FrameIndex`，进入客户端预测历史与服务端按帧消费路径；禁止用“客户端先改值 + 服务端即时消息立刻生效”的混合模式。

7. **服务器裁决型属性变化默认不做客户端预测**  
   如受击掉血、命中结算、Buff tick、依赖目标/碰撞/判定顺序的属性变化，默认继续走权威快照，后续若要预测，必须先补齐命令语义和回滚依据。

## 最小属性集

第一刀只落以下 5 项：

- `Health`
- `MaxHealth`
- `Mana`
- `MaxMana`
- `Attack`

原因：

- 已足够支撑后续最基础的伤害、耗蓝、Buff 修改与技能判定
- 仍然足够小，便于先验证快照/回滚/脏同步链路

## 实现步骤

### Step 0：补齐计划与协议定义

- 新增 `状态帧同步-v0.4b计划.md`
- 修正 `OuterMessage.proto` 与当前生成代码不一致的问题
- 在 `PlayerSnapshot` 中补齐物理字段现状，并新增属性脏同步字段

状态：`进行中`

### Step 1：共享层引入属性快照模型

- 新增 `PlayerAttributeSnapshot`
- 新增 `PlayerAttributeDirtyFlags`
- 新增 `PlayerAttributeSync`，统一做脏位 diff / merge
- 扩展 `PlayerState` 与 `PlayerStateSnapshot`
- 扩展 `BattleWorldState.TakeSnapshot()` / `RestoreSnapshot()`
- 扩展 `StateHasher`

预期结果：

- 属性正式进入完整快照
- 快照往返和状态哈希都能感知属性变化

### Step 2：服务端按玩家属性 diff 广播

- 服务端维护“上一次已广播属性基线”
- 每帧按玩家比较当前属性与上次广播值，生成 `AttributeDirtyMask`
- 仅在脏位上写入属性字段；无脏位字段保持默认值
- 玩家离开时同步清理该缓存

预期结果：

- 首帧全量
- 后续仅脏字段过线
- 不影响现有位置/物理同步链路

### Step 3：客户端合并权威属性基线

- 客户端维护“每个玩家最近一次权威属性”
- 收到 `PlayerSnapshot` 后，按 `AttributeDirtyMask` 合并为完整属性快照
- 用合并后的完整属性构建 `BattleWorldSnapshot`
- 再交给现有 `BattleSimulation` / `SnapshotManager` 路径处理

预期结果：

- 脏同步对回滚透明
- 状态哈希继续基于完整状态

### Step 4：补验证

- 共享自测新增：属性往返、属性哈希、脏位 merge
- 预测自测新增：权威快照恢复属性
- 无头测试继续走现有 `prediction-self` / `all`
