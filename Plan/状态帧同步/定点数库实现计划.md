# 定点数库实现计划：羽毛球弹道确定性 + 帧调度器修复

## Context

当前帧同步系统中所有数学运算（位置、速度、物理计算、时间累积）使用 `float`。MVP-a 验收时发现 `TickAccumulatorTests.Accumulate_Converts60FpsTo30TicksPerSecond` 测试因浮点累积误差失败（60 次 `1.0f / 60.0f` 累加不等于精确 `1.0f`）。

更重要的是，项目使用 Fantasy 网络框架的**服务端权威 + 客户端预测**架构。GameServer（C# 独立进程，可能运行在 Linux）和 Unity Client（多平台）需要执行相同的物理仿真。当前代码中的以下浮点运算在跨平台场景下**不可能保证位级一致**：

1. **`Math.Exp`**：`ShuttlecockPhysics.Step()` 每帧调用 2 次，CRT 实现跨平台不同
2. **`MathF.Sin`**：`ShuttlecockEntity.ExecuteLaunch()` 中发射角计算
3. **`MathF.Sqrt`**：`FrameSyncPhysicsWorld` 中碰撞法线计算和输入归一化
4. **浮点累积**：`TickAccumulator` 中时间累积的精度丢失

### 已锁定的设计决策（来自前序计划）

1. **帧率**：30Hz 逻辑帧（dt = 33.333ms，与 `DeterminismRules.FixedDeltaTime` 一致）
2. **弹道模型**：高空气阻力模型，水平速度指数衰减约 60%/s（不使用 Box2D）
3. **坐标约定**：2.5D 模型——XZ 为水平面，Y 为独立高度标量
4. **Box2D 范围**：羽毛球弹道不走 Box2D，角色移动走 Box2D
5. **确定性工具链**：`BitConverter.SingleToInt32Bits` 位比较 + `DeterminismRules` 约束

### 现有代码能力

- `ShuttlecockPhysics`：纯数学弹道计算（无 Box2D 依赖），是迁移的首选目标
- `FrameSyncPhysicsWorld`：封装 Box2D，内部全部使用 `System.Numerics.Vector2`（float）
- `TickAccumulator`：浮点时间累积器，已有失败的测试用例
- `DeterminismRules`：提供 `AssertFixedDt` / `AssertFinite` / `FloatToBits` 工具方法
- 快照/回滚体系：`ISnapshotable<T>` / `SnapshotBuffer<T>`，不关心内部数据类型

## 目标

1. **引入定点数库**：通过源码 vendoring 引入 FixedMathSharp（Q32.32 格式），为帧同步确定性奠定基础
2. **羽毛球弹道迁移**：`ShuttlecockPhysics` + `ShuttlecockEntity` + `CourtConstants` 全部运算从 float 迁移到 Fixed64
3. **时间累积修复**：`TickAccumulator` 内部迁移到 Fixed64 累积，修复已知测试失败
4. **确定性验证**：同进程内两次相同输入的羽毛球仿真，所有帧状态位级一致

**阶段定位**：本阶段是"为跨平台确定性打基础"的第一步，只闭环羽毛球纯数学链路。角色移动链路（`FrameSyncPhysicsWorld` / `PlayerState` / `MoveSystem`）的定点化留到 MVP-b。本阶段完成后，系统整体仍不能宣称"跨平台帧同步确定性"。

## 技术决策

### TD-1：引入 FixedMathSharp 库（Q32.32 格式）— 双端源码 vendoring

采用 [FixedMathSharp](https://github.com/mrdav30/FixedMathSharp) 库（MIT 许可证），**以源码形式放入共享目录**，确保 Unity 和 GameServer 编译完全相同的代码。

**FixedMathSharp 特性**：
- `Fixed64`：Q32.32 格式（64 位有符号整数，32 位整数 + 32 位小数），范围 ±2B，精度 ~10⁻¹⁰
- `FixedMath`：Sin/Cos/Sqrt/Exp/Pow/Atan2/Log 等全部超越函数
- `Vector2d`：2D 向量（含点积、长度、归一化）
- MIT 许可证，纯 C# 无外部依赖

**为什么不用 Q16.16 自己实现**：

| 方案 | 开发量 | 精度 | 维护负担 |
|------|--------|------|---------|
| 自研 Q16.16 | 高（查表 + 牛顿法 + 向量） | ~0.015mm | 需自己保证正确性 |
| FixedMathSharp Q32.32 | 低（源码 vendoring） | ~10⁻¹⁰ | 社区维护，已验证 |

**双端依赖策略（参见 TD-10）**：不使用 UPM / NuGet 安装。将 FixedMathSharp 源码拷贝到 `UnityProject/Assets/GameScripts/HotFix/GameShared/ThirdParty/FixedMathSharp/`。放在 GameShared asmdef 目录内，自动属于 GameShared 程序集（无需额外 asmdef 配置）。GameServer 的 `Entity.csproj` 已有 `<Compile Include="GameShared/**/*.cs">` glob，自动覆盖此目录（无需新增行）。

**落地**：源码 vendoring 到 `GameShared/ThirdParty/FixedMathSharp/`。项目代码使用 `Fixed64`（标量）、`FixedMath`（数学函数）、`Vector2d`（2D 向量）。

### TD-2：数学函数 — 由 FixedMathSharp 内建提供

`FixedMath` 类已内建以下函数，无需自己实现查表：

- **Sin / Cos / Tan**：三角函数
- **Exp / Log / Log2**：指数/对数（Exp 使用正确的 range reduction：`e^x = 2^k × e^r`）
- **Sqrt**：平方根
- **Atan2**：反正切
- **Pow**：幂运算
- **Abs / Min / Max / Clamp / Lerp / Sign / Floor / Ceil**：基础函数

迁移代码中直接调用 `FixedMath.Exp(x)` / `FixedMath.Sin(x)` / `FixedMath.Sqrt(x)` 等，无需关心内部实现。

### TD-3：向量类型 — 使用 FixedMathSharp 的 Vector2d

FixedMathSharp 提供 `Vector2d`（`Fixed64 X` + `Fixed64 Y`），含点积、长度、归一化、距离等全部所需操作。

**与外部 Vector2 的对接**：Vector2d 不引用 `UnityEngine`。需要转换时由调用方直接访问 `.X.ToDouble()` / `.Y.ToDouble()` 构造目标向量类型。

### TD-4：Box2D 边界策略 — 保留 float，转换层延后

Box2D 库（`Box2DSharp`）内部使用 `System.Numerics.Vector2`（float），无法改为定点数。但 Box2D 在相同输入下是确定性的（固定迭代次数、无随机性）。

**策略**：
- 本阶段**不修改** `FrameSyncPhysicsWorld` 内部逻辑
- `FrameSyncPhysicsWorld` 的输入输出仍为 float
- 后续 MVP-b（角色移动）时，在 `MoveSystem` 层添加 `Fixed64 ↔ float` 转换
- 依赖链：`游戏逻辑(Fixed64)` → `MoveSystem(转换)` → `FrameSyncPhysicsWorld(float)` → `Box2D`

**理由**：本阶段的重点是修复羽毛球弹道（纯数学计算）的确定性。Box2D 边界转换涉及 PlayerState 迁移，工作量大且与当前 MVP-a 问题无关。

### TD-5：文件组织 — FixedMathSharp 放 GameShared/ThirdParty，自建测试放 Tests

- FixedMathSharp 源码放在 `GameShared/ThirdParty/FixedMathSharp/`（GameShared asmdef 目录内）
- 自建的定点数验证测试放在 `GameShared/Tests/FixedPoint/`
- 迁移后的业务代码留在原目录（`Badminton/`、`FrameSync/Core/` 等）

**理由**：
- 放在 GameShared asmdef 目录内，自动属于 GameShared 程序集，无需额外 asmdef 或引用配置
- GameServer 的 Entity.csproj 已有 `<Compile Include="GameShared/**/*.cs">` glob，自动覆盖此目录
- ThirdParty 子目录与业务代码隔离，不污染现有代码组织

### TD-6：迁移策略 — 分层渐进

按依赖关系分 5 层迁移，每层可独立验证：

| 层 | 内容 | 依赖 |
|---|------|------|
| L1 | 安装 FixedMathSharp + 验证基本功能 | 无 |
| L2 | CourtConstants (float → Fixed64) | L1 |
| L3 | ShuttlecockPhysics 全链路迁移 | L1 + L2 |
| L4 | TickAccumulator + DeterminismRules | L1 |
| L5 | 确定性验证测试 | L1-L4 |

每层完成后可编译验证，不需要等所有层完成。

### TD-7：常量定义方式 — 编译期可推导

`CourtConstants` 等常量从 `const float` 改为 `static readonly Fixed64`。

**理由**：C# 不允许用户定义类型的 `const` 字段。但 `static readonly Fixed64` 在静态构造函数中初始化，性能等价（JIT 会内联）。`Fixed64` 的常量（如 `Pi`、`Zero`、`One`）使用 `static readonly` 定义。

### TD-8：测试策略 — 位比较 + 跨次一致

沿用现有 `BitConverter.SingleToInt32Bits` 位比较的思路，但改为 `Fixed64.m_rawValue` 直接比较（整数值比较，天然位级一致）。

**确定性自测**：运行两次相同输入的仿真，比对所有中间状态（每帧的位置、速度），`Fixed64.m_rawValue` 必须完全相等。这替代了现有的 `float` 位比较方案。

### TD-9：ITickable / TickDispatcher 边界 — 保留 float，入口处转换

`ITickable.Tick(uint frameIndex, float fixedDt)` 和 `TickDispatcher` 全链路使用 `float`。将它们改为 `Fixed64` 会级联影响所有 ITickable 实现（`BattleWorldState`、`ShuttlecockEntity` 等）以及 `TickDispatcher` 的构造函数和 `Update` 方法，超出本阶段范围。

**策略**：保留 `ITickable` / `TickDispatcher` 为 `float`。在羽毛球模块入口做一次受控转换：

- `ShuttlecockEntity.Tick(uint, float)` 保持接口签名不变（满足 `ITickable`）
- 方法内部第一行将 `float fixedDt` 转为 `Fixed64`：使用预计算的 `DeterminismRules.FixedDeltaTimeFixed64`（`static readonly Fixed64`），忽略传入的 float 参数
- 后续内部计算全部使用这个 `Fixed64` 常量值

**理由**：`fixedDt` 实际上永远是 `DeterminismRules.FixedDeltaTime`（由 `TickAccumulator` 保证），所以入口处的转换是安全的——直接用 Fixed64 常量替代 float 参数，既满足接口约束又保证内部纯 Fixed64 运算。

**TickAccumulator 策略**：保持 `Accumulate(float deltaTime)` 外部签名不变（`TickDispatcher.Update(float)` 调用此方法）。内部使用 Fixed64 进行累积计算，`_fixedDeltaTime` 和 `_maxDeltaTime` 存储为 Fixed64。构造函数接受 float 参数并立即转为 Fixed64。`FixedDeltaTime` 属性仍返回 `float`（通过 `ToFloat()`），确保 `TickDispatcher` 和 `DeterminismRules.AssertFixedDt(float)` 的现有调用方不受影响。

**已落地补充**：在本阶段 `ITickable` / `TickDispatcher` 仍保留 `float` 边界，因此 `DefaultFixedDeltaTimeFixed64` 必须从 `DefaultFixedDeltaTime` 转换得到，而不是直接使用数学意义上的 `FixedMath.ONE_L / 30L`。两者都接近 `1/30`，但 raw 值不同；若混用会导致 `AssertFixedDt` 与 EditMode 测试出现伪不一致。`TickAccumulator` 的整 tick 计算也使用确定性的 raw 级边界容差，避免 `0.5f / (1.0f / 30.0f)` 在 Fixed64 raw 表示下落到 14 tick。

### TD-10：双端构建一致性 — 源码 vendoring 到 GameShared 内部

**问题**：GameServer 的 `Entity.csproj` 不使用 Unity 的 UPM 包管理器，也不使用 NuGet。它通过 `<Compile Include>` 链接 `GameShared/**/*.cs` 源码，通过 `<Reference>` + `<HintPath>` 引用 `ThirdParty/Box2DSharp/Box2DSharp.dll`。如果 FixedMathSharp 只通过 UPM 安装，GameServer 无法编译 GameShared 中引用 `Fixed64` 的代码。

**方案**：源码 vendoring 到 `GameShared/ThirdParty/FixedMathSharp/`。

- **Unity 侧**：源码在 GameShared asmdef 目录内，自动属于 GameShared 程序集，无需额外 asmdef 或引用配置
- **GameServer 侧**：Entity.csproj 已有 `<Compile Include="GameShared/**/*.cs">` glob（排除 Tests），自动覆盖 `GameShared/ThirdParty/FixedMathSharp/**/*.cs`，**无需新增任何行**
- **同步保证**：两端编译同一份源码文件，不存在版本不一致的风险

**排除的替代方案**：

| 方案 | 问题 |
|------|------|
| UPM (Unity) + NuGet (Server) | 两个包源，版本可能不一致，破坏确定性 |
| 放在 HotFix/ThirdParty/（GameShared 外） | GameShared.asmdef 看不到，需要单独建 asmdef + 加引用 |
| 编译为 DLL 双端引用 | 增加构建步骤，调试困难 |
| 只在 Unity 用 UPM | GameServer 编译直接报错 |

**更新策略**：当需要升级 FixedMathSharp 版本时，替换 `GameShared/ThirdParty/FixedMathSharp/` 下的源码文件即可，双端自动同步。

## 实现步骤

### Step 1：安装 FixedMathSharp（源码 vendoring）

从 [FixedMathSharp GitHub](https://github.com/mrdav30/FixedMathSharp) 获取源码（Lean 版本，不含 MemoryPack），拷贝到项目共享目录。

**操作步骤**：

1. 克隆 FixedMathSharp 仓库，将核心源码（`Fixed64.cs`、`FixedMath.cs`、`Vector2d.cs` 等，排除测试和示例）拷贝到 `UnityProject/Assets/GameScripts/HotFix/GameShared/ThirdParty/FixedMathSharp/`
2. 确认两端编译通过：
   - Unity：打开编辑器，确认无编译错误（源码在 GameShared asmdef 内，自动可见）
   - GameServer：`dotnet build Entity.csproj`，确认无编译错误（现有 `<Compile Include="GameShared/**/*.cs">` glob 已覆盖）

安装后确认：
- `Fixed64` 类型可用（Q32.32 格式）
- `FixedMath` 类可用（含 Exp / Sin / Cos / Sqrt / Atan2 等）
- `Vector2d` 类型可用（含 Length / Normalized / Dot 等）
- GameShared 代码可以引用这些类型
- GameServer 的 `dotnet build` 通过

### Step 2：验证库的基本功能

创建 `Tests/FixedPoint/FixedMathSharpTests.cs`，验证安装后的库在项目环境中工作正常：

- `Fixed64.From(1.0) + Fixed64.From(2.0) == Fixed64.From(3.0)`
- `FixedMath.Exp(Fixed64.From(0.0)) == Fixed64.One`
- `FixedMath.Sin(Fixed64.PiOver2) ≈ Fixed64.One`（误差 < 10⁻⁴）
- `new Vector2d(3, 4).Length() ≈ Fixed64.From(5.0)`
- 两次运行相同运算，`Fixed64` 的 `m_rawValue` 字段完全相等

### Step 3：CourtConstants 迁移

修改 `Badminton/CourtConstants.cs`。

- 所有 `const float` → `static readonly Fixed64`
- 所有 `static readonly Vector2` 角落常量 → `static readonly Vector2d`
- `IsInBounds` 方法参数从 `Vector2` → `Vector2d`，内部用 `FixedMath.Abs` 替代 `Math.Abs`

### Step 4：ShuttlecockState / ShuttlecockSnapshot 迁移

修改 `Badminton/ShuttlecockState.cs`。

- `XZ`：`Vector2` → `Vector2d`
- `Y`：`float` → `Fixed64`
- `Vxz`：`Vector2` → `Vector2d`
- `Vy`：`float` → `Fixed64`
- `LandingXZ`：`Vector2` → `Vector2d`
- `HorizontalDrag`：`float` → `Fixed64`
- `Reset()` 方法中 `Vector2.zero` → `Vector2d.Zero`，`0.0f` → `Fixed64.Zero`

修改 `Badminton/ShuttlecockSnapshot.cs`。

- 同步更新所有字段类型
- 构造函数参数从 float/Vector2 → Fixed64/Vector2d
- `WithFrameIndex` 方法同步更新

### Step 5：ShuttlecockPhysics 迁移（核心）

修改 `Badminton/ShuttlecockPhysics.cs`。

这是最关键的迁移文件。核心变更：

- `Gravity`、`VerticalDrag` 常量：`float` → `Fixed64`
- `Step` 方法签名：`(ShuttlecockState state, float dt, uint frameIndex)` → `(ShuttlecockState state, Fixed64 dt, uint frameIndex)`。注意 `Step` 不走 `ITickable` 接口（它是被 `ShuttlecockEntity.Tick` 内部调用的纯函数），改签名无外部影响
- `Math.Exp(-state.HorizontalDrag * dt)` → `FixedMath.Exp(-state.HorizontalDrag * dt)`
- `Math.Exp(-VerticalDrag * dt)` → `FixedMath.Exp(-VerticalDrag * dt)`
- 所有浮点算术（`*`、`+`、`-`）自动通过 Fixed64 运算符重载处理
- `state.XZ += averageVxz * dt` 中 `*` 变为 `Vector2d * Fixed64`

### Step 6：ShuttlecockEntity 迁移

修改 `Badminton/ShuttlecockEntity.cs`。

- `ExecuteLaunch` 方法：
  - `definition.LaunchAngleDegrees * DegreesToRadians` → `FixedMath.Deg2Rad`
  - `MathF.Sin(angleRadians)` → `FixedMath.Sin(angleRadians)`
  - `MathF.Max(0.0f, ...)` → `FixedMath.Max(Fixed64.Zero, ...)`
  - `command.DirectionXZ.normalized` → `command.DirectionXZ.Normalized()`
- `Tick` 方法：保持 `void Tick(uint frameIndex, float fixedDt)` 签名不变（满足 `ITickable` 接口）。方法内部第一行用 `Fixed64 dt = DeterminismRules.FixedDeltaTimeFixed64` 替代 float 参数，后续全部使用 `Fixed64 dt`。参见 TD-9。
- `DeterminismSelfTest` / `RollbackSelfTest`：这些静态方法不走 `ITickable` 接口，内部直接使用 `DeterminismRules.FixedDeltaTimeFixed64` 作为 `Fixed64` 常量
- `EnsureSnapshotsMatch`：从 `BitConverter.SingleToInt32Bits` 比较改为 `Fixed64.m_rawValue` 比较
- `ValidateDirection`：`direction.sqrMagnitude` → `direction.LengthSquared()`

### Step 7：ShuttlecockLaunchCommand / ShuttlecockShotDefinition 迁移

修改 `Badminton/ShuttlecockLaunchCommand.cs`。

- `OriginXZ`：`Vector2` → `Vector2d`
- `OriginY`：`float` → `Fixed64`
- `DirectionXZ`：`Vector2` → `Vector2d`

修改 `Badminton/Config/ShuttlecockShotDefinition.cs`。

- `HorizontalSpeed`：`float` → `Fixed64`
- `LaunchAngleDegrees`：`float` → `Fixed64`

修改 `Badminton/Config/ShuttlecockShotConfigFallback.cs`。

- 所有球路参数的 `float` 字面量 → `Fixed64` 值（使用 `Fixed64.FromFloat()` 或直接构造）

### Step 8：TickAccumulator 迁移

修改 `FrameSync/Core/TickAccumulator.cs`。遵循 TD-9 策略：**保持外部 API 不变，内部用 Fixed64**。

- 构造函数：保持 `TickAccumulator(float fixedDeltaTime, float maxDeltaTime)` 签名，内部立即转 `Fixed64` 存储
- `_accumulator`、`_fixedDeltaTime`、`_maxDeltaTime`：内部存储改为 `Fixed64`
- `_maxTicksPerUpdate`：仍为 `int`，通过统一的整 tick 计算方法从 `Fixed64` 时长换算，处理 tick 边界 raw 级误差
- `Accumulate(float deltaTime)`：签名不变，内部先 `Fixed64.FromFloat(deltaTime)` 再累加。Fixed64 加法的结合律保证 60 次相同输入的累加结果精确
- `FixedDeltaTime` 属性：仍返回 `float`（`_fixedDeltaTime.ToFloat()`），确保 `TickDispatcher` 不受影响
- `Remainder` 属性：仍返回 `float`
- `Reset()`：`_accumulator = Fixed64.Zero`
- `CountWholeTicks(Fixed64 duration)`：统一负责整 tick 换算，并加入确定性的 raw 级边界容差，使 `DefaultMaxDeltaTime = 0.5f` 在 30Hz 下稳定得到 15 tick

**不标记 `[Obsolete]`**：`Accumulate(float)` 是正常的公共 API（外部调用者如 `TickDispatcher` 传的就是 float deltaTime），不是遗留接口。

### Step 9：DeterminismRules 适配

- `FloatToBits` / `FixedDeltaBits`：保留不动（供现有 float 代码使用）
