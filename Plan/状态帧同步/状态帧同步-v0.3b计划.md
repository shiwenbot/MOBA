# 状态帧同步-v0.3b计划：全局帧号重构（第一阶段）

## Context

当前代码里的客户端与服务端虽然都在按 30Hz 推进，但 `FrameIndex` 语义并不统一：

- 客户端通过 `_serverFrameOffset` 计算 `ToPredictedServerFrame()`
- `C2B_PlayerInput.FrameIndex` 发送的是“预测出来的服务端帧号”
- 服务端用 `LastFrameIndex + MaxFrameWindow` 做窗口校验
- 客户端一致性检查、输入历史、预测记录也都被迫围绕这层映射工作

这使得协议、预测、追帧、回滚耦合过深。根据 [状态帧同步-架构重构计划.md](/D:/unity/Tencent/TEngine/Plan/状态帧同步/状态帧同步-架构重构计划.md:1)，v0.3b 的任务不再是继续加深旧模型，而是先把主线切换到“全局帧号 + 服务端权威推进”。

**前置依赖**：v0.3a + v0.3-arch + v0.3-test（均已完成）

## 目标

- 统一客户端和服务端的 `FrameIndex` 语义为“全局逻辑帧号”
- 移除客户端 `_serverFrameOffset`、`ToPredictedServerFrame()`、`GetSendFrame()` 主路径
- 服务端废弃 `MaxFrameWindow + HardReject` 主模型，改为“未来输入缓冲 + 缺帧复用上一帧输入”
- 保留 `Ping/Pong`、RTT EMA、追帧基础设施，但只用于决定客户端目标领先量
- 让后续的预测、一致性检查、回滚重播都直接基于全局帧号工作

## 非目标

- 本阶段不实现基于 `bufferDepth` 的动态速率控制
- 不引入重传协议
- 不实现其他玩家表现层插值
- 不压缩协议字段；`InputSeq` 可以先保留，但不再作为主线帧语义依赖
- 不在本阶段处理断线重连

## 核心设计

### 1. `FrameIndex` 语义统一

重构后：

- 客户端本地逻辑帧号就是全局逻辑帧号
- 服务端 `LastFrameIndex` 也是同一套全局逻辑帧号
- `C2B_PlayerInput.FrameIndex` 表示“这份输入属于哪一帧”
- `S2C_FrameSnapshot.FrameIndex` 表示“这份权威状态是第几帧的结果”

主线里不再出现“本地帧 L 对应预测服务端帧 S”的二次映射。

### 2. 客户端加入时显式对齐本地逻辑帧

为了真正进入同一坐标系，客户端加入战斗后需要对齐自己的逻辑帧：

```text
currentLocalFrame = joinResponse.ServerFrameIndex + initialLeadFrames
```

因此需要给 `TickDispatcher` / `ClientTickDriver` 增加显式帧对齐能力，而不是继续依赖 `_serverFrameOffset`。

### 3. `leadFrames` 的新语义

`leadFrames` 保留，但只表示：

```text
客户端目标预测领先量 = 本地已执行帧 - 最新权威帧
```

推荐公式：

```text
leadFrames = jitterBufferFrames + ceil(rttEmaMs / 2 / fixedDtMs)
```

在本阶段可以先用：

- `jitterBufferFrames = 1`
- `MaxLeadFrames = 8`

收到快照 `Frame S` 后，客户端的目标本地帧为：

```text
targetLocalFrame = S + leadFrames
```

若当前本地帧落后于该值，则通过现有 `TickOnce()` 追上。

### 4. 服务端输入模型

服务端从“窗口拒绝”切换到“未来输入缓冲”：

- `frameIndex <= LastFrameIndex`：过期输入，直接丢弃
- `frameIndex > LastFrameIndex + MaxFutureInputFrames`：未来过远，拒绝
- 其他情况：写入该玩家的未来输入缓冲

服务端推进到 `Frame N` 时：

- 若该玩家存在 `Frame N` 输入，则消费它，并更新“上一帧已消费输入”
- 若该玩家不存在 `Frame N` 输入，则复用“上一帧已消费输入”

这样服务端不会因单帧缺失而停顿，也不再依赖对称 `±10` 窗口。

### 5. `InputSeq` 的过渡策略

本阶段不强制删掉协议字段 `InputSeq`，但口径调整为：

- 同帧出现多份输入时，可继续用 `InputSeq` 判断取最新一份
- 不再把 `InputSeq` 当作“因为帧号不连续，所以必须额外保序”的主前提

这能减少协议抖动，也方便后续是否彻底移除再做决定。

## 实现步骤

### Step 1：为客户端 Tick 系统增加帧对齐能力

修改 `TickDispatcher` / `ClientTickDriver`：

- 新增显式设置当前逻辑帧的方法，例如 `SetCurrentFrame(uint frame)` 或 `AlignToFrame(uint frame)`
- `JoinBattle` 成功后，将客户端当前逻辑帧对齐到 `ServerFrameIndex + initialLeadFrames`

要求：

- 不能通过 `_serverFrameOffset` 间接模拟对齐
- 对齐后 `Dispatcher.CurrentFrame` 本身就应处于全局帧坐标系

### Step 2：重构 BattleSimulation 的帧号主路径

修改 [BattleSimulation.cs](/D:/unity/Tencent/TEngine/UnityProject/Assets/GameScripts/HotFix/GameLogic/Battle/BattleSimulation.cs:1)：

- 删除 `_serverFrameOffset`
- 删除 `ToPredictedServerFrame()`
- 删除 `GetSendFrame()`
- `Tick(frameIndex, fixedDt, dx, dy)` 中直接把 `frameIndex` 当作输入所属帧
- `_selfPredictions`、`_inputHistory`、一致性检查全部直接用全局帧号索引

保留：

- `_leadFrames`
- `ProcessPong()`
- `_lastAppliedFrame`
- `_lastPredictedFrame`
- `AdvancePredictionTo()`

但这些字段的含义要围绕“预测领先量”重定义，不再围绕“帧号偏移映射”。

### Step 3：重构快照应用后的追帧目标

修改 `ApplyPendingServerSnapshot()` 与 `TickResult` 语义：

- 快照应用后不再更新 `_serverFrameOffset`
- 只计算 `targetLocalFrame = snapshot.FrameIndex + leadFrames`
- 若当前本地逻辑帧落后，则返回 `catchUpFrames = targetLocalFrame - currentLocalFrame`
- `BattleClientController` 继续通过 `_tickDriver.SetTargetFrame()` 驱动追帧

### Step 4：重构服务端 BattleLogic 输入处理

修改 [BattleLogic.cs](/D:/unity/Tencent/TEngine/GameServer/Server/Entity/Battle/BattleLogic.cs:1)：

- 删除 `MaxFrameWindow`
- 删除 `EnableHardReject`
- 删除接受/拒绝窗口统计主逻辑
- 新增 `MaxFutureInputFrames`
- 新增“上一帧已消费输入”缓存，例如 `LastConsumedInputByPlayerId`

`SubmitInput()` 新规则：

- `frameIndex <= LastFrameIndex`：丢弃
- `frameIndex > LastFrameIndex + MaxFutureInputFrames`：拒绝
- 其他：写入 `_pendingInputsByPlayerId[playerId][frameIndex]`

`Tick(frameIndex, fixedDt)` 新规则：

- 先尝试读取 `frameIndex` 对应输入
- 若读取不到，则使用上一帧已消费输入
- 若玩家从未提交过输入，则使用零输入

### Step 5：更新客户端控制器与协议使用方式

修改 [BattleClientController.cs](/D:/unity/Tencent/TEngine/UnityProject/Assets/GameScripts/HotFix/GameLogic/Battle/BattleClientController.cs:1)：

- `JoinBattleAsync()` 中在 `SetJoined()` 之外补上本地帧对齐调用
- `SendInputCommand()` 继续发送 `C2B_PlayerInput`，但 `FrameIndex` 直接使用当前全局逻辑帧
- `OnSnapshotMessage()` / `OnPongMessage()` 仍保留现有 Fantasy 适配职责

### Step 6：补充和改写自测

运行时自测至少覆盖：

1. **join-aligns-global-frame**
   客户端加入后，本地逻辑帧应对齐到 `serverFrame + initialLeadFrames`

2. **frame-index-is-global**
   `BattleSimulation.Tick(frameIndex, ...)` 发送的输入帧号就是 `frameIndex` 本身

3. **expired-input-is-dropped**
   服务端收到 `frameIndex <= LastFrameIndex` 的输入时直接丢弃

4. **future-input-is-buffered**
   服务端能缓存有限未来窗口内的输入

5. **missing-input-reuses-last**
   服务端缺少某帧输入时复用上一帧已消费输入推进

6. **catchup-target-is-auth-plus-lead**
   客户端收到快照后，追帧目标由 `snapshot.FrameIndex + leadFrames` 决定

7. **prediction-buffer-uses-global-frame**
   `_selfPredictions` 和 `_inputHistory` 直接按全局帧号索引

## 确定性约束

- 仿真 dt 仍固定为 `33.333ms`
- 追帧只增加单渲染帧内执行的 Tick 次数，不允许改 dt
- 缺帧复用“上一帧输入”只改变输入来源，不改变 `MoveSystem.Apply` 的确定性路径
- 全局帧号统一后，预测、快照、回滚、追帧都在同一帧坐标系下工作
