🔢 帧号模型：全局帧号 + 服务端权威

客户端和服务端共享同一个递增的 FrameIndex 坐标系。客户端不维护自己的帧号，而是维护 leadFrames（领先帧数）。

为什么废弃旧方案？ v0.2a 的"客户端预测帧号 + _serverFrameOffset"方案，需要维护客户端与服务端的帧号偏移量，在网络抖动时偏移量的同步本身就成了新问题。全局帧号方案让双方始终在同一个坐标系里，用 leadFrames 控制预测距离，简洁且可靠。

📸 快照系统

快照是整个回滚机制的基石，设计为不可变值对象。

快照接口

ISnapshotable<T>
  • TakeSnapshot() → T — 拍摄不可变快照
  • RestoreSnapshot(T) — 从快照恢复状态
BattleWorldState
  • 持有 Dictionary<long, PlayerState>
  • 持有 IPhysicsMovementWorld
  • TakeSnapshot 同时拍玩家 + 物理快照
  • RestoreSnapshot 同时恢复双方

基础设施

SnapshotBuffer<T>
滑动窗口缓冲，容量上限 + 自动驱逐最老快照。客户端用它保存权威快照历史（容量 32）和预测记录。
StateHasher
FNV-1a 64-bit 哈希。对玩家位置 + 物理刚体 + 碰撞状态计算。特别处理了 -0.0f == +0.0f 和 NaN 归一化。
确定性规则
DeterminismRules：FixedDeltaTime = 1/30，MoveSpeed = 5.0，通过 BitConverter 逐位比较 dt。

IPhysicsMovementWorld
继承 IPhysicsSnapshotProvider，定义完整物理操作接口：
  • ClearBodies / EnsureBody / RemoveBody — 刚体管理
  • SetBodyTransform — 设置位置（可选重置速度）
  • SetBodyMovementInput — 设置移动输入
  • Step — 推进物理世界一步
  • TakeSnapshot / RestoreSnapshot — 快照/恢复
FrameSyncPhysicsWorld
Box2DSharp World 封装实现：
  • 每个玩家 = 圆形刚体（密度 1.0）
  • FixedRotation = true, GravityScale = 0, AllowSleep = false, Bullet = true
  • Step() 先批量应用 pending 速度请求再模拟
  • ContactListener 跟踪碰撞对

物理已接入主流程：服务端 BattleLogic 每帧先 SetBodyMovementInput，再统一 Step，然后 SyncPlayerStatesFromPhysics 回写位置。客户端预测路径也通过物理世界驱动移动。

🛡 服务端输入校验

服务端对输入做了多层防御，防止异常输入污染权威状态。

1
拒绝过期输入：帧号 ≤ 已处理帧号的输入直接丢弃，计入 LateInputDropCount
2
拒绝过远未来输入：帧号 > 当前帧 + MaxFutureInputFrames 的输入丢弃，计入 FutureInputRejectCount
3
同帧去重：同一帧号多个输入用 inputSeq 环形序列号比较，保留较新的
4
边沿检测：只在输入实际变化时打日志，减少噪音
5
缺帧复用：某玩家本帧无输入时复用上一帧，再没有则零输入，保证不阻塞
