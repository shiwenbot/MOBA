# 状态帧同步-v0.5a计划：Buff 系统同步

## Context

`v0.4b` 已将属性（Health / MaxHealth / Mana / MaxMana / Attack）纳入统一快照、哈希与脏同步链路。当前主线路径具备：

- 服务端 30Hz 权威推进，属性脏同步已通
- 客户端预测自己，权威快照校正 + 回滚重播
- `PlayerStateSnapshot` 已包含 `ActiveBuffs` 和 `NextRuntimeBuffId` 字段
- `BuffSystem` 本身功能完整（叠加/刷新/互斥/数值修正）
- `OuterMessage.proto` 已定义 `BuffSnapshot` 消息，`PlayerSnapshot` 已包含 `repeated BuffSnapshot`
- 服务端广播已将 Buff 列表塞入快照

**但存在以下缺口**：

1. **客户端未应用 Buff 快照**：服务端每帧广播了 `ActiveBuffs`，但客户端 `BattleClientController` / `BattleSimulation` 收到快照后，没有将 Buff 状态写入本地 `PlayerState`，导致客户端本地 Buff 状态与服务端权威快照脱节。
2. **回滚时 Buff 状态不完整**：`RestoreSnapshot` 能恢复属性，但客户端预测路径中 Buff 的 Tick/Remove 逻辑没有纳入"预测帧 → 权威帧"的校正。
3. **全量广播、无脏裁剪**：每帧把所有玩家的所有 Buff 完整下发，即使没有任何 Buff 变化。对于 MOBA 场景（10 人，每人可能 0~5 个 Buff），这是带宽浪费。

因此 `v0.5a` 的核心目标是：**让 Buff 状态在"服务端权威 → 网络传输 → 客户端接收 → 回滚恢复"这条闭环中跑通并验证**。

## 阶段状态

- 状态：`已完成`
- 完成时间：`2026-05-24`
- 前置依赖：`v0.4b` 已完成

### 实际落地说明

- 实现时确认：`StateHasher` 对 `ActiveBuffs` / `NextRuntimeBuffId` 的哈希覆盖，以及客户端 `restore → replay` 主链路，已在 `v0.4b` 代码中具备。
- 因此 `v0.5a` 的实际新增重点集中在：`BuffDirtyFlags` / `BuffSync`、服务端按 `(observer, target)` 维度维护 Buff 广播基线、客户端 Buff 基线缓存与 delta 合并、协议字段补齐。

---

## 目标

1. 客户端收到权威快照后，正确将 Buff 状态写入本地 `PlayerState`，使本地 Buff 状态与权威快照一致。
2. Buff 状态进入客户端预测/回滚链路：回滚到历史帧时，Buff 状态随属性一起恢复。
3. 实现 Buff 脏同步：服务端只下发有变化的 Buff（新增/移除/层数变化/剩余帧变化），客户端用脏字段合并出完整 Buff 列表。
4. Buff 状态纳入 `StateHasher`，确保双端哈希一致性校验能覆盖 Buff。

## 非目标

- 本阶段不实现 Buff 的新类型（DoT / HoT / Aura / Shield 等），只确保现有 Buff 类型在同步链路中正确。
- 本阶段不做 Buff 的客户端预测（客户端预测自己释放的 Buff 效果），所有 Buff 走权威快照。
- 本阶段不做细粒度带宽统计面板。
- 本阶段不改动 BuffSystem 内部逻辑（叠加/互斥/数值修正）。

---

## 设计约束

1. **快照始终保存完整 Buff 列表**
   `BattleWorldSnapshot` 中每个玩家的 `ActiveBuffs` 必须是完整列表，保证回滚和哈希不依赖"上一包缓存"。

2. **脏同步只在传输层**
   服务端广播时可以只下发增量；服务端内部、快照、哈希仍基于完整 Buff 列表。

3. **首包必须全量；基线按观察者维护**
   - 某玩家第一次被客户端观察到时，必须下发其完整 Buff 列表。
   - 广播基线必须按 **（observer 连接, target 玩家）** 维度存储，而非只按 target 玩家维度。原因：A 客户端可能已观察 target 多帧有稳定基线，B 客户端刚进入视野时没有基线，此时发给 B 的必须是全量而非 delta。
   - 触发强制全量的条件：
     - 新观察者首次见到 target
     - 断线重连后的第一个包
     - 服务端检测到 observer 基线失效（如 observer 长时间未收到某 target 的包）

4. **Buff 变更与属性变更共享同一帧语义**
   同一逻辑帧内，Buff 的添加/移除/层数变化是该帧权威结果的一部分，和属性一起进入快照。

5. **增量包必须携带帧号，客户端校验基线版本**
   - 每个增量 `PlayerSnapshot` 必须携带 `SnapshotFrameIndex`，标识"这份 delta 是基于哪一帧的全量状态算出来的"。
   - 客户端收到增量包后，先校验本地基线的帧号与服务端 delta 的基准帧是否对齐。若不对齐（补包、跳帧、观战切换等），客户端必须丢弃增量，请求或等待下一次全量。
   - 这保证 `Merge` 不会在基线错配时静默产出脏数据。

6. **Buff 不走客户端预测**
   当前阶段，所有 Buff 状态走权威快照路径。客户端只应用权威结果，不主动预测 Buff 变化。后续如需预测（如本地释放 Buff 的即时反馈），需单独补齐命令语义和回滚依据。

## 实现步骤

### Step 0：StateHasher 补齐 Buff

- 在 `StateHasher` 中追加 Buff 字段的哈希计算
- 按固定顺序遍历 `ActiveBuffs`（按 RuntimeBuffId 排序），逐字段喂入哈希
- 确保 `NextRuntimeBuffId` 也参与哈希

预期结果：
- 哈希一致性校验能发现 Buff 不一致
- 现有自动测试（属性同步相关）不会因 Buff 哈希变化而误报

### Step 1：客户端 Buff 走权威快照 → restore → replay 链路

**核心原则**：Buff 必须和属性走同一条"写入权威帧的历史快照 → 回滚重播"链路，不能直接覆盖当前渲染态。

- 客户端收到权威快照后，将 Buff 状态写入**该权威帧对应的 `PlayerStateSnapshot`**（即 `SnapshotBuffer` 中对应帧的历史快照），而不是直接写当前态的 `PlayerState`。
- 写入方式：用权威 Buff 列表覆盖该帧快照中的 `ActiveBuffs` 和 `NextRuntimeBuffId`。
- 后续走现有 `BattleSimulation` 的 restore → replay 流程：
  1. 从写入权威 Buff 的那一帧开始 `RestoreSnapshot`
  2. 逐帧 replay 到当前预测帧，期间 `BuffSystem.ApplyTick` 会正常执行
  3. replay 结束后，Buff 状态自然与权威对齐
- 这保证：如果权威帧早于当前预测帧，中间帧的 Buff Tick 逻辑不会被跳过；属性和 Buff 始终处于同一帧语义。

预期结果：
- Buff 状态通过 restore → replay 链路与属性同步恢复，不会出现"位置回去了、Buff 没回去"
- 权威帧之后的预测帧中 Buff Tick 正常重播

### Step 2：Buff 脏标记模型

- 新增 `BuffDirtyFlags`（枚举或位掩码），标记单个 Buff 的变更类型：
  - `Added` — 本帧新增的 Buff
  - `Removed` — 本帧移除的 Buff
  - `Updated` — 已有 Buff 的任一字段发生变化（StackCount / RemainingFrames / Flags / 其他），采用"全量重发该 Buff"策略
  - 不细分到具体字段（如 StackChanged / DurationChanged），原因是 Buff 字段较少且单个 Buff 数据量小，细分收益不大，反而增加合并端复杂度和遗漏风险（如 `Flags` 变化被漏掉）。
- 新增 `PlayerBuffDirtyMask`，标记某玩家的 Buff 列表整体是否有变化（`HasAnyChange`）
- 新增 `BuffSync` 工具类：
  - `ComputeDirtyMask`：对比上帧与当前帧的 Buff 列表，生成脏标记
  - `Merge`：客户端用脏标记 + 增量数据合并出完整 Buff 列表

预期结果：
- 脏标记计算逻辑可单元测试
- 增量合并逻辑可单元测试

### Step 3：服务端 Buff 增量广播

- 服务端按 **（observer 连接, target 玩家）** 维护广播基线：`Dictionary<(long observerId, long targetId), BuffBroadcastBaseline>`
- 每帧对每个 observer-target 对：对比 target 当前的 Buff 列表与该 observer 的基线，生成脏标记
- 仅当有脏位时才在 `PlayerSnapshot` 中填充 Buff 数据；无变化时 ActiveBuffs 为空列表 + dirtyMask = 0
- 每个增量包必须携带 `SnapshotFrameIndex`（即基线对应的帧号），供客户端校验
- 强制全量的条件：
  - 新观察者首次见到 target（基线不存在）
  - 断线重连后首个包（基线可能过期）
  - 观察者长时间未收到某 target 的包（基线失效）
- 观察者离开或 target 离开时，清理对应的基线缓存

预期结果：
- 无 Buff 变化时，网络包中 Buff 部分为空
- 有 Buff 变化时，只传输变化的 Buff
- 不同观察者对同一 target 可以有不同的增量状态

### Step 4：客户端 Buff 增量合并

- 客户端按 target 玩家维护"权威 Buff 基线"（最近一次收到的完整/合并后的 Buff 列表 + 基线帧号）
- 收到 `PlayerSnapshot` 后的合并流程：
  1. **校验基线帧号**：比对本地基线帧号与包中的 `SnapshotFrameIndex`。若不匹配（基线过期、丢包、观战切换等），丢弃增量，将本帧标记为"等待全量"，客户端可主动请求或等待服务端下一次全量广播。
  2. `dirtyMask = 0`：基线帧号匹配且无变化，保留基线，不做任何操作。
  3. `dirtyMask != 0`：基线帧号匹配，按脏标记合并增量数据，更新基线。
  4. 收到全量包时（`isFullSync = true` 或基线不存在）：直接替换基线，无需合并。
- 合并后的完整 Buff 列表按 Step 1 的流程写入权威帧快照，走 restore → replay

预期结果：
- 增量同步对回滚逻辑透明（回滚仍基于完整快照）
- 基线错配时不会静默产出脏数据
- 网络带宽节省可测量

### Step 5：补验证

- 共享自测新增：
  - Buff round-trip（完整 Buff 列表的快照 → 恢复 → 对比）
  - Buff 哈希（相同 Buff 列表 → 相同哈希）
  - Buff 脏标记计算 + 增量合并
- 预测自测新增：
  - 权威快照恢复后 Buff 状态正确
  - 回滚后 Buff 状态正确
- 无头测试继续走现有 `prediction-self` / `all`
