# 状态帧同步-v0.3-arch：逻辑/渲染分离重构

## Context

v0.3a 完成后，帧同步系统约 85% 的代码已经是纯逻辑（GameShared/FrameSync/ 下 ~700 行）。唯一的混合点是 `BattleClientController`（416 行），它同时承担了四种职责：

1. **输入采集**（Unity）：`Input.GetKey()`、`Vector2`
2. **逻辑驱动**（纯逻辑）：快照入队/应用、帧预测、RTT/leadFrames 计算
3. **网络发送**（Fantasy）：`GameClient.Instance.Send()`
4. **渲染同步**（Unity）：`GameObject.CreatePrimitive()`、`transform.position`

这导致无法脱离 Unity 测试战斗逻辑。下一步 v0.3b（本地预测）和 v0.3c（回滚重播）的核心逻辑也将写在这一层，如果不先拆分，混合程度只会更高。

**前置依赖**：v0.3a（已完成）

---

## 阶段状态

- 状态：`已完成`
- 更新日期：`2026-04-28`

## 目标

- 将 `BattleClientController` 的纯逻辑部分提取为 `BattleSimulation`，零 Unity 依赖
- `BattleClientController` 瘦身为 Unity 适配层（输入采集 + 渲染同步 + 网络桥接）
- 所有 `Mathf` 调用替换为 `Math`，`Vector2` 替换为 `(float, float)`
- v0.3b/c 的预测/回滚逻辑将写在 `BattleSimulation` 中，天然可测试

---

## 非目标

- 不改变 `ClientTickDriver` 的 MonoBehaviour 结构（Unity 耦合已经很轻，仅 `Time.deltaTime`）
- 不改变网络协议或服务端逻辑
- 不实现新功能（预测/回滚是 v0.3b/c）
- 不创建新的程序集（`BattleSimulation` 仍在 GameLogic 程序集中，但无 `using UnityEngine`）

## 核心设计

### 职责边界

```
BattleSimulation (纯逻辑，被 Controller 调用，不实现 ITickable)
├── EnqueueServerSnapshot(BattleWorldSnapshot)       ← 入队，内部负责旧帧过滤
├── ProcessPong(long rttMs)                          ← RTT EMA + leadFrames 计算
├── Tick(frameIndex, fixedDt, dx, dy) → TickResult   ← 应用快照 + 构建输入命令
├── SetJoined(playerId, serverFrame, localFrame, x, y) ← Join 成功后初始化（含初始位置）
├── RollBack(uint targetFrame)                       ← 委托入口，v0.3c 实现
└── 状态属性：LeadFrames, LastAppliedFrame, IsJoined, ServerFrameOffset...

BattleClientController (Unity 适配层，MonoBehaviour，实现 ITickable)
├── Initialize() / DisposeController()           ← 生命周期
├── JoinBattleAsync()                            ← 网络连接 + 调用 simulation.SetJoined()
├── Update() 中读取 Input → 缓存 dx/dy           ← 输入采集
├── OnSnapshotMessage() → ConvertSnapshot() → simulation.EnqueueServerSnapshot()
├── OnPongMessage() → 计算 rttMs → simulation.ProcessPong()
├── Tick() → simulation.Tick(dx, dy) → SyncRendering() + 追帧控制
├── RollBack() → _simulation.RollBack()          ← ITickable 委托
├── SyncRendering()                              ← 读 WorldState → 更新 GameObjects
└── GetOrCreateCapsule() / ToWorldPosition()     ← 渲染工具
```

**设计决策：BattleSimulation 不实现 ITickable**

`ITickable.Tick(uint frameIndex, float fixedDt)` 签名没有输入参数，与 `BattleSimulation.Tick(frameIndex, fixedDt, dx, dy)` 不兼容。强行实现会导致：
- 方案 a：把输入缓存放进 BattleSimulation → 破坏"纯逻辑层不知道输入来源"的原则
- 方案 b：用 `SetInput(dx, dy)` 在 Tick 前注入 → 引入隐式时序依赖

因此 `BattleClientController` 继续作为 `ITickable` 注册到 `TickDispatcher`，在其 `Tick()` 中将缓存的输入传给 `_simulation.Tick()`。`BattleSimulation` 的 Tick 签名可以随需求自由扩展（如 v0.3b 加入技能输入），不受 `ITickable` 接口约束。

回滚调用链：`TickDispatcher → BattleClientController.RollBack() → _simulation.RollBack()`，保持分层一致性。

### 网络发送抽象

`BattleSimulation` 通过回调输出网络指令，不直接依赖 Fantasy：

```
构造函数注入：
  Action<uint frameIndex, uint inputSeq, float dx, float dy> onSendInput
  Action<ulong sendTimestampMs> onSendPing
  IFrameSyncLogger logger          ← 日志注入，复用已有接口

BattleClientController 在构造 BattleSimulation 时绑定：
  onSendInput = (frame, seq, dx, dy) => GameClient.Instance.Send(new C2B_PlayerInput {...})
  onSendPing = (ts) => GameClient.Instance.Send(new C2B_Ping {...})
  logger = ClientTickDriver 中已有的 UnityFrameSyncLogger 实例
```

回调在构造函数中校验非空。测试时可传空 lambda `(_, _, _, _) => {}` 或 null logger。

### WorldState 所有权

`BattleWorldState` 由 `ClientTickDriver` 创建并持有（现状不变）。`BattleSimulation` 通过构造函数接收引用，只读写不拥有。

写入顺序（同一 Tick 内）：
1. `BattleClientController.Tick()` → `_simulation.Tick()` → 应用服务端快照到 WorldState
2. `SnapshotManager.Tick()`（Priority = int.MaxValue）→ 对 WorldState 做 TakeSnapshot

**快照语义**：`SnapshotManager` 保存的是**应用服务端权威状态后**的快照。当前阶段（无本地预测）这就是最终状态。v0.3b 引入本地预测后，快照将变为"应用权威状态 + 本地预测执行后"的混合状态，v0.3c 回滚时需据此区分。

### 状态分类：确定性 vs 元数据

`BattleSimulation` 中的字段分为两类：

**仿真状态**（参与确定性，回滚时需要恢复）：
- `WorldState` 中的玩家数据（通过 SnapshotManager 管理）
- `_lastAppliedFrame`、`_serverFrameOffset`、`_lastSentFrameIndex`、`_inputSeq`

**元数据**（不参与确定性，回滚时不恢复）：
- `_rttEmaMs`、`_leadFrames`、`_hasRttSample`、`_pingCount`
- `DateTimeOffset.UtcNow` 调用（仅用于 RTT 测量）

这个分类对 v0.3c 回滚时"哪些状态需要回退"至关重要。

### 渲染同步策略

不引入事件系统，采用**轮询模式**：

- `BattleSimulation.Tick()` 返回 `TickResult`（轻量 struct，零 GC）
- `BattleClientController` 根据 `TickResult.SnapshotApplied` 决定是否刷新 GameObjects
- 刷新时直接从 `WorldState` 读取所有玩家数据，不通过 TickResult 传递玩家列表
- 追帧控制：Controller 读取 `TickResult.CatchUpFrames`，调用 `_tickDriver.SetTargetFrame()`

## 实现步骤

### Step 1：新建 BattleSimulation

路径：`GameLogic/Battle/BattleSimulation.cs`

从 `BattleClientController` 迁移以下内容：

**常量**：`PingIntervalFrames`、`InitialRttEmaMs`、`RttEmaAlpha`、`MaxLeadFrames`、`FixedDeltaMilliseconds`

**状态字段**：`_isJoined`、`_selfPlayerId`、`_inputSeq`、`_lastAppliedFrame`、`_lastSentFrameIndex`、`_serverFrameOffset`、`_leadFrames`、`_rttEmaMs`、`_hasRttSample`、`_pingCount`、`_hasPendingServerSnapshot`、`_pendingServerSnapshot`

**方法**（改造后迁移）：
- `Tick(frameIndex, fixedDt, dx, dy)` → 不再调用 `ReadKeyboardDirection()`，接收参数
- `ApplyPendingServerSnapshot()` → 只更新 `WorldState`，返回变更标记
- `ProcessPong(long rttMs)` → RTT EMA 计算，用 `Math.Ceiling` 和 `Math.Clamp`
- `SendPingIfNeeded()` → 通过 `_onSendPing` 回调发送
- `ToPredictedServerFrame()`
- `SetJoined(playerId, serverFrame, localFrame, x, y)` → 初始化状态 + WorldState 中添加自身玩家

**留在 BattleClientController 中的方法**（涉及 Fantasy 类型转换）：
- `ConvertSnapshot(S2C_FrameSnapshot)` → Fantasy 类型到 `BattleWorldSnapshot` 的桥梁，转换后调用 `simulation.EnqueueServerSnapshot()`
- `PlayerSnapshotComparer` → `ConvertSnapshot` 内部使用，一并保留

**关键改造点**：
- `Mathf.CeilToInt(x)` → `(int)Math.Ceiling(x)`（返回类型 double → 需显式转 int）
- `Mathf.Clamp(v, min, max)` → `Math.Clamp(v, min, max)`
- `Vector2 direction` → `(float dx, float dy)` 参数
- 输入归一化（`sqrMagnitude > 1 → Normalize`）→ `MathF.Sqrt` 纯逻辑实现
- 网络发送 → 回调委托

### Step 2：定义 TickResult

```
readonly struct TickResult
  bool SnapshotApplied          // 本帧是否应用了服务端快照
  uint LastAppliedFrame         // 最新应用的帧号
  int CatchUpFrames             // 追帧帧数（>0 表示需要追帧，Controller 调用 SetTargetFrame）
```

不在 TickResult 中传递玩家列表（避免每帧分配 `IReadOnlyList` 引起 GC）。渲染层根据 `SnapshotApplied` 标记，直接从 `WorldState` 读取所有玩家数据刷新 GameObjects。

追帧计算（`_serverFrameOffset` 更新、`targetLocalFrame` 计算）在 `BattleSimulation.Tick()` 内部完成，结果通过 `CatchUpFrames` 输出。Controller 读取后调用 `_tickDriver.SetTargetFrame()`，保持追帧执行留在 Unity 适配层。

放在 `BattleSimulation.cs` 同文件。

### Step 3：瘦身 BattleClientController

保留 MonoBehaviour + ITickable 角色，改为：

1. **构造 BattleSimulation**：在 `EnsureTickDriver()` 之后创建，注入网络回调 + WorldState 引用 + IFrameSyncLogger
2. **输入缓存**：在 `Update()` 中读取 `Input.GetKey()` → 缓存 `_cachedDx`, `_cachedDy`（注意：Input 必须在 Unity Update 中读取，不能在 TickDispatcher 的 Tick 中读取）
3. **Tick() 简化**：调用 `_simulation.Tick(frameIndex, fixedDt, _cachedDx, _cachedDy)` → 根据 `TickResult.SnapshotApplied` 调用 `SyncRendering()` → 根据 `TickResult.CatchUpFrames` 调用 `_tickDriver.SetTargetFrame()`
4. **RollBack() 委托**：`ITickable.RollBack(targetFrame)` → `_simulation.RollBack(targetFrame)`
5. **SyncRendering()**：直接从 `WorldState` 读取所有玩家 → 更新 `transform.position` → 管理胶囊体可见性
6. **网络回调**：`OnSnapshotMessage()` 做 Fantasy 类型转换（`ConvertSnapshot` 留在此处） → `_simulation.EnqueueServerSnapshot()`；`OnPongMessage()` 计算 `rttMs` → `_simulation.ProcessPong()`
7. **JoinBattleAsync()**：连接成功后调用 `_simulation.SetJoined(playerId, serverFrame, localFrame, x, y)` + 创建自身胶囊体
8. **DisposeController()**：将 `_simulation` 置 null（让 GC 回收），不逐字段 Reset。Controller 只重置自身渲染状态（销毁 GameObjects、清空字典）

### Step 4：输入采集时机调整

当前 `ReadKeyboardDirection()` 在 `Tick()` 中调用（由 TickDispatcher 驱动），但 `Input.GetKey()` 应在 Unity `Update()` 中采集。

调整为：
- `BattleClientController.Update()` 中每帧缓存输入方向
- `BattleClientController.Tick()` 中将缓存值传给 `BattleSimulation.Tick()`

这也修复了追帧时同一渲染帧内多次 Tick 读取相同输入的语义问题（追帧时应使用同一帧采集的输入）。

### Step 5：验证

**运行时自测**（类似 v0.3a 的 SnapshotSelfTest）：

1. **纯逻辑构造测试**：构造 BattleSimulation（空 lambda 回调）→ `SetJoined()` → `EnqueueServerSnapshot()` → `Tick()` → 验证 `WorldState` 更新正确
2. **RTT 计算测试**：`ProcessPong()` 多次 → 验证 `LeadFrames` 收敛到预期范围
3. **帧预测测试**：`SetJoined()` → 验证 `ToPredictedServerFrame()` 返回正确值
4. **归一化测试**：传入 `(dx=1, dy=1)` → 验证归一化后长度 ≤ 1.0（零向量不进入归一化分支）

输出 `[ArchTest] ALL PASS` 或 `[ArchTest] FAIL: <case>`。

**中间验证点**：
- Step 1 完成后：编译通过 + 构造测试通过
- Step 3 完成后：**完整双端联调**（最关键的验证点，确认行为无回归）
- Step 4 完成后：追帧场景下输入行为验证

## 确定性约束

- `BattleSimulation` 中所有浮点运算使用 `System.Math` / `System.MathF`，不引入 `UnityEngine.Mathf`
- `Math.Ceiling` / `Math.Clamp` 与 `Mathf.CeilToInt` / `Mathf.Clamp` 语义等价（后者内部就是调用前者）
- 输入归一化逻辑从 `Vector2.Normalize()` 改为显式 `MathF.Sqrt` 实现，条件为 `sqrMag > 1.0f`（零向量不进入分支，无除零风险）
- `ConvertSnapshot` 留在 Controller 中（依赖 Fantasy 类型），`PlayerSnapshotComparer` 排序逻辑不变，确保哈希确定性
- `DateTimeOffset.UtcNow`（RTT 测量）属于元数据操作，不影响仿真确定性

## 关键风险与应对

| 风险 | 影响 | 应对 |
|------|------|------|
| Input.GetKey 在 Tick 中调用导致追帧时输入异常 | 同一渲染帧内多次 Tick 读取相同按键状态 | 改为 Update 中缓存，Tick 中使用缓存值 |
| 网络回调委托为 null 导致空引用 | 未注入回调时 Tick 崩溃 | 构造函数校验非空，或使用空操作默认值 |
| `Math.Ceiling` 返回 double 而非 int | 隐式转换精度丢失 | 显式 `(int)Math.Ceiling(x)` |
| 重构后功能回归 | 行为不一致 | Step 3 完成后立即双端联调对比验证 |
| 输入归一化零向量除零 | `MathF.Sqrt(0)` 产生 NaN | 条件为 `sqrMag > 1.0f`，零向量不进入分支（invariant） |
| v0.3c 回滚缺少历史输入 | 回滚重播时无法获取历史输入 | 本阶段在 Tick 内预留 TODO 注释，v0.3c 实现输入历史缓冲区 |

## 后续衔接

### v0.3b（本地预测）

预测核心逻辑在 `BattleSimulation.Tick()` 中：没有收到服务端快照的帧，基于 `(dx, dy)` 做本地仿真，更新 WorldState。完全在 BattleSimulation 内部完成，不影响 Controller。天然可用纯 C# 测试。

### v0.3c（回滚重播）

回滚需要历史输入缓存。本阶段在 `BattleSimulation.Tick()` 内预留：
```
// TODO v0.3c: 保存 (frameIndex, dx, dy) 到输入历史缓冲区（类似 SnapshotBuffer 设计）
```

回滚调用链：`TickDispatcher → BattleClientController.RollBack() → _simulation.RollBack()`。`BattleSimulation.RollBack()` 负责调用 `WorldState.RestoreSnapshot()`，重播时从输入历史缓冲区读取。

### 测试

未来如需 NUnit 无 Unity 测试，只需引用 GameLogic + GameShared 程序集。`BattleSimulation` 无 Unity API 调用，构造时传入空 lambda 回调即可独立运行。
