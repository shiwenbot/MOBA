# 状态帧同步-v0.2b计划：输入缓冲与超前帧控制

## 历史说明（2026-05-06）

本文记录的是旧主线下“`_serverFrameOffset` + `leadFrames` + 追帧”的实现计划与验收结果。

其中以下产物仍然有效并会继续复用：

- `C2B_Ping` / `S2C_Pong`
- RTT EMA 计算
- `TickDispatcher.TickOnce()`
- `ClientTickDriver.SetTargetFrame()`
- `MaxCatchUpTicksPerFrame`

但以下设计已经退出主线：

- 用 `_serverFrameOffset` 把本地帧映射成 `PredictedServerFrame`
- 通过 `MaxFrameWindow` 维持客户端与服务端帧号的对称窗口关系
- 将 `leadFrames` 解释为“预测服务端帧号偏移量”

当前主线请以 [状态帧同步-架构重构计划.md](/D:/unity/Tencent/TEngine/Plan/状态帧同步/状态帧同步-架构重构计划.md:1) 为准。

## Context

v0.2a 已完成帧号策略验证并锁定方案 A（客户端预测帧号 + 服务端窗口校验，`MaxFrameWindow = 10`）。v0.2a 的 `FrameDelta` 日志揭示了客户端时钟与服务端时钟的偏差趋势，但没有任何机制去主动修正这个偏差。

当前问题：
- 客户端不知道自己的网络延迟，`_serverFrameOffset` 在 Join 时一次性计算后固定不变。
- 没有追帧机制：客户端帧号落后时只能等待，无法加速追上服务端节奏。
- 没有超前帧控制：客户端应该比服务端超前 `ceil(RTT/2/dt)` 帧发送输入，才能让输入恰好在服务端执行该帧时到达。

v0.2b 在 v0.2a 的基础上补全这两个机制。

前置依赖：
- v0.2a（已完成）：帧号策略锁定，`MaxFrameWindow = 10`，`_serverFrameOffset` 基础设施。

## 目标

- 客户端通过 Ping/Pong 消息测量 RTT，用 EMA 平滑后计算超前帧数 `leadFrames`。
- 客户端动态调整 `_serverFrameOffset`，使预测帧号始终超前服务端 `leadFrames` 帧。
- 当客户端帧号落后目标帧时，单渲染帧内多次执行固定 dt Tick（追帧），每次 Tick 的 dt 恒为 33.333ms。
- 模拟 50ms / 100ms / 200ms 延迟，验证超前帧数稳定收敛，追帧行为符合预期。

## 范围

- 协议层：新增 `C2B_Ping` / `S2C_Pong` 消息，修改 `.proto` 并重新生成。
- 服务端：新增 `C2B_PingHandler`，收到 Ping 后原样回 Pong（不做任何处理）。
- 客户端 `BattleClientController`：Ping 定时发送、Pong 接收与 RTT 计算、EMA 平滑、超前帧计算、动态调整 `_serverFrameOffset`、向 `ClientTickDriver` 请求追帧。
- 客户端 `ClientTickDriver`：接收目标帧，在 `Update()` 里执行追帧 Tick。
- 共享层 `TickDispatcher`：新增 `TickOnce()` 方法，供追帧使用（不经过累加器，dt 固定为 `FixedDeltaTime`）。

## 技术决策

### 1. Ping/Pong 协议设计

`C2B_Ping` 携带客户端本地时间戳（毫秒，`uint64 SendTimestampMs`）。服务端 `C2B_PingHandler` 收到后立即构造 `S2C_Pong`，将 `SendTimestampMs` 原样写入并发回，不附加任何服务端时间戳。

客户端收到 Pong 时：`rttMs = nowMs - pong.SendTimestampMs`。

时间戳来源：`DateTimeOffset.UtcNow.ToUnixTimeMilliseconds()`，避免 `Time.realtimeSinceStartup` 的精度问题。

Ping 发送频率：每 1 秒一次（30 帧发一次 Ping，不需要更高频率）。

### 2. RTT EMA 平滑

```
rttEmaMs = alpha * rttMs + (1 - alpha) * rttEmaMs
```

- `alpha = 0.2f`（平滑系数，对突发抖动不敏感）
- 初始值：`rttEmaMs = 100f`（保守估计，避免初始超前帧过小）
- 收到第一个 Pong 后直接赋值（不做 EMA），之后才开始平滑

### 3. 超前帧计算

```
leadFrames = ceil(rttEmaMs / 2f / 33.333f)
```

- 最小值：1（至少超前 1 帧，避免输入到达时服务端已经过了该帧）
- 最大值：`MaxLeadFrames = 8`（对应 266ms 单向延迟，超过此值说明网络极差，不再增加超前）
- 每次收到 Pong 后重新计算，不需要节流（1 秒一次本身已经足够低频）

### 4. 动态调整 `_serverFrameOffset`

`_serverFrameOffset` 的语义：`predictedServerFrame = localFrame + _serverFrameOffset`。

目标：让 `predictedServerFrame` 始终等于 `serverFrame + leadFrames`，即：

```
_serverFrameOffset = (serverFrame + leadFrames) - localFrame
```

每次收到 `S2C_FrameSnapshot` 时更新：

```
_serverFrameOffset = snapshot.FrameIndex + leadFrames - currentLocalFrame
```

**不做渐进调整**：直接覆盖。理由：v0.2b 阶段目标是观测收敛行为，渐进调整会掩盖真实的收敛速度。v0.3x 引入预测回滚后再考虑平滑调整。

### 5. 追帧机制

**触发条件**：`currentLocalFrame < targetLocalFrame`，其中：

```
targetLocalFrame = snapshot.FrameIndex + leadFrames - _serverFrameOffset
                 = currentLocalFrame（理想情况，offset 已调整）
```

实际上，offset 调整后 `targetLocalFrame ≈ currentLocalFrame`，追帧主要发生在：
- 刚 Join 时本地帧号落后
- 网络抖动导致 Snapshot 延迟到达，offset 突然变大

**追帧实现**：

`TickDispatcher` 新增 `TickOnce()` 方法：直接执行一次 Tick（`_currentFrame` 递增，dt = `FixedDeltaTime`），不经过 `_tickAccumulator`。

`ClientTickDriver` 新增 `SetTargetFrame(uint targetFrame)` 方法，在 `Update()` 里：
1. 先正常调用 `_dispatcher.Update(Time.deltaTime)`（正常 Tick）
2. 计算 `catchUpCount = min(targetFrame - CurrentFrame, MaxCatchUpTicksPerFrame)`
3. 循环调用 `_dispatcher.TickOnce()` 共 `catchUpCount` 次

**追帧上限**：`MaxCatchUpTicksPerFrame = 8`（单渲染帧最多追 8 帧，约 266ms，防止卡顿）。

**确定性硬约束**：`TickOnce()` 内部使用 `_tickAccumulator.FixedDeltaTime`（33.333ms），绝不传入动态 dt。

### 6. 验收日志

每 300 帧（约 10 秒）输出一次：

- `[PingStats]`：RTT 原始值 / EMA 值 / leadFrames
- `[CatchUp]`：本渲染帧追帧次数（每次追帧时实时输出，不等 300 帧）
- `[FrameOffset]`：当前 `_serverFrameOffset` / `targetLocalFrame` / `currentLocalFrame`

追帧时的 dt 断言：在 `TickOnce()` 内部调用 `DeterminismRules.AssertFixedDt(fixedDt)`，确保 dt 恒为 33.333ms。

## 实现步骤

### Step 1：扩展协议

修改 `GameServer/Tools/NetworkProtocol/Outer/OuterMessage.proto`，在 `S2C_FrameSnapshot` 之后追加：

```proto
// 客户端 Ping（单向消息，用于 RTT 测量）
message C2B_Ping // IMessage
{
    uint64 SendTimestampMs = 1;
}

// 服务端 Pong（原样回传时间戳）
message S2C_Pong // IMessage
{
    uint64 SendTimestampMs = 1;
}
```

运行 `GameServer/Tools/ProtocolExportTool/Run.bat` 重新生成 `OuterMessage.cs` / `OuterOpcode.cs`（服务端和客户端各一份）。

### Step 2：服务端 PingHandler

新建 `GameServer/Server/Hotfix/Battle/Handler/C2B_PingHandler.cs`：

收到 `C2B_Ping` 后，直接构造 `S2C_Pong`（`SendTimestampMs` 原样回传），通过 `session.Send()` 发回。不做任何帧号或状态处理。

### Step 3：TickDispatcher 新增 TickOnce()

修改 `TickDispatcher.cs`，新增 `public void TickOnce()` 方法：

- 执行一次完整的 Tick 循环（遍历 `_entries`，调用每个 `ITickable.Tick(_currentFrame, FixedDeltaTime)`）
- `_currentFrame++`
- 处理 `_pendingOperations`
- 不调用 `_tickAccumulator`

注意：`_isTicking` 标志需要正确设置/清除，与 `Update()` 内的 Tick 循环保持一致。

### Step 4：ClientTickDriver 新增追帧支持

修改 `ClientTickDriver.cs`：

- 新增 `private uint _targetFrame` 字段（默认 0）
- 新增 `public void SetTargetFrame(uint targetFrame)` 方法
- 在 `Update()` 末尾，正常 Tick 之后，计算 `catchUpCount` 并循环调用 `_dispatcher.TickOnce()`
- 每次追帧时输出 Debug 日志（帧号 + 追帧次数）

### Step 5：BattleClientController 集成 Ping 与超前帧

修改 `BattleClientController.cs`：

**新增字段**：
- `_pingIntervalFrames = 30`（每 30 帧发一次 Ping）
- `_rttEmaMs = 100f`（初始值）
- `_leadFrames = 1`（初始值）
- `_pingCount`（计数器，用于控制发送频率）
- `_pongHandler`（消息处理器引用，用于注销）

**新增字段（补充）**：
- `_lastSentFrameIndex`（uint，初始 0）：记录上一次发送的输入帧号，用于单调保护

**Tick() 里**：每 `_pingIntervalFrames` 帧发一次 `C2B_Ping`（`SendTimestampMs = DateTimeOffset.UtcNow.ToUnixTimeMilliseconds()`）。

发送输入时强制单调：
```
uint predictedFrame = ToPredictedServerFrame(frameIndex);
uint sendFrame = Math.Max(_lastSentFrameIndex + 1, predictedFrame);
_lastSentFrameIndex = sendFrame;
// 用 sendFrame 替代 predictedServerFrame 填入 C2B_PlayerInput.FrameIndex
```

**注册 Pong 处理器**（在 `RegisterSnapshotHandler()` 里一并注册）：
- 收到 `S2C_Pong` 时计算 RTT，更新 EMA，重新计算 `_leadFrames`

**OnSnapshotMessage() 里**：
- 更新 `_serverFrameOffset = snapshot.FrameIndex + _leadFrames - currentLocalFrame`
- 计算 `targetLocalFrame = currentLocalFrame + (snapshot.FrameIndex + _leadFrames - predictedServerFrame)`
- 调用 `_tickDriver.SetTargetFrame(targetLocalFrame)`

**DisposeController() 里**：注销 Pong 处理器。

### Step 6：验收运行

- 启动服务端（端口 20101）
- ParrelSync 双 Editor 运行，各自连接服务端
- 观察日志：
  - `[PingStats]`：RTT EMA 稳定，`leadFrames` 收敛（局域网预期 1-2 帧）
  - `[CatchUp]`：追帧只在启动初期出现，稳定后消失
  - `[FrameOffset]`：`_serverFrameOffset` 稳定，无持续漂移
  - 无 `DeterminismRules.AssertFixedDt` 断言触发

## 确定性验证

- `TickOnce()` 使用 `FixedDeltaTime`（33.333ms），`DeterminismRules.AssertFixedDt` 在每次 Tick 内断言，追帧过程中不触发。
- 追帧不改变仿真 dt，只改变单渲染帧内的 Tick 次数，不影响 `MoveSystem` 的确定性。
- `_serverFrameOffset` 调整只影响"发送哪个帧号"，不影响服务端执行逻辑。

## 关键风险与应对

| 风险 | 影响 | 应对 |
|------|------|------|
| `_serverFrameOffset` 直接覆盖导致帧号跳变 | 服务端窗口校验触发拒绝 | 观察拒绝率日志；若拒绝率升高，v0.2b 后期可改为渐进调整（每帧 ±1） |
| 追帧时 `TickOnce()` 与 `Update()` 的 `_isTicking` 状态冲突 | 注册/注销操作丢失 | `TickOnce()` 复用 `_isTicking` 标志，确保 `ApplyPendingOperations()` 在每次 TickOnce 后执行 |
| Ping 时间戳用 `Time.realtimeSinceStartup` 精度不足 | RTT 计算误差大 | 使用 `DateTimeOffset.UtcNow.ToUnixTimeMilliseconds()`，精度 1ms |
| 局域网 RTT 极低（< 1ms），`leadFrames` 始终为 1 | 无法验证高延迟场景 | 用 Windows 自带 `tc`（或 Clumsy 工具）模拟 50/100/200ms 延迟进行验收 |
| 追帧过多导致单帧耗时超过 16ms | 渲染卡顿 | `MaxCatchUpTicksPerFrame = 8` 硬上限；追帧日志记录实际追帧次数，便于观测 |

## 后续衔接

- v0.2b 的 `leadFrames` 是 v0.3b 预测回滚的关键参数：预测窗口大小 = `leadFrames`。
- `TickOnce()` 是 v0.3c 回滚重播的基础：回滚后逐帧重播到当前帧，每帧调用一次 `TickOnce()`。
- `_serverFrameOffset` 的动态调整机制在 v0.3x 引入快照后需要与快照帧号对齐，届时可能需要微调更新时机。
