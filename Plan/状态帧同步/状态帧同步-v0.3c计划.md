# 状态帧同步-v0.3c计划：回滚重播与输入缓冲闭环控制

## Context

`v0.3b` 已完成全局帧号统一、服务端未来输入缓冲和客户端基础预测/追帧。  
进入 `v0.3c` 后，主线问题从“帧号语义是否统一”切换为“高延迟场景下如何稳定触发回滚并控制预测窗口”。

在实际联调中，旧的 `leadFrames = RTT/2 + safety` 模型会在 `Clumsy` 双边 `100ms` 以上场景暴露出两个问题：

- 单纯依赖 RTT 估算 `leadFrames`，无法反映服务端当前真实持有了多少未来输入。
- 快照到达后只按 `snapshot.FrameIndex + leadFrames` 追帧，缺少服务端输入缓冲深度反馈，容易在输入边缘产生持续性一帧偏差。

因此本阶段不再把 `leadFrames` 视为纯 RTT 推导值，而是升级为：

`RTT baseline + 服务端 accepted-input feedback + 客户端 bufferDepth 闭环控制`

## 目标

- 在全局帧号坐标系上完成正式的回滚与逐帧重播。
- 通过服务端回传 `LatestAcceptedInputFrame`，让客户端用真实输入缓冲深度闭环调节 `leadFrames`。
- 修正追帧目标的 1 帧语义错位，避免 `CatchUpFrames` 与 `SetTargetFrame()` 之间再引入稳定偏差。
- 保持 `TickOnce()` 重播路径、状态哈希、一致性检查和回滚日志继续可在无头环境中验证。

## 非目标

- 本阶段不实现断线重连。
- 本阶段不引入重传协议。
- 本阶段不实现“时间膨胀”或动态仿真速率调整。
- 本阶段不处理其他玩家表现层插值。

## 核心设计

### 1. 服务端回传 accepted-input 上界

扩展 `PlayerSnapshot`，新增：

```text
LatestAcceptedInputFrame
```

语义：

- 表示服务端对该玩家“已经接受进入未来输入缓冲区的最远帧号”。
- 它不是“最后已消费帧”，而是“当前权威帧视角下，服务端手里最多攒到了哪一帧输入”。

这样客户端收到快照时，可以直接计算：

```text
serverBufferedFrames = LatestAcceptedInputFrame - snapshot.FrameIndex
```

### 2. `leadFrames` 改为闭环控制

客户端内部保留一条 RTT 推导出来的 baseline：

```text
baselineLeadFrames = jitterBufferFrames + inputSendSafetyFrames + ceil(rttEmaMs / 2 / fixedDtMs)
```

但真正生效的 `_leadFrames` 不再只等于 baseline，而是由以下闭环控制：

- 若 `serverBufferedFrames < MinAcceptedInputBufferFrames`
  说明服务端未来输入缓冲偏浅，立即增大 `leadFrames`
- 若 `serverBufferedFrames > MaxAcceptedInputBufferFrames`
  说明客户端预测过于保守，在冷却窗口后缓慢减小 `leadFrames`
- 若缓冲深度处于健康区间
  则保持当前 `leadFrames`，并确保它不低于 baseline

本阶段的共享调参集中在：

- `InputBufferTuning.MinLeadFrames`
- `InputBufferTuning.MaxLeadFrames`
- `InputBufferTuning.MaxFutureInputFrames`
- `InputBufferTuning.MinAcceptedInputBufferFrames`
- `InputBufferTuning.MaxAcceptedInputBufferFrames`
- `InputBufferTuning.LeadDecreaseCooldownSnapshots`

### 3. 追帧目标改为显式 `TargetFrameExclusive`

旧实现里，`BattleSimulation` 返回的是 `CatchUpFrames`，`BattleClientController` 再用：

```text
frameIndex + catchUpFrames
```

自行推导 `SetTargetFrame()` 目标。  
这会把“最后已执行帧”和“下一待执行帧”两个语义混在一起。

本阶段改为：

- `BattleSimulation` 直接返回 `TargetFrameExclusive`
- `BattleClientController` 原样传给 `ClientTickDriver.SetTargetFrame()`

这样追帧语义只保留一套，不再在 Controller 层二次推导。

### 4. 回滚路径保持“权威快照 + 输入历史 + 逐帧重播”

收到服务端快照后：

1. 先做一致性检查
2. 若不一致，则应用权威快照
3. 丢弃该帧及之后的预测记录
4. 从权威帧开始，按 `_inputHistory` 逐帧重播到目标帧

这样回滚仍然完全工作在“全局帧号 + 固定 dt”的确定性坐标系上。

## 实现摘要

### 协议层

- `PlayerSnapshot` 增加 `LatestAcceptedInputFrame`
- 服务端/客户端生成代码同步更新

- `BattleLogic` 新增 `_latestAcceptedInputFrameByPlayerId`
- `SubmitInput()` 接受合法未来输入时更新 accepted-input 上界

- 引入 `PendingAuthoritativeSnapshot`
- 新增 `RefreshBaselineLeadFrames()` 和 `UpdateLeadFramesFromAcceptedInput()`
- `TickResult` 新增 `TargetFrameExclusive`
- `BattleClientController` 改为直接使用 `TargetFrameExclusive`

- `BattlePredictionSelfTestSuite` 增加 `accepted-input-feedback-raises-lead`
- `catchup-target-is-auth-plus-lead` 用例改为同时校验 `TargetFrameExclusive`
- `TestRunner` 的 future-input 拒绝用例改为依赖共享调参 `InputBufferTuning.MaxFutureInputFrames`
