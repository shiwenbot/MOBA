自动化验收方案 - 测试效率提升计划

Context

当前高频验收流程仍然主要依赖人工操作：

  • 启动 server
  • 启动两个 Unity 客户端
  • 手动进入战斗
  • 手动执行移动 / 联调操作
  • 通过肉眼观察与日志判断 PASS / FAIL

这套流程在项目早期可以接受，但随着 状态帧同步 → 属性同步 → Buff → Skill → 黑板 → 回滚联动 逐步推进，人工验收成本会快速上升：

  1. 验收频率低：改动一个点就要重新拉起 3 个进程
  2. 回归成本高：很多小改动难以及时验证
  3. 结果不稳定：不同人的操作节奏不同，日志观察口径也不一致
  4. agent 无法自主闭环：即便逻辑改动已经完成，仍然需要人工继续操作验收
  5. 后续复杂链路难以持续维护：一旦 Buff / 技能 / 回滚叠加，单纯靠人肉联调会很快失控

当前仓库并不是"完全没有自动化测试能力"，而是：

  • 已经有 dotnet run -- --mode=test 的无头测试入口
  • 已经有 TestHarness / SimulatedClient / SnapshotSelfTest / PredictSelfTest
  • 还没有形成一套足够适合高频调用、结构化输出、可长期扩展的验收体系

因此，本方案的重点不是"重新发明一套全新测试系统"，而是先把已有能力收敛成一套可执行、可迭代、可扩展的自动化验收架构。

目标

  1. 让 agent 可以自主完成大部分逻辑验收
  2. 将当前"server + 2 client + 手动操作"的流程降级为少量冒烟验收
  3. 为 状态帧同步 / 属性同步 / Buff / Skill / 回滚 建立长期可复用的测试护栏
  4. 优先复用现有无头测试入口，避免过早引入高成本新系统
  5. 为后续真实客户端自动驾驶与联调脚本预留扩展位

非目标

  • 本阶段不追求一次性做出完整的 CI/CD 测试平台
  • 本阶段不要求所有 Unity 表现层问题都可自动化验证
  • 本阶段不要求所有双客户端联调都完全替代人工
  • 本阶段不将 puerts 直接作为主验收底座
  • 本阶段不重构当前战斗主逻辑去适配新的脚本运行时

核心结论

自动化验收应该拆层，但真实客户端联调必须升级为强制验收门槛

当前人工联调同时混合了三类问题：逻辑正确性、真实链路正确性、客户端壳层正确性。这三类问题不应继续由"手工拉三进程"统一承担，但也不能只靠无头测试兜底。

根据当前项目实践，已经反复出现：无头逻辑验收通过，人工真实联调仍然出现问题。

  • 无头逻辑验收必须保留，负责高频、低成本、可定位的快速回归
  • 真实 server + 真客户端验收必须升级为每个实现步骤的强制验收门槛

每个实现步骤都必须通过"双层强制验收"

后续所有主线开发步骤，统一采用以下完成标准：

  1. 无头逻辑验收通过
  2. 真 server + 真客户端验收通过

只有两层都通过，才能视为该步骤真正完成。

  • 无头层是快速门
  • 真客户端层是强制门

主力快速回归层应继续建立在现有 CLI / TestHarness 之上。这是当前性价比最高、见效最快、返工最少的路线。状态帧同步相关的大部分高价值风险，本质上都属于"纯逻辑一致性问题"，最适合无头回归。

真双客户端联调不再只是"补充冒烟"，而是标准化强制验收层

真实客户端和真实协议链路依然不适合承担所有细粒度逻辑回归，但它必须承担：

  • 每个实现步骤的最终落地确认
  • Unity 生命周期问题暴露
  • 热更集成问题暴露
  • 真协议链路问题暴露
  • 客户端表现壳层与逻辑链路的缝隙确认

因此这层的目标不再是"有空跑一下"，而是建立固定验收流程、标准输入脚本、日志与状态判定口径，尽可能从"人工随意联调"演进为"可重复执行的标准化联调"。

ParrelSync 与 puerts 可以成为真实客户端验收层的关键支撑

  • ParrelSync：本地快速拉起多个 Unity 客户端实例、多客户端联调环境标准化、降低每次真实双客户端验证的启动成本
  • puerts：客户端自动执行测试脚本、自动 Join / 自动输入 / 自动退出、自动采集客户端关键状态与日志、客户端调试控制台 / 自动驾驶层

两者不是替代关系，而是可以组合使用：ParrelSync 负责"多开环境"，puerts 负责"客户端自动驱动"。

puerts 仍不建议替代 CLI 成为主验收底座。puerts 更擅长解决客户端行为编排、联调脚本编写、状态收集等问题，不直接解决服务端逻辑高频无头回归、回滚/快照/帧语义验证、agent 低成本闭环等核心问题。因此不建议当前抢在 CLI 强化之前，把它提升为底层主测试框架。

推荐架构

Layer 1

无头逻辑验收层

使用现有 CLI / TestHarness / --mode=test 作为主力验收层。

职责

  • 状态帧同步主逻辑回归
  • 输入缓冲 / 缺帧复用
  • 快照保存 / 恢复
  • 正式回滚 / 重播
  • 物理状态一致性
  • 属性快照 / 属性脏同步
  • 后续 Buff / Skill 命令链路

特点

单进程 纯 C# 无 Unity 依赖 运行快 适合 agent 高频执行
结论：这是后续自动化验收的主验收层，优先级最高。
Layer 2

真 server + 真客户端强制验收层

建立"真 server + 真客户端"的标准化验收层。

职责

  • JoinBattle 链路验证
  • 真实协议收发验证
  • 双客户端基础同步验证
  • 玩家离开 / 重入等集成行为验证
  • Unity 生命周期 / 热更集成 / 表现壳层确认
  • 每个实现步骤的最终落地确认

特点

真实进程 强制执行 覆盖集成问题 可逐步从人工演进为自动化
结论：这是所有开发步骤的强制验收层，优先级与无头逻辑层并列为必过门槛。
Layer 3

客户端脚本驱动层

评估引入 puerts 作为 Unity 客户端的脚本驱动与调试层。

职责

  • 驱动客户端执行预设输入脚本
  • 自动 Join / 自动操作 / 自动退出
  • 自动订阅客户端关键状态
  • 自动收集客户端日志和结果摘要
  • 长期演进为测试控制台 / 调试面板

特点

提升真实客户端自动化效率 更适合"客户端自动驾驶" 不作为底层逻辑验收主框架
结论：这是一个增强层，优先级第三，可先做 PoC 再决定是否正式接入。

为什么不建议直接让 puerts 替代底层测试框架

1. 当前主矛盾不只是"客户端脚本能力不足"

目前真正影响效率的核心问题是：

  • 纯逻辑改完后无法立即无头回归
  • 每次验证都过度依赖真实客户端
  • 很多错误本质上是逻辑一致性问题，而非 Unity 客户端壳层问题

因此第一刀仍应优先解决"逻辑自动回归"，同时把真实客户端验收标准化，而不是先用 puerts 重建整个测试底层。

2. 现有无头测试基础已经能直接复用

仓库当前已经具备：

  • --mode=test
  • TestRunner
  • SimulatedClient
  • SnapshotSelfTest
  • PredictSelfTest
  • Battle / Snapshot / Prediction 的现有验证链路

这意味着最短路径不是新引入脚本运行时，而是增强现有能力。

3. puerts 会引入额外集成与维护成本

  • Unity 工程接入成本
  • JS / TS 运行时组织方式
  • 测试脚本目录和生命周期管理
  • 日志与状态桥接规范
  • 团队协作和代码评审边界
如果在当前阶段直接引入，很容易把"测试提效"变成"新增技术栈治理任务"。

第一阶段：强化现有 CLI 无头测试，形成快速回归门

目标

让 agent 在改完逻辑代码后，可以直接自主完成主线快速回归。

建议补齐的命令能力

--mode=test
--scenario <name>
--frames <count>
--clients <count>
--output console|markdown|json
--report <path>

退出码约定：0 = PASS，1 = FAIL

第一批建议重点场景

  • prediction-self
  • all
  • player-collision
  • authoritative-snapshot-restores-physics-world
  • authoritative-snapshot-restores-player-attributes
  • snapshot-attribute-roundtrip
  • attribute-dirty-merge

后续扩展场景

  • attribute-sync
  • rollback-restores-attributes
  • client-predictable-cost
  • buff-minimal
  • skill-command-issued
阶段收益：大部分主逻辑问题可以由 agent 自行验证；大幅降低人工拉起三进程的频率；建立"进入真实客户端强制验收之前的快速过滤层"。

第二阶段：建立真 server + 真客户端的标准化强制验收流程

目标

将当前完全手动、随意性较高的双客户端联调，收敛为每一步都可重复执行的标准化验收流程。

实施重点

  • 自动启动 server
  • 基于 ParrelSync 自动启动两个客户端实例
  • 自动 JoinBattle
  • 自动执行标准输入脚本
  • 自动收集 server / clientA / clientB 日志
  • 自动导出关键状态摘要
  • 自动给出 PASS / FAIL 结论

第一批建议标准化场景

  • 双客户端都能进入战斗
  • 双方基础移动同步正确
  • 玩家离开后另一方继续正常
  • 属性权威快照恢复正确
  • 回滚发生时日志与结果符合预期

技术路径

  • 真 server
  • ParrelSync 多开客户端
  • Unity -batchmode / -executeMethod
  • 客户端内置自动测试入口
  • 后续若接入 puerts，由 puerts 驱动客户端测试脚本
阶段收益：把真实联调从"经验操作"变成"标准化门槛"；真正覆盖无头层无法发现的集成问题；为后续全自动联调打基础。

第三阶段：评估并接入 puerts 作为客户端自动化驱动层

目标

验证 puerts 是否能显著降低 Unity 客户端联调脚本的编写与维护成本。

推荐定位

  • 自动驱动客户端执行测试流程
  • 统一编排输入脚本
  • 订阅客户端关键状态变化
  • 收集并输出测试摘要
  • 支撑调试控制台与测试工具面板

不建议承担的职责

  • 不替代 CLI 成为主逻辑验收底座
  • 不承接服务端主测试框架职责
  • 不改写当前状态帧同步核心实现
  • 不作为当前阶段真实客户端强制验收的唯一前置依赖
阶段产物：一个最小 PoC + 一两个真实客户端测试脚本 + 一份是否正式接入的收益评估结论。

日志与判定策略

真实 server + 真客户端 验收中，推荐采用"日志判流程，结构化状态判结果"的双轨策略。

日志的职责

判断链路是否按预期发生：

  • 客户端是否成功 JoinBattle
  • 服务端是否收到了某帧输入
  • 权威快照是否成功广播并应用
  • 是否触发 MISMATCH
  • 是否触发 ROLLBACK
  • 某个属性 / Buff / 技能命令是否在目标帧执行

结构化状态的职责

判断最终结果是否真正正确：

  • 指定帧时 server / clientA / clientB 的位置是否一致
  • 指定帧时属性是否一致
  • Buff 列表是否一致
  • 回滚后是否回到权威状态
  • 最终哈希 / 统计值是否满足断言

判定原则

自动验收时建议统一采用三层判断：

  1. 进程是否正常 — server 是否正常启动、clientA / clientB 是否正常启动、是否有崩溃 / 未处理异常
  2. 关键流程日志是否出现 — JoinBattle success、Input accepted、Snapshot applied、Rollback triggered、Buff added/removed
  3. 结构化状态断言是否满足 — 指定帧位置 / 属性 / Buff / 哈希 / 回滚统计是否满足预期
日志更适合判断"链路有没有走通"；结构化状态更适合判断"结果到底对不对"。

强制验收规则

后续所有实现步骤统一采用以下验收规则：

Step 完成定义

任一开发步骤只有同时满足以下条件，才可视为完成：

1 无头逻辑验收通过
2 真 server + 真客户端 验收通过

真客户端验收最小要求

每个步骤至少需要：

  • 1 条标准真实联调用例
  • 1 组 server / clientA / clientB 日志记录
  • 1 组结构化结果断言

人工体验确认

在自动化流程尚未完全覆盖前，仍允许保留少量人工体验确认，但它不替代上述两层强制验收。

推荐里程碑

Milestone 1：无头快速回归门收敛

目标：让无头测试入口真正成为高频可用的主力工具。

  • 统一 --mode=test 入口参数
  • 支持 --scenario
  • 支持 --frames
  • 支持 --clients
  • 支持 --output
  • 支持 --report
  • 固定 0/1 退出码
  • 补齐属性同步相关测试场景
  • 明确控制台 / Markdown / JSON 输出格式

完成标准：agent 修改主逻辑后可直接自主回归；输出稳定可读；v0.4b 相关属性链路可无头验证。

Milestone 2：真 server + 双客户端强制验收闭环

目标：减少"必须人工手动拉三进程"的频率。

  • 自动启动 server
  • 基于 ParrelSync 启动两个客户端实例
  • 自动 JoinBattle
  • 自动执行一段预设输入脚本
  • 自动收集 server / clientA / clientB 日志
  • 自动导出关键状态摘要
  • 自动给出 PASS / FAIL 结论

完成标准：至少 2~3 条高价值联调场景可标准化执行；每个主线步骤都可挂接真实客户端强制验收。

Milestone 3：puerts PoC 评估

目标：验证 puerts 是否适合承接客户端自动驾驶层。

  • 在 Unity 客户端完成最小接入验证
  • 编写 1 条自动驱动测试脚本
  • 编写 1 条自动日志收集脚本
  • 编写 1 条结构化状态导出脚本
  • 评估脚本编写效率、调试体验、集成复杂度
  • 输出正式接入 / 暂缓接入结论

完成标准：能明确回答 puerts 是否值得作为客户端自动化增强方案继续推进。

风险与应对

风险影响应对
过早把所有验证都压到真实双客户端运行慢、定位难、反馈周期长保留 Layer 1 作为快速门，Layer 2 作为强制门
过早引入 puerts 取代底层测试框架引入额外技术栈治理成本只做 PoC，不提前替代 CLI
测试入口继续分散agent 不知道该跑什么统一命令入口和输出规范
后续 Buff / Skill 测试场景爆炸测试维护困难先建立通用快照 / 命令 / 回滚测试骨架
只靠日志字符串判定正确性容易误判，结果不稳增加结构化状态导出与断言
过度依赖人工体验确认回归速度持续受限将人工验收收敛为少量体验确认，不替代强制门

最终建议

当前最优先、性价比最高的路线是：

  1. 优先强化现有 CLI / TestHarness，形成真正可高频使用的快速回归门
  2. 将真 server + 真客户端 升级为每个实现步骤都必须通过的强制验收门
  3. 优先基于 ParrelSync 标准化双客户端联调环境
  4. 以 PoC 方式评估 puerts 是否适合作为客户端自动驱动与状态导出增强层

换句话说：

  • CLI 解决的是"主逻辑能不能高频、稳定、低成本回归"
  • 真 server + 真客户端 解决的是"真实链路和真实运行时是否真的正确"
  • ParrelSync 解决的是"多客户端环境能不能稳定、低成本拉起"
  • puerts 解决的是"真实客户端能不能更快自动驾驶、导出状态和编排测试"
保留无头快速门，强制真实客户端门，再用 ParrelSync + puerts 持续降低真实联调成本。
