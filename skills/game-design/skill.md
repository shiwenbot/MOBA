# 游戏策划文档写作 Skill

从"我有一个游戏想法"到"产出一份完整的策划文档"的自包含流程。
适用于单人独立开发者，无外部 agent 依赖。

## 整体流程

```
Phase 1: 头脑风暴（概念探索）
    ↓
Phase 2: 核心循环设计（30秒/5分钟/Session/进度循环）
    ↓
Phase 3: 支柱与边界（设计支柱 + 反支柱）
    ↓
Phase 4: 系统分解（显性→隐性系统推导 + 依赖映射）
    ↓
Phase 5: GDD 撰写（逐章节引导，8 个必需章节）
    ↓
Phase 6: 自审 Checklist（完整性、一致性、可实现性）
```

---

## Phase 1: 头脑风暴

### 1.1 创意探索

以对话方式了解用户，不是审问而是共创。关注以下维度：

**情感锚点**：
- 什么游戏时刻曾让你真正感动、兴奋或忘记时间？具体是什么创造了那种感觉？
- 有什么你一直想在游戏中体验但从未找到的幻想？

**品味画像**：
- 你花时间最多的 3 款游戏是什么？是什么让你反复回来？
- 你喜欢挑战、放松、叙事还是自由表达？

**实用约束**：
- 目标平台是什么？
- 开发周期预期？
- 开发经验水平？

### 1.2 概念生成

基于创意探索，用以下三种技术生成 3 个不同方向的概念：

**技术 A：动词优先设计**
从核心玩家动词出发（建造、战斗、探索、解谜、生存、创造、管理），向外构建。动词就是游戏。

**技术 B：混搭法**
组合两个意外元素：[类型 A] + [主题 B]。两者之间的张力构成独特卖点。（例如"网球场 + 角色技能对战"）

**技术 C：体验先行设计（MDA 反推）**
从期望的玩家情绪出发（ sensation、fantasy、narrative、challenge、fellowship、discovery、expression、submission），反向推导产生该情绪的动态和机制。

### 1.3 概念模板

为每个概念呈现：

- **工作标题**
- **电梯演讲**（1-2 句话，必须通过"10 秒测试"）
- **核心动词**（最常见的玩家操作）
- **核心幻想**（情感承诺）
- **独特卖点**（"像 X，但还有 Y"）
- **MDA 美学**（主导情绪）
- **预估规模**（小/中/大）
- **为什么可能成功**（1 句话）
- **最大风险**（1 句话）

呈现所有概念后，让用户选择一个、合并多个或要求新方向。

### 1.4 输出：游戏概念文档

确定概念后，写入 `Plan/游戏概念-[项目名].md`，包含：

```markdown
# [游戏名称] — 游戏概念文档

## 创意简报
[3-5 句话总结情感目标、品味画像和约束]

## 电梯演讲
[1-2 句话]

## 核心幻想
[玩家应该感受到什么]

## 独特卖点
[与同类游戏的差异化]

## MDA 分析
- **美学目标**: [主导情绪]
- **动态**: [玩家的 emergent 行为]
- **机制**: [产生动态的基础规则]

## 参考游戏
- [游戏名]: [借鉴什么]

## 目标平台
[PC/Mobile/Console]

## 预估规模
[小/中/大，附时间线]

## 最大风险
[技术/设计/市场风险]
```

## Phase 2: 核心循环设计

核心循环是游戏的心跳。如果它在孤立状态下不好玩，再多内容也救不了。

### 2.1 四层循环拆解

**30 秒循环（即时操作）**：
- 玩家每时每刻在做什么？
- 核心操作的手感目标是什么？
- 这个动作本身是否有趣？（音效反馈、视觉打击感、时机满足感、战术深度）

**5 分钟循环（短期目标）**：
- 什么结构把即时操作组织成周期？
- "再来一局"的心理学在哪里生效？
- 这个层级上玩家做什么选择？

**Session 循环（30-120 分钟）**：
- 一个完整游戏过程是什么样的？
- 自然的停止点在哪里？
- 什么让玩家在不玩的时候还想着游戏？

**进度循环（天/周）**：
- 玩家如何成长？（力量？知识？选项？故事？）
- 长期目标是什么？游戏何时"完成"？

### 2.2 玩家动机分析（基于自我决定理论）

- **自主性**：玩家有多少有意义的选择？
- **胜任感**：玩家如何感受到技能在成长？
- **关联性**：玩家如何感到连接（与角色、世界）？

### 2.3 输出：核心循环文档

追加到概念文档，或单独写入 `Plan/核心循环-[项目名].md`：

```markdown
## 核心循环

### 30 秒循环
[描述即时操作的 flow]

### 5 分钟循环
[描述短期目标结构]

### Session 循环
[描述完整游戏过程]

### 进度循环
[描述长期成长路径]

### 玩家动机
- 自主性: [分析]
- 胜任感: [分析]
- 关联性: [分析]
```

## Phase 3: 支柱与边界

### 3.1 设计支柱（3-5 个）

支柱确保所有设计决策指向同一方向，防止范围蔓延。

每个支柱包含：
- **名称** 和 **一句话定义**
- **设计测试**："如果我们在 X 和 Y 之间犹豫，这个支柱说我们选 __"
- 支柱之间应该有张力——如果所有支柱指向同一方向，它们没在做够多的工作

### 3.2 反支柱（3+ 个）

防止最常见的范围蔓延："加个 XX 会很酷吧..."

格式："我们不会做 [事情]，因为那会损害 [支柱]"

### 3.3 输出：支柱文档

```markdown
## 设计支柱

### 支柱 1: [名称]
- 定义: [一句话]
- 设计测试: [如果犹豫，选什么]

### 支柱 2: [名称]
...

### 支柱 3: [名称]
...

## 反支柱
- 不做 [X] — 因为会损害 [支柱名]
- 不做 [Y] — 因为会损害 [支柱名]
- 不做 [Z] — 因为会损害 [支柱名]
```

## Phase 4: 系统分解

### 4.1 提取显性系统

从游戏概念和核心循环中扫描直接提及的系统：
- 核心机制段落（最明确）
- 核心循环段落（暗示驱动每个循环层的系统）
- MVP 定义段落（必需功能 = 必需系统）

### 4.2 推导隐性系统

对于每个显性系统，识别它所暗示的隐藏系统。游戏总是比概念文档提到的需要更多系统。

推导模式示例：
- "战斗" 暗示：伤害计算、血量系统、碰撞检测、状态效果、敌人 AI、战斗 UI
- "物品栏" 暗示：物品数据库、装备槽位、容量规则、物品序列化
- "开放世界" 暗示：流式加载/分区、LOD 系统、快速旅行、地图系统
- "对话" 暗示：对话树系统、对话 UI、选择追踪、NPC 状态管理
- "进度" 暗示：经验值系统、升级机制、技能树、解锁追踪

### 4.3 依赖映射

对每个系统，确定它依赖什么。系统"依赖于"另一个系统 = 如果没有另一个系统先存在，它无法运转。

**依赖启发式**：
- **输入/输出依赖**：系统 A 产生系统 B 需要的数据
- **结构依赖**：系统 A 提供系统 B 插入的框架
- **UI 依赖**：每个玩法系统都有对应的 UI 系统（但 UI 在玩法系统之后设计）

### 4.4 分层排序

将系统分层：

| 层级 | 描述 | 设计顺序 |
|------|------|----------|
| **基础层** | 零依赖的系统 | 最先设计 |
| **核心层** | 仅依赖基础层的系统 | 第二批 |
| **功能层** | 依赖核心层的系统 | 第三批 |
| **表现层** | UI 和反馈系统 | 最后 |
| **打磨层** | 教程、辅助功能 | 可延后 |

检查循环依赖。如果发现，标记并提议解决方案（接口抽象、同步设计、打破循环）。

### 4.5 优先级分配

基于里程碑分配优先级：
- **MVP**：概念中"Required for MVP"提到的系统 + 其基础层依赖
- **垂直切片**：一个完整区域体验所需的系统
- **Alpha**：剩余玩法系统
- **完整愿景**：打磨、Meta、锦上添花

### 4.6 输出：系统索引文档

写入 `Plan/系统索引-[项目名].md`：

```markdown
# [游戏名称] — 系统索引

## 系统清单

| 系统 | 类别 | 来源 | 优先级 | 层级 | 状态 | 设计文档 |
|------|------|------|--------|------|------|----------|
| [系统名] | [类别] | 显性/隐性 | MVP/VS/Alpha | 基础/核心/功能/表现 | 未开始 | - |

## 依赖图

[列出每个系统的上下游依赖]

## 高风险系统

[多个系统依赖的瓶颈系统]

## 推荐设计顺序

1. [系统名] — 基础层/MVP
2. [系统名] — 基础层/MVP
3. ...
```

## Phase 5: GDD 撰写（逐章节引导）

对系统索引中的每个系统，按推荐设计顺序撰写 GDD。

### 5.1 GDD 模板（8 个必需章节）

```markdown
# [系统名称]

> **状态**: 设计中
> **最后更新**: [日期]
> **服务支柱**: [支柱名]

## A. 概述
[一段话，让陌生人能看懂]

## B. 玩家幻想
[这个系统应该让玩家感受到什么]

## C. 详细设计

### 核心规则
[基本机制。用编号规则描述流程，用要点描述属性]

### 状态与转换
[如果系统有状态，列出每个状态和合法转换]

### 与其他系统的交互
[每个依赖：什么数据流入、什么流出、谁拥有接口]

## D. 公式
[所有数学公式，变量定义、范围标注]

格式要求：
```
[公式名] = [表达式]

**变量:**
| 变量 | 符号 | 类型 | 范围 | 描述 |
|------|------|------|------|------|

**输出范围:** [最小值] 到 [最大值]
**示例:** [带实际数字的计算示例]
```

## E. 边界情况
[异常场景的明确处理]

格式要求：
- **如果 [条件]**: [确切结果]。[理由]

## F. 依赖
[列出所有上下游系统，标注硬依赖/软依赖]

## G. 调节旋钮
[设计师可调参数，附安全范围和极端值表现]

## H. 验收标准
[可测试的成功条件]

格式要求：
- **给定** [初始状态]，**当** [动作或触发]，**则** [可测量结果]
```

### 5.2 章节撰写流程

对每个章节，遵循此循环：

```
上下文 → 提问 → 选项 → 决策 → 草稿 → 确认 → 写入
```

1. **上下文**：说明这个章节需要包含什么，呈现依赖 GDD 中的相关决策约束
2. **提问**：提出澄清性问题（开放性用对话，约束性用选项）
3. **选项**：涉及设计选择时，呈现 2-4 个方案及优劣
4. **决策**：用户选择方案或提供自定义方向
5. **草稿**：在对话中写出章节内容供审阅
6. **确认**：用户确认后写入文件
7. **写入**：立即写入文件（增量写入）

### 5.3 各章节设计要点

**A. 概述**：
- 一段话总结
- 说明玩家如何交互（主动/被动/自动）
- 这个系统存在的理由——没有它游戏失去什么
- 与系统索引的描述对齐

**B. 玩家幻想**：
- 服务于什么情绪或力量幻想？
- 参考游戏如何做到这种感觉？
- 必须与游戏支柱对齐

**C. 详细设计**（通常最大的章节）：
- 核心规则必须足够明确，程序员无需猜测即可实现
- 状态机必须列出每个状态和每个合法转换
- 系统交互必须指明数据流向和接口归属

**D. 公式**：
- 每个公式必须有变量表、范围、计算示例
- 不允许写"[公式待定]"——没有变量定义的公式无法实现
- 如果依赖 GDD 定义了此系统用到的公式，引用它而不是重新发明

**E. 边界情况**：
- 零值？最大值？超范围值？
- 两条规则同时适用时怎么办？
- 玩家发现意外交互时怎么办？
- 不允许写"适当处理"——每个边界情况必须有确切的解决方案

**F. 依赖**：
- 必须双向一致：如果此系统列出"依赖战斗"，战斗 GDD 应列出"被 [此系统] 依赖"
- 标注硬依赖（没有就不能运转）vs 软依赖（增强但可以没有）

**G. 调节旋钮**：
- 设计师无需改代码就能调的值
- 每个旋钮：太高会怎样？太低会怎样？
- 哪些旋钮会互相影响？

**H. 验收标准**：
- 每个核心规则至少一条标准
- 每个公式至少一条标准
- 不允许写"系统按设计工作"——每条标准必须 QA 可独立验证
- 包含跨系统交互的验证条件

### 5.4 输出

每个系统的 GDD 写入 `Plan/GDD-[系统名].md`。

## Phase 6: 自审 Checklist

完成 GDD 后，用以下清单自我审查。

### 6.1 完整性检查

- [ ] 有概述段落（一段话总结）
- [ ] 有玩家幻想（预期感受）
- [ ] 有详细规则（无歧义机制）
- [ ] 有公式（所有数学有变量定义）
- [ ] 有边界情况（异常场景已处理）
- [ ] 有依赖（其他系统已列出）
- [ ] 有调节旋钮（可配置值已识别）
- [ ] 有验收标准（可测试的成功条件）

### 6.2 一致性检查

**内部一致性**：
- 公式产生的值是否与描述的行为匹配？
- 边界情况是否与主规则矛盾？
- 依赖是否双向一致？

**可实现性**：
- 规则是否足够精确，程序员可以无猜测实现？
- 有没有"含糊带过"的部分缺少细节？
- 性能影响是否考虑？

**跨系统一致性**：
- 是否与已有机制冲突？
- 是否与其他系统产生意外交互？
- 是否与游戏的调性和支柱一致？

### 6.3 范围信号

基于依赖数、公式数、涉及系统数、是否需要新 ADR 来估算实现规模：
- **S** — 单系统，无公式，<3 依赖
- **M** — 中等复杂度，1-2 公式，3-6 依赖
- **L** — 多系统集成，3+ 公式
- **XL** — 跨领域关注，5+ 依赖

### 6.4 审查输出格式

```markdown
## 设计审查: [文档标题]

### 完整性: [X/8 章节完整]
[列出缺失章节]

### 依赖图验证
[每个声明的依赖及其 GDD 文件是否存在]

### 必须修正（阻塞项）
[编号列表 — 不解决就不能进入实现]

### 建议修改
[编号列表 — 重要但不阻塞]

### 锦上添花
[小改进，低优先级]

### 范围信号: [S/M/L/XL]

### 判定: [通过 / 需修改 / 需重大修改]
```

## 使用方式

### 方式 1：从零开始（完整流程）

```
/game-design concept
```

运行 Phase 1-3（头脑风暴 → 核心循环 → 支柱），产出游戏概念文档。

然后继续 Phase 4（系统分解），产出系统索引。

### 方式 2：设计单个系统

```
/game-design [系统名]
```

直接进入 Phase 5，为指定系统撰写 GDD。会自动读取已有的概念文档和系统索引作为上下文。

### 方式 3：审查已有文档

```
/game-design review [文件路径]
```

运行 Phase 6 的自审 Checklist，检查指定 GDD 的完整性、一致性和可实现性。

## 文件约定

- 所有策划文档输出到 `Plan/` 目录
- 文档用中文撰写
- 遵循"思路和设计方向"原则：**不包含具体实现代码**
- 文档命名规范：
  - 游戏概念：`Plan/游戏概念-[项目名].md`
  - 核心循环：`Plan/核心循环-[项目名].md`（或合并到概念文档）
  - 系统索引：`Plan/系统索引-[项目名].md`
  - 系统 GDD：`Plan/GDD-[系统名].md`

## 核心原则

1. **协作而非替代**：AI 是创意引导者，不是人类愿景的替代品。每个决策点都询问用户。
2. **增量写入**：每个章节确认后立即写入文件，不积压到末尾。
3. **文件即记忆**：对话会消失，文件持久。所有决策写入文件，而非依赖对话记忆。
4. **不含实现代码**：策划文档描述行为和规则，不描述技术实现。实现模式属于架构决策文档。
5. **交叉引用**：每个章节检查已有 GDD 的冲突。不自相矛盾。
