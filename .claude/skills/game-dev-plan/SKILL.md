# 游戏开发阶段计划 Skill

编写游戏开发阶段性实现计划，确保计划与代码实际能力对齐、与 GDD 设计一致，并产出 MD（给 Codex）+ HTML（给人看）双版本。

## 整体流程

```
Phase 1: 上下文收集
    ↓
Phase 2: 编写计划（MD 版）
    ↓
Phase 3: 校验 Pipeline（4 步自动校验）
    ↓
Phase 4: 输出 HTML 版
    ↓
Phase 5: 汇总报告
```

## Phase 1: 上下文收集

计划必须基于真实的代码现状和设计文档，不能凭空想象。按以下顺序收集信息：

### 1.1 定位阶段总目录

根据用户指定的模块名，找到对应的阶段总目录文件：
- 搜索 `Plan/[模块名]/*阶段总目录*.md` 或 `Plan/*阶段总目录*.md`
- 从总目录中提取：当前阶段定义、已锁定决策、阶段依赖图、前/后阶段边界

**已锁定决策是硬约束**：总目录中的"已锁定决策"不是建议，是已经做出的不可更改的架构选择。在编写计划时，必须逐条传播到计划的 Context 和技术决策中。例如：如果总目录锁定"羽毛球弹道不使用 Box2D"，计划中就不能出现"用 Box2D 做球网碰撞"——这是实现方向的错误，不是细节问题。

**提取方法**：不仅读总目录的文字，还要**追问每个锁定决策的含义**。比如"不使用 Box2D"意味着：不做 Box2D 刚体、不参与 Box2D World.Step()、碰撞检测不走 Box2D 管线。把这些推论写进计划的 Context。

### 1.2 读取相关设计文档（如有）

搜索模块目录下的设计文档：`Plan/[模块名]/GDD-*.md`、`Plan/[模块名]/*夺势*.md` 等。

**有两种情况**：
- **有 GDD**：提取核心规则、参数值、公式、系统交互，用于计划编写和后续校验
- **无 GDD**：从总目录的阶段描述（聚焦点/核心产出）推导设计方向，在计划的技术决策中说明"本阶段无详细 GDD，参数基于总目录描述 + 合理推断"，数值参数标注"待调优"

无论是否有 GDD，都继续后续流程。GDD 一致性校验会自动适配（见 Phase 3）。

### 1.3 扫描代码现状

了解已有的代码基础，避免计划中引用不存在的类/方法：
- 搜索相关目录下的 `.cs` 文件（`GameScripts/HotFix/GameShared/`、`GameScripts/HotFix/GameLogic/`）
- 记录关键类名、接口名、公共方法签名
- 确认前序阶段产出的代码是否已存在

### 1.4 理解现有代码模式（关键步骤）

这一步决定了计划的深度。不仅要扫描有哪些类，还要理解它们**怎么协作**。

**必须识别并记录的代码模式**：

1. **快照/回滚模式**：找到 `ISnapshotable<T>` 接口，理解项目中 State/Snapshot/Entity 的职责分离方式（State 是可变运行时数据，Snapshot 是不可变快照结构体，Entity 持有 State 并实现 ISnapshotable）。在计划中新增任何需要回滚的实体时，必须遵循这个模式。

2. **命令/池化模式**：找到 `IResettable` 接口和 `CommandPool<T>`，理解帧命令的设计方式（携带 FrameIndex，只在目标帧消费，用完归还池）。如果本阶段有任何"在特定帧触发操作"的需求，必须用这个模式。

3. **帧驱动模式**：找到 `ITickable` 接口和 `TickDispatcher`，理解所有仿真逻辑都通过 Tick 调度执行。新增的仿真实体必须实现 ITickable。

4. **确定性约束模式**：找到 `DeterminismRules`，理解项目对浮点、随机数、帧间隔的约束。在计划的技术决策中说明本阶段如何处理确定性。

5. **程序集边界**：确认哪些代码在 GameShared（可被服务端共用，无 UnityEditor 引用），哪些在 GameLogic（仅客户端）。新增文件必须放在正确的程序集下。

6. **系统边界**（最容易被忽视）：理解每个现有系统的**能力边界**——它负责什么、不负责什么。例如，FrameSyncPhysicsWorld 封装了 Box2D，但不是所有物理对象都需要进 Box2D。在计划中决定"用还是不用某个系统"时，必须说明理由。**如果总目录或前序计划明确说了"不用 XX 系统"，计划中绝不能出现把 XX 系统用在本阶段核心功能上的情况**。

**方法**：用 Grep 搜索上述接口/类的定义，读取关键文件头部的接口签名和注释。重点关注它们的公共方法签名——这些是计划中新代码必须遵循的约定。

**边界追问法**：对每个现有系统，问自己三个问题：
1. 这个系统为本阶段提供什么能力？（应该复用）
2. 这个系统的能力范围是什么？（不应该超范围使用）
3. 本阶段有没有功能是这个系统**不适合**处理的？（需要替代方案）

### 1.5 读取前序计划

如果当前阶段有前置依赖，读取前序阶段的计划文档：
- 了解前序阶段的产出（文件结构、新增类/接口）
- 确认前序阶段的完成标准中哪些是当前阶段可以复用的

使用 `ctx_batch_execute` 并行执行上述收集任务，效率更高。

## Phase 2: 编写计划（MD 版）

### 2.1 谁在读这份计划

计划的**主要读者是另一个 AI agent**（Codex 或另一个 Claude 实例），它会拿到这份计划后独立实现，期间无法向你提问。

所以计划的唯一衡量标准是：**一个不了解项目历史的 agent 能否只凭这份计划 + 代码库完成实现？**

从这个标准出发，计划必须回答以下问题：

| 问题 | 对应内容 |
|------|---------|
| 我在哪？为什么现在做这个？ | Context：前置依赖、已锁定决策、现有代码能力 |
| 要做到什么程度？ | 目标：可验证的产出，不是"写代码"而是"能做什么" |
| 做什么、不做什么？ | 范围边界：防止 agent 越界实现后续阶段的功能 |
| 怎么做？ | 实现步骤：每步聚焦一个问题，有逻辑递进 |
| 关键技术选型是什么？ | 技术决策：选了什么、为什么、怎么落地 |
| 文件放哪里？ | 文件结构：目录树，让 agent 知道往哪写 |
| 怎么判断做完了？ | 完成标准：可勾选的验证项，不仅是"编译通过" |
| 做完之后呢？ | 后续衔接：下一阶段复用哪些产出 |

**不要求固定章节**。参考同模块前序计划的结构保持一致性即可。如果某个问题在本阶段不适用（比如没有架构选择就不需要"技术决策"），跳过它。

### 2.2 技术决策怎么写

技术决策（TD）是计划中最有价值的部分。每个 TD 用 `### TD-N：标题` 编号格式，包含三个层次：

**层次 1：选了什么**
- 一句话说清楚决策结论

**层次 2：为什么选这个**
- 对比替代方案（至少提一个被排除的方案）
- 解释与现有架构的兼容性
- 如果这个决策与某个已有代码模式有关（快照模式、命令模式等），明确说明如何对接

**层次 3：怎么落地**
- 具体的类名、字段名、方法签名（伪代码级别）
- 文件放在哪个目录、属于哪个程序集
- 需要实现哪些已有接口（如 ISnapshotable、ITickable、IResettable）

**什么样的决策需要编号 TD**：任何会影响实现 agent 工作方式的决策。包括但不限于：
- 架构选择（用什么物理引擎、2D/3D/2.5D）
- 数据结构设计（状态/快照/命令怎么拆）
- 与已有框架的集成方式（走哪条代码路径）
- 确定性策略（浮点/定点/查表）
- 配置管理方案（Luban/硬编码/ScriptableObject）
- 文件组织和程序集归属

**什么不需要 TD**：纯实现细节（用什么循环结构、变量命名等）。

**TD 覆盖度自查（强制）**：写完所有 TD 后，**必须逐个**检查以下 8 个类别。每个类别要么有对应 TD，要么在计划中显式写一句话说明为什么本阶段不需要。

| 类别 | 判断标准 | 典型遗漏信号 |
|------|---------|-------------|
| 坐标模型（2D/2.5D/3D） | 如果涉及空间计算，**必须明确约定** | 状态字段里有位置/速度但没说用什么坐标系 |
| 物理引擎选型 | 用 Box2D/Unity 物理/纯数学？为什么？ | 提到物理计算但没说走哪条管线 |
| "不使用 XX 系统"的决策 | 如果本阶段不用某个现有系统，**必须**写 TD 说明原因和替代方案 | 代码库有物理引擎但你的物理计算不用它 |
| 数据模型（State/Snapshot/Entity） | 新增仿真实体时，快照模式怎么拆 | 新增了 State 但没说 Snapshot 怎么对应 |
| 操作语义（即时/帧命令） | **在帧同步系统中，"在特定帧触发操作"默认应该是帧命令**，除非有充分理由用即时调用。如果你写了 Launch/Fire/Spawn 等操作，几乎一定需要帧命令 | 有"发射""触发""击发"等操作但没定义命令类 |
| 配置管理 | 本项目用 Luban 管理配置。**默认用 Luban + 纯 C# 兜底类**，不要重新发明配置方案 | 参数写死在代码里，没有配置表也没有兜底类 |
| 状态机设计 | 有 3 个以上状态转换时需要独立 TD | 有 Idle/Flying/Landed 等状态但没定义枚举和转换规则 |
| 文件组织和程序集归属 | 新增文件放在 GameShared 还是 GameLogic？为什么？ | 没有目录树或目录树太模糊 |

**操作语义特别说明**：在帧同步项目中，操作语义是最高频遗漏的 TD。如果一个操作（发射、击球、生成、销毁）需要"在特定逻辑帧发生"，它**必须是帧命令**（实现 IResettable，通过 CommandPool 池化），不能是普通的 `void Launch()` 方法调用。如果你不确定，问自己：回滚重播时，系统需要知道"哪一帧发生了这个操作"吗？如果需要，就是帧命令。

### 2.3 实现步骤怎么写

实现步骤是 agent 的工作清单。每步必须足够具体，让 agent 知道：
- 要创建什么文件（精确路径）
- 要定义什么类/接口（名称、字段）
- 要实现什么方法（签名级别）
- 与哪步产出有依赖关系

**粒度原则**：每步只做一件事。如果一个步骤包含"定义枚举 + 定义状态结构体 + 定义快照结构体"，拆成多步。

**递进关系**：步骤之间应该有清晰的依赖链：
- 常量/枚举 → 数据结构 → 核心算法 → 帧同步集成 → 配置 → 可视化 → 验证

### 2.4 编写原则

**实现 agent 能独立工作**：这是最高优先级原则。如果某个设计决策的理由不写清楚，agent 可能会做出不同选择。技术决策不仅要写"选了什么"，还要写"为什么选这个"。

**思路为主，不含代码**：计划描述设计方向和实现思路，不包含可直接复制粘贴的代码块。例外：关键接口签名（用于定义约定）和配置文件格式可以用伪代码说明——因为这些是 agent 需要遵循的约定。

**参数有出处**：数值参数（速度、角度、时间等）必须来自 GDD 文档。无 GDD 时标注"待调优"并给出初始值和调优方向——让 agent 知道这个值不是确定的，实现时需要可配置。

**对接现有架构**：引用已有类/接口时使用精确名称（如 `FrameSyncPhysicsWorld`、`ISnapshotable<T>`、`ITickable`），文件路径用精确路径。这样 agent 可以直接 grep 找到参考代码。

**显式说明边界**：非目标和范围边界至少和目标一样重要。agent 没有"常识"，如果不在计划里明确说"本阶段不做 XX"，它可能会顺手实现。

**完成标准格式**：完成标准必须使用 `- [ ]` 复选框格式，每条标准可直接验证。分为三个子类别：功能验证（能做什么）、确定性验证（输入一致则输出一致）、工程验证（代码质量、程序集边界、接口实现）。至少 10 条标准。

### 2.5 验证方式怎么写

每个计划必须包含 **验证方式** 章节（放在完成标准之前），定义实现 agent 可以直接执行的测试命令和通过标准。这是 agent 能"自动化验证"的关键。

#### 三层测试体系

| 层次 | 定位 | 适用场景 | 命令模式 |
|------|------|---------|---------|
| **L1 编译验证** | 双端编译通过 | 所有计划 | `dotnet build` + Unity Editor |
| **L2 无头逻辑测试** | 纯 C# 逻辑快速回归 | 涉及帧同步逻辑的计划 | `dotnet run --mode=test --scenario=xxx` |
| **L3 真实链路验收** | 真服务器 + 真客户端 | 涉及网络同步/双端交互的计划 | `Run-BattleAcceptance.ps1 -Scenario xxx` |

不是所有计划都需要全部三层。根据阶段特点选择：

- **纯数学/数据结构变更**（如定点数迁移）：L1 + L2
- **帧同步逻辑变更**（如 Buff 系统）：L1 + L2 + L3
- **纯客户端表现**（如相机/反馈）：L1 + Unity PlayMode

#### 编译验证（所有计划必须有）

```bash
# 服务端编译
dotnet build 'GameServer/Server/Server.sln' -c Debug -v minimal
# 预期：0 error

# 客户端编译（如果改了 GameLogic）
dotnet build 'UnityProject/GameLogic.csproj' -c Debug -v minimal -m:1
# 预期：0 error

# Unity Editor 打开无编译错误
```

#### 无头逻辑测试（帧同步相关计划必须有）

```bash
# 注意：三个 csproj 是单目标 net9.0，必须用 Rider 那套 dotnet 全路径。
# 系统 dotnet 无 net9.0 SDK 会报 NETSDK1045，--framework net8.0 对单目标项目无效。
# 跑 Main.csproj 前先停掉运行中的服务端，否则锁 dll 报 MSB3027。

# 全部自测
"C:/Users/shiwe/.dotnet/dotnet.exe" run --project 'GameServer/Server/Main/Main.csproj' -- --mode=test --scenario=all

# 单场景自测
"C:/Users/shiwe/.dotnet/dotnet.exe" run --project 'GameServer/Server/Main/Main.csproj' -- --mode=test --scenario=prediction-self

# 只验证编译（不受服务端进程锁影响）
"C:/Users/shiwe/.dotnet/dotnet.exe" build 'GameServer/Server/Entity/Entity.csproj' -v q --nologo
```

**自测模式参考**：

| 自测类型 | 用途 | 实现模式 |
|---------|------|---------|
| `DeterminismSelfTest` | 同输入两次仿真，逐帧比较二进制表示 | 相同参数运行两次，任一帧不一致则抛异常 |
| `RollbackSelfTest` | 快照保存 → 推进 N 帧 → 恢复 → 继续，与无中断连续运行逐帧比较 | 验证快照/回滚一致性 |
| `PredictSelfTest` | 客户端预测 → 权威快照校正 → 回滚重播 | 验证预测链路 |
| `SnapshotSelfTest` | 快照 round-trip / hash / dirty merge | 验证快照完整性 |

#### 真实链路验收（双端交互计划必须有）

```bash
# 通过验收脚本
powershell -ExecutionPolicy Bypass -File 'Tools/AutomationAcceptance/Run-BattleAcceptance.ps1' -Scenario 'two-client-buff-lifecycle' -InteractiveEditor
```

**测试场景命名规范**：`{客户端数}-client-{功能}-{场景}`，例如：
- `two-client-basic-move`：双客户端基础移动
- `two-client-buff-lifecycle`：双客户端 Buff 生命周期
- `single-client-prediction`：单客户端预测

**判定标准**：
- 退出码 `0` = PASS
- 服务端/客户端正常启动，无崩溃
- 关键流程日志出现预期关键字（如 `JoinBattle success`、`Buff added`）
- 指定帧的状态/属性/哈希满足预期

#### 验证方式章节格式

计划中的 **验证方式** 章节按以下格式写：

```markdown

- Unity Editor 打开无编译错误

### 自动验证
- `"C:/Users/shiwe/.dotnet/dotnet.exe" run --project 'GameServer/Server/Main/Main.csproj' -- --mode=test --scenario=all`
- Unity EditMode 测试：N 项全部通过

### 一致性验证（如涉及确定性）
- `XxxEntity.DeterminismSelfTest`：同输入两次仿真，所有帧 m_rawValue 完全相等
- `XxxEntity.RollbackSelfTest`：快照恢复 + 重播后状态位级一致

### 自动化验收（如涉及双端交互）
- 场景：`two-client-xxx`
- 预期通过标准：...
```

#### 验收指南文件

涉及双端交互的计划，还需产出验收指南文件到 `Tools/AutomationAcceptance/`，命名格式 `模块名-验收测试指南-日期.md`，包含：

1. **前置条件**：Unity 版本、端口、进程依赖
2. **执行命令**：可直接复制的完整 CLI 命令
3. **预期通过标准**：退出码、report.json 关键字段、日志关键字
4. **失败排查顺序**：按优先级列出排查文件和关注点
5. **相关实现文件**：方便验收 agent 快速定位代码

## Phase 3: 校验 Pipeline

计划写完后，依次执行 4 步校验。每步输出校验结果，发现问题则修改计划后重新校验。

### 3.1 代码可行性扫描

**目的**：确保计划引用的类/接口/方法在代码库中真实存在。

**方法**：
- 从计划中提取所有引用的类名、接口名（通常在"技术决策"和"实现步骤"章节）
- 对每个名称，用 Grep 搜索代码库中的定义
- 检查引用的方法签名是否与实际代码匹配

**输出格式**：
```
✅ FrameSyncPhysicsWorld — 存在于 GameShared/FrameSync/Battle/FrameSyncPhysicsWorld.cs
✅ ISnapshotable<T> — 存在于 GameShared/FrameSync/Snapshot/ISnapshotable.cs
⚠️ ShuttlecockState — 不存在（本阶段新建，符合预期）
❌ PhysicsWorld2D — 不存在（拼写错误？应为 FrameSyncPhysicsWorld）
```

### 3.2 GDD 参数一致性检查

**目的**：确保计划中的设计参数与设计文档一致。

**前提**：此校验仅在存在相关 GDD 文档时执行。如果 Phase 1 中未找到 GDD，跳过此步，在校验总结中标注"⚠️ 无 GDD，参数一致性检查已跳过"。

**方法**：
- 从计划中提取所有数值参数（速度、角度、时间、尺寸等）
- 从相关 GDD 文档中提取对应参数
- 逐一比对，发现不一致则标记

**比对重点**：
- 物理参数（速度、角度、阻力系数、重力）
- 时间参数（窗口时长、硬直时间、动画时间）
- 空间参数（球场尺寸、击球范围、角色高度）
- 公式中的常量和系数

**输出格式**：
```
✅ 水平速度衰减 60%/s — GDD: "水平速度按指数衰减（每秒衰减约 60%）"
✅ 扣杀初速度 22 m/s — GDD: 击球系统参数表
⚠️ 击球范围 1.2m — GDD 定义为 1.2m，但计划中未提及移动中缩小至 0.9m
❌ 网高 1.5m — GDD: 网高 1.55m（边柱）/ 1.524m（中央）
```

### 3.3 总目录边界检查

**目的**：确保计划的范围与阶段总目录的定义一致。

**方法**：
- 读取阶段总目录中当前阶段的定义（聚焦点、核心产出、对应 GDD）
- 读取前序和后续阶段的定义
- 检查：
  - 计划的目标是否与总目录的定义对齐
  - 计划是否越界实现了属于后续阶段的功能
  - 计划是否遗漏了总目录中定义的核心产出
  - 计划的前后衔接是否与依赖图一致

**输出格式**：
```
✅ 目标"建立球场场景和羽毛球物理引擎"对齐总目录 MVP-a 定义
✅ 未越界实现角色移动（属于 MVP-b）
⚠️ 总目录提到"球场与球物理"但计划中缺少网的物理碰撞说明
❌ 计划包含"简单 AI 发球"——这属于 v0.4a 范围
```

### 3.4 实现可行性检查

**目的**：站在实现 agent 的视角，检查计划是否足以让它独立完成工作。

**检查清单**：

1. **上下文充分性**：agent 能理解"为什么做这个"吗？前置依赖和已锁定决策是否交代清楚？
2. **架构方向一致性**（最容易出错）：计划的核心技术选型是否与已锁定决策矛盾？特别检查：
   - 如果总目录锁定了"不用 XX 系统"，计划中是否还在用 XX 系统做核心功能？
   - 本阶段新增的物理/计算逻辑，是否选对了引擎/方法（Box2D vs 纯数学 vs Unity 物理）？
   - 帧命令模式是否用在了"在特定帧触发操作"的场景？
3. **目标明确性**：每条目标是否都能转化为具体的代码任务？避免"优化体验"这种模糊目标。
4. **边界清晰度**：范围/非目标是否足够明确，agent 不会越界？特别注意：如果本阶段不做某个功能，要说清楚。
5. **步骤可执行性**：每步实现步骤是否足够具体，agent 知道要创建什么类、修改什么方法？
6. **参数确定性**：计划中的数值参数是否有出处？标注为"待调优"的参数是否说明了初始值和调优方向？
7. **文件路径精确性**：如果有文件结构，路径是否精确（不是"某目录下"）？
8. **完成标准可验证性**：标准是否真的可验证？不接受"代码编译通过"作为唯一标准。完成标准应覆盖：功能验证（能做什么）、确定性验证（输入一致则输出一致）、工程验证（代码质量、程序集边界）。

**输出格式**：
```
✅ 上下文：有前置依赖 + 已锁定决策 + 现有代码能力说明
✅ 目标：4 条，每条可转化为代码任务
✅ 边界：范围 5 条 + 非目标 4 条，边界清晰
⚠️ 步骤：Step 3 "实现击球判定"偏模糊，agent 可能不确定要创建几个类
❌ 参数：扣杀速度 25 m/s 无出处，GDD 定义为 22 m/s
```

### 3.5 校验总结

4 步校验完成后，输出总结：

```markdown
## 校验结果

| 校验项 | 结果 | 发现问题数 |
|--------|------|-----------|
| 代码可行性 | ✅ 通过 / ⚠️ 有警告 / ❌ 有错误 | N |
| GDD 一致性 | ✅ 通过 / ⚠️ 有警告 / ❌ 有错误 | N |
| 总目录边界 | ✅ 通过 / ⚠️ 有警告 / ❌ 有错误 | N |
| 结构完整性 | ✅ 通过 / ⚠️ 有警告 / ❌ 有错误 | N |

### 必须修正（阻塞项）
[❌ 标记的问题，不修正就不能进入实现]

### 建议修改
[⚠️ 标记的问题，重要但不阻塞]

### 判定: [通过 / 需修改 / 需重大修改]
```

如果判定为"需修改"或"需重大修改"，修正计划后重新跑校验 pipeline，直到通过。
