Source 网络同步（二）客户端预测

Source SDK 2013 源码阅读 · 网络同步四部曲第二篇
game/client/prediction.cpp · game/shared/gamemovement.cpp · game/shared/usercmd.h

上一篇讲的是"服务端怎么把状态送到客户端"。但状态送到时已经晚了 —— 你按下 W 的那一刻，服务端在 100ms 之外。

如果老老实实等服务端确认才移动，操作手感直接毁掉。客户端预测的目标就一句话：让本地输入立即生效，事后再和服务端对账。

这一篇的核心洞察 预测能成立不是因为算法聪明，而是因为一个工程决定：客户端和服务端跑的是同一份移动代码（gamemovement.cpp，141KB）。

同样的输入 + 同样的起始状态 + 同样的代码 = 同样的结果。预测的正确性建立在这个确定性上，而不是建立在"猜得准"上。

一、一次预测的完整时间线

从按键到对账 【客户端 · 第 N 帧】 1. 采集输入 CreateMove 2. 打包成 CUserCmd 带 command_number = N 3. 本地立即执行 RunCommand → gamemovement 4. 存档结果 StorePredictionResults( N ) 5. 发送（含历史命令） WriteUsercmdDeltaToBuffer ↓ 网络延迟 ~50ms 【服务端】 6. 收到命令 N 7. 执行 同一份 gamemovement 8. 结果进快照 ↓ 网络延迟 ~50ms 【客户端 · 第 N+6 帧】 9. 快照到达，说"命令 N 的结果是这样" 10. 对账：预测存档 N ←→ 服务端快照 11a. 一致 → 走优化路径，只跑最新那条命令 11b. 不一致 → 回滚到 N，重跑 N+1..N+6

注意第 4 步和第 10 步的配对：不存档就没法对账。这是第三篇的主题，本篇先讲清楚 1-8 步。

二、CUserCmd：预测的输入单元

整套机制的原子是 CUserCmd —— 一条"玩家在某一刻做了什么"的记录。

game/shared/usercmd.h（字段节选）
int     command_number;    // ★ 序号，对账的钥匙
int     tick_count;        // 客户端的 tick，延迟补偿要用（第四篇）
QAngle  viewangles;        // 视角
float   forwardmove, sidemove, upmove;
int     buttons;           // 按键位图
int     random_seed;       // ★ 共享随机数的种子，见 §5
bool    hasbeenpredicted;  // ★ 本地标记：这条跑过没有

command_number 是对账的钥匙。服务端确认"我处理完了命令 N"，客户端才知道该拿哪个存档去比。

2.1 为什么一次要发多条历史命令

UDP 会丢包。如果每个包只带一条命令，丢一个包就意味着那一刻的输入永久丢失 —— 玩家按下的跳跃直接消失。

Source 的做法是每个包携带最近若干条命令，并用 delta 编码压缩（相邻命令差异很小）。服务端收到后按 command_number 去重，补上漏掉的。

这个思路和 KCP 的对照 KCP 用 ARQ 重传解决丢包：丢了就重发，保证送达。
UserCmd 用冗余解决丢包：不等发现丢包，直接每次都多带几条。

差别在于输入有时效性。100ms 后才重传到的跳跃指令，玩家已经不想跳了。所以宁可浪费带宽也不能等重传 —— 和 KCP "用带宽换延迟"是同一种取舍，只是更极端。

三、共用移动代码：预测正确的必要条件

这是整篇最重要的一节。

game/shared/gamemovement.cpp 这个路径里的 shared 是字面意思：这个文件被编译进客户端 DLL 和服务端 DLL 两次。

3.1 编译期怎么做到的

靠 #ifdef CLIENT_DLL 和一层 typedef。同一个符号 CBasePlayer 在两边指向不同的类：

// 客户端编译时
#define CBasePlayer C_BasePlayer

// 服务端编译时：CBasePlayer 就是 CBasePlayer

所以 gamemovement.cpp 里写 CBasePlayer *player，在客户端编译出来操作的是 C_BasePlayer，在服务端操作的是 CBasePlayer。一份源码，两个二进制，行为一致。

3.2 为什么"一致"是必要条件而非优化

假设两边移动代码有任何差异 —— 比如客户端的摩擦力算法少了一个 clamp。那么：

  • 每一帧预测都会产生微小误差
  • 每一帧都判定"预测失败"
  • 每一帧都触发误差修正和插值重置
  • 玩家体验：移动持续抖动，且找不到原因

预测不是"猜"，是"用相同的确定性函数算出相同的结果"。一旦确定性被破坏，整套机制从"偶尔纠错"退化成"永久纠错"，比不做预测更糟。

这条对 Unity 项目的意义最直接 如果你在 Unity 里做预测，客户端和服务端必须调用同一个移动函数，不能是"客户端一套 CharacterController，服务端一套物理"。

更隐蔽的破坏源：Time.deltaTime（每帧不同）、Random（两边序列不同）、浮点运算顺序差异、以及 Unity 物理引擎本身的非确定性。后者是最难缠的 —— Rigidbody 在不同帧率下结果不同，这就是为什么帧同步/预测类项目往往要自己写移动而不用内置物理。

4.1 哪些命令会被重放

关键判据是 hasbeenpredicted：

game/client/prediction.cpp:1632
m_bFirstTimePredicted = !cmd->hasbeenpredicted;

循环末尾置 cmd->hasbeenpredicted = true。所以：

  • 第一次跑某条命令 → m_bFirstTimePredicted == true
  • 重放同一条命令 → false

这个标志是重放机制的灵魂，下一节专讲。

五、两个"跑两遍不能出错"的问题

同一条命令被跑多次，会撞上两类麻烦。Source 各有一套解法，都很值得学。

5.1 副作用：一枪五响问题

命令 N 里包含"开火"。第一次预测时播了枪声、生成了弹壳。重放 5 次 → 枪声响 5 次。

解法是三层：

第一层：全局抑制开关。RunSimulation 开头：

game/client/prediction.cpp:1208
IPredictionSystem::SuppressEvents( !IsFirstTimePredicted() );

第二层：游戏代码显式判断。TF2 里数十处 if ( IsFirstTimePredicted() ) 包裹音效、粒子、震动。

第三层（最漂亮的一层）：服务端反向配合。

game/server/recipientfilter.cpp:115 等处
// IPredictionSystem::GetSuppressHost() 让服务端把本地玩家
// 从特效/声音的接收者列表里剔除

客户端自己预测出的效果，服务端不再重复发一遍。不只是客户端"重放时闭嘴"，还有服务端"知道你已经自己演过了"。这一层配合是 Source 预测系统成熟度的体现。

Unity 落地时这是最容易漏、症状最明显的坑 你需要一个全局可查的 IsReplaying 标志，并且所有产生副作用的代码都要检查它：音效、粒子、震动、UI 提示、成就计数、分析埋点。

漏一个的症状很好认（一枪五响、成就+5），但如果漏的是分析埋点，你可能几个月后才发现数据被污染了。

5.2 随机数：后坐力怎么两端一致

这是我认为整套设计里最精彩的一个点。

问题：开枪有弹道散射、后坐力抖动，这些是随机的。客户端预测时随机出 A，服务端算的时候随机出 B —— 必然不一致，且每次开枪都不一致。

朴素解法是"随机数只由服务端算，客户端不预测开火" —— 那开火手感就毁了。

Source 的解法：让随机数变成输入的函数。

game/shared/util_shared.cpp:142-155
static int SeedFileLineHash( int seedvalue, const char *sharedname, int additionalSeed )
{
    CRC32_t retval;  CRC32_Init( &retval );
    CRC32_ProcessBuffer( &retval, &seedvalue, sizeof( int ) );
    CRC32_ProcessBuffer( &retval, &additionalSeed, sizeof( int ) );
    CRC32_ProcessBuffer( &retval, (void *)sharedname, Q_strlen( sharedname ) );
    CRC32_Final( &retval );  return (int)( retval );
}

然后 SharedRandomFloat / SharedRandomInt / SharedRandomVector 都是同一模式：种子 = hash(命令的 random_seed, 调用点字符串, 附加种子)，然后 RandomSeed(seed) + RandomFloat()。

种子随每条 usercmd 设置（prediction.cpp:753），命令结束时清空（:768）。

三个设计要点

(1) 种子绑定命令，不绑定时间。这是重放能收敛的前提 —— 重放同一条命令，得到完全相同的随机序列。如果种子来自 Time.time 或帧号，重放就会产生不同结果。

(2) 调用点字符串参与 hash。同一条命令里可能有多个随机调用（后坐力、散射、暴击判定）。用字符串区分后，它们各自独立，不会因为调用顺序变化而串味。

对比朴素方案"一个命令一个种子，按调用顺序取随机数"：如果某个分支条件让客户端少调了一次随机，后面所有随机数全部错位。用调用点名字做 key 就免疫这个问题。

(3) 断言保护。Assert( GetPredictionRandomSeed() != -1 ) —— 在预测上下文外调用会被抓住。

C# 里的等价写法 
public static float SharedRandom(string callSite, int extraSeed = 0)
{
    int seed = HashCombine(_currentCmd.RandomSeed, callSite.GetHashCode(), extraSeed);
    return new System.Random(seed).NextSingle();  // 或用无分配的确定性 PRNG
}

// 调用处：字符串写死，两端必须一致
float spread = SharedRandom("WeaponSpread") * _maxSpread;
注意：不要用 System.Random 在热路径上（每次 new 会分配）。实际项目用 xorshift 之类的确定性 PRNG，把状态放在栈上。

另外 C# 的 string.GetHashCode() 跨进程不保证一致（.NET 有随机化 hash seed）。要用固定算法自己算，比如 FNV-1a。这个坑很隐蔽，会导致"本地测试正常、联机就散射不同步"。

一个诚实的例外

TF2 里 GetPredictionRandomSeed 有个参数 bUseUnSyncedServerPlatTime（c_baseentity.h:1233），部分武器传 UseServerRandomSeed()。

意思是：有一部分随机是故意不同步的，某些武器的散射刻意只由服务端决定，客户端无法预测。这是明确的取舍点 —— 大概是为了防止客户端通过预测提前知道散射方向。

六、预测的边界：什么不预测

Valve 划界限划得很清楚，而且态度务实 —— 做不对的就不做，然后想办法缩小损害。

6.1 其他玩家：完全不预测

game/client/c_baseplayer.cpp:2324-2334
if ( IsLocalPlayer() ) return true;
return false;

本地玩家走预测（即时但可能错），其他玩家走插值（滞后但平滑）。命中判定交给服务端的延迟补偿。

这是 Source 网络模型的基本分工，不是缺陷。三条路径各管一段，第四篇会把它们拼起来。

6.2 视角：索性不预测

视角来自本地鼠标输入，本来就是零延迟的，根本不需要预测。所以 _Update 直接两次强制覆盖：

game/client/prediction.cpp:1750-1754, 1790-1791
engine->GetViewAngles( viewangles );
localPlayer->SetLocalAngles( viewangles );
// … PerformPrediction 之后 …
localPlayer->SetLocalAngles( viewangles );   // 再覆盖一次

注释是 // Always using current view angles no matter what。配套地把 m_angNetworkAngles 标为不参与误差比对（第三篇细讲）。

6.3 血量与伤害：只保证语义正确

伤害计算需要服务端才有的信息（其他玩家真实位置、命中判定、护甲、buff）。客户端预测不出准确血量。

TF2 的处理很聪明 —— 加了一个 flag，只在"跨零"时才算误差：

public/datamap.h:236（TF2 分支）
// Only throw a prediction error if this changes from > 0 -> <= 0
FTYPEDESC_ONLY_ERROR_IF_ABOVE_ZERO_TO_ZERO_OR_BELOW_ETC

血量数值预测不准无所谓，但"活着 vs 死了"必须一致。这是把"容差"概念从数值域推广到语义域 —— 我觉得这个思路很有启发性。

6.4 武器逻辑：承认失败，局部关闭

最诚实的一批。cl_predictweapons 可以整体关闭武器预测，而且大量武器计时字段被标记为"不比对"。配套注释：

game/client/c_basecombatweapon.cpp:522-532
// Although I have tried to fix many of the pred errors in HL2MP.
// Still many remain, and many things remain unpredictable
// without a rewrite of the weapon code.

这段注释比任何设计文档都有教学价值 —— 它告诉你哪些东西是真的难。武器逻辑涉及大量状态机、计时器、弹药、换弹中断，每一个都是预测误差的来源。

6.5 严重滞后：直接放弃

game/client/prediction.cpp:1620, 1691-1695
if ( i >= MULTIPLAYER_BACKUP ) break;
// Somehow we looped past the end of the list (severe lag), don't predict at all

MULTIPLAYER_BACKUP = 90，66 tick 下约 1.36 秒。环形缓冲的容量直接决定了系统能容忍的最大延迟。超了就不预测。

Unity 落地要点：超容量时放弃，不要绕回覆盖 绕回覆盖会让你比对到错误的历史帧，产生假误差 —— 而且是那种"看起来在正常工作但结果全错"的假误差，比直接不预测危险得多。

七、一个容易被忽略的细节：站在移动平台上

重放之前有一步处理，不看代码想不到：

game/client/prediction.cpp:1583-1591
// undo interpolation changes for entities we stand on
C_BaseEntity *entity = localPlayer->GetGroundEntity();
while ( entity && entity->entindex() > 0)
{
    entity->MoveToLastReceivedPosition();
    entity = entity->GetMoveParent();
}

你脚下的平台正在被插值系统平滑处理（因为它是远程实体）。但预测必须用它的权威位置，否则平台的插值误差会传导成你的预测误差。

这是"三套时间轴机制互相干扰"的第一个具体案例。预测（提前）和插值（延后）在这里正面冲突，Source 的裁决是：预测优先，临时把平台拉回权威位置。

Unity 里同样会遇到 如果玩家站在一个网络同步的移动平台上（电梯、船、传送带），而平台走的是插值路径，你的预测就必须临时使用平台的最新快照位置而非插值位置。

症状：站在电梯上时角色轻微抖动或缓慢下沉。根因和现象距离很远，值得提前知道。

八、调试手段

convar作用
cl_predict总开关。关掉可以直接对比"有无预测"的手感差异
cl_predictweapons只关武器预测，保留移动预测
cl_showerror打印预测误差数值 —— 最有用的一个
cl_pred_optimize0/1/2 控制优化路径（第三篇细讲）
cl_pdump屏幕上实时 dump 预测字段的值

还有个编译期开关 PREDICTION_ERROR_CHECK_LEVEL（默认 0）。调高时会取消所有浮点容差，逼出全部细微不一致 —— 开发期排查用。

值得照抄的调试设计 cl_showerror 这个开关的价值在于：预测误差是个不可见的量，不打印出来你根本不知道有没有、有多大。

自己做预测系统时，第一天就该做一个"误差可视化"：打印数值、画出预测位置和权威位置的差异线。否则你只能靠"手感不对"来 debug，那几乎是不可能的。

九、Unity 落地要点

9.1 确定性是地基，先验证它

在写任何预测逻辑之前，先做这个测试：同一个输入序列 + 同一个起始状态，跑两次，结果必须逐位相同。

常见的确定性杀手： Time.deltaTime（用固定 tick 代替）、 UnityEngine.Random（用共享种子 PRNG 代替）、 内置物理引擎（往往要自己写移动）、 foreach 遍历 Dictionary（顺序不保证）。

9.2 输入用冗余而非重传

每个包带最近 N 条命令（Source 的做法），而不是靠可靠传输重发。输入有时效性，迟到的输入等于丢失的输入。

9.3 共享随机数用"调用点名字"做 key

不要用"调用顺序"。顺序会因分支变化而错位，名字不会。注意 C# 的 string.GetHashCode() 跨进程不稳定，要自己实现 FNV-1a 之类的固定哈希。

9.4 划清不预测的边界，并接受它

Valve 的态度值得学：其他玩家不预测、伤害不预测、做不对的武器逻辑局部关闭。硬撑着全部预测，结果是全都不准。

9.5 第一天就做误差可视化

见 §8。这不是"以后再优化"的事，是"没有它就无法开发"的事。
