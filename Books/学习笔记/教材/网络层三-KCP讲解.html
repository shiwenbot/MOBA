网络层（三）KCP —— 把保证造回来

Fantasy 源码阅读 · 传输层三部曲第三篇
Network/Protocol/KCP/ · 算法核心 1367 行

前两篇铺完了：TCP 把可靠有序外包给内核，UDP 把这些全丢掉换来低延迟和数据报语义。

KCP 的定位是 「用 10%~20% 的带宽浪费，换 30%~40% 的延迟降低」。它不追求 TCP 那样的公平和效率，只追求「快」。手游选它是因为：卡一下比慢一点更致命。

这一篇分两层读：

  • 算法层（Base/c/kcp.cs，1367 行）：ARQ 重传、RTO 估算、快速重传、拥塞窗口。从 C 版 kcp 逐行移植，是全项目唯一有算法分量的代码。
  • 集成层（KCPClientNetwork.cs 的剩余部分）：Fantasy 如何驱动这个算法 —— 时间轮、零拷贝、断线策略。
读法建议 Base/c/kcp.cs 是 C 代码的机械翻译，充斥 IQUEUEHEAD* 裸指针和 iqueue_add_tail 这类宏改写。不要试图通读。

按本篇顺序，只读六个函数：ikcp_send → ikcp_input → ikcp_parse_data → ikcp_recv → ikcp_flush → ikcp_update。这六个撑起了整个协议，加起来约 500 行，其余是编解码和链表操作。

一、24 字节里的全部秘密

先看协议头。KCP 的所有能力都编码在这 24 字节里，理解它们相当于理解了一半。

Network/Protocol/KCP/Base/include/kcp.cs
internal unsafe struct IKCPSEG
{
    public IQUEUEHEAD node;   // 链表节点，不上网
    public uint conv;         // ↓ 以下 24 字节要上网
    public uint cmd;
    public uint frg;
    public uint wnd;
    public uint ts;
    public uint sn;
    public uint una;
    public uint len;
    public uint resendts;     // ↓ 以下是本地状态，不上网
    public uint rto;
    public uint fastack;
    public uint xmit;
    public fixed byte data[1];  // 柔性数组，实际长度 = len
}

上网的部分由 ikcp_encode_seg 按序写出：

KCP 头 24 字节布局 偏移 0 4 5 6 8 12 16 20 24 ├────────┼────┼────┼──────┼──────────┼──────────┼──────────┼─────────┤ │ conv │cmd │frg │ wnd │ ts │ sn │ una │ len │ data… │ u32 │ u8 │ u8 │ u16 │ u32 │ u32 │ u32 │ u32 │ └────────┴────┴────┴──────┴──────────┴──────────┴──────────┴─────────┘
字段含义支撑的能力
conv会话号，Fantasy 传的是 ChannelId校验归属：if (conv != kcp->conv) return -1;
cmd81=PUSH 82=ACK 83=WASK 84=WINS四种报文类型
frg分片倒序号，0 表示末片分片重组
wnd发送方剩余接收窗口流量控制
ts发送时刻RTT 测量（ACK 带回原 ts）
sn包序号有序、去重、选择性重传
una「我已连续收到 una 之前的全部」累积确认，一次清一批
lendata 长度一个 UDP 包里塞多个 seg

sn + una 的组合是 KCP 效率的关键。una 是累积确认（像 TCP 的 ACK），一个字段就能确认一大批；sn 配合 ACK 报文是选择性确认，能精确确认乱序到达的单个包。两者并用，既省带宽又能精确重传。

二、发送侧：ikcp_send 只做分片

第一个反直觉的点：ikcp_send 不发送任何数据。它只做一件事 —— 把用户 buffer 切成 MSS 大小的段，挂进 snd_queue 链表。

if (len <= (int)kcp->mss) count = 1;
else count = (int)((len + kcp->mss - 1) / kcp->mss);   // 向上取整

if (kcp->stream == 0 && count > 255) return -2;      // frg 是 u8，最多 255 片
if (count >= (int)kcp->rcv_wnd) return -2;         // 超过对端窗口，拒绝

for (i = 0; i < count; i++)
{
    int size = len > (int)kcp->mss ? (int)kcp->mss : len;
    seg = ikcp_segment_new(kcp, size);
    memcpy(seg->data, buffer, (nuint)size);

    seg->len = (uint)size;
    seg->frg = (uint)((kcp->stream == 0) ? (count - i - 1) : 0);   // ← 倒序

    iqueue_add_tail(&seg->node, &kcp->snd_queue);
    kcp->nsnd_que++;
    buffer += size;  len -= size;
}

2.1 frg 为什么是倒序

seg->frg = count - i - 1。发 3 片时 frg 依次是 2, 1, 0。

好处是接收侧不需要知道总片数就能判断完整性 —— 看到 frg == 0 就知道到末片了。对比正序方案（0,1,2）：接收侧必须额外传一个「总数」字段，或者等超时才敢断定收完。

这个技巧在 ikcp_peeksize 里直接兑现：

public static int ikcp_peeksize(IKCPCB* kcp)
{
    if (iqueue_is_empty(&kcp->rcv_queue)) return -1;

    seg = iqueue_entry<IKCPSEG>(kcp->rcv_queue.next);
    if (seg->frg == 0) return (int)seg->len;        // 单片，直接返回

    if (kcp->nrcv_que < seg->frg + 1) return -1;      // 队列里凑不够片数，还没齐

    for (p = kcp->rcv_queue.next; p != &kcp->rcv_queue; p = p->next)
    {
        seg = iqueue_entry<IKCPSEG>(p);
        length += (int)seg->len;
        if (seg->frg == 0) break;                      // 走到末片，收工
    }
    return length;
}

nrcv_que < seg->frg + 1 这行是一次廉价预检：首片说自己后面还有 frg 片，那队列里至少要有 frg+1 个才可能完整。不够就直接返回 -1，省掉整个遍历。

这是 Fantasy 集成层的直接依赖 KCPClientNetwork.Input() 里 peekSize = _kcp.PeekSize() 返回 < 0 就退出循环，正是靠这个「-1 表示还没齐」的约定。「先问长度、再按长度取」这套 API 设计让调用方能精确分配 buffer，不用猜。

2.2 stream 模式：Fantasy 没开

ikcp_send 前半段有一大块 if (kcp->stream != 0) 的逻辑，做的是「把新数据追加到上一个未满的 segment 里」—— 也就是让 KCP 退化成字节流，像 TCP 一样。

Fantasy 没有调用 SetStreamMode，所以 stream 恒为 0，这段代码是死路。可以跳过。

但要理解这个选择的含义：Fantasy 走的是「消息模式」—— 一次 Send 对应一次完整交付，边界由 frg 维护。这正是第二篇里 BufferPacketParser 能省掉分包粘包状态机的根本原因。如果哪天有人开了 stream 模式，那个解析器会立刻出错。

三、接收侧：三个队列的流水线

KCP 内部有四个链表，理解它们的分工是读懂算法的前提：

四个队列 发送方向 ┌─────────────┐ flush 时按窗口搬运 ┌────────────┐ │ snd_queue │ ────────────────────→ │ snd_buf │ ──→ 网络 │ 待发，无序号 │ 受 cwnd/rmt_wnd 限制 │ 已发，等 ACK │ └─────────────┘ └────────────┘ ↑ ACK 到达后删除 接收方向 ┌─────────────┐ sn 连续时搬运 ┌────────────┐ │ rcv_buf │ ────────────────────→ │ rcv_queue │ ──→ 用户 │ 已收，可乱序 │ 按 rcv_nxt 顺序 │ 有序，可交付 │ └─────────────┘ └────────────┘

「buf 存乱序，queue 存有序」是这套设计的核心。乱序到达的包先在 rcv_buf 里按 sn 插入排好，只有当 sn == rcv_nxt（正好是下一个期待的）时才搬进 rcv_queue。这就是「有序交付」的实现。

3.1 ikcp_input：拆包 + 分发

一个 UDP 数据报里可能塞了多个 segment，所以是 while (true) 循环拆：

while (true)
{
    if (size < (int)IKCP_OVERHEAD) break;         // 不足 24 字节，收工

    data = ikcp_decode32u(data, &conv);
    if (conv != kcp->conv) return -1;            // ← 会话校验

    // …依次解出 cmd/frg/wnd/ts/sn/una/len

    if (cmd != IKCP_CMD_PUSH && cmd != IKCP_CMD_ACK &&
        cmd != IKCP_CMD_WASK && cmd != IKCP_CMD_WINS)
        return -3;                                 // 未知命令，整包丢弃

    kcp->rmt_wnd = wnd;              // ① 无论什么包，都更新对端窗口
    ikcp_parse_una(kcp, una);        // ② 累积确认，批量清 snd_buf
    ikcp_shrink_buf(kcp);            // ③ 重算 snd_una

    // ④ 按 cmd 分头处理…
}

①②③ 三步对所有报文类型无条件执行，这是 KCP 的一个效率设计：每个包都携带 wnd 和 una，所以哪怕收到的是一个纯数据包，也能顺带更新窗口和清理已确认的发送缓冲。控制信息搭数据包的车，不额外占带宽。

三个「清理」函数分工：

函数做什么依据
ikcp_parse_una删除 snd_buf 里所有 sn < una 的段累积确认，批量
ikcp_parse_ack删除 snd_buf 里 sn == 指定值 的单个段选择性确认
ikcp_shrink_buf把 snd_una 更新为 buf 里最小的 sn删完后重算水位

3.2 序号比较：必须用 _itimediff

public static long _itimediff(uint later, uint earlier)
    => (int)(later - earlier);   // 关键：uint 相减，转 int

全文所有序号和时间戳比较都走这个函数，一处都没有直接用 < / >。

原因是回绕（wraparound）。sn 和 ts 都是 uint，会溢出归零。假设 later = 5（刚回绕），earlier = 0xFFFFFFF0：

  • 直接比较：5 < 0xFFFFFFF0 → 「5 更早」 → 错
  • _itimediff：5 - 0xFFFFFFF0 = 21（uint 环绕），转 int 为 21 > 0 → 「5 更晚」 → 对

成立条件是两个值的真实差距小于 2³¹。对序号和毫秒时间戳都远远满足。

这是所有滑动窗口协议的必备工具 自己实现任何带序号的协议（帧同步的帧号、状态同步的版本号、消息去重的 ID），只要用了定长无符号整数就必须这么比。写 if (seq > lastSeq) 的那一刻，就埋了一个平均 49 天后爆发的 bug（uint 毫秒时间戳的回绕周期）。

Fantasy 集成层的 IsTimeGreaterThan 是同一思路的另一种写法，见 §6.2。

3.3 ikcp_parse_data：乱序插入 + 顺序搬运

public static void ikcp_parse_data(IKCPCB* kcp, IKCPSEG* newseg)
{
    uint sn = newseg->sn;

    // 窗口外 或 已经交付过的 → 丢弃
    if (_itimediff(sn, kcp->rcv_nxt + kcp->rcv_wnd) >= 0 ||
        _itimediff(sn, kcp->rcv_nxt) < 0)
    {
        ikcp_segment_delete(kcp, newseg);
        return;
    }

    // 从尾往头找插入点（新包通常序号大，尾部命中快）
    for (p = kcp->rcv_buf.prev; p != &kcp->rcv_buf; p = prev)
    {
        IKCPSEG* seg = iqueue_entry<IKCPSEG>(p);
        prev = p->prev;
        if (seg->sn == sn) { repeat = 1; break; }     // ← 去重
        if (_itimediff(sn, seg->sn) > 0) break;        // 找到位置
    }

    if (repeat == 0) { iqueue_add(&newseg->node, p); kcp->nrcv_buf++; }
    else              { ikcp_segment_delete(kcp, newseg); }

    // rcv_buf → rcv_queue：只搬连续的
    while (!iqueue_is_empty(&kcp->rcv_buf))
    {
        IKCPSEG* seg = iqueue_entry<IKCPSEG>(kcp->rcv_buf.next);
        if (seg->sn == kcp->rcv_nxt && kcp->nrcv_que < kcp->rcv_wnd)
        {
            iqueue_del(&seg->node);          kcp->nrcv_buf--;
            iqueue_add_tail(&seg->node, &kcp->rcv_queue);  kcp->nrcv_que++;
            kcp->rcv_nxt++;                  // 期待值前进
        }
        else break;                           // 断档了，停
    }
}

去重、有序、窗口限制三件事全在这一个函数里。三十行代码解决了 UDP 丢掉的三个保证中的两个（有序、去重）。

两个细节：

  • 从尾部反向查找。正常情况新包序号最大，插尾部，第一次比较就命中，O(1)。只有乱序时才往前找。这是针对「大多数包按序到达」这个事实的优化。
  • nrcv_que < rcv_wnd 是搬运条件之一。接收队列满了就不再搬，让包积压在 rcv_buf。这个背压最终通过 wnd 字段告知对端 —— 见 ikcp_wnd_unused。

3.4 ikcp_recv：合并分片 + 二次搬运

// merge fragment
for (len = 0, p = kcp->rcv_queue.next; p != &kcp->rcv_queue;)
{
    seg = iqueue_entry<IKCPSEG>(p);  p = p->next;

    memcpy(buffer, seg->data, (nuint)seg->len);   // 拼进用户 buffer
    buffer += seg->len;   len += (int)seg->len;
    fragment = (int)seg->frg;

    iqueue_del(&seg->node);  ikcp_segment_delete(kcp, seg);  kcp->nrcv_que--;

    if (fragment == 0) break;                       // 末片，一条消息完整了
}

// 又搬一次 rcv_buf → rcv_queue（因为刚腾出了空位）
while (!iqueue_is_empty(&kcp->rcv_buf)) { /* 同 parse_data */ }

// fast recover
if (kcp->nrcv_que < kcp->rcv_wnd && recover != 0)
{
    kcp->probe |= IKCP_ASK_TELL;      // 主动告知对端"我腾出空间了"
}

最后那个 fast recover 是个漂亮的优化。recover 在函数开头被置位（if (kcp->nrcv_que >= kcp->rcv_wnd) recover = 1;），表示「进来时窗口是满的」。

场景：接收窗口满了 → 上报 wnd = 0 → 对端停止发送 → 用户 Receive 腾出空间。此时若不主动通知，对端要等到 IKCP_PROBE_INIT = 7000ms 后才会来探测窗口。7 秒的静默。

所以这里立刻标记 IKCP_ASK_TELL，下次 flush 会发一个 IKCP_CMD_WINS 主动告知新窗口。把 7 秒缩短到一个 interval（5ms）。

四、可靠的核心：ikcp_flush

239 行，KCP 最长也最重要的函数。所有实际的网络发送都发生在这里，其余函数只是在改状态。

它按顺序做六件事：

ikcp_flush 的六个阶段 ① 发 ACK 列表 acklist → IKCP_CMD_ACK ② 窗口探测 rmt_wnd == 0 时发 WASK / 收到 WASK 则发 WINS ③ 计算发送窗口 cwnd = min(snd_wnd, rmt_wnd, cwnd) ④ snd_queue → snd_buf 按窗口搬运，分配 sn ⑤ 遍历 snd_buf 决定谁要发 ← 重传逻辑全在这里 ⑥ 拥塞控制调整 根据 lost / change 调 cwnd 和 ssthresh

第一行就有个前提：

if (kcp->updated == 0) return;   // 'ikcp_update' haven't been called.

没调过 ikcp_update 就什么都不做。因为 kcp->current（当前时间）还没被设置过，所有基于时间的判断都会算错。这是「时间由外部注入」这个设计的必然约束 —— 见 §5。

4.1 阶段⑤：三种发送触发条件

整个 KCP 的可靠性就在这个循环里：

for (p = kcp->snd_buf.next; p != &kcp->snd_buf; p = p->next)
{
    IKCPSEG* segment = iqueue_entry<IKCPSEG>(p);
    int needsend = 0;

    if (segment->xmit == 0)
    {
        // ═══ 情况 A：首次发送 ═══
        needsend = 1;
        segment->xmit++;
        segment->rto = (uint)kcp->rx_rto;
        segment->resendts = current + segment->rto + rtomin;
    }
    else if (_itimediff(current, segment->resendts) >= 0)
    {
        // ═══ 情况 B：超时重传 ═══
        needsend = 1;
        segment->xmit++;   kcp->xmit++;

        if (kcp->nodelay == 0)
            segment->rto += _imax_(segment->rto, (uint)kcp->rx_rto);   // ×2 退避
        else
        {
            int step = (kcp->nodelay < 2) ? ((int)(segment->rto)) : kcp->rx_rto;
            segment->rto += (uint)(step / 2);                        // ×1.5 退避
        }

        segment->resendts = current + segment->rto;
        lost = 1;        // ← 标记丢包，阶段⑥要用
    }
    else if (segment->fastack >= resent)
    {
        // ═══ 情况 C：快速重传 ═══
        if ((int)segment->xmit <= kcp->fastlimit || kcp->fastlimit <= 0)
        {
            needsend = 1;
            segment->xmit++;
            segment->fastack = 0;
            segment->resendts = current + segment->rto;
            change++;      // ← 标记快重传，阶段⑥要用
        }
    }
    // …needsend 则编码进 buffer，满 MTU 就 output 一次
}

A 首次发送 —— rtomin 的作用

rtomin = (uint)((kcp->nodelay == 0) ? (kcp->rx_rto >> 3) : 0);

普通模式下首包的超时时间额外加 rto/8 的余量；nodelay 模式下这个余量是 0，超时判定更激进 —— 宁可多重传也不多等。Fantasy 开了 nodelay，所以走后者。

B 超时重传 —— 退避策略的差异

nodelay退避公式倍率含义
0rto += max(rto, rx_rto)约 ×2TCP 式指数退避，对网络友好
1rto += rto / 2×1.5缓和退避，重传更积极
2rto += rx_rto / 2线性最激进，几乎不退避

Fantasy 传的是 nodelay = 1，取 ×1.5。退避越缓，丢包时恢复越快，但重复发送越多。这就是「用带宽换延迟」的具体兑现点之一。

C 快速重传 —— 不等超时

这是 KCP 相比朴素 ARQ 的关键提升。segment->fastack 的累加发生在 ikcp_parse_fastack：

for (p = kcp->snd_buf.next; p != &kcp->snd_buf; p = next)
{
    IKCPSEG* seg = iqueue_entry<IKCPSEG>(p);
    if (_itimediff(sn, seg->sn) < 0) break;
    else if (sn != seg->sn) seg->fastack++;   // 比我序号大的被确认了
}

逻辑：收到 sn=10 的 ACK，说明 10 已经到达对端。那 snd_buf 里所有 sn < 10 还没被确认的段（比如 7），就被跳过了一次 —— seg[7].fastack++。

攒够 resent = fastresend = 2 次跳过，就认定 7 是丢了（而不是慢了），立刻重传。

快速重传示例（fastresend = 2） 发送: 6 7 8 9 10 11 7 丢了 ↓ 收到 ACK: 6 ... 8 ... 9 ... 10 │ │ │ ↓ ↓ ↓ seg[7].fastack: 1 → 2 → 触发！ 此时不等 RTO 超时（可能 100ms+），直接重传 7 vs 纯超时重传：要等 resendts 到点

fastlimit（默认 5）限制同一个段最多被快重传几次，防止在极差网络下无限快重传把带宽打满。

4.2 阶段⑥：拥塞控制

if (change != 0)          // 发生过快速重传
{
    uint inflight = kcp->snd_nxt - kcp->snd_una;   // 在途包数
    kcp->ssthresh = inflight / 2;
    if (kcp->ssthresh < IKCP_THRESH_MIN) kcp->ssthresh = IKCP_THRESH_MIN;
    kcp->cwnd = kcp->ssthresh + resent;            // 温和下调
    kcp->incr = kcp->cwnd * kcp->mss;
}

if (lost != 0)            // 发生过超时重传
{
    kcp->ssthresh = cwnd / 2;
    if (kcp->ssthresh < IKCP_THRESH_MIN) kcp->ssthresh = IKCP_THRESH_MIN;
    kcp->cwnd = 1;                                // ← 直接砸到 1！
    kcp->incr = kcp->mss;
}

两种丢包信号的惩罚力度差了一个数量级，这个区分很讲究：

信号推断惩罚
change（快重传）个别包丢了，但链路还通（因为后续包的 ACK 回来了）cwnd 降到 ssthresh + resent
lost（超时）可能整条路断了 / 严重拥塞（连 ACK 都没有）cwnd = 1，退回慢启动

增长侧在 ikcp_input 末尾，是标准的慢启动 + 拥塞避免：

if (_itimediff(kcp->snd_una, prev_una) > 0)   // 本次 input 有新数据被确认
{
    if (kcp->cwnd < kcp->rmt_wnd)
    {
        uint mss = kcp->mss;
        if (kcp->cwnd < kcp->ssthresh)
        {
            kcp->cwnd++;                    // 慢启动：每 RTT 翻倍
            kcp->incr += mss;
        }
        else
        {
            if (kcp->incr < mss) kcp->incr = mss;
            kcp->incr += (mss * mss) / kcp->incr + (mss / 16);   // 拥塞避免：每 RTT +1
            if ((kcp->cwnd + 1) * mss <= kcp->incr)
                kcp->cwnd = (kcp->incr + mss - 1) / mss;
        }
        if (kcp->cwnd > kcp->rmt_wnd) { /* 夹到对端窗口 */ }
    }
}

incr 是字节级的小数累加器 —— 拥塞避免阶段每个 RTT 只该涨 1 个 MSS，但 ACK 是一个个来的，直接 cwnd++ 会涨太快。用 incr 攒够一个 MSS 才把 cwnd 加 1，实现「平滑增长」。

但 Fantasy 把这一整套关掉了 SetNoDelay(1, 5, 2, 1) 第四个参数 nc = 1 即 nocwnd = 1。看阶段③：

cwnd = _imin_(snd_wnd, rmt_wnd);
if (kcp->nocwnd == 0) cwnd = _imin_(kcp->cwnd, cwnd); // ← 被跳过

拥塞窗口 kcp->cwnd 仍在计算，但不参与发送决策。实际窗口只受配置的 snd_wnd（客户端 2048）和对端 rmt_wnd 限制。

这是「无视网络拥塞，全速发」。对小流量的游戏消息可以接受，但如果哪天要传大文件或高频状态同步，这个配置需要重新评估 —— 它可能在弱网下把链路打爆，反而加剧丢包。

4.3 RTO 估算

public static void ikcp_update_ack(IKCPCB* kcp, int rtt)
{
    if (kcp->rx_srtt == 0)
    {
        kcp->rx_srtt = rtt;
        kcp->rx_rttval = rtt / 2;
    }
    else
    {
        long delta = rtt - kcp->rx_srtt;
        if (delta < 0) delta = -delta;
        kcp->rx_rttval = (int)((3 * kcp->rx_rttval + delta) / 4);   // 抖动，α=1/4
        kcp->rx_srtt = (7 * kcp->rx_srtt + rtt) / 8;              // 平滑，α=1/8
        if (kcp->rx_srtt < 1) kcp->rx_srtt = 1;
    }

    rto = (int)(kcp->rx_srtt + _imax_(kcp->interval, (uint)(4 * kcp->rx_rttval)));
    kcp->rx_rto = (int)_ibound_((uint)kcp->rx_minrto, (uint)rto, IKCP_RTO_MAX);
}

这是 Jacobson/Karels 算法，和 TCP 用的同一套：

  • rx_srtt：平滑 RTT，指数移动平均，权重 7/8 旧 + 1/8 新
  • rx_rttval：RTT 抖动的移动平均
  • rto = srtt + max(interval, 4 × rttval) —— 抖动越大，安全余量越大。这是精髓：稳定网络下 RTO 贴近 RTT（重传快），抖动网络下自动放宽（避免误判）
  • 最后夹在 [rx_minrto, 60000]

RTT 的测量来源是 ts 字段的往返：

if (cmd == IKCP_CMD_ACK)
{
    if (_itimediff(kcp->current, ts) >= 0)
        ikcp_update_ack(kcp, (int)_itimediff(kcp->current, ts));
}

发数据时写入 ts = current，对端 ACK 时原样带回，收到 ACK 用 current - ts 就是 RTT。不需要维护任何发送时间表 —— 时间戳跟着包走。这个技巧值得记住。

五、Fantasy 的配置：四个数字的取舍

Network/Protocol/KCP/KCPSettings.cs
internal static class KCPFactory
{
    public const int FANTASY_KCP_RESERVED_HEAD = 5;   // ← 见 §6.3

    public static Kcp Create(NetworkTarget networkTarget, uint conv,
                             KcpCallback output, out KCPSettings kcpSettings)
    {
        var kcp = new Kcp(conv, output, FANTASY_KCP_RESERVED_HEAD);
        kcpSettings = KCPSettings.Create(networkTarget);

        kcp.SetNoDelay(1, 5, 2, 1);   // ← 这一行是全部性能取向
        kcp.SetWindowSize(kcpSettings.SendWindowSize, kcpSettings.ReceiveWindowSize);
        kcp.SetMtu(kcpSettings.Mtu);
        kcp.SetMinrto(30);
        return kcp;
    }
}

5.1 SetNoDelay(1, 5, 2, 1) 逐个拆

参数值默认作用代价
nodelay10RTO 退避 ×1.5 而非 ×2；首包 rtomin = 0重传更频繁
interval5 ms100flush 间隔，决定响应粒度CPU 与调度开销 ×20
resend20（关）被跳过 2 次即快速重传误判时白发一个包
nc10关闭拥塞控制弱网下可能加剧拥塞

interval = 5 是四个里影响最大的。它同时决定：

  • ACK 最快多久发出（影响对端 RTT 测量和快重传触发）
  • ikcp_update 内部 ts_flush 的推进步长
  • RTO 公式里的下限项：rto = srtt + max(interval, 4 × rttval)

再配合 SetMinrto(30)（默认 nodelay 下是 IKCP_RTO_NDL = 30，普通是 100），最快 30ms 就会触发一次超时重传。

这套配置的取向很明确 (1, 5, 2, 1) 是 kcp 作者文档里推荐的「极速模式」。四个参数全部指向同一个方向：牺牲带宽效率和网络友好度，换取最低延迟。

适合：实时对战、动作游戏、帧同步。
不适合：文件传输、大量玩家共享带宽的场景、需要与其他 TCP 流公平竞争的环境。

如果你的项目将来做大规模同屏或者要在弱网下稳定运行，nc 这个参数是第一个该重新评估的。

5.2 MTU = 470 的理由

case NetworkTarget.Outer:
{
    // 外网设置470的原因:
    // 1、mtu设置过大有可能路由器过滤掉
    // 2、降低 mtu 到 470，同样数据虽然会发更多的包，
    //    但是小包在路由层优先级更高
    settings.Mtu = 470;
    settings.SendWindowSize    = 2048;   // Unity 客户端
    settings.ReceiveWindowSize = 2048;
    settings.MaxSendWindowSize = 2048 * 2048 * 7;
}
case NetworkTarget.Inner:
{
    // 内网设置1400的原因
    // 1、一般都是同一台服务器来运行多个进程来处理
    // 2、内网每个进程跟其他进程只有一个通道进行发送、所以发送的数量会比较大
    // 3、如果不把窗口设置大点、会出现消息滞后。
    settings.Mtu = 1200;
    settings.SendWindowSize = 8192;
    // …
}

470 远低于以太网 MTU 1500，也低于 kcp 默认的 1400。作者给的两条理由都是经验性的：小包更不容易被中间设备丢弃或降级。代价是头部开销占比升高 —— 24 字节 KCP 头 + 5 字节 Fantasy 头 + 8 字节 UDP 头 + 20 字节 IP 头 = 57 字节，在 470 的载荷里占约 12%。

注意注释写 1400 但代码是 1200 —— 又一处注释没跟上代码，不影响功能。

六、集成层：Fantasy 怎么驱动这个算法

算法本身是被动的：它不认识 socket，不知道时间，只在你调 Update 时干活。集成层要解决三个问题。

6.1 谁来调 Update

internal sealed class KCPClientNetworkUpdateSystem : UpdateSystem<KCPClientNetwork>
{
    protected override void Update(KCPClientNetwork self)
    {
        self.CheckUpdate();
    }
}

这就是为什么 NetworkProtocolFactory.CreateClient 里 KCP 那支写的是 Entity.Create<KCPClientNetwork>(scene, false, true) 而 TCP 是 false —— 最后那个参数是「是否注册 Update 系统」。TCP 全靠 socket 事件驱动，KCP 必须有心跳驱动，因为重传和 flush 是时间触发的。

这个 UpdateSystem<T> 就是索引里阶段二 Entitas 部分的东西，在这里闭环了。

6.2 定时器：不要每帧都 flush

朴素做法是每帧调 _kcp.Update(now)。但 ikcp_check 存在的意义就是告诉你「下次真正需要 flush 的时刻」，可以跳过大量空转。Fantasy 用一个 SortedSet<uint> 实现：

private void KcpUpdate()
{
    var nowTime = TimeNow;
    _kcp.Update(nowTime);
    AddToUpdate(_kcp.Check(nowTime));   // 把下次时刻登记进去
}

private void AddToUpdate(uint tillTime)
{
    if (tillTime == 0) { KcpUpdate(); return; }   // 0 = 立刻

    if (IsTimeGreaterThan(_updateMinTime, tillTime) || _updateMinTime == 0)
        _updateMinTime = tillTime;                    // 维护最小值，快速跳过

    _updateTimer.Add(tillTime);
}

_updateMinTime 是个短路优化：CheckUpdate 每帧先比一次它，没到就整个跳过，不用遍历 SortedSet。

另外 AddToUpdate(0) 在三处被调用 —— Input() 收到数据后、SendMemoryStream() 发送后。意思是「有事件发生，别等定时器，立刻 flush」。这是低延迟的另一半：定时器保证兜底，事件驱动保证即时。

回绕处理的另一种写法

public void CheckUpdate()
{
    var nowTime = TimeNow;
    _allowWraparound = nowTime < _updateMinTime;   // ← 关键
    // …遍历 _updateTimer
    _allowWraparound = true;
}

private bool IsTimeGreaterThan(uint timeId, uint nowTime)
{
    if (!_allowWraparound) return timeId > nowTime;   // 普通比较

    var diff = timeId - nowTime;
    // 如果 diff 的值在 [0, HalfMaxUint] 范围内，说明 timeId 是在 nowTime 之后或相等。
    // 如果 diff 的值在 (HalfMaxUint, uint.MaxValue] 范围内，说明 timeId 是在 nowTime 之前（时间回绕）。
    return diff < HalfMaxUint || diff == HalfMaxUint;
}

和 _itimediff 同样的原理（用差值落在哪半区间来判断先后），但多了一个 _allowWraparound 开关。

这个开关的必要性我没有完全推演清楚 —— nowTime < _updateMinTime 为 false 时（即已经到点了）切换成普通比较，看起来是在处理某个特定的边界情况。这里留给你自己对着调试器验证。

值得注意的是 TimeNow 的定义：

private uint TimeNow => (uint)(TimeHelper.Now - _startTime);

相对时间，不是绝对时间戳。_startTime 在 Connect() 里设为当时的 TimeHelper.Now。这样 uint 从 0 开始计，要跑满 2³² 毫秒（约 49.7 天）才回绕 —— 一个连接活不了这么久。用相对时间把回绕问题从「必然发生」降级为「几乎不可能」，再加上 _itimediff 兜底。

6.3 预留 5 字节：零拷贝的小技巧

这是我认为整个集成层最巧的一处。

回顾第二篇：每个 UDP 包前面要加 5 字节的 Fantasy 头（1 字节 header + 4 字节 channelId）。朴素做法是 KCP 输出一个 buffer，再申请一个大 5 字节的新 buffer，拷过去，前面填头。每个包一次分配 + 一次拷贝。

Fantasy 的做法是让 KCP 从一开始就把数据写在偏移 5 的位置：

public const int FANTASY_KCP_RESERVED_HEAD = 5;
var kcp = new Kcp(conv, output, FANTASY_KCP_RESERVED_HEAD);

Kcp.Update() 里可以看到 reserved 怎么生效：

Network/Protocol/KCP/Base/Kcp.cs
public void Update(uint current)
{
    fixed (byte* ptr = &_buffer[_reserved])      // ← 从第 5 字节开始写
    {
        ikcp_update(_kcp, current, ptr, _buffer, _output);
    }
}

注意传给 ikcp_update 的是两个东西：ptr（偏移 5 的写入位置）和 _buffer（完整数组）。算法在 ptr 上写，回调时把完整数组交给你。于是回调里可以原地填头：

private unsafe void KcpSpanCallback(byte[] buffer, int count)
{
    if (IsDisposed) return;
    if (count == 0) throw new Exception("KcpOutput count 0");

    fixed (byte* p = buffer)
    {
        p[0] = KcpHeaderReceiveData;      // 原地写第 0 字节
        *(uint*)(p + 1) = ChannelId;       // 原地写第 1~4 字节
    }

    SendAsync(buffer, 0, count + 5);        // 从 0 发 count+5 字节
}
预留头的内存布局 _buffer: ┌───┬────────────┬─────────────────────────────────────┐ │ 0 │ 1 2 3 4 │ 5 ... │ ├───┼────────────┼─────────────────────────────────────┤ │hdr│ channelId │ ← KCP 算法从这里开始写（ptr） │ └───┴────────────┴─────────────────────────────────────┘ ↑ ↑ ↑ └───┴────────────┘ 回调里原地填这 5 字节 零分配、零拷贝 SendAsync(buffer, 0, count + 5)
「预留头部空间」是网络库的标准做法 Netty 的 ByteBuf 有 writerIndex 前的预留区，Linux 的 skb 有 headroom，都是同一个思路：在最内层分配内存时就为外层协议头留出空间，让每一层协议都能原地填头而不是层层拷贝。

自己写协议栈时值得照抄。判断标准很简单：如果你在某一层写了 Array.Copy 只为了腾出前缀空间，那就该用预留了。

6.4 断线策略：WaitSendCount 超限

private void SendMemoryStream(MemoryStreamBuffer memoryStream)
{
    if (_kcp.WaitSendCount > _maxSndWnd)
    {
        // 检查等待发送的消息，如果超出两倍窗口大小，KCP作者给的建议是要断开连接
        Log.Warning($"ERR_KcpWaitSendSizeTooLarge {_kcp.WaitSendCount} > {_maxSndWnd}");
        Dispose();
        return;
    }

    try
    {
        _kcp.Send(memoryStream.GetBuffer().AsSpan(0, (int)memoryStream.Position));
        AddToUpdate(0);      // 立刻 flush
    }
    finally
    {
        if (memoryStream.MemoryStreamBufferSource == MemoryStreamBufferSource.Pack)
            MemoryStreamBufferPool.ReturnMemoryStream(memoryStream);
    }
}

WaitSendCount = nsnd_buf + nsnd_que，即「已发未确认 + 排队待发」的总包数。_maxSndWnd 客户端是 2048 × 2048 × 7。

为什么积压要断线而不是等？因为 KCP 的重传是无限的 —— 只要不 Dispose，它会一直重传下去。积压持续增长说明链路已经实质不可用，继续等只会：内存持续增长、每次 flush 遍历越来越长的 snd_buf、玩家看到的画面早已不可玩。

快速失败比慢性死亡好。断开后走重连流程，比让玩家盯着一个卡死的界面强。

注意 finally 里的还池 —— 无论 _kcp.Send 成功还是抛异常都归还。这里可以还池是因为 _kcp.Send 内部把数据 memcpy 进了自己的 segment，不再引用外部 buffer。这是「拷贝换所有权清晰」的取舍，和 §6.3 的零拷贝并不矛盾：那边省的是输出路径的拷贝，这边花的是输入路径的拷贝，后者换来了内存池能立刻回收。

6.5 Input：收到数据后的完整链路

private void Input(ReadOnlyMemory<byte> buffer)
{
    _kcp.Input(buffer.Span);      // ① 喂给算法
    AddToUpdate(0);               // ② 立刻 flush（把 ACK 发出去）

    while (!_cancellationTokenSource.IsCancellationRequested)
    {
        var peekSize = _kcp.PeekSize();
        if (peekSize < 0) return;                    // ③ 没有完整消息，收工

        var receiveCount = _kcp.Receive(_receiveBuffer.AsSpan(0, peekSize));
        if (receiveCount != peekSize) return;         // 防御

        if (!_packetParser.UnPack(_receiveBuffer, ref receiveCount, out var packInfo))
            continue;

        Session.Receive(packInfo);                    // ④ 交给上层
    }
}

三个点：

  • AddToUpdate(0) 紧跟 Input。收到数据要尽快把 ACK 发回去 —— ACK 延迟直接影响对端的 RTT 测量和快重传判断。不能等下一个 5ms 定时器。
  • while 循环榨干。一次 Input 可能让多条消息同时变为可交付（之前乱序积压的一下子连上了）。必须循环取到 PeekSize() < 0。
  • _receiveBuffer 是预分配的固定数组（MaxMessageSize + 20）。整个接收路径零分配。
