Source 网络同步（一）属性同步

Source SDK 2013 源码阅读 · 网络同步四部曲第一篇
public/dt_send.cpp · public/networkvar.h · public/edict.h
这一系列和 Fantasy 三部曲的关系 Fantasy 的 TCP/UDP/KCP 三篇讲的是传输层：字节怎么可靠地送到。Source 这四篇讲的是表现层：字节到了之后，怎么让玩家感觉不到延迟。

两边不重叠。Source SDK 是游戏 DLL 层的开源，引擎（engine.dll）闭源 —— public/inetchannel.h 只有接口，没有实现。所以传输层在这里是个黑盒，正好是你已经吃透的那一层。

零、四篇的主线：所有招数都在操纵时间

网络同步的根本矛盾只有一句话：信息传递需要时间，但玩家要求即时反馈。

服务端是唯一权威，但它在 100ms 之外。你看到的一切都是过去，你的操作要 100ms 后才生效。Valve 的整套方案是三个方向的时间操纵：

机制时间方向解决什么代价
客户端预测把未来提前按下 W 立刻走会预测错，需要回滚
实体插值把过去延后别人不抖动你看到的别人更旧
延迟补偿把过去倒带高 ping 也能打中躲到墙后还被打死

三者是一个闭环，不是三个独立优化。插值制造的延迟必须由延迟补偿抵消，否则你瞄准的是别人 100ms 前的位置，永远打不中。很多人在 Unity 里只做了预测就上线，然后发现打不中人 —— 就是没意识到插值欠下的时间债必须还。

本篇讲的属性同步是这一切的地基：服务端怎么把状态送到客户端，且只送变化的部分。它本身不操纵时间，但后面三篇全建立在它之上。

一、SendTable 的本质：一张运行时元数据表

Source 里每个可联网的类都要声明一张 SendTable（服务端）和一张 RecvTable（客户端）。表里没有任何逻辑，只有一个 SendProp 数组：

public/dt_send.h:468-474
SendProp   *m_pProps;
int        m_nProps;
const char *m_pNetTableName;   // 客户端与服务端匹配用的名字
CSendTablePrecalc *m_pPrecalc;   // 引擎把预计算结果挂这里（闭源）

每个 SendProp 描述一个字段：类型、位数、值域、flag、以及这个字段在对象里的字节偏移。

偏移量是整套设计的支点。表里存的不是"怎么读这个字段"的代码，而是"它在对象里的第几个字节"。宏 SENDINFO 用编译期 offsetof 算出来。

C# 类比 相当于你不写 Serialize()，而是维护一份"字段清单"，每项记录 { 字段名, 类型, 位数, 内存偏移 }。序列化时遍历清单按偏移取值。C# 有真反射，可以扫 attribute 生成清单；C++ 没有，Valve 用宏手搓了一个。

1.1 为什么不每个类手写 Serialize()

这是本篇第一个值得吸收的架构决策，理由比"避免重复代码"深得多。

核心理由：客户端和服务端是两个独立编译的 DLL，且必须能版本错配。

手写 Serialize()/Deserialize() 要求两边字段读写顺序严格一致，任何一边改动就崩。而表是运行时按字符串名字匹配的 —— 服务端在连接建立时把整张表结构发给客户端，引擎按名字对齐。所以客户端可以缺字段、多字段、顺序不同。

这是 mod 生态的生命线。讨论要不要支持 int64 时的注释很说明问题：

public/dt_common.h:104
// The day we do this, we break all mods until they recompile.

另外三条理由：

  • 增量编码需要引擎"看懂"字段结构。引擎要做的不是"序列化一个对象"，而是"对比上一帧，只发变化的字段，且发字段索引而不是字段名"。这要求能枚举、排序、索引所有属性 —— 手写函数是黑盒，做不到。
  • 一处声明换来多项能力。同一张表同时驱动 delta 压缩、per-client 过滤、新客户端加入时的初始快照（baseline）、demo 录制回放。
  • 编译期强制正确性。见 §4.3。

二、量化：用精度换带宽

你在 KCP 那篇见过"用 10%~20% 带宽换 30%~40% 延迟"。这里是同一种取舍思维用在另一层：用精度损失换带宽。

SendPropFloat(SENDINFO(m_flMaxspeed), 12, SPROP_ROUNDDOWN, 0.0f, 2048.0f) 的意思是：把 0~2048 的浮点压成 12 bit。构造时预计算一个乘数：

public/dt_send.cpp:215-217
iHighValue = ((1 << nBits) - 1);
float fHighLowMul = iHighValue / range;   // range = high - low

编码就是 (value - low) * fHighLowMul 取整，解码反向。12 bit 装 2048 的值域，精度约 0.5 单位。

有段防御性代码值得一提（dt_send.cpp:222-248）：如果浮点精度导致乘数算出来会溢出 N bit，就依次乘 {0.9999, 0.99, 0.9, 0.8, 0.7} 收缩直到不溢出。因为一旦最大值编码成超出 N bit 的整数，会污染相邻字段的 bit。这种"宁可损失一点精度也不能越界"的处理是位打包协议的必备防线。

2.1 几个关键 flag

flag作用什么时候用
SPROP_COORD世界坐标专用变长编码，忽略 nBits。整数 14 bit + 小数 5 bit（精度 1/32）位置。变长意味着静止在整数格点的物体只花几个 bit
SPROP_NOSCALE不量化，直接发 32 bit 原始 float精度敏感处，如玩家速度。显式声明"放弃压缩换正确性"
SPROP_UNSIGNED无符号。省符号位，且换用 UInt proxy注释说换 proxy 不是为了编码正确，是为了范围校验能抓到 bug
SPROP_CHANGES_OFTEN见 §2.2高频变化的字段

角度有专门的 SendPropAngle，值域硬编码 0~360，且 proxy 先做 anglemod() 归一化（dt_send.cpp:72-80, 440-441）。避免"355° → 5°"被当成 350° 的大跳变。这个环绕问题在第四篇的插值里还会以另一种形式出现。

2.2 SPROP_CHANGES_OFTEN 优化的是元数据，不是数据

这个 flag 我一开始理解错了，它值得单独讲。定义处的注释就是全部答案：

public/dt_common.h:65
// this is an often changed field, moved to head of
// sendtable so it gets a small index

机制：delta 编码时每个变化的属性要先发一个变长编码的属性索引。把高频变化的属性排到列表最前面，索引就小，索引本身占的 bit 就少。

关键洞察 一个 1 bit 的 bool，如果索引要花 10 bit，那索引才是主要成本。

这和你在 KCP 那篇算过的"24 字节 KCP 头在 470 载荷里占 12%"是同一个问题的另一个尺度。协议设计到一定程度，元数据开销会超过数据本身。

2.3 这个优化有个坑，代码里有直接证据

排序会破坏属性的到达顺序，而某些客户端 RecvProxy 依赖顺序：

game/server/fish.cpp:87-89
* NOTE: Do NOT use SPROP_CHANGES_OFTEN, as it will reorder this list.
* The pool origin must arrive befoore m_x and m_y or the fish will
* respawn at the origin and zip back to their proper places.

（befoore 是原文的拼写错误。）同文件里三处 flag 因此被注释掉了。

Source 甚至专门造了一个子表来强制顺序：

game/server/baseentity.cpp:261-263
// NOTE: Animtime must be sent before origin and angles because it has a
//  proxy on the client that stores off the old values before writing in
//  the new values and if it is sent after, then it will only have the new...

子表叫 DT_AnimTimeMustBeFirst —— 名字本身就是文档。

可以带走的一条经验 "优化"和"正确性"冲突时，Valve 选了正确性，并留下注释解释为什么。你自己做同步系统时，如果引入了任何会改变字段顺序或时序的优化，要先确认没有接收侧逻辑依赖顺序。这类 bug 的症状（鱼在原点重生然后飞回去）和根因（属性排序）距离极远，极难查。

三、SendProxy：per-client 过滤

Proxy 是取值/存值的拦截钩子。最有架构价值的用法是让一整张子表只发给"这个实体本人"：

public/dt_send.cpp:196-200
void* SendProxy_SendLocalDataTable( ..., CSendProxyRecipients *pRecipients, int objectID )
{
    pRecipients->SetOnly( objectID - 1 );   // 只发给自己
    return ( void * )pVarData;
}

用在玩家表的最后一行（player.cpp:8199），子表 DT_LocalPlayerExclusive 里装着弹药、摩擦力、tickbase、约束参数 —— 只有你自己需要。

这既省带宽，也是反作弊：其他玩家的客户端根本收不到这些数据。想想那些"透视自己队友弹药"之类的需求，服务端不发就是最彻底的防护。

客户端两张表都声明了，注释点明这个不对称：

game/client/c_baseplayer.cpp:271-273
// We have both the local and nonlocal data in here, but the server proxies
// only send one.

3.1 EHANDLE：对象引用怎么同步

你不能直接同步一个指针。Source 把 EHANDLE 打包成一个 int：

game/server/sendproxy.cpp:30-31
pOut->m_Int = pHandle->GetEntryIndex() | (iSerialNum << MAX_EDICT_BITS);

低位是实体索引，高位是序列号。序列号解决的是槽位复用：索引 42 的实体销毁后，新实体占用同一槽位，旧 handle 因序列号不匹配自动失效。没有它，旧引用会静默指向一个完全不相干的新对象。

和 Unity 的对照 NGO 的 NetworkObjectId 是单调递增不复用的，所以不需要序列号 —— 代价是 ID 空间理论上会耗尽。Source 选了固定槽位 + 版本号，上限是同时存在的实体数而非累计创建数。

两种方案看你的对象生命周期特征：大量短命对象（子弹、特效）用 Source 这套更省。

3.2 继承与组合是同一个原语

BEGIN_SEND_TABLE 自动插入一条指向基类表的 DataTable 属性（dt_send.h:551-553）。所以类继承 → 表嵌套，自动同构。

而"组合"（嵌套一个成员对象的表）用的是同一个 SendPropDataTable，区别只在偏移量是 0 还是成员偏移。这是个很干净的设计 —— 一个原语覆盖两种关系。

偏移为 0 且用默认 proxy 时会打上 SPROP_COLLAPSIBLE，引擎可以直接把这一层折叠掉，省去遍历层级的开销。

反向操作是 SendPropExclude —— 它不是真属性，只是一条指令："把继承来的某个字段剔除"。真实用法：

game/server/hl2mp/hl2mp_player.cpp:72
SendPropExclude( "DT_BaseEntity", "m_vecOrigin" ),

动机在另一个文件里写得最清楚：// client has its own orientation logic（eyeball_boss.cpp:58）。继承带来了不需要的带宽，就显式减掉。

四、脏标记：CNetworkVar 宏体系

服务端不可能每帧全量比对所有实体的所有字段。脏标记的作用是把昂贵的精确比对限制在极小的候选集上。

4.1 一次赋值发生了什么

CNetworkVar( int, m_iHealth ) 展开后大致是：

// 一个纯静态的"变更通知策略"类
class NetworkVar_m_iHealth {
    static inline void NetworkStateChanged( void *ptr ) {
        ((ThisClass*)(((char*)ptr) - MyOffsetOf(ThisClass,m_iHealth)))
            ->NetworkStateChanged( ptr );
    }
};
CNetworkVarBase< int, NetworkVar_m_iHealth > m_iHealth;   // 真正的成员
typedef ThisClass MakeANetworkVar_m_iHealth;              // 编译期检查用

三个要点：

(1) 靠指针算术反查宿主对象。((char*)ptr) - offsetof(...) —— 从成员地址减去偏移得到实体地址。所以这些包装器零额外内存开销：不需要存一个 back-pointer，偏移量是编译期常量。这个技巧是整套设计能"几乎免费"的关键。

(2) 赋值即通知，且带相等性检查。

public/networkvar.h:246-254
const Type& Set( const Type &val )
{
    if ( NetworkParanoidUnequal( m_Value, val ) )
    {
        NetworkStateChanged();
        m_Value = val;
    }
    return m_Value;
}

(3) 浮点用位比较而非数值比较。NetworkParanoidUnequal 对 float/double 通过 union 转成整数比（networkvar.h:190-216）。原因：-0.0f == 0.0f 在数值上成立但位模式不同，而量化编码看的是位。这种细节是用了十年被磨出来的。

4.2 脏标记的粒度：精确到字节偏移

传播链是四跳，全部在开源代码里：

脏标记传播链 m_iHealth = 50 ↓ networkvar.h:246 位级相等性检查 CNetworkVarBase::Set() ↓ networkvar.h:813 指针算术反查实体 NetworkVar_m_iHealth::NetworkStateChanged() ↓ CBaseEntity::NetworkStateChanged() → NetworkProp() ↓ ServerNetworkProperty.h:201 可选 timer 节流 CServerNetworkProperty::NetworkStateChanged( offset ) ↓ edict.h:286 edict_t::StateChanged( offset ) 置 FL_EDICT_CHANGED + 把 offset 记进变更列表

终点不只是"这个实体变了"，还有"变的是偏移 0x40 处那个"。引擎可以直接定位到属性而不必遍历整棵属性树。

但这个精确列表有容量上限，超了就降级：

public/edict.h:291-313（节选）
m_fStateFlags |= FL_EDICT_CHANGED;
// …去重后…
p->m_ChangeOffsets[p->m_nChangeOffsets++] = offset;

最多记 19 个偏移，超了就打 FL_FULL_EDICT_CHANGED 当"全变了"处理。

这个降级策略本身是个好设计 "精确追踪有上限，超限降级为保守正确"。而且它在数值上是合理的：一帧改 20 个字段的实体，全量比对反而更划算 —— 维护精确列表的开销超过了它节省的比对开销。

自己做脏标记时值得照抄这个思路：不要为了"永远精确"付出无界的记账成本。

4.3 那个静默 bug，和编译期怎么堵住它

如果绕过 CNetworkVar 直接改字段，后果是：服务端值变了，edict 从未标脏，引擎认为实体没变化，客户端永远收不到更新。

不报错、不崩溃，只是静默不同步。表现是"服务端血量 50，客户端一直显示 100"。代码逻辑看起来完全正确，问题在于你没告诉框架你改了东西。

Valve 用编译期检查堵住了大部分情况。回看 §4.1 那个 typedef ThisClass MakeANetworkVar_m_iHealth; —— SENDINFO 宏会引用它：

public/dt_send.h:586
#define SENDINFO(varName)  #varName, \
    _hacky_dtsend_offsetof(currentSendDTClass::MakeANetworkVar_##varName, varName), ...

对普通成员变量写 SENDINFO(m_foo)，这个 typedef 不存在，编译失败。

但有后门 SENDINFO_NOCHECK(m_foo) 跳过检查（dt_send.h:601-602，注释 // Use this when you're not using a CNetworkVar）。它的正当用途是非实体的一次性结构体，那里根本没有 delta 机制 —— effect_dispatch_data.cpp:81-84 的注释是标准答案。

用在实体上就是自找麻烦。Unity 里的对应物：直接改 NetworkVariable 的内部字段而不走 Value setter。NGO 没有编译期保护，全靠自觉。

4.4 变体：把粒度做到分量级

宏解决什么
CNetworkVector分量级脏标记。SetX/SetY/SetZ 各自独立检查，只改 X 不会让 YZ 也标脏
CNetworkArray元素级脏标记。通知传的是 &m_Value[i]，偏移精确到元素
CNetworkString只有 Get() 和 GetForModify()，没有 Set() —— char 数组无法用值比较做廉价的相等检查
CNetworkHandle内部存 handle，但重载 operator-> 让它用起来像裸指针
CNetworkVarEmbedded让嵌套结构体里的 CNetworkVar 能把通知传出来。故意禁用了赋值操作符 —— 整体赋值不会调各标量成员的 copy ctor，导致它们不被标脏

还有一个专门解决继承层级浪费的变体，思路很值得看：

CBaseEntity 有 m_iHealth，但基类的表不发它 —— 只有 CBasePlayer 等派生类才发。用普通 CNetworkVar 的话，每一个实体（包括一万个不联网的道具）改血量都要走一遍标脏流程。

解法是把通知虚化并默认关闭：

public/networkvar.h:655-659
#define CNetworkVarForDerived( type, name ) \
    virtual void NetworkStateChanged_##name() {} \          // 空实现
    virtual void NetworkStateChanged_##name( void *pVar ) {} \
    ...

基类里写它 = 零成本。真正要发的派生类粘一行 IMPLEMENT_NETWORK_VAR_FOR_DERIVED( m_iHealth ) 把虚函数接回真实现。player.h:872-885 一次打开 11 个。

注释很直白：

game/server/baseentity.h:1239
CNetworkVarForDerived( int, m_iHealth ); // CBaseEntity doesn't care about
    // changes to this variable, but there are derived classes that do.

5.1 两个反直觉的事实

客户端不知道哪些属性变了 引擎不下发变更清单。客户端只能靠"我的 RecvProxy 有没有被调用"隐式感知，或者自己存旧值手动比对：

bool originChanged = ( m_vecOldOrigin != GetLocalOrigin() );　c_baseentity.cpp:2570-2576

由此推出第二个事实：客户端侧的成员是普通变量，不是 CNetworkVar。客户端不需要标脏，它是纯接收端。

整套 CNetworkVar 机制是服务端专属的发送优化。这个不对称性我一开始没想到 —— 看名字容易以为是"网络变量"，实际是"发送方的变更追踪器"。

5.2 PostDataUpdate 与 OnDataChanged 的区别

这个区分很关键，注释在 iclientnetworkable.h:62-77：

频率时机能不能用
Pre/PostDataUpdate每包一次（一帧可能多次）解析包的过程中其他实体的坐标、attachment 可能还是旧的
OnPre/OnDataChanged每帧一次渲染起点所有实体状态已一致

注释明确建议：90% 的情况用后者。

还有个反向信号 OnDataUnchangedInPVS —— 实体在 PVS 内但零属性变化，一次解码都没发生。

六、Unity 落地要点

本篇能直接搬到你项目里的，按重要性排：

6.1 网络字段的标识用名字或稳定 ID，不要用顺序

如果你要支持热更或长期维护多版本客户端，字段的协议不能靠声明顺序。Source 用字符串名字在连接时对齐一次，之后传数字索引 —— 建立连接时松耦合，运行时紧凑编码。

这是个架构层决策，早定省事。改起来是伤筋动骨的。

6.2 脏标记的粒度要匹配你的字段特征

Source 做到字节偏移级，NGO 的 NetworkVariable 只到变量级。

如果你有大数组或大结构体要同步（比如背包、技能栏），变量级脏标记意味着改一格就全量重发。这时候要么手动拆成多个 NetworkVariable，要么自己实现元素级脏标记（NetworkList 有部分支持）。

6.3 别忘了元数据开销

同步一个 bool 时，"这是第几个字段"这个信息可能比 bool 本身贵一个数量级。

实践建议：把高频变化的字段集中放在一个小结构里同步，而不是散在几十个字段中间。这样索引空间小，索引编码短。这就是 SPROP_CHANGES_OFTEN 的手工版。

6.4 用 C# 反射把两件事合一

Source 受 C++ 限制才用宏。C# 可以做得干净得多：

// 启动时扫一遍生成字段清单，缓存成委托（Expression 或 source generator）
[Sync(Bits = 12, Low = 0, High = 2048)]     // 量化
private float _maxSpeed;

[Sync(Owner = SyncScope.OwnerOnly)]           // per-client 过滤
private int _ammo;

设计意图和 Source 完全相同，但把"宏 + 手工偏移"换成"attribute + 反射生成"，同时消掉了一整类"表和类定义不一致"的 bug。
