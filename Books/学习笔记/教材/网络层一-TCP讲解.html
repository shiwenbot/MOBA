网络层（一）TCP —— 字节流与分包粘包

Fantasy 源码阅读 · 传输层三部曲第一篇
Fantasy.Unity/Runtime/Core/Network/

这三篇的顺序不是按「项目实际用哪个」排的，是按理解成本排的。

你的项目实际走 KCP（GameClient.cs:57 写死了 NetworkProtocolType.KCP）。但直接读 KCP 会同时撞上三件事：可靠传输算法、UDP 的无连接语义、Fantasy 自己的握手协议。三者纠缠在一起，很难分清哪个问题是谁造成的。

所以先读 TCP。它是唯一一个「传输保证由操作系统提供」的分支，代码里剩下的东西才是 Fantasy 自己的框架逻辑 —— 接口抽象、Pipe 缓冲、消息头解析、生命周期管理。这套东西 KCP 分支也要用，而且在 TCP 分支里看最干净。

三篇的分工 第一篇：把「框架层」看透 —— 接口抽象、Pipe、包头协议、发送队列。TCP 只是载体。
第二篇：把 TCP 的保证一条条拿掉，看 UDP 剩下什么，以及 Fantasy 为此补了哪些代码。
第三篇：看 KCP 如何用算法把拿掉的东西重新造回来。

一、先明确 TCP 到底给了你什么

做游戏网络时，「用 TCP」这个决定其实是在向内核外包四件事：

保证含义后面读 UDP 时会失去
可靠丢了会重传，直到对方确认✗ 全丢
有序按发送顺序交付✗ 全丢
去重重复包被丢弃✗ 全丢
流量/拥塞控制不会压垮对方和链路✗ 全丢
—— 以下是 TCP 没有给你的，所以 TCP 分支也要自己处理 ——
消息边界TCP 是字节流，不保留你 Send 的切分UDP 反而有（后面详述）

最后一行是这一篇的主线。TCP 的可靠有序是免费的，消息边界是要自己付钱的。这就是「分包粘包」问题的本质，也是 ReadOnlyMemoryPacketParser 那 374 行存在的全部理由。

二、接口抽象：三种协议如何共用一套上层

先读这四个文件，一共 252 行，读完你就知道 Session 之上的代码为什么完全不关心底下跑的是 TCP 还是 KCP。

2.1 INetworkChannel —— 最小契约（13 行）

Network/Protocol/Interface/INetworkChannel.cs
public interface INetworkChannel : IDisposable
{
    public Session Session { get; }
    public bool IsDisposed { get; }
    public void Send(uint rpcId, long address,
                     MemoryStreamBuffer memoryStream,
                     IMessage message, Type messageType);
}

13 行定义了「一条通道」：能发消息、能销毁、关联一个 Session。注意 Send 里没有任何协议痕迹 —— 没有 socket、没有 endpoint、没有序号。这是抽象成功的标志。

参数里那个 memoryStream 和 message 二选一的设计要留意：传 message 表示「还没序列化，你帮我打包」；传 memoryStream 表示「已经打包好了，你只需要改写包头里的 rpcId」。后者用于消息转发，避免反复序列化。OuterBufferPacketParser.Pack 里那两个重载正好对应这两条路。

2.2 ANetwork —— 共享设施（149 行）

所有协议实现的基类。它不管收发，只提供三样东西：

  • 三个身份标识：NetworkType（Client/Server）、NetworkTarget（Outer 外网 / Inner 内网）、NetworkProtocolType（TCP/KCP/WebSocket/HTTP）。后面很多分支逻辑靠它们决策，尤其 NetworkTarget —— 内外网的包头长度、MTU、窗口大小全都不同。
  • 消息调度器：Initialize 里按 networkType 选 ClientMessageScheduler 或 OuterMessageScheduler。收到的包最终交给它分发。
  • PackInfo 对象池：RentOuterPackInfo() / ReturnOuterPackInfo()。

PackInfo 池那段有个细节值得看：

public void ReturnOuterPackInfo(OuterPackInfo outerPackInfo)
{
    if (_outerPackInfoPool.Count > 512)
    {
        // 池子里最多缓存256个、其实这样设置有点多了…
        // 反而设置越大内存会占用越多。
        return;   // ← 超了就直接丢弃，不入池
    }
    _outerPackInfoPool.Enqueue(outerPackInfo);
}

对象池必须有上限。没上限的池在流量尖峰后会永久占住峰值内存 —— 池子本身成了内存泄漏。这里的做法是超限直接丢给 GC，用一次短暂的分配换掉长期驻留。注释里那句「设置越大内存占用越多」说的就是这个权衡。（注释写 256、代码写 512，属于注释没跟上，无功能影响。）

另外注意每次 Rent 都会 ++_outerPackInfoId。这个自增 Id 是复用检测用的 —— 异步回调拿着一个 PackInfo，回来时先比对 Id，不一致说明对象已被回收复用，这一路结果必须丢弃。这是池化对象的通用防御手法，和第一篇 FTask 里 isPool: false 的坑是同一类问题的两种解法：FTask 选择关掉池化，PackInfo 选择加版本号。

2.3 AClientNetwork —— 客户端专属（37 行）

Network/Protocol/Interface/AClientNetwork.cs
public abstract class AClientNetwork : ANetwork, INetworkChannel
{
    protected bool IsInit;
    public Session Session { get; protected set; }

    public abstract Session Connect(
        string remoteAddress,
        Action onConnectComplete, Action onConnectFail, Action onConnectDisconnect,
        bool isHttps, int connectTimeout = 5000);
}

两个设计点：

  1. 客户端的 Network 自己就是 Channel。它同时继承 ANetwork 和实现 INetworkChannel —— 因为客户端只有一条连接，没必要再分层。服务端则相反：一个 ANetwork 管 N 个 ANetworkServerChannel（55 行，看一眼即可）。这个不对称是刻意的。
  2. 三个回调而不是一个 Task。Connect 同步返回 Session，连接结果通过 onConnectComplete / onConnectFail / onConnectDisconnect 异步通知。这正是你项目 GameClient.cs 里要手动搓一个 FTask<bool> 把回调转成 await 的原因 —— 框架给的是回调风格，业务层想要 await 风格，中间那层胶水得自己写。
把第一篇的知识接上 m_connectTask = FTask<bool>.Create(isPool: false) 加上「三个回调分别 SetResult 后立刻置 null」，本质就是在实现一个只允许完成一次的 promise。框架这边有三条独立路径可能触发完成（成功/失败/断开），业务那边只能被 await 一次，所以必须防重。

三、TCPClientNetwork 的四条执行流

TCP/Client/TCPClientNetwork.cs（427 行）是这一篇的正餐。它有四条独立运行的流程，不要顺着行号读，按流程读：

四条流 ① 连接流 Connect() → ConnectAsync → OnConnectSocketCompleted → OnReceiveSocketComplete │ ┌─────────────────┴────────────┐ ↓ ↓ ② 收流 ReceiveSocketAsync() ── socket → Pipe.Writer ③ 解流 ReadPipeDataAsync() （生产者，独立循环） （消费者，独立循环） ↓ UnPack → Session.Receive ④ 发流 Send() → _sendBuffers 队列 → SendAsync → OnSendCompleted → 继续下一个

3.1 连接流：三个回调 + 一个超时定时器

Connect() 做的事按顺序是：防重入检查 → 存三个回调 → 挂超时定时器 → 造 socket → 发起异步连接 → 创建 Session 并立即返回。

if (IsInit)
{
    throw new NotSupportedException(
        "TCPClientNetwork Has already been initialized. " +
        "If you want to call Connect again, please re instantiate it.");
}

一个实例只能 Connect 一次。重连必须新建实例。这个约束贯穿 TCP / KCP / WebSocket 三份实现，理由是内部有太多一次性状态（_cancellationTokenSource、Pipe、_packetParser 的解析进度），逐个重置比重建更容易出错。这也解释了为什么你项目里 ClientConnectWatcher 走的是「Dispose 旧的 → 造新的」而不是「复用同一个」。

超时定时器与「断开事件抑制」

_connectTimeoutId = Scene.TimerComponent.Net.OnceTimer(connectTimeout, () =>
{
    _connectDisconnectEvent = false;   // ← 关键
    _onConnectFail?.Invoke();
    Dispose();
});

_connectDisconnectEvent 这个 bool 是全文件最容易忽略、又最值得学的设计。看 Dispose() 里的用法：

if (_connectDisconnectEvent)
{
    _onConnectDisconnect?.Invoke();
}

问题是这样的：Dispose() 默认要通知业务层「连接断了」。但连接失败和连接断开是两种语义 —— 连都没连上，不该报「断开」。而失败路径又必须调 Dispose() 清理资源。

所以用一个标志位在调 Dispose() 之前把断开通知关掉。三处失败路径（超时、connect 返回错误、connect 抛异常）全都是同一个模式：

失败路径统一写法 _connectDisconnectEvent = false; ← 先抑制 _onConnectFail?.Invoke(); ← 报"失败" Dispose(); ← 清理时不会再报"断开"
可迁移的经验 当一个清理方法（Dispose/Close）自带副作用通知，而某些调用方需要「静默清理」时，标志位是最省事的解法。替代方案是 Dispose(bool notify) 重载，但那会让 IDisposable 的契约变脏。KCP 分支里有一模一样的字段和一模一样的用法 —— 第三篇会再遇到它。

连接完成的两条路

if (!_socket.ConnectAsync(outArgs))
{
    OnReceiveSocketComplete();   // 同步就完成了，直接走
}

ConnectAsync 返回 false 表示「操作已同步完成，不会触发 Completed 事件」。这是 SocketAsyncEventArgs 系列 API 的统一约定，忘了处理这条同步路径是这套 API 最常见的 bug。本地连接、地址已缓存等情况下真的会走到。

另一条路是 OnConnectSocketCompleted，它在 IO 完成线程上被调用，所以要 Post 回来：

Scene.ThreadSynchronizationContext.Post(OnReceiveSocketComplete);

Fantasy 的 Scene 是单线程模型（配合 Scene/Scheduler/ 下那几个十几行的调度器）。所有业务逻辑必须回到 Scene 线程执行，socket 回调是唯一需要跨线程的地方，所以这里的 Post 是整个网络层的线程边界。注意上面那条同步路径没有 Post —— 因为 Connect() 本身就在 Scene 线程上调用，同步完成时线程没变。

3.2 收流与解流：为什么中间要插一个 Pipe

连接成功后启动两个互不等待的循环：

private void OnReceiveSocketComplete()
{
    ClearConnectTimeout();
    _onConnectComplete?.Invoke();
    ReadPipeDataAsync().Coroutine();      // 消费者
    ReceiveSocketAsync().Coroutine();    // 生产者
}

.Coroutine() 就是第一篇里的 fire-and-forget。这两个 async FTask 方法会一直循环到 _cancellationTokenSource 被取消。

生产者：socket → Pipe

while (!_cancellationTokenSource.IsCancellationRequested)
{
    var memory = _pipe.Writer.GetMemory(8192);   // 借一块写入区
    count = await _socket.ReceiveAsync(memory, SocketFlags.None, token);

    if (count == 0)
    {
        Dispose();   // 对端正常关闭
        return;
    }

    _pipe.Writer.Advance(count);       // 告知实际写了多少
    await _pipe.Writer.FlushAsync();   // 唤醒消费者
}

count == 0 是 TCP 的 FIN 信号 —— 对端调用了 close/shutdown。这是唯一的「优雅关闭」判据，不能靠异常。

GetMemory / Advance / FlushAsync 是 System.IO.Pipelines 的写入三部曲。它比「自己 new byte[8192] 然后 Array.Copy」好在两点：内存由 Pipe 池化管理，且 FlushAsync 在缓冲超过阈值时会异步阻塞，天然形成背压（backpressure）—— 解析跟不上时，接收会自动降速，而不是无限堆积内存。

消费者：Pipe → UnPack → Session

var result = await pipeReader.ReadAsync(token);
var buffer   = result.Buffer;
var consumed = buffer.Start;
var examined = buffer.End;

while (TryReadMessage(ref buffer, out var message))
{
    ReceiveData(ref message);
    consumed = buffer.Start;
}

pipeReader.AdvanceTo(consumed, examined);

AdvanceTo(consumed, examined) 的双参数是 Pipelines 的核心概念，值得停一下：

参数含义说错的后果
consumed「这些我处理完了，可以回收」报大了 → 数据丢失；报小了 → 重复处理
examined「这些我看过了，都不够凑成一个包」报小了 → ReadAsync 立刻返回同样的数据，死循环空转

examined = buffer.End 的意思是「整段我都看过了，别再拿同样的数据来烦我，等有新数据再唤醒」。这两个位置能不同，正是 Pipelines 为「消息可能跨多次读取才完整」这个场景设计的。

这里的 TryReadMessage 名字有误导性 它不做消息切分，只是把 ReadOnlySequence 的第一个连续段（buffer.First）取出来。真正的切分在下游 _packetParser.UnPack。

换句话说：TryReadMessage 是「取一块连续内存」，UnPack 是「从连续内存里凿出完整消息」。ReadOnlySequence 可能由多个不连续段组成，逐段喂给解析器，解析器自己维护跨段状态。

3.3 分包粘包：ReadOnlyMemoryPacketParser 的状态机

这是 TCP 分支最核心的一段，也是整篇最值得精读的代码。

先看包头长什么样

Network/Message/PacketParser/Packet.cs
public const int PacketLength        = sizeof(int);    // 4 消息体长度
public const int ProtocolCodeLength  = sizeof(uint);   // 4 协议号
public const int RpcIdLength         = sizeof(uint);   // 4 RPC 序号
public const int PacketAddressLength = sizeof(long);   // 8 路由地址

// 外网包头 = 4 + 4 + 4 + 8 = 20 字节
public const int OuterPacketHeadLength = PacketLength + ProtocolCodeLength
                                        + RpcIdLength + PacketAddressLength;
20 字节包头布局 偏移 0 4 8 12 20 ├────────┼──────────────┼──────────┼───────────────────┤ │ 长度 │ ProtocolCode │ RpcId │ Address │ 消息体… │ int32 │ uint32 │ uint32 │ int64 │ ├────────┴──────────────┴──────────┴───────────────────┤ │ 「长度」= 消息体字节数，不含这 20 字节 │

这是「长度前缀」方案 —— 解决分包粘包的三种通用做法（长度前缀 / 分隔符 / 定长）里唯一适合二进制协议的那个。外网与内网包头长度在当前代码里都是 20，但常量分开定义，字段语义也不同（内网的 Address 用于进程路由）。

状态机的五个字段

protected int  Offset;               // 当前 buffer 的读取位置
protected int  MessageHeadOffset;    // 包头已攒了几个字节
protected int  MessageBodyOffset;    // 包体已攒了几个字节
protected int  MessagePacketLength;  // 从包头解出的包体总长
protected bool IsUnPackHead = true;  // 当前在攒头还是攒体
protected readonly byte[] MessageHead = new byte[20];  // 包头暂存区

这些字段是跨 UnPack 调用存活的，这是整个设计的关键。一次 UnPack 可能只攒到半个包头就返回 false，下次调用接着攒。解析器是有记忆的。

攒包头

if (IsUnPackHead)
{
    var outerPacketHeadLength = Packet.OuterPacketHeadLength - MessageHeadOffset;
    var copyLength = Math.Min(bufferLength, outerPacketHeadLength);   // ← 能拿多少拿多少

    readOnlySpan.Slice(Offset, copyLength)
                .CopyTo(MessageHead.AsSpan(MessageHeadOffset, copyLength));

    Offset            += copyLength;
    MessageHeadOffset += copyLength;

    if (MessageHeadOffset == Packet.OuterPacketHeadLength)
    {
        // 头齐了，解字段
        MessagePacketLength = Unsafe.ReadUnaligned<int>(ref messageRef);

        if (MessagePacketLength > ProgramDefine.MaxMessageSize)
        {
            throw new ScanException(...);   // ← 安全边界，见下文
        }

        PackInfo = OuterPackInfo.Create(Network);
        // …读 ProtocolCode / RpcId，按总长一次性租好 stream
        var memoryStream = PackInfo.RentMemoryStream(
            MemoryStreamBufferSource.UnPack,
            Packet.OuterPacketHeadLength + MessagePacketLength);
        memoryStream.Write(MessageHead);   // 包头也写进去

        IsUnPackHead      = false;   // 切换到攒包体
        bufferLength     -= copyLength;
        MessageHeadOffset = 0;
    }
    else
    {
        Offset = 0;
        return false;   // 头没齐，下次继续
    }
}

三个值得学的点：

  1. Math.Min 那行是整段的灵魂。「需要 20 字节，现有 7 字节，那就先拿 7 字节存着」。不做任何假设、不要求一次到位 —— 这就是流式解析的正确姿势。
  2. 长度校验必须在分配之前。MessagePacketLength 来自网络，是完全不可信的。如果不校验就拿去 RentMemoryStream，一个伪造的 0x7FFFFFFF 就是一次 OOM 攻击。抛 ScanException 后上层 ReceiveData 会 Log.Warning + Dispose() —— 降级为断开连接，而不是崩进程。这是网络代码处理恶意输入的标准姿势。
  3. 按最终总长一次性租 stream。OuterPacketHeadLength + MessagePacketLength 让 stream 一次分配到位，后续写包体不再扩容。包头也一并写入，是为了下游反序列化时能拿到完整原始字节。

攒包体

var outerPacketBodyLength = MessagePacketLength - MessageBodyOffset;
var copyBodyLength = Math.Min(bufferLength, outerPacketBodyLength);   // 同样的 Min

PackInfo.MemoryStream.Write(readOnlySpan.Slice(Offset, copyBodyLength));
Offset            += copyBodyLength;
MessageBodyOffset += copyBodyLength;

if (MessageBodyOffset == MessagePacketLength)
{
    packInfo          = PackInfo;    // 交付
    PackInfo          = null;
    IsUnPackHead      = true;      // 重置，准备下一个包
    MessageBodyOffset = 0;
    return true;
}

Offset = 0;
return false;

逻辑和攒包头对称。注意成功交付时把 PackInfo 置 null 再返回 —— 和第一篇 SetResult 里「先清字段再 Invoke」是同一条纪律：所有权转移后立即断开自己的引用。

那个 -1 的特例

if (MessagePacketLength == -1)
{
    // protoBuf做了一个优化、就是当序列化的对象里的属性和字段都为默认值的时候
    // 就不会序列化任何东西。
    // 为了TCP的分包和粘包、需要判定下是当前包数据不完整还是本应该如此、
    // 所以用-1代表。
    packInfo     = PackInfo;
    PackInfo     = null;
    IsUnPackHead = true;
    return true;   // 直接交付，不用等包体
}

这个特例很能说明「协议设计要留出不可能值」的价值。

问题：Protobuf 序列化一个全默认值的消息，结果是零字节。于是包体长度 = 0。但在流式解析里，「长度 0」和「我还没读到长度」难以区分，容易走进等待更多数据的死路。

解法：打包时把 0 改写成 -1（packetBodyCount = -1），解包时 -1 走单独分支立即交付。-1 在「长度」这个语义下是不可能出现的合法值，所以可以安全地征用为哨兵。

作者在注释里还留了一句「其实可以不用设置-1、解包的时候判断如果是0也可以、但我仔细想了下，还是用-1代表更加清晰」—— 这是可读性优先于最小改动的取舍，值得赞同：-1 一眼就知道是特殊标记，0 需要读者自己推断。

3.4 发流：单飞 + 队列

public override void Send(...)
{
    _sendBuffers.Enqueue(_packetParser.Pack(...));   // 先打包入队

    if (!_isSending)
    {
        Send();   // 没在发就启动
    }
}

_isSending 是「单飞标志」（single-flight）。TCP socket 上不能并发发起多个 SendAsync —— 会乱序或异常。所以模式固定为：入队 + 一个驱动者。

private void Send()
{
    if (_isSending || IsDisposed) return;
    _isSending = true;

    while (_sendBuffers.Count > 0)
    {
        var buf = _sendBuffers.Dequeue();
        _sendArgs.UserToken = buf;             // 挂上，回调里要还池
        _sendArgs.SetBuffer(...);

        if (_socket.SendAsync(_sendArgs))
        {
            return;   // 异步了，交给 OnSendCompleted 接着跑（注意 _isSending 仍为 true）
        }

        ReturnMemoryStream(buf);   // 同步完成，立刻还池，继续循环
    }

    _isSending = false;   // 队列空了才放锁
}

这个方法有两个出口，含义完全不同，是最容易读错的地方：

出口_isSending谁接着跑
return（异步挂起）保持 trueOnSendCompleted 回调
循环结束置 false没人，等下次 Send() 唤醒

异步出口故意不清标志 —— 发送仍在进行中，此时若有新 Send() 进来，只入队不启动，避免并发。接力棒在回调里：

private void OnSendCompleted(object sender, SocketAsyncEventArgs args)
{
    if (args.SocketError != SocketError.Success || args.BytesTransferred == 0)
    {
        _isSending = false;
        return;
    }

    var buf = (MemoryStreamBuffer)args.UserToken;
    Scene.ThreadSynchronizationContext.Post(() =>
    {
        ReturnMemoryStream(buf);

        if (_sendBuffers.Count > 0)
        {
            Send();          // 注意：此时 _isSending 还是 true
        }
        else
        {
            _isSending = false;
        }
    });
}
这里有个矛盾，读的时候会卡住 回调里 _isSending 仍为 true，却调用了 Send()；而 Send() 开头写着 if (_isSending) return;。看起来这次调用会被自己的守卫挡掉。

按代码字面推演，这条路径确实会直接 return，队列靠下一次 Send(...) 外部调用（此时 _isSending 已被某处置 false）来驱动。我没有实机验证这是否会造成发送延迟，但这是全文件我认为最可疑的一处。

把它当成一道题：读到这里时对照 KCP 分支的发送逻辑（第三篇），看看那边是怎么处理接力的。读源码时遇到自己推不通的地方，标记出来比强行自洽更诚实。

还池的条件

private void ReturnMemoryStream(MemoryStreamBuffer memoryStream)
{
    if (memoryStream.MemoryStreamBufferSource == MemoryStreamBufferSource.Pack)
    {
        MemoryStreamBufferPool.ReturnMemoryStream(memoryStream);
    }
}

MemoryStreamBufferSource 记录了这块内存是谁创建的。只有 Pack（本层为发送而打包）才归本层还池；如果是上层传进来的（转发场景），所有权不在这里，不能还。

这是解决「共享缓冲所有权」的轻量方案 不引入引用计数，只在对象上记一个来源标签，各层只回收自己创建的。适用于所有权清晰、层次不深的场景。比 IMemoryOwner<T> 简单，比裸 byte[] 安全。

四、TCP 分支的完整数据流

发送 业务 Send(message) ↓ Pack ─ 租 stream → Seek(20) → 序列化 → 回填包头(长度/opcode/rpcId) ↓ _sendBuffers.Enqueue ↓ socket.SendAsync ── OS 负责可靠、有序、拥塞控制 ──→ 网络 ↓ OnSendCompleted → 还池 接收 网络 ──→ socket.ReceiveAsync （字节流，边界已丢失） ↓ Pipe.Writer.Advance + FlushAsync 背压在此生效 ↓ Pipe.Reader.ReadAsync ↓ UnPack ─ 攒头(20B) → 校验长度 → 攒体 → 凑齐一个包 ↓ 状态跨调用保留 Session.Receive(packInfo) ↓ NetworkMessageScheduler 分发到 Handler
