Source 网络同步（三）回滚与误差修正

Source SDK 2013 源码阅读 · 网络同步四部曲第三篇 · 本系列最核心的一篇
game/shared/predictioncopy.cpp · game/client/prediction.cpp · game/shared/predictable_entity.h

预测一定会错。网络有丢包、服务端有你不知道的信息、其他玩家在动。这一篇讲错了之后怎么办 —— 而 Source 的答案比"拉回正确位置"精妙得多。

先纠正一个常见的错误说法 很多资料（包括我最初的理解）说 Source 是"平滑修正预测误差"。这个说法不准确。

实际是双轨：模拟状态瞬间硬拉回，摄像机眼位平滑追赶。两者并存。你的碰撞盒立刻在正确位置，但眼睛还"留在"错误位置，然后在 0.1 秒内追上去。

这是本篇最重要的一条，§4 详讲。

一、三份数据：理解一切的地图

读这套代码前必须先分清同一个实体的三份数据。搞混了后面全看不懂。

名称存哪是什么内存布局
活体
live object		对象自身的成员变量当前正在渲染/模拟的值C++ 类布局
权威态
original / pristine		m_pOriginalData，一块堆内存服务端最新快照解包后的值紧凑打包
中间态
intermediate		m_pIntermediateData[90]每条命令跑完后的存档紧凑打包
game/client/c_baseentity.cpp:5182-5200（AllocateIntermediateData）
m_pOriginalData = new unsigned char[ allocsize ];
for ( int i = 0; i < MULTIPLAYER_BACKUP; i++ )
    m_pIntermediateData[ i ] = new unsigned char[ allocsize ];

MULTIPLAYER_BACKUP = 90，另有一个特殊 slot 号 SLOT_ORIGINALDATA = -1 用来指代权威态 —— 存取函数靠它分流。

1.1 为什么中间态用"打包布局"而不是 memcpy 整个对象

一个 C_TFPlayer 有几 KB，但真正参与预测的字段只有几百字节。90 份 × 几百字节可以接受；90 份完整对象拷贝不行。

所以每个字段记两套偏移：

public/datamap.h:266
fieldOffset[2]   // [0] = 在对象里的偏移，[1] = 在打包缓冲里的偏移

对应两个常量 PC_DATA_NORMAL / PC_DATA_PACKED。拷贝时告诉拷贝器"源用哪套、目标用哪套"。

C# 里怎么做 用一个 struct 装参与预测的字段，struct[] 或 NativeArray<T> 做环形缓冲。C# 的 struct 天然是紧凑布局，不需要手工算偏移 —— 这块比 C++ 简单得多。

容量怎么定：能容忍的最大延迟 ÷ tick 间隔，再取二的幂方便掩码取模。tick 30、容忍 500ms → 15 → 取 32。

二、CPredictionCopy：一个类干三件事

这个类的名字有误导性。它不是"拷贝类"，是"遍历字段表并对每个字段做三件事之一或全部"的类：比较、拷贝、描述。

构造时三个开关互相独立（predictioncopy.cpp:64-86）：counterrors / reporterrors / performcopy。

误差检测那次调用传的是 copydata = false —— 只比不拷：

game/client/c_baseentity.cpp:4692-4708（PostNetworkDataReceived）
void *predicted_state_data = GetPredictedFrame( commands_acknowledged - 1 );
const void *original_state_data = GetOriginalNetworkDataObject();
CPredictionCopy errorCheckHelper( PC_NETWORKED_ONLY,
    predicted_state_data, PC_DATA_PACKED,
    original_state_data,  PC_DATA_PACKED,
    counterrors, reporterrors, copydata /* = false */ );

两个操作数：

  • 左：中间态 slot commands_acknowledged - 1 —— "客户端预测命令 N 跑完时的状态"
  • 右：权威态 —— "服务端说命令 N 跑完应该是什么"

两边都是 PC_DATA_PACKED，同构内存块比对，字段偏移完全一致。

2.1 三种过滤模式

判据是字段有没有 FTYPEDESC_INSENDTABLE 标记：

game/shared/predictioncopy.cpp:1050-1056
if ( m_nType == PC_NON_NETWORKED_ONLY && ( flags & FTYPEDESC_INSENDTABLE ) )
    continue;
if ( m_nType == PC_NETWORKED_ONLY && !( flags & FTYPEDESC_INSENDTABLE ) )
    continue;
模式用在哪用了几处
PC_EVERYTHING存档、恢复起点、初始化多处
PC_NETWORKED_ONLY存权威态、误差比对2 处
PC_NON_NETWORKED_ONLY只 1 处，但那一处是整套设计最精妙的一步1 处（§5.2）

三、两张表为什么不能合并

SendTable 说"什么要发给客户端"，PredictionData 说"什么要存档回滚"。这两个集合有交集，但都不包含另一个。

3.1 四类字段

这是本篇最有实用价值的一张表。你在 Unity 里做同步系统时，每个字段都要归类。

类别发给客户端参与回滚参与比对Source 实例
A 完整同步✓✓✓m_nTickBase、m_vecOrigin
B 纯本地预测态✗✓—m_nButtons、m_flStepSoundTime
C 纯展示✓✗—渲染颜色 m_clrRender
D 预测但不可比✓✓✗m_flCycle、m_nSequence

声明方式的差别：

game/client/c_baseplayer.cpp:382, 403
DEFINE_PRED_FIELD( m_nTickBase, FIELD_INTEGER, FTYPEDESC_INSENDTABLE ),  // A
DEFINE_FIELD( m_nButtons, FIELD_INTEGER ),                              // B（无 flag）
关键：交集靠手写标记维护，没有任何工具自动同步 FTYPEDESC_INSENDTABLE 是程序员手写在 DEFINE_PRED_FIELD 第三个参数里的。

标错了，误差检测就会去比服务端从未发送过的字段，产生永久性的假误差。这是 Source 预测系统最经典的一类 bug 来源。

3.2 B 类和 D 类是最容易漏的，后果完全不同

漏了 B（该进预测表没进）→ 重放时本地状态被服务端快照覆盖 → 脚步声重复播放、计时器错乱。

漏了 D（该标"不比对"没标）→ 动画周期永远对不上 → 每帧都判定预测失败 → 每帧都触发平滑修正和插值重置 → 画面持续抖动。

第二种尤其阴险：症状是"移动手感很糟"，但根因在动画字段上，排查方向完全错位。

3.3 D 类为什么还要参与回滚

既然 m_flCycle（动画周期）永远和服务端对不上，为什么不干脆从预测表里删掉？

因为回滚和比对是两件事。

FTYPEDESC_NOERRORCHECK 只屏蔽"报错"，不屏蔽"回滚"—— 那道闸只挡在比较函数前面：

game/shared/predictioncopy.cpp:190-200
bool CPredictionCopy::CanCheck( void )
{
    if ( m_pCurrentField->flags & FTYPEDESC_NOERRORCHECK )
        return false;
    return true;
}

如果把 m_flCycle 从预测表删掉，重放 5 条命令时它不会被恢复到起点，而是从当前值继续推进 5 次 —— 重放本身不自洽。同一条命令跑两遍得到不同结果，这比"和服务端不一致"更糟。

一句话总结这个区分 参与回滚保证客户端内部自洽，不参与比对是承认跨端无法一致。两个目标独立，所以用两个开关表达。

Unity 里对应两个 attribute 参数：[Predicted(Networked = true, NoErrorCheck = true)]。

3.4 NOERRORCHECK 的三类用途 —— 一份坦白的技术债清单

类别一：动画状态（两端天然不同步）

game/client/c_baseanimating.cpp:214-226
DEFINE_PRED_FIELD( m_nSequence, ..., FTYPEDESC_INSENDTABLE | FTYPEDESC_NOERRORCHECK ),
DEFINE_PRED_FIELD( m_flCycle, ..., FTYPEDESC_INSENDTABLE | FTYPEDESC_NOERRORCHECK ),

类别二：客户端主动做了不同的事。m_angNetworkAngles —— 上一篇讲过视角每帧被强制覆盖，既然客户端故意不采用预测值，比较它毫无意义。

类别三：明知有 bug，先屏蔽掉。最诚实的一批 —— 三个武器计时字段全标了，配套注释见第二篇 §6.4。

四、双轨修正：本篇的核心

4.1 模拟状态：瞬间硬拉回

RestoreOriginalEntityState（prediction.cpp:1162-1185）用 PC_EVERYTHING 直接覆盖活体数据。零平滑。

为什么必须瞬间：后续预测必须从正确起点开始，否则误差累积失控。如果起点是"平滑过渡中的中间值"，下一帧预测的结果会更错，越滚越大。

4.2 摄像机眼位：平滑追赶

误差被记下来（c_baseplayer.cpp:2641-2660）：

if ( !IsAlive() ) return;          // 死亡时不平滑
GetPredictionErrorSmoothingVector( vOldDelta );
m_vecPredictionError = vDelta + vOldDelta;   // ★ 累加未衰减完的旧误差
m_flPredictionErrorTime = gpGlobals->curtime;

误差是累加的：新误差叠加到"上次尚未衰减完的剩余部分"上，然后重置计时器。连续误判不会互相截断，视觉上是连续的一段追赶。

平滑曲线简单到意外 —— 全部逻辑就这几行：

game/client/c_baseplayer.cpp:2715-2738
float errorAmount = ( gpGlobals->curtime - m_flPredictionErrorTime )
                     / cl_smoothtime.GetFloat();
if ( errorAmount >= 1.0f ) { vOffset.Init(); return; }
errorAmount = 1.0f - errorAmount;
vOffset = m_vecPredictionError * errorAmount;

纯线性衰减。没有 ease-in/out，没有 smoothstep，没有指数衰减。offset = error × (1 - elapsed/duration)。

时长 cl_smoothtime 默认 0.1 秒，范围钳在 0.01–2.0。

4.3 偏移量施加在哪 —— 双轨的实证

game/shared/baseplayer_shared.cpp:1630-1636
Vector vSmoothOffset;
GetPredictionErrorSmoothingVector( vSmoothOffset );
eyeOrigin += vSmoothOffset;   // ★ 只加在渲染用的眼位上

GetAbsOrigin()（碰撞与后续预测用的位置）一点没动。

双轨修正 预测错了 50 单位 │ ├─→ 模拟轨：GetAbsOrigin() 瞬间 = 服务端值 │ 碰撞、后续预测立刻正确 │ └─→ 视觉轨：eyeOrigin = GetAbsOrigin() + offset offset 从 50 线性降到 0，历时 0.1s 玩家看到：镜头平滑追上去 物理感受：碰撞盒已经在对的地方

4.4 为什么视角不能瞬间拉回

按严重程度排：

  1. 画面跳动。人眼对摄像机的单帧不连续位移极度敏感 —— 比对场景中物体的同等位移敏感得多。
  2. 误判频繁时呈持续抖动。弱网下每个包都可能带误差，逐帧跳动累积成"镜头发抖"。
  3. 触发晕动症。摄像机不连续位移是第一人称/VR 公认的晕动症诱因。
  4. 误差被放大感知。0.1 秒的线性追赶几乎不可察觉；同样幅度的瞬变非常难受。同一个数值，平滑与否决定它是"看不见"还是"很难受"。

4.5 三段式误差判定

CheckError（prediction.cpp:128-199）只关心一个字段 —— 位置：

if (len > MAX_PREDICTION_ERROR )        { len = 0; }   // > 64 单位：视为传送，完全忽略
else if ( len > MIN_PREDICTION_EPSILON ) {                 // > 0.5 单位：记录误差
    player->NotePredictionError( delta );
}
// 0.5 以内：什么也不做

上限那一档很重要：传送、复活、被推入传送门不是预测错误。若按误差处理会产生一段长达 64+ 单位的诡异漂移 —— 镜头缓慢追赶一个传送距离，非常怪。所以直接放弃平滑，让位置瞬间到位。

Unity 落地：三档判定都要有
  • 下限（忽略）：小于量化精度的差异，不算错
  • 中间（平滑）：正常的预测误差
  • 上限（放弃平滑）：传送、复活、重生 —— 这些是合法的位置突变，不该被当成误差平滑
少了上限那一档，你的传送会变成"镜头缓慢飞过去"。

五、重放的完整机制

5.1 浮点容差：必须从传输格式反推

比较用绝对差，默认容差是 0（精确按位相等），只有显式用 _TOL 变体才有容差。

关键实例：

字段容差怎么来的
m_vecNetworkOrigin0.0625 = 2.0f / (1 << 5)两倍量化步长
m_vecViewOffset0.25经验值
m_vecBaseVelocity0.05经验值

坐标容差的推导：网络传输时坐标量化到 1/32 精度（第一篇 SPROP_COORD），所以服务端值经过量化-反量化后与客户端全精度浮点天然差最多 1/32。容差取 2/32，把量化噪声完全排除在误差判定外。

这条能直接用 容差不是拍脑袋，是从你的压缩格式反推的。

Unity 里如果你把坐标量化到 0.01，误差容差就必须 ≥ 0.02。
填 0.001 → 永久假误差（每帧都判失败）；
填 1.0 → 漏掉真误差（明显错位却不修正）。

5.2 那四行代码：网络包到达之前

这是整套机制里我认为最精妙的一步。

game/client/c_baseentity.cpp:4613-4639（PreEntityPacketReceived）
bool copyintermediate = ( commands_acknowledged > 0 );
if ( copyintermediate )
{
    RestoreData( ..., commands_acknowledged - 1, PC_NON_NETWORKED_ONLY );
    RestoreData( ..., SLOT_ORIGINALDATA,        PC_NETWORKED_ONLY );
}
else
    RestoreData( ..., SLOT_ORIGINALDATA, PC_EVERYTHING );

两次恢复，来源不同，字段集互补：

  • 第一次：从预测存档恢复非网络化字段 —— 服务端对这些一无所知，客户端预测结果就是唯一真相，必须保留
  • 第二次：从权威态恢复网络化字段 —— 这些即将被新包覆盖，先退回上一个权威值作干净底座
  • else 分支：服务端没确认任何新命令，无所谓哪个更可信，整体退回权威态

原始注释把结果说得很清楚：

game/client/c_baseentity.cpp:4633-4637
// At this point the entity has original network data restored as of the last
// time the networking was updated, and it has any intermediate predicted
// values properly copied over. Unpacked and OnDataChanged will fill in any
// changed, networked fields.
这是 PC_NON_NETWORKED_ONLY 存在的唯一理由 整个代码库只在这一处用它。Unity 落地时这是最容易漏的一步：做回滚不能一股脑全恢复，得区分"服务端管的"和"只有本地知道的"，后者绝不能被服务端快照覆盖。

漏了的症状：脚步声重复播放、连击计时错乱、技能 CD 跳变。

5.3 一个周期里保存/恢复各几次

单帧时序（收到包 + 有误差） 解包前 ① RestoreData( 预测 N, NON_NETWORKED_ONLY ) 恢复：捞回本地字段 ② RestoreData( 权威态, NETWORKED_ONLY ) 恢复：网络字段回退 解包后（每包一次） ③ SaveData( 权威态, NETWORKED_ONLY ) ★ 权威态的建立点 帧末（每帧一次） ④ SaveData( 权威态, EVERYTHING ) 完整刷新 ⑤ CPredictionCopy 比对 NETWORKED_ONLY ★ 纯比较，不拷 下一帧预测开始 ⑥ RestoreOriginalEntityState( EVERYTHING ) 活体 ← 权威态 ⑦ 每跑完一条命令：StorePredictionResults() ★ 存档 × M

恢复 3 次，保存 3+M 次，纯比较 1 次。走优化捷径时 ⑥ 被替换，M 降到 1。

5.4 重放不是常态 —— 这点最容易误解

cl_pred_optimize 默认 2。稳定网络下走的是这条路：

game/client/prediction.cpp:1471-1492
if ( cl_pred_optimize.GetInt() >= 2 && !m_bPreviousAckHadErrors && ... )
{
    RestoreEntityToPredictedFrame( m_nCommandsPredicted - 1 );
    ShiftIntermediateDataForward( ... );
    skipahead = ( m_nCommandsPredicted - m_nServerCommandsAcknowledged );
}

预测全对 → 上次结果依然有效 → 恢复到最后一个预测 slot，把 slot 数组前移，只跑最新那一条命令。

而且 ShiftIntermediateDataForward（c_baseentity.cpp:5227-5256）只搬指针，不 memcpy。

"Source 每帧重放 N 条命令"是个误解 重放是异常处理，不是主循环。稳定网络下绝大多数帧只跑一条新命令。

Unity 落地：如果你写成每帧无条件重放 N 条，性能会随延迟线性恶化。应该先比对、无误差就走捷径。

还有一条捷径（cl_pred_optimize >= 1）：压根没收到新世界更新时，服务端没说话就不可能有新误差，直接跳到最后一条。但注释强调必须先恢复：

game/client/prediction.cpp:1454
// Always restore since otherwise we might start prediction using an
// 'interpolated' value instead of a purely predicted value

微妙的坑：活体数据在渲染过程中被插值系统动过手脚，直接拿来当预测起点会污染结果。

5.5 回滚不能只是"把字节写回去"

RestoreData 里有一串补救逻辑（c_baseentity.cpp:5764-5820）：

int savedEFlags = GetEFlags() & savedEFlagsMask;
int oldModelIndex = m_nModelIndex;
/* ... TransferData ... */
RemoveEFlags( savedEFlagsMask );  AddEFlags( savedEFlags );
// model index 必须走 SetModelIndex 以维护动态模型引用计数

结尾 OnPostRestoreData() 还要 InvalidatePhysicsRecursive、重挂 aim ents 链表、同步模型指针。

这是一份现成的检查清单 任何"值改变时需要副作用"的字段，回滚后都必须手工补做：
引用计数 · 缓存失效 · 事件注册 · 脏标记 · 物理状态失效

Unity 里典型的：改了 transform.position 要不要 Physics.SyncTransforms()、改了动画状态要不要重算骨骼、改了父子关系要不要重挂。这些都不是"写回字节"能覆盖的。

六、误差的第二个善后动作：清插值历史

这一步和位置平滑无关，但同属"误差善后"，而且原始注释把问题说得很清楚：

game/client/prediction.cpp:1499-1503
// If an entity gets a prediction error, then we want to clear out its
// interpolated variables so we don't mix different samples at the same
// timestamps. We subtract 1 tick interval here because if we don't, we'll
// have 3 interpolation entries with the same timestamp as this predicted
// frame, so we won't be able to interpolate (which leads to jerky movement
// in the player when ANY entity like your gun gets a prediction error).

注意括号里那句：任何实体（包括你的枪）出预测误差，都会导致玩家本体移动抖动。

TF2 分支为此加了"全量重置 vs 部分重置"的分野（prediction.cpp:1510-1550）。旧行为是"任何实体出错就清所有 predictable 的插值历史"，新行为让实体自己决定 —— C_BaseCombatWeapon 在有主人时返回 false，不再连带清掉玩家的插值历史。

这是"缩小误差传播范围"的典型做法：既然武器预测做不对（第二篇 §6.4），至少别让它污染移动手感。

七、Unity 落地要点

7.1 双轨修正（最重要的一条）

// 模拟轨：瞬间硬拉回
transform.position = authoritativePosition;

// 视觉轨：摄像机加衰减偏移
float t = (Time.time - _errorTime) / SmoothDuration;   // SmoothDuration = 0.1f
if (t < 1f)
    _cameraTarget.position = transform.position + _error * (1f - t);
else
    _cameraTarget.position = transform.position;

关键是别把两件事混在一起。混了之后会陷入"平滑了但物理飘"或"物理准了但画面抖"的两难。

7.2 误差要累加

新误差叠加到旧误差的剩余部分上，而不是覆盖。否则连续误判会互相截断，视觉上是一顿一顿的。

7.3 三档判定 + 容差从压缩格式反推

见 §4.5 和 §5.1。这两条是最容易做错且最难 debug 的。

7.4 区分"服务端管的"和"只有本地知道的"

见 §5.2。回滚时后者绝不能被服务端快照覆盖。

7.5 无误差时走捷径

见 §5.4。重放是异常处理，不是主循环。

7.6 回滚后补做副作用

见 §5.5。Physics.SyncTransforms()、动画重算、父子关系重挂。

7.7 用一张表管字段分类

见 §3.1 的四类。建议在 C# 里用 attribute 表达，把 Source 的"两张表 + 手工标记交集"压成"一张表 + 声明式参数"：

[Predicted]                                          // B 类：只回滚
[Predicted(Networked = true)]                        // A 类：回滚 + 比对
[Predicted(Networked = true, NoErrorCheck = true)]    // D 类：回滚不比对
[Predicted(Networked = true, Tolerance = 0.02f)]      // A 类带容差
// 不打特性 = C 类，纯展示

这样就消掉了"标错 FTYPEDESC_INSENDTABLE"这一整类 bug。
