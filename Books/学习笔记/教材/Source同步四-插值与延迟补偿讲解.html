Source 网络同步（四）插值与延迟补偿

Source SDK 2013 源码阅读 · 网络同步四部曲第四篇（终）
game/client/interpolatedvar.h · game/server/player_lagcompensation.cpp

前两篇讲的是本地玩家：预测让你的输入立即生效，回滚保证正确性。

这一篇讲另外两个方向：其他玩家在你屏幕上怎么才不抖（插值，把时间往后推），以及你开枪时服务端怎么判定命中（延迟补偿，把时间倒带）。

为什么这两个必须放在一篇里讲 它们是同一笔时间债的两面。

插值为了平滑，让你看到的敌人比真实位置旧 100ms。如果服务端按"当前真实位置"判定命中，你瞄准的地方永远是空的 —— 永远打不中。

所以延迟补偿必须把这 100ms 原样还回来。代码里有直接证据（§7），插值时间是延迟补偿公式里的一个加数。

这就是我在第一篇说的"闭环"。只做预测不做这两个，游戏是不可玩的。

一、纠正一个常见混淆

public/interpolatortypes.h 和实体插值无关。它是 Faceposer/SFM 的表情曲线（Catmull-Rom、Kochanek-Bartels、B-Spline），只被 expressionsample.h 和 movieobjects/dmelog.h 引用。

实体插值的类型标志在 game/client/interpolatedvar.h:30-37。两者名字相似但完全是两个系统，网上不少资料把它们混为一谈（我一开始也是）。

二、为什么远程实体必须插值

服务端只在每个 tick 结束时发快照（TF2 约 66Hz = 15ms），客户端渲染帧率独立且远高于此（144fps ≈ 6.9ms）。

直接把最新快照的值贴给远程实体的后果：

不插值 vs 插值 不插值（直接用最新快照） 快照: A────────B────────C 渲染: AAA BBB CCC 同一值渲染 2-3 帧不动 └─ 卡住 ─┘└ 瞬移 ┘ 结果：20Hz 级别的抽帧跳动，无论本地多少帧 插值（渲染过去某一时刻） 快照: A────────B────────C 目标: ↑ 渲染时间 = 当前 - 延迟 渲染: A·a·a·b·B·b·b·c·C 连续 结果：平滑，代价是看到的是过去

更糟的是网络抖动会让快照间隔忽长忽短，跳动幅度也随之不均。

核心一行：

game/client/interpolatedvar.h:810
float targettime = currentTime - interpolation_amount;

客户端渲染的远程实体，永远是过去某个时刻的状态。这样手上总有目标时间前后各一个真实采样点，可以连续插值。

三、插值延迟的实际公式（比流传版本多一层）

game/client/cdll_bounded_cvars.cpp:134
return MAX( cl_interp->GetFloat(),
            cl_interp_ratio->GetFloat() / pUpdateRate->GetFloat() );

是取大，不是相加。默认 cl_interp = 0.1、cl_interp_ratio = 2.0、cl_updaterate = 66：

max(0.1, 2/66) = max(0.1, 0.0303) = 0.1 秒

这就是为什么竞技玩家要把 cl_interp 设成 0 —— 让 ratio 项生效，把延迟从 100ms 降到 30ms。

但还没完，最终值要再加服务端 tick 余量：

game/client/c_baseentity.cpp:5937
return AdjustInterpolationAmount( this,
    TICKS_TO_TIME( TIME_TO_TICKS( GetClientInterpAmount() ) + serverTickMultiple ) );

serverTickMultiple 通常是 1（alternate ticks 时为 2）。无条件多加一个 tick 的余量 —— 宁可多延迟也不冒"采样点还没到就要插值"的风险。

netgraph 显示的数字比实际值小一个 tick vgui_netgraphpanel.cpp:771 显示的 lerp: xx ms 不含这个 +1 tick 余量。

所以你在游戏里看到的插值延迟数字，比真实值小 15ms（66 tick）。这是个典型的"显示值 ≠ 实际值"陷阱。

完整公式：

插值延迟的完整计算 base = MAX( cl_interp', cl_interp_ratio' / cl_updaterate' ) cl_interp' = MAX( cl_interp, sv_min / updaterate ) cl_interp_ratio' = clamp( ratio, sv_client_min, sv_client_max ) delay = TICKS_TO_TIME( TIME_TO_TICKS( base ) + 1 ) ← +1 tick 余量 target = curtime - delay

3.1 cl_interp_ratio 的语义

"我要缓冲几个快照间隔"。

  • ratio = 2：留两个更新周期余量，能容忍丢一个包而插值不断流
  • ratio = 1：只留一个周期，任何丢包立刻断流

这是"延迟"和"抗丢包"的直接权衡，也是竞技玩家和普通玩家配置分歧的根源。

3.2 本地玩家走另一条路

game/client/c_baseentity.cpp:5925-5928
// 可预测/客户端创建的实体
return TICK_INTERVAL * serverTickMultiple;   // 只有一个 tick

自己的身体不能被延后，那是预测的地盘。三套机制在这里划清了边界。

四、历史采样怎么存

不是固定环形数组，是可增长的环形缓冲 CSimpleRingBuffer（interpolatedvar.h:304-429）：

  • 初始容量 4，增长步长 16
  • AddToHead() 插到头部，索引 0 恒为最新，越大越旧
  • 每条 entry 存 { changetime, 值 }

保留多少个点不是固定数字，是按时间窗口裁剪：

game/client/interpolatedvar.h:1057
RemoveEntriesPreviousTo( currentTime - interpolation_amount
                          - EXTRA_INTERPOLATION_HISTORY_STORED );

EXTRA_INTERPOLATION_HISTORY_STORED = 0.05f，多留 50ms 余量。裁剪时刻意保留目标时刻之前的 3 个采样（因为 Hermite 需要三点），所以稳态下典型是 3-5 个点。

4.1 选点与插值系数

从最新往旧遍历，找到第一个 changetime <= targettime 的作为 older，前一个作为 newer：

game/client/interpolatedvar.h:846-847
pInfo->frac = ( targettime - older_time ) / ( newer_time - older_time );
pInfo->frac = MIN( pInfo->frac, 2.0f );   // 上限 2.0

若还能再往旧取到第 3 个点且未设 INTERPOLATE_LINEAR_ONLY，就走三点 Hermite。

五、不同数据类型需要不同插值方式

这一节的三个案例都是"朴素线性插值会出错"的典型，值得单独记。

5.1 角度的 360° 环绕 —— 用四元数 slerp

QAngle 的线性插值被特化为四元数 slerp（mathlib.h:661，注释 "Specialization for interpolating euler angles via quaternions"）。

这样 350° → 10° 走 20° 短弧，而不是欧拉数值上倒退 340°。

而角度的 Hermite 被显式禁用：

game/client/lerp_functions.h:104-108
inline QAngle Lerp_Hermite<QAngle>( float t, ... )
{
    // Can't do hermite with QAngles, get discontinuities,
    // just do a regular interpolation
    return Lerp( t, p1, p2 );
}

原因：Hermite 要用前一点估切线（速度），而角度的环绕会让"速度"算出天文数字 —— 350° 到 10° 看起来是 -340° 的位移，切线完全错。

5.2 动画周期的循环 —— LoopingLerp

m_flCycle 是 0→1 循环量。用 0.5 作为"是否跨越环绕点"的判据：

game/client/lerp_functions.h:22-29
if ( fabs( flTo - flFrom ) >= 0.5f )
{
    if (flFrom < flTo) flFrom += 1.0f;
    else               flTo   += 1.0f;
}

0.9 → 0.1 被理解成 0.9 → 1.1（继续前进），而不是倒退 0.8。

而且是否走 looping 由序列本身是否循环动态决定（c_baseanimating.cpp:4472）：

m_iv_flCycle.SetLooping( IsSequenceLooping( GetSequence() ) );

5.3 位置用 Hermite，但要夹逼

位置是连续物理量，三点 Hermite 能沿运动曲线走出带速度连续性的弧线，比纯线性的折线更贴近真实轨迹。

但 Hermite 会过冲，所以每个分量事后都过 Lerp_Clamp。注释里有个生动的记录（interpolatedvar.h:1452-1455）：m_flCycle 曾被 Hermite 甩到 la-la land。

Unity 落地：三类量三种处理
数据类型正确做法错误做法的症状
位置Vector3.Lerp 或三点 Hermite + clampHermite 不夹逼 → 转向时过冲
旋转Quaternion.Slerp，绝不插欧拉角过 ±180° 时整个转一圈
循环量
（动画周期、进度条）		先判断是否跨环绕点0.9→0.1 时倒着播
第二条最常见。Unity 里 Vector3.Lerp(eulerAngles) 是新手最经典的坑之一，而它在网络插值里出现的概率极高，因为你拿到的往往是压缩后的角度值。

5.4 外插：门槛设得很高

当目标时间已经晚于所有采样时才考虑外插，且四个条件全满足（interpolatedvar.h:1002-1006）。最关键的一条：

CInterpolationContext::GetLastTimeStamp() <= m_LastNetworkedTime

代码用一大段注释解释（:1008-1021）：只有当整个连接都没收到新数据（服务器在 choke）才外插。

如果服务器还在正常发包、只是这个实体不再更新，说明它真的停下了 —— 此时外插会造成"物体飘出去又被拽回来"。

外插量上限 cl_extrapolate_amount 默认 0.25 秒。而且 CInterpolationContext 构造时默认关闭外插，必须显式开启 —— fail-safe 设计。

这个判据值得照抄 "没数据"和"数据说它没动"是两件完全不同的事。

Unity 里做外插时，要能区分"网络卡了"和"这个物体停下了"。区分方法就是 Source 这招：看整个连接的最后收包时间，而不是看这个实体的最后更新时间。

另外超过 0.5 秒没收包，整个插值系统停摆（c_baseentity.cpp:3231-3239）。

六、延迟补偿：把时间倒带

文件 game/server/player_lagcompensation.cpp（约 875 行），接口只有 3 个虚函数。

6.1 完整流程

一次开枪的服务端处理 第 0 步 · 持续录像 每帧为每个玩家追加一条 LagRecord FrameUpdatePostEntityThink，:245-342 第 1 步 · 客户端在自己的时间线开枪 屏幕上的对手是"过去"的（插值延迟） 开火写进 CUserCmd，带 tick_count + viewangles 第 2 步 · 武器代码主动开启补偿 ← 不是框架自动的！ StartLagCompensation( pPlayer, pPlayer->GetCurrentCommand() ); ... FireBullets / 射线检测 ... FinishLagCompensation( pPlayer ); 全树约 20 处这样的配对 第 3 步 · 算出倒带到哪一刻 ← §7 详讲 第 4 步 · 把其他玩家搬回去 跳过自己 → WantsLagCompensationOnEntity 过滤 → BacktrackPlayer()：改写 origin/angles/bbox/动画状态 原值记进 m_RestoreData 第 5 步 · 在倒带后的世界做射线检测 命中判定自然打在"客户端当时看到的位置" 第 6 步 · 恢复 只在"当前值仍等于我们改成的值"时才还原

第 2 步值得强调：延迟补偿不是自动的，每把武器要显式包裹射线检测。这意味着漏了就没有补偿，而症状是"这把枪特别难打中人"。

第 6 步的谨慎很有代表性：射线检测过程中游戏逻辑可能合法地又改动了玩家（击退、死亡），这时新值优先，不能覆盖。

6.2 LagRecord 存什么

m_fFlags            // LC_ALIVE
m_vecOrigin, m_vecAngles
m_vecMinsPreScaled, m_vecMaxsPreScaled   // 碰撞盒
m_flSimulationTime  // ★ 索引键
m_masterSequence, m_masterCycle          // ↓ 完整动画姿态
m_layerRecords[]                         // 叠加层
m_flPoseParameters[]

历史窗口 = sv_maxunlag，默认 1.0 秒，上限也是 1.0。每帧从尾部剔除过期记录。

为什么必须有上限 没有上限的话，一个 ping 3 秒的玩家能让服务端把所有人倒带 3 秒 —— 等于在别人的"三秒前"射击，对被打的一方完全不可理解。同时历史缓冲的内存和遍历成本也会失控。

超出这个延迟的玩家，补偿被截断，只能自己"打提前量"。

七、倒带时刻的计算 —— 时间债的直接证据

这是整个系列最关键的一段代码：

game/server/player_lagcompensation.cpp:389-402
correct += nci->GetLatency( FLOW_OUTGOING );          // ① 网络单程延迟
int lerpTicks = TIME_TO_TICKS( player->m_fLerpTime );  // ② 客户端插值量
correct += TICKS_TO_TIME( lerpTicks );                 // ★ 加上插值延迟
correct = clamp( correct, 0.0f, sv_maxunlag.GetFloat() );
int targettick = cmd->tick_count - lerpTicks;

倒带量 = 网络延迟 + 插值延迟。

这就是我在第一篇说的"插值欠下的时间债必须由延迟补偿来还"—— 代码层面的直接证据。服务端倒带时不只减去网络延迟，还要再减去客户端插值造成的额外延迟，两笔加起来才是"玩家开枪那一刻真正看到的画面"。

7.1 服务端不信任客户端上报的插值量

cl_interp 是 FCVAR_USERINFO —— 玩家能改。如果服务端照着客户端说的倒带，把 cl_interp 调到 0.5 就能打"半秒前"的敌人。

所以服务端用完全复制客户端逻辑的方式自己重算一遍：

game/server/player.cpp:3510
this->m_fLerpTime = MAX( flLerpAmount, flLerpRatio / this->m_nUpdateRate );

同文件 :3479-3482 的注释坦承这是在重复客户端的代码。而且会用 sv_client_min/max_interp_ratio 夹逼。

7.2 两条路径互相校验（反作弊防线）

game/server/player_lagcompensation.cpp:405-412
float deltaTime = correct - TICKS_TO_TIME(gpGlobals->tickcount - targettick);
if ( fabs( deltaTime ) > 0.2f )
    targettick = gpGlobals->tickcount - TIME_TO_TICKS( correct );

优先信任客户端上报的 tick_count，但如果它与"按延迟推算的 tick"相差超过 200ms，判定客户端在撒谎或时钟严重失准，回退到纯延迟推算。

否则客户端可以伪造 tick_count 任意倒带。

可以带走的安全模式 客户端上报的任何"时间"都是不可信输入。正确做法是：
① 服务端自己也能算一份（哪怕要复制客户端代码）
② 客户端值只在合理区间内被采纳
③ 超出区间就回退到服务端自算值

不要简单地拒绝或截断 —— 那会让高延迟的诚实玩家受损。要的是"信任但验证"。

八、边界情况：倒带会遇到的麻烦

8.1 目标中途死过 —— 整个倒带放弃

game/server/player_lagcompensation.cpp:473-477
if ( !(record->m_fFlags & LC_ALIVE) )
{
    // player most be alive, lost track
    return;
}

"目标在这段时间里死过"就不补偿，避免复活尸体作为靶子。

8.2 传送/换队 —— 靠位移突变检测

相邻记录 2D 位移超过 sv_lagcompensation_teleport_dist（默认 64 单位）就判定 "lost track" 并放弃倒带。

换队通常伴随死亡+重生，会被 LC_ALIVE 拦住。

8.3 倒带后的位置被占了 —— sv_unlag_fixstuck

A 被搬回 1 秒前的位置，但那里现在站着 B —— A 就卡在实体内部。

sv_unlag_fixstuck 默认 0（关闭）。开启后会先 trace 探测，若 startsolid 就尝试把挡路的那个玩家也倒带（带防递归保护），否则沿路径 trace 到能到达的最远点，还留 5% 余量避免贴面卡住。

默认关闭说明 Valve 认为"轻微卡住"比"补偿位置被改得不准"危害更小。

8.4 骨骼必须一起倒带 —— 最关键的一条

Source 的 hitbox 是跟着骨骼跑的，而骨骼由 sequence + cycle + pose parameters 求解得出。

光把 origin 搬回去不够 —— 姿势不对，hitbox 位置就不对。一个正在跑动、腿部大幅摆动、上半身转向的玩家，其 hitbox 分布与站立姿势差别很大。

而骨骼求解结果是缓存的，所以改完动画状态必须让缓存失效：

game/server/player_lagcompensation.cpp:748-749
if ( sv_lagflushbonecache.GetBool() )
    pPlayer->InvalidateBoneCache();
如果不刷缓存会怎样 服务端会拿着上一帧算好的骨骼去做命中检测 —— 你把模型搬回了过去，hitbox 却留在现在。

补偿等于白做，还会产生"明显打中却不掉血"或反之的诡异结果。这个 convar 默认 1，正常绝不该关。

动画插值这里也复刻了周期环绕问题（§5.2 的服务端版），而且更保守：sequence 变化时禁止插值（"can't interpolate across a sequence or order change"），pose parameter 干脆不插值只取最近的。

调试工具：sv_showlagcompensation 可以画出补偿后的 hitbox。

九、固有不公平：墙后击杀

9.1 成因

两段延迟叠加。射手 S 的屏幕上，目标 T 的位置是 S的当前时间 − 网络延迟 − 插值延迟。服务端倒带的正是这个总量。

假设 S ping 100ms、插值 100ms → 服务端回到 200ms 前做判定。

墙后击杀的时间线 T 的视角（T 是预测的，处于"未来"） t=0ms 在开阔处 t=150ms 已经进掩体了 t=200ms "我明明在掩体后面！" ← 收到死亡 S 的视角（看到的 T 落后 200ms） t=200ms 屏幕上 T 还在开阔处 → 开枪 → 准星对上了 服务端裁决 倒带 200ms：T 确实在开阔处，S 确实瞄准了 → 判定命中

这不是 bug，是补偿模型的数学必然。两个玩家对"现在"的定义不同，而服务端必须选一个。Source 选了射手的。

9.2 Valve 为什么接受这个取舍

对比另一种选择 —— 完全不补偿，服务端只按"当前真实位置"判定：

那么 S 必须瞄准 T 在 200ms 后的位置。也就是说，每个玩家都必须手动打提前量，且提前量随自己的 ping 实时变化。ping 越高越难，高 ping 玩家几乎无法命中移动目标 —— 游戏对他们直接不可玩。

伤害谁代价性质
不补偿射手与 ping 成正比，持续的、每一枪都有的技能税。高 ping 玩家永久劣势
补偿被射者偶发的"墙后击杀"，且分摊到所有人（每个人既是射手也是被射者）

后者把不公平从"系统性歧视高延迟玩家"转成了"偶发的、双向对称的判定争议"。

而且它保住了最重要的一条主观体验：准星对上了就该命中。这是 FPS 手感的基石，一旦破坏，游戏就不成立了。

所以代价被限制（sv_maxunlag 1 秒上限、锥形剪枝）而非消除。

9.3 一个常被误解的点

延迟补偿只作用于玩家。世界几何、门、平台都不倒带 —— 所以你的子弹是在"过去的玩家位置"和"现在的世界"之间做检测。

TF2 为 Passtime 的球单独手写了一套并行实现，其注释直言 // it would be better if all entities could opt-in to this。这个架构局限 Valve 自己也知道。

十、三套机制的统一视角

机制方向谁的时间被改关键量
客户端预测提前本地玩家一个 tick
远程实体插值延后其他实体max(cl_interp, ratio/updaterate) + 1 tick
服务端延迟补偿倒带服务端上的其他玩家网络延迟 + 插值延迟，夹在 [0, sv_maxunlag]

三者共同目标：让每个玩家都感觉自己在一个零延迟的世界里。

代价是 —— 这是整个系列最重要的一句话：

没有单一的"现在" 服务端和每个客户端对同一时刻的世界状态有各自不同、且都"正确"的版本。

所有网络 FPS 的判定争议都源于这个根本事实。不是实现缺陷，是分布式系统 + 光速有限的必然结果。

理解这一点之后，你就不会再试图"消除"不公平，而是转向"选择哪种不公平更能接受"。

十一、Unity 生态对照

11.1 三套机制在 Unity 里的对应

SourceNGO / Mirror要不要自己写
属性同步 + 脏标记NetworkVariable / SyncVar❌ 内置，但粒度只到变量级
远程实体插值NetworkTransform 的 Interpolate 开关⚠ 内置但可控性差，讲究的项目要自己写
客户端预测 + 回滚无✅ 完全自己写
服务端延迟补偿无✅ 完全自己写

后两项是 Unity 网络生态最大的空缺。这也是为什么严肃的 FPS 项目往往要么用 Photon Quantum/Fusion（自带预测回滚），要么自己造一套。

11.2 延迟补偿在 Unity 里怎么做

// 1. 每个 tick 记录所有玩家的碰撞体状态
struct LagSnapshot {
    public double ServerTime;
    public Vector3 Position;
    public Quaternion Rotation;
    public Vector3[] BonePositions;   // 如果用骨骼 hitbox
    public bool IsAlive;              // ★ 别忘了这个
}

// 2. 开枪时倒带
double rewindTo = serverTime - (latency + clientInterpDelay);   // ★ 两笔都要减
rewindTo = Math.Clamp(rewindTo, serverTime - MaxUnlag, serverTime);

foreach (var target in targets) {
    if (!target.TryGetSnapshotAt(rewindTo, out var snap)) continue;
    if (!snap.IsAlive) continue;                    // 死过就放弃
    target.ApplyRewind(snap);                        // 临时移动 Collider
}
Physics.SyncTransforms();                              // ★★ 关键！等价于刷骨骼缓存
// … Physics.Raycast …
foreach (var target in targets) target.RestoreRewind();

Physics.SyncTransforms() 那一行是 Unity 版的 InvalidateBoneCache()。Unity 的物理场景状态不会在你改 transform 后立刻更新，不调它 Raycast 打的还是旧位置 —— 和 §8.4 的坑一模一样。

11.3 值得直接借鉴的三点

  1. 以时间戳而非帧号为索引键。帧率会变，时间不会。
  2. 倒带前做有效性校验：位移突变（传送）、存活状态。校验失败就放弃补偿而不是硬倒带。
  3. 务必让物理/骨骼缓存失效。这是最容易漏且症状最诡异的一条。

11.4 插值自己写的话

关键是三件事：

  • 延迟量要能配置，并且遵循 max(固定值, ratio/updaterate) 这个模式 —— 让它随 updaterate 自适应
  • 旋转用 Slerp，循环量单独处理（§5.3 那张表）
  • 外插要能区分"网络卡了"和"物体停了"（§5.4）
