网络层（二）UDP —— 拿掉保证之后

Fantasy 源码阅读 · 传输层三部曲第二篇
Network/Protocol/KCP/ 的非算法部分

这一篇是过渡篇，也是三篇里最短的。

Fantasy 里没有「纯 UDP 协议实现」这个文件 —— UDP 只作为 KCP 的载体存在。但如果直接跳到 KCP，你会把两类代码混为一谈：哪些是在处理「UDP 是数据报」，哪些是在处理「UDP 不可靠」。前者是几十行的琐碎适配，后者是 1367 行的算法。分清这两者，第三篇才读得动。

所以这一篇只干一件事：把 KCPClientNetwork.cs 里与 KCP 算法无关的部分挑出来单独看。读完你会发现，Fantasy 为了「用 UDP」这个决定，付出了握手协议、通道 ID、平台补丁三笔额外成本 —— 而这些成本和可靠传输完全无关，纯粹是 UDP 的语义差异带来的。

一、拿掉 TCP 的保证，剩下什么

第一篇那张表现在可以填完整了：

特性TCPUDP后果
可靠✓✗丢了就没了，没人告诉你
有序✓✗后发的可能先到
去重✓✗同一个包可能收两次
拥塞控制✓✗你可以轻易打满上行把自己搞死
连接✓ 三次握手✗ 无连接没有「连上了」这个状态
消息边界✗ 字节流✓ 数据报反而不用处理分包粘包

前四行是 KCP 要补的（第三篇）。这一篇关心后两行 —— 一个是纯亏，一个是纯赚。

1.1 赚的那个：消息边界白送

UDP 是数据报协议。SendTo 一次 = ReceiveFrom 一次，边界由 IP 层保留。既不会两个包粘在一起，也不会半个包先到（IP 分片由内核重组，重组失败则整个包丢弃，绝不会给你半个）。

这个差异在代码里立刻体现出来。对比两个解析器基类：

ReadOnlyMemoryPacketParser（TCP）BufferPacketParser（KCP）
签名UnPack(ref ReadOnlyMemory<byte>, out APackInfo)UnPack(byte[], ref int count, out APackInfo)
跨调用状态6 个字段（Offset / HeadOffset / BodyOffset / ...）无（4 个字段只是临时中转）
返回 false 的含义「数据不够，下次接着攒」「这个包有问题，丢掉」
行数占比状态机占大半几乎全是 Pack 逻辑

作者在 BufferPacketParser 的类注释里把理由写得很直白：

Network/Message/PacketParser/Handler/BufferPacketParser.cs
/// BufferPacketParser消息格式化器抽象类
/// 这个不会用在TCP协议中、因此不用考虑分包和粘包的问题。
/// 目前这个只会用在KCP协议中、因为KCP出来的就是一个完整的包、
/// 所以可以一次性全部解析出来。
/// 如果是用在其他协议上可能会出现问题。

于是 OuterBufferPacketParser.UnPack 变成了直白的一次性解析：

if (count < Packet.OuterPacketHeadLength)
{
    return false;   // 连头都不够 → 这个包坏了，丢弃（不是"等更多数据"）
}

MessagePacketLength = Unsafe.ReadUnaligned<int>(ref bufferRef);

if (MessagePacketLength > ProgramDefine.MaxMessageSize || count < MessagePacketLength)
{
    throw new ScanException(...);
}

ProtocolCode = ...;  RpcId = ...;

packInfo = OuterPackInfo.Create(Network);
packInfo.RentMemoryStream(MemoryStreamBufferSource.UnPack, count)
        .Write(buffer, 0, count);   // 一次写完
return true;

没有 Math.Min、没有 IsUnPackHead、没有 Offset 累加。同样的 20 字节包头协议，解析代码短了一大截。

包头协议为什么不变 既然 KCP 保留边界，那 20 字节包头里的「长度」字段其实是冗余的？

不是。包头是应用层协议，跨传输层复用。TCP / KCP / WebSocket 三个分支共用同一套 Packet 常量和同一套 PackInfo，上层的 MessageScheduler、MessageDispatcherComponent 因此完全不需要知道底下是谁。多花 4 字节换来整个上层零改动，这笔账很划算。

而且长度字段在 KCP 侧仍有校验价值 —— count < MessagePacketLength 这个判断能识别出被截断或伪造的包。

1.2 亏的那个：没有「连接」

这是 UDP 带来的最大工程成本，比不可靠更麻烦。

TCP 的 ConnectAsync 成功回调，含义是「三次握手完成，对端确认了」。UDP 的 ConnectAsync 完全不是这个意思：

Network/Protocol/KCP/Client/KCPClientNetwork.cs
_socket = new Socket(_remoteAddress.AddressFamily,
                     SocketType.Dgram, ProtocolType.Udp);
_socket.Blocking = false;
_socket.SetSocketBufferToOsLimit();
_socket.SetSioUdpConnReset();          // ← Windows 专属，见 §3
_socket.Bind(new IPEndPoint(... IPAddress.Any, 0));

if (!_socket.ConnectAsync(_connectEventArgs))
{
    OnReceiveSocketComplete();
}

UDP socket 上的 Connect 只是本地行为：记下默认远端地址，之后可以用 Send/Receive 而不必每次带 endpoint，并且内核会过滤掉非该地址的来包。一个字节都没发出去，对端根本不知道你存在。

所以 OnReceiveSocketComplete 在两个分支里做的事完全不同：

TCPKCP/UDP
OnReceive
SocketComplete		ClearConnectTimeout() ← 连接已成，撤超时SendRequestConnection() ← 握手才刚开始
_onConnectComplete?.Invoke() ← 立刻通知业务—（要等服务端回应）
启动收发循环启动收发循环

KCP 分支里，ClearConnectTimeout() 和 OnConnectComplete?.Invoke() 被推迟到收到服务端确认之后。这就引出了下一节：Fantasy 必须自己实现一套握手。

二、自建握手：5 字节头 + 四步交换

2.1 应用层再加一层头

UDP 之上、KCP 之下，Fantasy 插了 5 个字节：

KCP 分支的完整分层 ┌──────────────────────────────────────────────┐ │ 业务消息（Protobuf / MemoryPack 序列化） │ ├──────────────────────────────────────────────┤ │ 20 字节 应用包头 长度│opcode│rpcId│address │ ← 三协议共用 ├──────────────────────────────────────────────┤ │ 24 字节 KCP 头 conv│cmd│frg│wnd│ts│sn│una│len│ ← 第三篇 ├──────────────────────────────────────────────┤ │ 5 字节 Fantasy 头 header(1) + channelId(4) │ ← 本节 ├──────────────────────────────────────────────┤ │ UDP 数据报 │ └──────────────────────────────────────────────┘
Network/Protocol/KCP/KcpHeader.cs（13 行，全文）
internal enum KcpHeader : byte
{
    None                  = 0x00,
    RequestConnection     = 0x01,   // C→S 我要连
    WaitConfirmConnection = 0x02,   // S→C 可以，你确认下
    ConfirmConnection     = 0x03,   // C→S 确认
    RepeatChannelId       = 0x04,   // S→C 换个 ID 重来
    ReceiveData           = 0x06,   // 双向 这是 KCP 数据
    Disconnect            = 0x07    // 双向 断开
}

13 行的文件，是理解 KCP 分支的钥匙。注意 0x05 被跳过了 —— 大概是历史上删掉的某个类型，留个空位不复用，避免和旧版本客户端撞语义。这个细节说明作者考虑过协议兼容。

2.2 四步握手

握手时序（客户端左，服务端右） Connect() ChannelId = CreateChannelId() │ ├──── 0x01 RequestConnection + channelId ────→ 查 _pendingConnection / _connectionChannel │ │ │ ┌────────────┴─────────────┐ │ ID 冲突 ID 可用 │ │ │ │←──── 0x04 RepeatChannelId ───────┘ AddPendingConnection │ 重新 CreateChannelId() │ │ 回到第一步 │ │ │ │←──────────── 0x02 WaitConfirmConnection ──────────────────┘ │ ├── ClearConnectTimeout() ← 撤销超时定时器 ├── SendConfirmConnection() ├── OnConnectComplete?.Invoke() ← 此刻才通知业务"连上了" ├── _isConnected = true └── 冲刷 _messageCache ← 见 §2.4 │ ├──── 0x03 ConfirmConnection ────→ ConfirmPendingConnection → AddConnection │ 创建 KCPServerNetworkChannel │ ├──── 0x06 ReceiveData + KCP 数据 ←──→ 正式通信 │ └──── 0x07 Disconnect ──────────→ RemoveChannel

为什么要四步而不是两步？因为需要双向确认。两步（请求 + 应答）只能证明「客户端能到服务端」和「服务端的回包能到客户端」；第三步 ConfirmConnection 才让服务端确认「客户端确实收到了我的应答」。只有到这一步，服务端才真正创建 channel 分配资源。

这和 TCP 三次握手是同一个道理，也顺带防了一类反射放大攻击：伪造源 IP 发 RequestConnection，服务端只会挂一个轻量 pending 记录并回一个 5 字节包，不会分配 channel。收不到第三步，pending 会被 PendingTimerOut 清掉。

2.3 ChannelId：UDP 没有连接，那用什么区分

TCP 服务端靠「一个 accept 出来的 socket」天然区分客户端。UDP 服务端只有一个 socket 收所有人的包，必须靠数据内容区分。这就是 ChannelId 的职责。

[MethodImpl(MethodImplOptions.AggressiveInlining)]
private static unsafe uint CreateChannelId()
{
    uint value;
    RandomNumberGenerator.Fill(
        MemoryMarshal.CreateSpan(ref *(byte*)&value, 4));
    return 0xC0000000 | (value & int.MaxValue);
}

三个设计点，都值得学：

  1. 用 RandomNumberGenerator（密码学随机）而不是 Random。ChannelId 是这条连接的唯一凭据 —— 后面所有包只靠 channelId == ChannelId 来判定归属。如果可预测，第三方就能伪造包注入到别人的会话里。这里选强随机是安全考量，不是洁癖。
  2. 0xC0000000 | 强制置高两位。这是给 ID 分段：0xC0000000 段标记「客户端主动发起的外网连接」。服务端可以据此区分不同来源的 channel（内网连接、Roaming 迁移过来的等）用不同 ID 段，一眼看出类型。
  3. & int.MaxValue 清掉最高位后再或。保证结果落在确定区间，避免与其他段重叠。

然后是冲突处理。随机 32 位（实际熵 30 位）撞车概率极低但非零，服务端的处理是：

case KcpHeader.RequestConnection:
{
    _endPoint.TryDequeue(out var ipEndPoint);

    if (_pendingConnection.TryGetValue(channelId, out var pendingConnection))
    {
        if (!ipEndPoint.IPEndPointEquals(pendingConnection.RemoteEndPoint))
        {
            SendRepeatChannelId(ref channelId, ipEndPoint);   // 不同来源撞 ID
        }
        break;   // 同一来源重发 → 幂等忽略
    }

    if (_connectionChannel.ContainsKey(channelId))
    {
        SendRepeatChannelId(ref channelId, ipEndPoint);
        break;
    }

    AddPendingConnection(ref channelId, ipEndPoint);
}

注意 break 那一行 —— 同一个 endpoint 重发 RequestConnection 被静默忽略。这是必须的：UDP 下客户端的第一个握手包可能丢了在重发，也可能服务端的应答丢了导致客户端重试。UDP 协议的每个消息处理都必须考虑幂等，这是和 TCP 编程最大的思维差异。

2.4 连接前发的消息去哪了

因为「连上」这个状态被推迟到握手第二步之后，中间这段窗口期业务层可能已经在发消息了：

public override void Send(...)
{
    var buffer = _packetParser.Pack(...);

    if (!_isConnected)
    {
        _messageCache.Enqueue(buffer);   // 先攒着
        return;
    }

    SendMemoryStream(buffer);
}

握手完成时一次性冲刷：

case KcpHeader.WaitConfirmConnection:
{
    if (channelId != ChannelId) break;

    ClearConnectTimeout();
    SendConfirmConnection();
    OnConnectComplete?.Invoke();
    _isConnected = true;

    while (_messageCache.TryDequeue(out var memoryStream))
    {
        SendMemoryStream(memoryStream);   // 补发
    }
    break;
}

TCP 分支没有这个队列，因为 TCP 的 onConnectComplete 一响就真的能发了。这个 _messageCache 是「握手推迟」直接导致的额外机制。

这个队列没有上限 _messageCache 是裸 Queue<MemoryStreamBuffer>，没有容量检查。如果握手一直不成功而业务层持续发消息，它会一直涨。

实际影响有限 —— 5 秒后连接超时会 Dispose() 并 _messageCache.Clear()。但如果你的业务层在连接建立前有高频发送（比如每帧上报），这 5 秒足够攒出可观内存。这是我基于代码结构的判断，未做压测验证。

注意 if (channelId != ChannelId) break; 这个校验在 WaitConfirmConnection / ReceiveData / Disconnect 三处都有。UDP 下任何人都能往你的端口发包，每个包都必须验 ChannelId。这是 UDP 编程的基本纪律，TCP 分支完全不需要考虑。

三、平台补丁：UDP 在真实世界里的麻脸

这一节的代码没有任何设计美感，纯粹是踩坑记录。但它们恰恰是「UDP 比 TCP 难用」的最真实体现 —— 读一遍能省你以后几天的调试时间。

3.1 SetSioUdpConnReset —— Windows 的 ICMP 陷阱

_socket.SetSioUdpConnReset();

这个扩展方法本身我没有读到实现，但它对应的是一个非常经典的 Windows UDP 问题：

UDP 往一个没有程序监听的端口发包，对端主机会回一个 ICMP Port Unreachable。Windows 的默认行为是把这个 ICMP 转成 socket 错误 —— 于是你下一次 ReceiveFrom 会抛 SocketException(ConnectionReset)，即使你的 socket 从未「连接」过任何东西。

后果：服务端在收包循环里，只要有一个客户端进程被杀掉，服务端的接收循环就会被一个异常打断。SIO_UDP_CONNRESET 这个 IOControl 就是关掉这个行为。

凡是写 Windows 上的 UDP 服务，这一行是必须的 Linux 没有这个行为（除非 socket 做了 connect）。这是最典型的「Windows 上跑得挂、Linux 上跑得好」的网络 bug，而且现象诡异 —— 服务端因为客户端崩溃而报连接重置。

3.2 Unity 的 ReceiveAsync 坑

接收循环里有一段平台分叉：

private async FTask ReceiveSocketAsync()
{
    while (!_cancellationTokenSource.IsCancellationRequested)
    {
        var memory = _pipe.Writer.GetMemory(8192);
#if FANTASY_UNITY
        MemoryMarshal.TryGetArray(memory, out ArraySegment<byte> arraySegment);
        var result = await _socket.ReceiveFromAsync(
                          arraySegment, SocketFlags.None, _ipEndPoint);
        _pipe.Writer.Advance(result.ReceivedBytes);
        DrainReceiveBacklog();                     // ← Unity 专属
        await _pipe.Writer.FlushAsync();
#else
        var result = await _socket.ReceiveAsync(
                          memory, SocketFlags.None, token);
        _pipe.Writer.Advance(result);
        await _pipe.Writer.FlushAsync();
#endif
    }
}

TCP 分支里有一条同样的分叉，注释写得更明白：

TCPClientNetwork.cs:201
#if UNITY_2021
    // Unity2021.3.14f有个恶心的问题，使用ReceiveAsync会导致memory不能正确写入
    // 所有只能使用ReceiveFromAsync来接收消息，
    // 但ReceiveFromAsync只有一个接受ArraySegment的接口。

Unity 用的 Mono / 老版 .NET 运行时，Socket.ReceiveAsync(Memory<byte>) 这个基于 Memory<T> 的重载有 bug —— 数据没写进你给的内存。只能退回到 ArraySegment 版本的 ReceiveFromAsync。

MemoryMarshal.TryGetArray 就是把 Memory<byte> 拆回底层的 ArraySegment<byte>。能拆成功的前提是这块 Memory 底层真的由数组支撑 —— Pipe 的默认实现满足，所以可行。

3.3 DrainReceiveBacklog —— 补偿单包读取

#if FANTASY_UNITY
private void DrainReceiveBacklog()
{
    while (_socket.Available > 0)          // 内核缓冲还有包
    {
        var memory = _pipe.Writer.GetMemory(8192);
        if (!MemoryMarshal.TryGetArray(memory, out var arraySegment)) break;

        int receivedBytes;
        try
        {
            receivedBytes = _socket.ReceiveFrom(...);   // 同步读，socket 是非阻塞的
        }
        catch (SocketException e) when (e.SocketErrorCode == SocketError.WouldBlock)
        {
            break;   // 没了，正常退出
        }

        if (receivedBytes <= 0) break;
        _pipe.Writer.Advance(receivedBytes);
    }
}
#endif

这段是这一篇最能说明「UDP 与 TCP 编程模型差异」的代码。

问题：UDP 的一次 ReceiveFrom 只能拿一个数据报，哪怕内核缓冲里排了 100 个。而 TCP 的一次 Receive 会把缓冲里的字节尽量一次读满。

结果是：在 Unity 上走 await ReceiveFromAsync 的路径，每收一个包就要过一次异步调度（回到 Unity 主循环，等下一帧或下一个调度点）。高频小包场景下，接收速率被调度频率钉死了 —— 每帧只能处理一个包。KCP 的 MTU 是 470 字节，一次业务消息就可能拆成好几个包，这个瓶颈会直接变成延迟。

解法：异步收到一个包后，用 _socket.Available 探测内核里还有没有，有就同步连续榨干。因为 _socket.Blocking = false，同步 ReceiveFrom 在无数据时立刻抛 WouldBlock 而不是卡住，所以这个循环是安全的。

「异步等第一个，同步榨干后续」是 UDP 高吞吐的通用模式 异步调用负责「有数据了叫我」，同步循环负责「一次处理干净」。两者结合既不空转 CPU（不像纯轮询），又不受调度频率限制（不像纯异步）。

非 Unity 平台没写这段 —— 推测是 .NET 的 ReceiveAsync 在 socket 有数据时会走同步完成路径，不产生真正的线程调度，所以瓶颈不明显。这是我的推断，未验证。
