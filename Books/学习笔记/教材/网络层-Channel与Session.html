Channel 与 Session 的区别

Fantasy 源码阅读 · 网络层概念辨析
Fantasy.Unity/Runtime/Core/Network/

读网络层接口（INetworkChannel）时几乎人人会卡在同一个地方：接口里赫然有个 Session 属性，而 Session 类里又持有一个 Channel。两个东西互相持有，到底谁是谁、为什么分两层？

一句话先放结论：

结论 Channel 管物理连接（怎么发字节），Session 管逻辑会话（发什么、谁接收、RPC 怎么配对）。
这是传输 vs 业务的经典分层，不是同一个东西的两个名字。

一、一张图看清分工

业务层（你的代码） │ │ session.Send(msg) / session.Call(req) ▼ ┌───────────────┐ │ Session │ 逻辑会话层（继承 Entity） │ - rpcId 配对 │ - 消息分发（NetworkMessageScheduler） │ - Call(RPC) │ - 持有 Channel（internal） └───────┬───────┘ │ channel.Send(rpcId, address, memoryStream, ...) ▼ ┌───────────────┐ │ Channel │ 传输层（INetworkChannel，13 行契约） │ TCP/KCP/WS │ - 打包/分包、socket 收发 │ (具体实现) │ - 反向持有 Session └───────────────┘ │ ▼ 操作系统 socket

维度Channel（INetworkChannel）Session（Session）
是什么传输抽象（TCP 笔记 2.1「最小契约」13 行）逻辑会话（继承 Entity，是个实体）

三、三个能直接对上号的关键点

3.1 Channel 不懂业务，只懂「发字节」

回头看 TCP 笔记 2.1 那段话：

13 行定义了「一条通道」：能发消息、能销毁、关联一个 Session。注意 Send 里没有任何协议痕迹 —— 没有 socket、没有 endpoint、没有序号。这是抽象成功的标志。

Send 的签名是 Send(uint rpcId, long address, MemoryStreamBuffer, IMessage, Type)，全是为「打包」服务的参数，没有任何业务语义。它不知道这条消息是什么、谁该处理它。

3.2 Session 才懂「消息分发」和「RPC」

接收方向的代码路径在 TCP 笔记第四节的数据流图里：

接收 UnPack 凿出完整包 → Session.Receive(packInfo) → NetworkMessageScheduler 分发到 Handler

Session.Receive（Session.cs:224）干的是「更新心跳时间 + 交给调度器分发」——这才是业务语义。Channel 交付的是 packInfo（一坨解好的字节），它根本不知道里面是什么消息。

发送方向上，Session.Call<T>(request)（Session.cs:210）这个 RPC 方法用 _rpcId + RequestCallback 字典实现「请求-响应配对」—— 这层逻辑 Channel 完全不参与，Channel 只负责把配好 rpcId 的字节发出去。

3.3 客户端的「一人分饰两角」

TCP 笔记 2.3 的第一条设计点最关键：

客户端的 Network 自己就是 Channel。它同时继承 ANetwork 和实现 INetworkChannel —— 因为客户端只有一条连接，没必要再分层。服务端则相反：一个 ANetwork 管 N 个 ANetworkServerChannel。

所以在代码里，客户端的 Channel 实现类就是 Network 类本身（TCPClientNetwork : AClientNetwork, INetworkChannel）。但 Session 始终是独立的那个 —— 不管 Channel 是独立的还是合体的，Session 都是外面那一层业务壳。

四、为什么非要分两层

TCP 笔记开篇「三篇的分工」其实埋了答案：底下会换。

同一个 Session，今天底下挂着 TCPClientNetwork，明天换成 KCPClientNetwork，后天出 WebGL 又换成 WebSocketClientNetwork —— Session 一行代码都不用改。如果没这层 Channel 抽象，业务代码就得跟 socket、Pipe、分包状态机耦合死。

这就是「Session 之上的代码完全不关心底下跑的是 TCP 还是 KCP」的真正含义：Channel 是可替换的传输插件，Session 是不动的业务外壳。

可迁移的类比 「Channel vs Session」和这些是同一类思路：
• HttpClient（传输） vs HttpRequest（语义）
• TCP 里 socket（传输） vs connection（会话）
• 数据库 DbConnection（传输） vs DbTransaction（会话）
