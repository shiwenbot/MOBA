一、物理引擎在解什么问题

先建立心智模型，否则后面的代码只是一堆函数名。

核心矛盾：离散时间 vs 连续世界

真实世界里物体连续运动、碰撞瞬间产生约束力。计算机只能按帧采样。所有物理引擎的复杂度都来自这一个矛盾，而它衍生出三个必须解决的子问题：

一帧的三件事 1. 积分 已知速度和力，算出「如果没有障碍，物体会在哪」 v += a·dt; p += v·dt │ │ 问题：算出来的位置可能已经穿进别的物体了 ▼ 2. 检测 找出哪些物体对可能碰撞，算出接触点与法线 宽相位（粗筛）→ 窄相位（精算） │ │ 问题：知道穿了，但该怎么把它们分开？ ▼ 3. 求解 算出需要多大的力/冲量才能让它们不穿透 速度求解（不再继续穿入）+ 位置求解（消除已有穿透）

这个顺序不能改。而每一步都有「精确但慢」和「近似但快」的选择，Box2D 的每个设计决策基本都可以还原成这个权衡。

为什么「求解」需要迭代

这是最不直观的一步。单个接触点的约束能一次解析求出，但接触点之间互相耦合：

三个箱子叠在地上

解完「箱子 A 与地面」的接触，A 的速度变了 → 「A 与 B」的接触被破坏 → 解完 A-B，B 的速度变了 → 「B 与 C」被破坏 → 解完 C，又影响回 B……

所以只能反复扫描，让误差逐轮衰减。这叫 Gauss-Seidel 迭代，是全库最核心的算法思想。

更本质的困难：接触是不等式约束（可以推不能拉），构成 LCP 而非线性方程组。哪些接触点实际承力事先未知，必须靠迭代加钳制来「发现」。

三个层次的近似

理解了这三层，你就知道 Box2D 的精度边界在哪：

层次近似手段代价
碰撞检测宽相位用 AABB 粗筛，窄相位才算真实几何AABB 是保守超集，会产生「还没真接触」的候选对
约束求解固定次数迭代，不求收敛到精确解迭代不足时堆叠会「软」、会下沉
穿透处理容许一个固定的微小穿透量（slop）物体之间总有一条极小的缝或重叠

第三条尤其重要：Box2D 从不追求「零穿透」，它追求「穿透量稳定在一个可接受的小值」。理解这一点，后面很多常量（LinearSlop、Baumgarte）就都讲得通了。

二、单位与尺度：第一个必须先知道的坑

Settings.cs 开头第 13-14 行有一句注释，它是整个库最重要的一句话：

LinearSlop 的注释（:36-37）把设计意图说得最清楚：A small length used as a collision and constraint tolerance. Usually it is chosen to be numerically significant, but visually insignificant.

「数值上显著」意味着它不能太小，否则浮点误差会淹没它；「视觉上不显著」意味着它相对物体尺寸要足够小。这两个要求同时成立，只有当物体尺寸在米的量级时才成立。

经典错误：用像素当单位

如果一个角色是 50 单位高 你的直觉是「50 像素高的角色」，但引擎理解成「50 米高的角色」—— 一栋 16 层楼。于是：

① slop 相对变得无意义。0.005 相对 50 是 万分之一 —— 位置求解器容许的穿透小到被浮点误差淹没， 求解器会在临界点反复抖动。

② 重力看起来像慢动作。-9.8 m/s² 作用在「50 米高的角色」上， 下落一个身位要 3 秒多。你会本能地把重力调到 -300 来「修正」，然后掉进下一个坑。

③ MaxTranslation = 2.0 变成致命钳制。角色想以「每帧 5 像素」移动， 引擎认为你要每帧移动 5 米，接近钳制阈值；跑得再快一点就被静默限速。

反方向的错误同样存在：

如果物体只有 0.05 单位大 PolygonRadius 的 0.01 skin 占了物体尺寸的 20% —— 两个方块之间会有一条肉眼可见的、 占体积五分之一的缝。而 LinearSlop 的 0.005 占 10%，物体会明显互相嵌入。

更糟的是 PolygonShape.Set 会焊接距离平方小于 (0.5 * LinearSlop)² 的顶点 （PolygonShape.cs:83-84）—— 小物体的顶点可能被直接焊掉，形状静默退化。

推荐的尺寸范围

源码没有直接写「物体应该多大」，但可以从常量反推：

各常量隐含的安全区间 0.005 LinearSlop ← 物体尺寸要远大于这个（至少 20 倍 → 0.1 米） 0.01 PolygonRadius 0.1 AABBExtension ← 单帧位移最好小于这个（否则每帧都重建树节点） 0.2 MaxLinearCorrection 2.0 MaxTranslation ← 单帧位移的硬上限 结论：物体尺寸落在 0.1 ~ 10 米区间最安全 这正好是「弹珠到卡车」的范围 —— Box2D 就是按这个调的

正确做法：物理单位与渲染单位分离

不要试图改 LengthUnitsPerMeter 去适配你的像素 —— 它是 const，改它要重新编译，而且所有派生常量的相对关系是精心调过的。

标准解法 物理世界用米，渲染时乘一个缩放系数。比如 1 米 = 32 像素：

screenPos = physicsPos * 32f;

一个 1.8 米高的角色在物理世界里就是 1.8，渲染出来 57.6 像素。 重力保持 -9.8，手感直接就是真实的。

Unity 用户注意：Unity 的默认单位本身就是米，所以只要不乱缩放，天然对齐。

为什么这一章放在最前面

因为尺度错误的症状看起来完全不像尺度问题：物体抖动、堆叠不稳、穿透、速度莫名被限、重力手感不对。你会去调迭代次数、调 Baumgarte、调重力，全都治不了根。

而它又是唯一一个「一开始定错、后面全部要重做」的决策。

三、对象模型：World / Body / Fixture / Shape

为什么是四层而不是两层

新手常问「为什么不能直接给物体一个形状」。四层各管一件事：

层管什么关键字段
World容器 + 调度：重力、Step、宽相位树、接触管理BodyList、ContactManager
Body运动状态与质量，没有任何几何字段LinearVelocity、_mass、Transform、Sweep
Fixture几何 + 表面性质，是宽相位的注册单位Shape、Density、Friction、Restitution、Filter、IsSensor
Shape纯几何，可独立于世界存在顶点 / 半径

Fixture 的类头注释（Fixture.cs:13-17）就是这层存在的理由：

A fixture is used to attach a shape to a body for collision detection. A fixture inherits its transform from its parent. Fixtures hold additional non-geometric data such as friction, collision filters, etc.
@warning you cannot reuse fixtures.

一个 Body 挂多个 Fixture 的三个理由

  1. 表达凹形。PolygonShape 必须凸（PolygonShape.cs:10-11）且顶点上限 8（Settings.cs:24）。L 形、飞船轮廓只能拼多个凸 Fixture。
  2. 逐块不同材质。密度、摩擦、弹性都是 per-Fixture 的。「重底盘 + 轻顶棚」会让质心自动偏向重的一侧（Body.cs:1065-1076 逐个累加）。
  3. 实体与传感器混挂。IsSensor 在 Fixture 层，所以一个 Body 可以有实体碰撞体 + 一个更大的感应范围。
Shape 是被拷贝的 Fixture.Create 内部做 Shape = def.Shape.Clone()（Fixture.cs:118）。 所以 FixtureDef.Shape 可以是栈上临时对象、可以复用同一个 shape 实例建多个 fixture。

四、碰撞检测：宽相位 → 窄相位 → 接触生命周期

为什么分两相

n 个物体两两检测是 O(n²)，而精确几何求交本身就贵。分两相是为了让「贵的计算」只发生在少数候选对上：

两相分工 宽相位 用 AABB（轴对齐包围盒）快速筛出「可能碰撞」的对 数据结构：动态 AABB 树，查询 O(log n) 输出：候选 pair 列表 —— 保守超集，会有假阳性 │ ▼ 窄相位 对每个候选对算真实几何：接触点、法线、穿透深度 输出：Manifold（最多 2 个接触点）

宽相位：动态 AABB 树

本体是 TreeNode[]，从 ArrayPool 租借（DynamicTree.cs:26、32-34），二叉树 + 自由链表管理节点。proxyId 就是数组下标，会被回收复用。

所以：没动树 = 不进 move buffer = 这一帧它不发起宽相位查询。这是宽相位省开销的主要机制。

树的平衡

  • 插入位置：SAH 启发式下降（DynamicTree.cs:544-618），比较「就地新建父节点」与「继续下沉」的代价。2D 下代价度量用周长（AABB.GetPerimeter()）不是面积
  • 旋转：AVL 风格，平衡因子阈值 ±1（Balance，DynamicTree.cs:737-880），插入与删除后沿 parent 链回溯
树的遍历用共享 Stack，不可重入 Query 用 _queryStack、RayCast 用 _rayCastStack，都是预分配 256 的实例字段， 每次 Clear() 复用（DynamicTree.cs:233、274）。

同一个 DynamicTree 上的查询不可重入、不可多线程并发。 这是移植 C++ 单线程假设的典型痕迹。

钳制作用在累积冲量，不是增量

这是 sequential impulse 最容易看错的地方：

src/Dynamics/Contacts/ContactSolver.cs:402-408
vn = dot(dv, normal);
lambda = -vcp.NormalMass * (vn - vcp.VelocityBias);

newImpulse = Math.Max(vcp.NormalImpulse + lambda, 0.0f);  // 钳「累积值」
lambda     = newImpulse - vcp.NormalImpulse;                // 反解实际增量
vcp.NormalImpulse = newImpulse;

钳的是累积量，然后回推出实际增量再施加到速度上。这允许中间轮次出现负的 lambda（回撤上一轮给多了的冲量），只要累积值不为负 —— 接触只能推不能拉。

源码注释（:439-440）：because of the iterative nature of the solver which only requires that the accumulated impulse is clamped and not the incremental impulse。

这个设计和 warm start 是一体的 如果钳的是增量，跨帧保存的累积值就不是一个合法初值，warm starting 无法成立。 两个知识点是同一设计的两面。

  • 法向在后 → 法向的解不会被摩擦的后续修改污染
  • 代价：本轮摩擦上界 maxFriction = friction * vcp.NormalImpulse（:363）用的是上一轮/上一帧的法向冲量。这个滞后由多轮迭代抹平
  • 法向钳制单侧 max(x, 0)，摩擦双侧 clamp(x, -max, +max) —— 摩擦可以朝任一侧

系数混合律：摩擦取几何平均 sqrt(f1*f2)（Contact.cs:105），弹性取最大值，弹性阈值取较小值。

为什么加速收敛：Gauss-Seidel 的收敛速度取决于初值离解多远。稳态堆叠场景相邻两帧的接触冲量几乎相同，用上一帧的解当初值，前几轮迭代不必从 0 重新爬到支撑重力所需的量级。

这是所有「回滚/存档」类需求的最大障碍 warm starting 让第 N 帧的结果依赖第 N-1 帧的累积冲量，而这个冲量存在 Contact.Manifold 上 —— 一个 internal 字段，0.6 没有公开 API 能读写它。

七、Island 与休眠

Island 是什么，为什么要分

Island（岛）是通过接触或关节互相连通的一组 body。分岛有两个目的：

目的说明
求解的局部性两堆互不接触的箱子之间没有约束耦合，分开解等价于一起解，但每次求解的规模更小、缓存更友好
休眠的单位休眠必须整岛一起 —— 一堆箱子里有一个还在动，整堆都不能睡（否则动的那个会穿进睡着的那些）

一、static body 不传播岛 源码注释（World.cs:750）：we don't propagate islands across static bodies。

二、只有 touching 的 contact 进岛 World.cs:777-781 显式跳过 IsTouching == false 的 contact。

呼应第四章：因为 fat AABB 的存在，场上常态有一批「AABB 碰上但几何没碰」的 Contact。 它们每帧跑窄相位，但不参与求解、不连通岛。

八、连续碰撞（CCD / TOI）

要解决的问题：穿隧

离散仿真每帧把物体从 A 直接搬到 B。若一帧位移超过障碍物厚度，帧首在墙前、帧尾在墙后，两个采样点的窄相位都算不出接触 —— 物体穿过了墙。

穿隧 帧 N 帧 N+1 ●───────────────→ ● 子弹 │ 子弹 │ 薄墙 ← 两个采样点都不与墙相交，窄相位无从发现

宽相位其实已经做了一层廉价的扫掠近似：Fixture.Synchronize 把 t1 与 t2 的 AABB 合并后才送进 MoveProxy（Fixture.cs:261-264）。这保证「高速物体的 Contact 至少会被建立」，但窄相位在两个离散点上仍算不出接触 —— 所以还需要 TOI。

TOI 求什么

函数注释（TimeOfImpact.cs:66-70）坦承：uses a swept separating axis and may miss some intermediate, non-tunneling collisions —— 它保证不穿隧，不保证捕获所有中间接触。

故意留出 slop 余量，让后续求解器有可工作的间隙。

返回五态（ToiState）：Unknown / Failed / Overlapped / Touching / Separated。只有 Touching 会产生有效 TOI 时刻，其余全部退化为 alpha = 1.0f（等于「这一帧不发生 TOI 事件」）。

拿到 minAlpha 后：备份 sweep → Advance 推进到碰撞时刻 → 重跑 Update() → 若结果竟然 not touching，则回滚 sweep 并禁用该 contact（World.cs:1060-1081）。这是对数值误差的兜底。

性能观测

ToiProfile 记录 ToiCalls、ToiIters、ToiMaxIters、ToiRootIters、ToiTime 等（TimeOfImpact.cs:45-62）。它默认是 null（World.cs:115），传 null 时连 Stopwatch.GetTimestamp() 都不调 —— 性能调查时要显式打开。

什么时候真的需要 bullet 判断标准是几何的：单帧位移是否接近或超过目标物体的厚度。

以 60Hz、物体半径 0.45 米为例，单帧位移要超过 0.9 米才可能穿过它自己那么大的物体 —— 即速度超过 54 米/秒。低于这个量级，bullet 是纯开销。

注意 MaxTranslation = 2.0（Settings.cs:67）会把单帧位移钳到 2 米， 所以极高速物体必须靠 CCD 而不是单纯提高速度值。

正确做法：延迟到 Step 之后

标准模式是在回调里只记录、不执行：

private readonly List<Body> _pendingDestroy = new List<Body>();

public void BeginContact(Contact contact)
{
    // ✗ 不能在这里 DestroyBody
    // ✓ 只入队
    if (IsBullet(contact)) _pendingDestroy.Add(GetBulletBody(contact));
}

public void Update(float dt)
{
    _world.Step(dt, 8, 3);          // 锁定窗口在这里面

    foreach (var body in _pendingDestroy)  // 已解锁，安全
        _world.DestroyBody(body);
    _pendingDestroy.Clear();
}

IDestructionListener：被动通知

当 body 被销毁时，挂在它上面的 fixture 和 joint 会被连带销毁。如果你的游戏代码持有这些对象的引用，就会变成悬空引用。

IDestructionListener 就是为此存在的 —— 引擎在连带销毁时通知你，让你清理自己的引用。接口有两个方法（fixture 版和 joint 版）。

什么时候需要它 如果你的架构是「游戏对象持有 Fixture 引用」，就需要。 如果你只持有 Body 引用、且总是自己主动 DestroyBody，可以不用。

注意 joint 的连带销毁尤其隐蔽：DestroyBody 会销毁所有连到它的 joint， 而那些 joint 的另一端是别的 body —— 你可能完全没想到那边的引用失效了。

销毁的正确顺序

操作连带效果
World.DestroyBody(b)销毁 b 的所有 fixture、所有连接的 joint、所有 contact（先发 EndContact）、所有 broadphase proxy
Body.DestroyFixture(f)销毁 f 相关的 contact 与 proxy，无条件触发 ResetMassData()
World.DestroyJoint(j)若 CollideConnected == false，会唤醒两端 body 并重建它们之间的 contact

所以不需要手动先删 fixture 再删 body —— 直接 DestroyBody 即可，引擎会处理层级。

时间步长必须固定

HelloWorld 示例的注释直接写了（HelloWorldTest.cs:85）：

It is generally best to keep the time step and iterations fixed.

源码层面的证据是 DtRatio（World.cs:460）：

DtRatio = _invDt0 * timeStep;   // dt 不变时恒为 1

它唯一的用途是给 warm starting 的冲量做量纲换算（ContactSolver.cs:93-97）—— 即引擎知道 dt 可能变，并为此打了个补丁。但这只是让冲量的量纲对上，并不能消除变步长带来的行为不一致。

变步长的三个后果 ① 阻尼行为变化：v *= 1/(1 + h*damping)（Island.cs:145-146）对 h 非线性， 同样的总时间分不同步长积分，结果不同。

② 迭代收敛质量变化：迭代次数固定，但 dt 越大每步要解决的误差越大，同样次数的收敛效果越差。 大 dt 会让堆叠明显变软。

③ 穿隧风险随 dt 增大：单帧位移 = v·dt，dt 翻倍就等于速度翻倍。

标准做法是累加器 + 固定步长：

_accumulator += Time.deltaTime;
while (_accumulator >= FixedDt)
{
    _world.Step(FixedDt, 8, 3);
    _accumulator -= FixedDt;
}

注意这个循环要加单帧上限，否则卡顿时会「追帧雪崩」—— 一帧里跑几十次 Step 反而更卡。
