阶段一：FTask —— 自定义 awaitable

Fantasy 源码阅读 · 1248 行 / 9 个文件
Fantasy.Unity/Runtime/Core/FTask/

这是全项目学习价值密度最高的模块。绝大多数 C# 开发者只会用 async/await，读完这里你会写。

核心文件 Task/FTask.cs 只有 262 行，却完整实现了一个可被 await 的类型，以及让 async FTask 方法能通过编译的全套机制。干净到可以一口气读完。

一、先建立问题意识

写 await someTask 时，编译器到底要求 someTask 长什么样？

答案出人意料地宽松：C# 不要求它是 Task，甚至不要求实现任何接口。编译器只做「鸭子类型」检查 —— 只要这个类型有一个 GetAwaiter() 方法，返回的对象具备三个成员，就能被 await。

这三个成员构成了所谓的 awaiter 契约：

成员签名作用
IsCompletedbool 属性同步快速路径：已完成就不挂起
OnCompletedvoid (Action)未完成时，登记「完成后要执行什么」
GetResultvoid 或 T取结果，或把异常抛出来

再加上 ICriticalNotifyCompletion 里的 UnsafeOnCompleted，就是我在索引里说的「四件套」。

为什么值得读 这套契约平时被 Task 完全遮住了。自己看一遍实现，之后再看 UniTask、ValueTask、Unity 的 Awaitable，会发现它们全是同一个模子，差别只在「谁来存回调」和「要不要池化」。

二、从最简单的开始：FVoid

不要一上来读 FTask.cs。先看 Task/FVoid.cs（28 行），它是整个体系里最小的 awaitable，用来做 fire-and-forget。

读它的目的只有一个：确认「一个可 await 的类型可以有多小」。28 行里没有池化、没有异常捕获、没有泛型，骨架一目了然。

三、核心：FTask.cs 的状态机

整个类围绕一个三态枚举运转：

Core/FTask/Task/FTask.cs
public enum STaskStatus : byte
{
    Pending = 0,   // 尚未完成
    Succeeded = 1, // 成功完成
    Faulted = 2    // 带异常完成
}

[AsyncMethodBuilder(typeof(AsyncFTaskMethodBuilder))]
public sealed partial class FTask : ICriticalNotifyCompletion
{
    private Action _callBack;
    private ExceptionDispatchInfo _exception;
    private STaskStatus _status = STaskStatus.Pending;

三个字段就是全部状态：一个回调、一个异常、一个状态位。对比 System.Threading.Tasks.Task 动辄十几个字段（含 ExecutionContext、TaskScheduler、continuation 链表），这里的极简是刻意的。

3.1 GetAwaiter 返回自己

public FTask GetAwaiter() => this;

这是个关键设计。Task 的 GetAwaiter() 会新建一个 TaskAwaiter 结构体，而这里 task 和 awaiter 是同一个对象。少一次分配，也少一层间接。

代价是职责耦合：同一个类既是「结果的持有者」（对外提供 SetResult），又是「等待的协议实现者」（对内提供 GetResult）。读代码时要分清哪些方法给谁用 —— 这也是后面那个坑的根源。

3.2 IsCompleted：同步快速路径

public bool IsCompleted
{
    get => _status != STaskStatus.Pending;
}

编译器生成的状态机会先查这个属性。为 true 时直接调 GetResult() 继续往下跑，完全不挂起、不分配状态机堆对象。这就是为什么「await 一个已完成的任务」几乎零开销。

3.3 OnCompleted：存回调，就这么简单

public void OnCompleted(Action action)
{
    UnsafeOnCompleted(action);
}

public void UnsafeOnCompleted(Action action)
{
    if (_status != STaskStatus.Pending)
    {
        action?.Invoke();  // 竞态兜底：已完成则立刻执行
        return;
    }

    _callBack = action;   // 注意：直接赋值，不是 +=
}

两处值得停下来想：

  1. _callBack = action 是赋值而非累加。意味着一个 FTask 只支持一个等待者。Task 允许多处 await 同一个实例，FTask 不行 —— 第二个 await 会覆盖第一个的续体，前一个永久丢失。这是有意的取舍：游戏逻辑里一个异步操作通常只有一个等待方，换来了字段从「链表」简化成「单个委托」。
  2. OnCompleted 直接转发给 UnsafeOnCompleted。标准库里这两者的区别是：前者要捕获并还原 ExecutionContext（保证 AsyncLocal、身份凭据等跨 await 传递），后者跳过。这里全部跳过 —— 纯性能取向，代价是不支持 ExecutionContext 流转。对单线程驱动的游戏客户端来说是合理的。
ICriticalNotifyCompletion 的意义 实现这个接口，就是在向编译器声明「我知道我在跳过 ExecutionContext」。状态机会优先调用 UnsafeOnCompleted。接口名里的 Critical/Unsafe 不是指线程不安全，而是指安全上下文不流转。

3.4 SetResult：完成并触发

public void SetResult()
{
    if (_status != STaskStatus.Pending)
    {
        throw new InvalidOperationException("The task has been completed");
    }

    _status = STaskStatus.Succeeded;

    if (_callBack == null)
    {
        return;
    }

    var callBack = _callBack;
    _callBack = null;      // 先清空，再调用
    callBack.Invoke();
}

「先把字段清空、再 Invoke」这个顺序是关键。如果先 Invoke 后清空，回调内部若又对这个对象做操作（在池化场景下它可能已经被复用），就会踩到已经失效的引用。这是写池化对象的通用纪律，值得记住。

3.5 GetResult：取结果，兼归还对象

这是全文件最需要细看的方法。以 FTask<T> 版本为例：

public T GetResult()
{
    switch (_status)
    {
        case STaskStatus.Succeeded:
        {
            var value = _value;
            Return();          // ← 归还到对象池！
            return value;      // 先存值再归还，顺序不可颠倒
        }
        case STaskStatus.Faulted:
        {
            Return();

            if (_exception == null) return default;

            var exception = _exception;
            _exception = null;
            exception.Throw();  // 保留原始调用栈
            return default;
        }
        default:
        {
            throw new NotSupportedException(
                "Direct call to getResult is not allowed");
        }
    }
}

三个细节：

  • GetResult() 有副作用 —— 它会归还对象。这不是「读取属性」而是「消费并销毁」。所以它天然只能调用一次。
  • ExceptionDispatchInfo.Throw() 而非 throw exception。后者会重置 StackTrace，让你只看到抛出点、丢失原始现场。前者保留完整调用栈。这个 API 在任何需要「跨线程/跨帧转发异常」的场合都该用。
  • default 分支抛异常。状态还是 Pending 却调了 GetResult，说明有人绕过 await 直接手调。这个防御把误用变成显式崩溃。

四、AsyncMethodBuilder：让 async FTask 能编译

光有 awaiter 契约，只解决了「FTask 能被 await」。反方向的问题是：

public async FTask<bool> ConnectAsync(...)  // 凭什么能这么写？

async 方法的返回类型不是随便挑的。编译器要求该类型上标注 [AsyncMethodBuilder(...)]，指向一个「建造者」，由它负责创建 task、驱动状态机、写入结果。这就是类声明上那行特性的作用：

[AsyncMethodBuilder(typeof(AsyncFTaskMethodBuilder<>))]
public sealed partial class FTask<T> : ICriticalNotifyCompletion

Builder 需要实现一组固定签名的成员（Create / Start / SetResult / SetException / AwaitOnCompleted / AwaitUnsafeOnCompleted / Task）。这三个 Builder 文件（51 / 139 / 61 行）我这次没读到内部实现，留给你自己对照上面的成员清单去看 —— 重点是找出「状态机在哪一步被推进」和「异常怎么从 async 方法体流到 task 上」。

编译器把 async 方法变成了什么

理解 Builder 最有效的方式是看编译产物。下面这段 async 方法：

async FTask<bool> Foo()
{
    var ok = await Bar();
    return ok;
}

大致等价于（伪代码，省略大量细节）：

FTask<bool> Foo()
{
    var sm = new FooStateMachine();
    sm.builder = AsyncFTaskMethodBuilder<bool>.Create();
    sm.state = -1;
    sm.builder.Start(ref sm);   // 同步跑到第一个 await
    return sm.builder.Task;
}

// 状态机的 MoveNext，被反复调用
void MoveNext()
{
    switch (state)
    {
        case -1:
            awaiter = Bar().GetAwaiter();        // ① 拿 awaiter
            if (awaiter.IsCompleted) goto done; // ② 快速路径
            state = 0;
            builder.AwaitUnsafeOnCompleted(       // ③ 登记续体
                ref awaiter, ref this);
            return;                              // 挂起，控制权交还调用方
        case 0:
            goto done;                           // 被回调唤醒，从这里续跑
    }
done:
    var ok = awaiter.GetResult();             // ④ 取结果
    builder.SetResult(ok);                     // ⑤ 写回外层 task
}
把四件套的调用时机连起来看： await 表达式 │ ├─→ ① GetAwaiter() 返回 this（零分配） │ ├─→ ② IsCompleted ─── true ──→ 不挂起，直奔 ④ │ │ │ false │ ↓ ├─→ ③ UnsafeOnCompleted(续体) _callBack = 续体 │ ↓ │ [ 方法返回，线程去干别的 ] │ ↓ │ 外部某处调用 SetResult(value) │ ↓ │ _status = Succeeded → Invoke 续体 → MoveNext 恢复 │ ↓ └─→ ④ GetResult() 取值 + Return() 归还池 ↓ ⑤ builder.SetResult() 让外层 task 也完成

看懂这张图，async/await 就不再是魔法了。它只是「编译器把方法切成若干片段，用 _callBack 把片段串起来」。

五、池化的代价 —— 项目里的真实坑

这是本阶段最有实践价值的部分。回到你项目的代码：

GameScripts/HotFix/GameLogic/DataCenter/GameClient.cs
// 创建待完成的 Task
m_connectTask = FTask<bool>.Create(isPool: false);
if (Scene.Session == null || Scene.Session.IsDisposed)
{
    Scene.Connect(..., OnConnectComplete, OnConnectFail, OnConnectDisconnect, false);
}
return await m_connectTask;

那个 isPool: false 不是随手写的。把前面两处源码事实拼起来就明白了：

  1. GetResult() 在返回值后立刻调 Return() 归还对象池；
  2. m_connectTask 是个字段，会跨帧存活，还被 OnConnectComplete / OnConnectFail / Disconnect 等多处引用。

如果启用池化，一旦某处 await 完成触发归还，这个实例就可能被框架内部其它异步操作取走复用。而 m_connectTask 字段还指向它 —— 此时任何一处再调 SetResult(false)（比如紧接着来的断线回调），就会把结果写到别人的 task 上。表现是随机的、极难复现的逻辑错乱。

池化 awaitable 的铁律 池化 task 的生命周期必须严格等于「创建 → 单次 await → 结束」。任何需要长期持有、跨帧保存、多处引用的场景，都要关掉池化。

这条规则对 UniTask 的 UniTaskCompletionSource、ValueTask 的 IValueTaskSource 同样成立 —— 官方文档反复强调「ValueTask 不要 await 两次、不要存起来」，原因就是这个。

顺带解释了另一处代码：

public void Disconnect()
{
    m_connectTask?.SetResult(false);
    m_connectTask = null;      // 立刻断开引用，避免二次 SetResult 抛异常
    ...
}

因为 SetResult 在非 Pending 状态会抛 InvalidOperationException，所以每个完成路径（OnConnectComplete / OnConnectFail / OnConnectDisconnect / Disconnect）都遵循「SetResult 后立刻置 null」。这四处的写法完全一致，是防御同一个问题。

六、FTask 与 UniTask 混用

你项目里两套异步体系并存。已知的交界点：

GameScripts/HotFix/GameLogic/DataCenter/ClientConnectWatcher.cs:242
public async UniTaskVoid CheckClientVersion()
{
    ...
    await operation.ToUniTask();
}

目前全项目只有这一处桥接，且是 YooAsset 的 operation 转 UniTask，并未真正跨越 FTask 与 UniTask。这是好事 —— 两套 awaitable 各有独立的池和调度假设，混合传递容易出问题。

建议维持的边界 Fantasy 网络层内部用 FTask（框架要求），业务层用 UniTask（TEngine 生态）。交界处就放在 GameClient 这一层，用普通回调或 UniTaskCompletionSource 转接，不要让 FTask 泄漏到业务代码里。你现在的结构已经是这样了。
