讲解说「有 GetAwaiter 就能 await」，但 FVoid 里没有这个方法，为什么它也能被 await？

2026-07-28 · 相关：Fantasy.Unity/Runtime/Core/FTask/Task/FVoid.cs

线索

  • 「鸭子类型 awaitable 契约」和「awaiter 形态」是两条不同的路
  • FVoid 自己就是 awaiter，不是 awaitable

核心理解

C# 让一个类型可被 await 有两条路径。讲解里说的「有 GetAwaiter() 就能 await」描述的是 通用 awaitable 契约（鸭子类型：提供 GetAwaiter() 返回一个具备 IsCompleted/OnCompleted/GetResult 的 awaiter）。 FTask、Task、UniTask 都走这条。

FVoid 走的是另一条：它自己直接实现 awaiter 接口（ICriticalNotifyCompletion）， 自己当 awaiter，省掉了 GetAwaiter() 这一跳。它只在 async FVoid 方法的编译器状态机内部使用， 配合 [AsyncMethodBuilder] 由编译器直接调用它的 IsCompleted/UnsafeOnCompleted， 所以根本不需要 GetAwaiter。

证据

FVoid.cs —— 整个类型没有 GetAwaiter()，直接把 awaiter 三件套长在自己身上

[AsyncMethodBuilder(typeof(AsyncFVoidMethodBuilder))]
internal struct FVoid : ICriticalNotifyCompletion
{
    public bool IsCompleted => true;          // 恒完成，永不挂起
    public void OnCompleted(Action continuation) { }
    public void UnsafeOnCompleted(Action continuation) { }
}

引用：Fantasy.Unity/Runtime/Core/FTask/Task/FVoid.cs:8-28。注意 FVoid 连 GetResult() 都没有，只有个空的 Coroutine()——因为 IsCompleted 恒为 true，编译器走快速路径直接跳过 GetResult。

对比表

形态需要 GetAwaiter()?代表
awaitable（鸭子类型）必须，返回一个 awaiterFTask、Task、UniTask
awaiter 本身不需要FVoid（仅编译器状态机内部用）
关键区分 讲解那句「有 GetAwaiter 就能 await」没错，但它讲的是通用规则。FVoid 是特例：awaitable 与 awaiter 合一、只服务于 async FVoid 的零开销 fire-and-forget。看到没有 GetAwaiter 却能 await 的类型，先查它是不是直接实现了 INotifyCompletion/ICriticalNotifyCompletion。

AsyncMethodBuilder 到底是什么？为什么 FVoid、FTask 上都要贴这个特性？

2026-07-28 · 相关：Fantasy.Unity/Runtime/Core/FTask/Builder/AsyncFVoidMethodBuilder.cs

线索

  • async 关键字 = 编译时把方法切成状态机的语法糖
  • 编译器不认识你造的类型，Builder 就是状态机和你类型之间的「胶水层」
  • 7 个固定签名方法的契约

核心理解

AsyncMethodBuilder 是编译器的脚手架。async 关键字在 C# 里不是运行时魔法，是编译时把方法体改写成 IAsyncStateMachine 状态机的语法糖。但编译器只认识 System.Threading.Tasks.Task， 碰到第三方自己造的 FTask/FVoid/UniTask，它不知道「怎么创建这个 task、完成时怎么收尾、异常往哪抛」。

所以 C# 提供了一个约定：你在类型上贴 [AsyncMethodBuilder(typeof(XxxBuilder))]， 指向一个实现了 7 个固定签名方法的「建造者」，由它负责在状态机的每个关键节点跟你的类型打交道。 Builder = 状态机和自定义 Task 类型之间的胶水层。

证据 —— Builder 的 7 个固定方法，对应状态机的 7 个调用点

AsyncFVoidMethodBuilder.cs —— 最简 builder，struct 零字段全 inline

internal struct AsyncFVoidMethodBuilder
{
    public FVoid Task => default;                       // 读 Task 属性：返回最终对象
    public static AsyncFVoidMethodBuilder Create() => default;  // 进 async 方法时调用
    public void Start<TSM>(ref TSM sm) where TSM : IAsyncStateMachine
        => sm.MoveNext();                              // 启动状态机，同步跑第一片段
    public void SetResult() { }                      // 方法正常 return 完
    public void SetException(Exception ex)                 // 方法体抛异常
        => ExceptionDispatchInfo.Capture(ex).Throw();
    public void AwaitOnCompleted<...>(...)             // 挂起：登记续体（普通版）
        => awaiter.OnCompleted(sm.MoveNext);
    public void AwaitUnsafeOnCompleted<...>(...)         // 挂起：登记续体（跳过上下文版）
        => awaiter.UnsafeOnCompleted(sm.MoveNext);
}

引用：Fantasy.Unity/Runtime/Core/FTask/Builder/AsyncFVoidMethodBuilder.cs:11-61

对照：编译器把 async 方法翻成了什么

// 你写的：
async FVoid Foo() { await Bar(); }

// 编译器翻译成（伪代码）：
FVoid Foo() {
    var sm = new FooStateMachine();
    sm.builder = AsyncFVoidMethodBuilder.Create();   // ← Create()
    sm.builder.Start(ref sm);                     // ← Start()，跑到第一个 await
    return sm.builder.Task;                      // ← Task 属性
}
void MoveNext() {
    // ...await 一个未完成 task...
    builder.AwaitUnsafeOnCompleted(ref awaiter, ref this);  // ← 登记续体
    return;
    // ...被唤醒跑完...
    builder.SetResult();      // ← 或 SetException(ex)
}
FVoid 的 Builder 为什么这么空 Create()/Task 都 return default（struct 零值就够，不分配），SetResult() 空实现（fire-and-forget，完成了不用通知任何人），Start() 同步调一次 MoveNext。整个 builder 是 struct、零字段、全 [AggressiveInlining]，编译器内联后 async FVoid 几乎零开销——这正是 Fantasy 要为 fire-and-forget 单独造 FVoid 而不用 FTask 的原因。
造自己的 awaitable 类型，两样都不能少 除了实现 awaiter 契约（IsCompleted/OnCompleted/GetResult），还必须配一个 Builder 并在类型上贴 [AsyncMethodBuilder(typeof(...))]。缺任何一个，async YourType 都编译不过。

FTask 的 GetAwaiter/IsCompleted/OnCompleted/GetResult 这些函数到底在哪里被调用？

2026-07-28 · 相关：Fantasy.Unity/Runtime/Core/FTask/Task/FTask.cs:24,38

线索

  • 这些函数你自己写的业务代码里几乎从不直接调
  • await 是编译时语法糖，不是运行时魔法
  • await 一侧 vs 完成 task 一侧，是两条独立的线

核心理解

这五个函数的调用方是 C# 编译器生成的状态机代码，不是任何运行时机制，更不是你写的代码。 await expr 是纯编译时语法糖——编译器把它展开成一个 IAsyncStateMachine 状态机的 MoveNext 方法， 在里面硬编码了对 GetAwaiter/IsCompleted/GetResult 的调用。 所以"在哪被调用"的答案是：在那个你看不到源码、但确实存在于编译后 dll 里的 MoveNext 方法里。

SetResult 是唯一的例外——它属于完成 task 的一侧，由你的业务回调（比如 OnConnectComplete）手动调。 它内部 Invoke 之前 await 登记的回调（就是状态机的 MoveNext），从而把两条线串起来。

证据 —— 编译器把 await m_connectTask 翻成了什么

编译器生成的状态机 MoveNext（伪代码，简化到只剩骨架）

void MoveNext()
{
    switch (state)
    {
        default:                 // 第一次进，state == -1
            awaiter = m_connectTask.GetAwaiter();     // ① 编译器硬编码调
            if (!awaiter.IsCompleted)           // ② 编译器硬编码调
            {
                state = 0;
                builder.AwaitUnsafeOnCompleted(       // ③ Builder 转调 awaiter.UnsafeOnCompleted
                    ref awaiter, ref this);
                return;                        // ← 挂起，控制权还给调用方
            }
            goto done;
        case 0:                    // 续体被唤醒，从这续跑
            break;
    }
done:
    awaiter.GetResult();               // ④ 编译器硬编码调
    builder.SetResult();                 // ⑤ 方法正常结束（这个 SetResult 是 Builder 的，不是 FTask 的）
}

引用：编译产物在 Library/ScriptAssemblies/<程序集>.dll，用 ILSpy/dnSpy 反编译可见真实 MoveNext。

函数 → 调用方 对照表

FTask 的函数在哪被调谁调的
GetAwaiter()编译器生成的 MoveNext状态机
IsCompleted编译器生成的 MoveNext状态机
UnsafeOnCompletedBuilder 的 AwaitUnsafeOnCompleted 内部转调Builder 转发
GetResult()编译器生成的 MoveNext状态机
SetResult()你的业务回调（如 OnConnectComplete）你手写的代码

两条独立的线，在 SetResult 交汇

线 A：await 一侧（读 task 的人）
你的 async 方法 → 状态机 MoveNext
  → GetAwaiter / IsCompleted / UnsafeOnCompleted（登记"完成后要干什么"）
  → 方法挂起，返回调用方 → [等待] → 被唤醒 → GetResult() → 继续跑

线 B：完成 task 一侧（写 task 的人）
业务回调 OnConnectComplete
  → m_connectTask.SetResult()
  → 内部 _status = Succeeded → Invoke 之前登记的回调（= 状态机 MoveNext）
  → 线 A 被唤醒，继续往下跑
理解 await 最快的办法 别看讲解，去看真实的编译产物。对用了 async FTask 的程序集，编译后去 Library/ScriptAssemblies/ 找对应 dll，用 ILSpy 打开，找到你的 async 方法，会亲眼看到编译器生成的 MoveNext 里那套 GetAwaiter/IsCompleted/GetResult 调用。比任何文档都直观。
注意区分两个 SetResult 生成代码里同时出现两个 SetResult：builder.SetResult()（Builder 的，标记"整个 async 方法跑完了"）和 m_connectTask.SetResult()（FTask 的，标记"这个 task 完成了"）。前者驱动状态机收尾，后者驱动 await 唤醒。别混。

FTask.Coroutine() 到底是干什么的？为什么要包一层 async FVoid InnerCoroutine？

2026-07-28 · 相关：Fantasy.Unity/Runtime/Core/FTask/Task/FTask.cs:42-52、FTask.Tools.cs:319-336

线索

  • fire-and-forget：启动 task 但不等它
  • 为什么不直接 SomeTask() 不管它 —— async 方法的状态机会停在第一个 await
  • FVoid 是自驱动载体（IsCompleted 恒 true）

核心理解

Coroutine() 是 FTask 的 fire-and-forget 入口——让 task 在后台自驱跑完，调用方不用 await 它。 为什么不能直接 SomeTask(); 不管？因为 async FTask 方法你不 await 它， 它的编译器状态机会在第一个 await 处挂起后停在那，没人驱动它继续。 Coroutine() 的作用就是包一层"自驱动的壳"把这个 task 跑完。

这层壳的实现很巧：用 private async FVoid InnerCoroutine() { await this; }。 关键在壳是 FVoid 不是 FTask——FVoid 的 Builder（AsyncFVoidMethodBuilder）在 Start() 时 同步调一次 MoveNext，能自己跑起来，不需要外部 await 驱动。所以包在 FVoid 里的 await this 能自己等 task 完成后收尾，调用方完全不用管。

证据 —— Coroutine 的三层实现

FTask.cs:42-52 —— Coroutine 包了一层 async FVoid 当自驱动壳

private async FVoid InnerCoroutine()
{
    await this;                          // 在 FVoid 壳里等当前 FTask 完成
}

public void Coroutine()
{
    InnerCoroutine().Coroutine();           // 启动这个 FVoid（FVoid.Coroutine 是空方法，仅占位）
}

引用：FTask.cs:42-52（FTask<T> 版本在 FTask.cs:160-172，结构相同）。FVoid.Coroutine 是空实现：FVoid.cs:20。

真实用法 —— WaitAll 并行点火

FTask.Tools.cs:319-336 —— 没有 Coroutine() 写不出"并行启动、汇总等待"

var sTaskCompletionSource = Create();         // 只等这一个汇总点

foreach (var task in tasks)
{
    RunSTask(task).Coroutine();               // ← 每个 task 后台自驱跑
}

await sTaskCompletionSource;                  // 只等汇总，不串行等每个

async FVoid RunSTask(FTask task)
{
    await task;
    count--;
    if (count <= 0) sTaskCompletionSource.SetResult();
}

跨框架对照

概念FTaskUniTask
fire-and-forget 入口task.Coroutine()UniTaskVoid.Forget() / UniTask.Void()
自驱动载体FVoidUniTaskVoid
忘记调的后果异步逻辑不执行（无警告）编译器警告 CS4014
何时用 await vs Coroutine() 需要结果 / 必须等完成才能继续 → await。不在乎何时完成、点火就不管 → Coroutine()。 典型场景：后台日志/埋点、并行加载（配 WaitAll）、触发特效后立刻返回、心跳定时清理。 GameClient 里没用 Coroutine()，因为网络连接必须等结果（return await m_connectTask）。
FVoid 才是自驱动的关键 Coroutine() 能成立，完全依赖壳是 async FVoid 而不是 async FTask。FVoid 的 AsyncFVoidMethodBuilder 在 Start 时同步调 MoveNext、永不挂起，所以不需要外部驱动。如果壳写成 async FTask，不 await 它就又回到"状态机停在第一个 await"的死循环。这也是 Fantasy 为何要单独造 FVoid——它是 fire-and-forget 的零开销载体。
