零、先说结论：这一篇的真正主题

本来的计划是讲「Box2D 怎么工作」。读完源码后主题变了，因为核实出一件更要紧的事：

Box2D 在本项目里几乎没有工作 全项目只有一处 CreateBody，只创建玩家圆形体，没有墙、没有静态体。所有 fixture 的 Filter.GroupIndex = -1，而这个值会让 Box2D 在创建 Contact 之前就拒绝所有配对。

结果：接触点从不产生 → 速度求解器和位置求解器全程空转 → IContactListener 四个回调一次都不触发。 Box2D 实际执行的运算只剩 Island.cs:220 的 c += h * v，一次乘加。

所以这一篇的结构是倒过来的：先把 Box2D 的机制讲清楚（第一、二章），然后用它解释你的代码为什么绕过了这些机制、绕过之后失去了什么、以及一旦加一堵墙会同时激活哪些问题（第三章往后）。

这个视角对面试更有用。「Box2D 的 solver 怎么迭代」是公共知识，「我知道我的物理层实际只用到了积分器，因此哪些确定性问题被侥幸绕过」是只有你能讲的东西。

读法 19057 行不要通读。本篇只覆盖你项目实际踩到的路径：World.Step 主流程、ContactSolver、 DefaultContactFilter、Island 的积分与休眠。Joints（5370 行）、Rope、Distance/TOI 的数学推导全部跳过。

接触点的创建与销毁是两个不同的地方

这是第一个容易记错的点。Collide() 从不创建接触点，它只做两件事：更新既有接触点的流形、销毁失效的接触点。

body 的遍历顺序是创建顺序的逆序

src/Dynamics/World.cs:251-252
// 源码原注释：添加物体到物体链表头部
body.Node = BodyList.AddFirst(body);

BodyList 是 LinkedList<Body>（World.cs:127），头插。Solve 的 island 种子选择按链表顺序走（World.cs:710-712），所以最后创建的 body 最先被处理。Contact 和 Joint 同样是 AddFirst（ContactManager.cs:191、World.cs:329）。

顺序传导链：链表逆序 → DFS 用 LIFO 栈（World.cs:657 的 Stack<Body>）→ Island.Add 写入数组下标（Island.cs:441-447）→ 数组顺序即 Gauss-Seidel 求解顺序 → 浮点累加顺序。

为什么这条对帧同步重要 确定性依赖「相同的 body 创建顺序」+「相同的 contact 创建顺序」。任何改变创建顺序的操作 （包括 DestroyBody 后重建，也就是你的 RestoreSnapshot）都会改变遍历序， 从而改变浮点累加顺序。

但在你的项目里这条当前不生效 —— 因为没有 contact，island 内 body 之间没有耦合， 每个 body 独立积分，顺序不影响结果。这是第四章的主题。

二、ContactSolver —— 两种迭代与跨帧冲量

这一章是 Box2D 唯一有算法分量的部分，也是你传 12, 8 两个参数时实际在配置的东西。

两个循环解的不是同一个问题

循环位置Island.cs:181-189Island.cs:232-249

位置求解器不碰速度这一点是关键设计。它直接位移质心（ContactSolver.cs:785-789），因此不会给系统注入伪造动能 —— 堆叠的箱子不会自己弹开。这叫 NGS（Non-linear Gauss-Seidel），non-linear 是因为每轮都用最新位置重算 separation（ContactSolver.cs:749-761），而不是沿用一开始线性化的雅可比。

钳制作用在累积冲量，不是增量

这是 sequential impulse 最容易看错的地方：

src/Dynamics/Contacts/ContactSolver.cs:402-408
vn = dot(dv, normal);
lambda = -vcp.NormalMass * (vn - vcp.VelocityBias);

newImpulse = Math.Max(vcp.NormalImpulse + lambda, 0.0f);  // 钳「累积值」
lambda     = newImpulse - vcp.NormalImpulse;                // 反解真正要施加的增量
vcp.NormalImpulse = newImpulse;

钳的是 NormalImpulse + lambda 这个累积量，然后回推出实际增量再施加到速度上。这允许中间轮次出现负的 lambda（回撤上一轮给多了的冲量），只要累积值不为负 —— 接触只能推不能拉。

源码注释直接点明了原因（ContactSolver.cs:439-440）：because of the iterative nature of the solver which only requires that the accumulated impulse is clamped and not the incremental impulse。

这个细节值得在面试讲 它同时解释了下面 warm start 为什么能成立：如果钳的是增量，跨帧保存的累积值就不是一个合法初值。 两个知识点是同一个设计的两面。

先摩擦后法向

源码注释（ContactSolver.cs:344-345）：Solve tangent constraints first because non-penetration is more important than friction.

  • 切向在前（349-387），法向在后（392-685）→ 法向的解不会被摩擦的后续修改污染
  • 代价：本轮摩擦上界 maxFriction = friction * vcp.NormalImpulse（363）用的是上一轮/上一帧的法向冲量
  • 法向钳制是单侧 max(x, 0)，摩擦是双侧 clamp(x, -max, +max)（365-368）—— 因为摩擦可以朝切向任一侧

warm starting：跨帧复用冲量

冲量的跨帧传递链 上一帧速度迭代结束 └─ StoreImpulses() ContactSolver.cs:696-719 └─ 写回 manifold.Points[j] ← manifold 挂在 Contact 上，跨帧存活 本帧 Setup └─ 读回并按 DtRatio 缩放 ContactSolver.cs:93-97 DtRatio = _invDt0 * timeStep（World.cs:460），dt 不变时 = 1 速度迭代之前 └─ WarmStart() ContactSolver.cs:291-299 P = Pn*normal + Pt*tangent，直接施加，不做任何钳制

为什么能加速收敛：Gauss-Seidel 的收敛速度取决于初值离解多远。稳态堆叠场景相邻两帧的接触冲量几乎相同，用上一帧的解当初值，前几轮迭代不必从 0 重新爬到支撑重力所需的量级。

这是 Box2D 上做回滚帧同步的头号障碍 warm starting 让第 N 帧的求解结果依赖第 N-1 帧的累积冲量，而这个冲量存在 Contact.Manifold 上 —— 一个 internal 字段，Box2DSharp 没有公开 API 能读写它。

也就是说：快照不含冲量 → 回滚重演的轨迹与原轨迹分叉。想修就只能反射或改源码。

你的项目当前不受影响，原因见下一章。但这是「任何在 Box2D 上做回滚的项目都必须解决的问题」， 知道它存在并能说出为什么自己绕过了，比不知道要好得多。

后果一：你的 ContactListener 是死代码

约 50 行不可达代码 FrameSyncPhysicsWorld.cs:563-613 的 ContactListener 内部类、 _physicsContacts 字典（33）、SetContactListener 调用（43-44）、 RemoveContactsForBody 对它的处理（277）—— 全部不可达。

这也解释了你为什么必须自己写 RebuildOccupancyContacts（353-382）用纯几何距离重算「谁在贴着谁」：Box2D 侧的接触事件源被你自己关掉了。

这里有个值得讲的架构自相矛盾：项目同时做了 (a) 用 GroupIndex=-1 关掉 Box2D 的玩家间碰撞，(b) 自己写几何检测重建接触关系。等价于「引入 Box2D 之后把它的碰撞检测关掉，再手写一遍」。

教学价值：配置驱动的远距离耦合 第 102 行一个 -1，静默地让 460 行之外的 50 行代码失效。没有编译警告、没有运行时报错、 测试也不会失败（因为死代码的输出被合并进了另一个有值的字典）。

这类 bug 极难发现，因为「配置」和「被影响的代码」在阅读时距离太远。

后果二：12/8 在当前配置下零代价

我一开始判断「12/8 比官方 8/3 高，代价在速度迭代」。核实后这是错的：

实际行为
速度迭代 12 次SolveVelocityConstraints 内部是 for (i < _contactCount)，_contactCount == 0 → 12 次空调用
位置迭代 8 次空循环后 minSeparation 保持 0.0f（ContactSolver.cs:723）→ 0 >= -0.015 为真 → Island.cs:243-248 第一次就 break，8 次只跑 1 次
正确的表述方式 不要说「12/8 过高」。要说：在 contact 恒空的当前配置下这两个参数不产生任何效果；一旦引入静态碰撞体， 应回退到官方 8/3 并实测。

顺带一个很多人搞错的点：迭代次数的成本正比于 contact 数量，不是 body 数量。

真正的固定开销在别处：Island.Setup（Island.cs:32-49）每次 Solve/SolveTOI 都从 ArrayPool rent 五个数组，Reset（51-71）以 clearArray: true 归还 —— 每帧约 10 次 rent + 清零，无论有没有 contact。

后果三：Bullet = true 完全没必要

你给所有 body 设了 Bullet = true（FrameSyncPhysicsWorld.cs:76）。这个标记只在 SolveTOI 内被读，两处：

src/Dynamics/World.cs:992-999
var collideA = bA.IsBullet || typeA != BodyType.DynamicBody;
var collideB = bB.IsBullet || typeB != BodyType.DynamicBody;
if (collideA == false && collideB == false) { continue; }

语义是：dynamic-vs-dynamic 的 CCD 默认关闭，标了 bullet 才启用（dynamic-vs-static 的 CCD 始终开启，与此标记无关）。

两条独立理由说明它不必要：

  1. TOI 循环空转。SolveTOI 遍历 ContactManager.ContactList（World.cs:940-1045），恒空 → minContact == null → 立即 break（1047-1052）。那两处 IsBullet 判断永不执行。
  2. 即便有 contact 也不必要。MoveSpeed = 5、dt = 1/30 → 单帧位移 0.1667，而玩家半径 0.45。位移只有直径的 18.5%，穿隧在几何上不可能。CCD 是为「子弹 100 m/s 穿 0.1 m 薄墙」设计的。

源码注释本身也警告过（Body.cs:79）：You should use this flag sparingly since it increases processing time.

建议 Bullet = false，并显式设 _world.ContinuousPhysics = false（可整段跳过 SolveTOI， World.cs:485）。保留 Bullet = true 会让读代码的人以为项目有高速穿隧问题需要 CCD —— 防御性配置反而增加了认知负担。

后果四：Box2D 的实际贡献剩下一行

把前面的结论叠起来：没有 contact → 两个求解器空转 → 重力为零 → Force 恒零 → 阻尼为零。Island.Solve 里真正改变数值的只剩：

src/Dynamics/Island.cs:220
c += h * v;   // 一次乘加
需要正视的问题 引入一个 19057 行的物理引擎，最终使用的是「按速度积分位置」这一次乘加，加上一个从未产出任何结果的 broadphase。收益与复杂度的比值应当被重新评估。

这不是说当初的选择错了 —— 引入 Box2D 的合理理由是「为将来的墙体、障碍物、道具碰撞留出路径」。 但如果 demo 定型为当前形态，那么它带来的是净负担：额外的确定性风险面、 反射绕 internal API 的技术债、以及 50 行死代码。

四、快照与回滚：漏了什么，为什么当前不出问题

你的 RestoreSnapshot（FrameSyncPhysicsWorld.cs:200-229）走的是「全拆全建」：ClearBodies() → 逐 body EnsureBody + SetTransform + 设速度 → 重填 _occupancyContacts。

Box2D 有一批跨帧存活的内部状态。逐项核对哪些没被恢复：

状态恢复?当前影响加墙体后
warm start 累积冲量
ManifoldPoint.NormalImpulse		否零 —— contact 不存在，字段从不被写入P0 缺陷，回滚轨迹必分叉
Contact 存在性 / wasTouching否零 —— 无 contact影响 Begin/EndContact 事件序
BroadPhase DynamicTree 结构否，完全重建零 —— 所有 pair 都被 filter 丢弃第二个杀手：pair 顺序 → ContactList 顺序 → 求解顺序 → 数值结果
Body.SleepTime否（重建为 0）零，可证明：AllowSleep=false → Island.cs:285 每帧强制 SleepTime=0同
Body.Sweep.Alpha0否（重建为 0）零 —— World.cs:911-931 每帧归零需注意 SetTransform 不重置它（Body.cs:747-772）
Body.Force / Torque否（重建为 0）零 —— ClearForces 每帧清（World.cs:517-527）同

一个反复出现的模式 每一行的「当前影响」都是零，但每一行的原因都是某个功能被关掉了，而不是设计防住了它。

GroupIndex=-1 挡住了前三行，AllowSleep=false 挡住了 SleepTime， SubStepping=false 挡住了 Alpha0，零重力零力挡住了 Force。

把这些前提中的任何一条改掉，对应的缺口立刻打开。这是这份笔记最该记住的一句话。

warm start 冲量为什么是「无法优雅修复」的

假设你明天加了一堵墙。这一项立刻成为 P0，而修它很难：

  • 冲量存在 Contact.Manifold，是 internal 字段
  • Box2DSharp 没有公开 API 能读写 Manifold.Points[i].NormalImpulse
  • 可选路径：反射（又一处技术债）／改源码自编 dll（失去升级路径）／World.WarmStarting = false（牺牲收敛质量，稳定堆叠会变软）

最后那条其实是最干净的：帧同步项目主动关掉 warm starting，用「多几轮迭代」换「无跨帧隐藏状态」。这是个可以在面试里讲的权衡判断。

正面案例：确定性处理是对的

报告里也核实了几处写得正确的地方，这些同样值得在面试讲：

  • 字典遍历后强制排序：TakeSnapshot（184-198）先遍历 Dictionary 再 Array.Sort，比较器用 BodyId / (BodyAId, BodyBId) 全序唯一（615-634），排序不稳定性无影响。Dictionary 的枚举顺序在 .NET 上从不是契约，这是标准做法。
  • bodyId 定序的 Gauss-Seidel：ResolvePlayerOccupancy 外层按 _sortedBodyIdsBuffer（384-393，升序）遍历，求解顺序由 bodyId 全序唯一确定，与字典枚举序无关。
  • 重合退化时的确定性法线：DetermineSeparationNormal（395-418）先试相对意图速度，再退化到 bodyId 定序的 ±UnitX（417）。Box2D 在完全重合时法线由 GJK 退化路径决定，行为更难预测 —— 你这里比 Box2D 更可控。

ResolvePlayerOccupancy vs Box2D 位置求解器

你用 70 行替换掉了 Box2D 的整个位置求解器。这是刻意的，而且方向选对了：

Box2D SolvePositionConstraints你的 ResolvePlayerOccupancy
分离量分配依据质量倒数 mA/mB（ContactSolver.cs:785-789）移动意图 —— 谁在推谁让位（420-465）
每次修正幅度Baumgarte 0.2，每轮消 20%一次性消 100%（308、439-464）
容差LinearSlop 0.005OccupancyEpsilon 0.0001

为什么必须自己写：所有玩家等质量（同密度同半径），Box2D 只会各退一半 —— 会出现「站着不动的人被推开」的反手感现象。而 Box2D 原生没有 per-contact 的权重钩子，PreSolve 能改 friction/restitution 但改不了位置求解的质量分配。这条路走不通，所以自己写是对的。

但有两个隐患 一、一次性消 100% 穿透。Box2D 用 Baumgarte 0.2 正是为了避免 overshoot （Settings.cs:77-80 注释：values close to 1 often lead to overshoot）。 3 个以上玩家互挤时会出现「弹开-再挤入」的往复抖动，4 次迭代不足以收敛。

二、OccupancyEpsilon 量纲混用。同一个常量在 305 行当距离平方阈值用（等效距离 0.01），在 309 行当长度阈值用（0.0001）， 402 行又是距离平方。两个语义相差 100 倍。当前不产生错误行为（都足够小）， 但是明确的维护陷阱 —— 建议拆成两个命名清晰的常量。

五、定点外壳 + float 内核的真实风险

你的文档里写着「gameplay 层定点、Box2D 内核仍为 float，是混合架构」。这个表述准确，但核实之后发现定点覆盖率比这句话给人的印象还要低。

Fixed64 实际只参与了一处运算

FrameSyncPhysicsWorld.cs
数据流 外部接口（IPhysicsSnapshotProvider） 全部 Fixed64 │ ├─ EnsureBody: (float)x, (float)y 68-69 ← 立刻转 float ├─ SetBodyMovementInput: (float)(dx * MoveSpeed) 144-145 ← 立刻转 float │ │ ┌──────────────────────────────────────────────┐ │ │ Box2D 内部：全程 float + Vector2 │ │ │ Island.cs:220 c += h * v │ │ └──────────────────────────────────────────────┘ │ └─ CaptureBodySnapshot: (Fixed64)position.X 237-241 ← 转回定点 唯一真正在定点域完成的运算： NormalizeInput → FixedMath.Sqrt(lenSq) 513
定点数外壳不提供跨平台一致性 它只保证「同一个 float 结果被量化到同一个 Fixed64」。如果两个平台的 float 计算本身分叉了， 量化只会把两个不同的值量化成两个不同的定点值 —— 甚至可能掩盖小于量化精度的分叉， 让你在测试中看不到问题，直到某次分歧被放大。

确定性要求定点贯穿整条计算链。任何一段 float 都是缺口。

逐项风险评估

风险源位置评级说明
Math.Sin / Math.CosRotation.cs:29-35当前安全libm 实现跨平台不保证逐位一致。本项目侥幸安全：FixedRotation=true 使角度恒为 0，sin(0)=0/cos(0)=1 精确。但 SetTransform 每次都会调它 —— 一旦引入旋转立刻成为缺口

为什么当前风险仍然是低的

回到第三章的结论：Box2D 在本项目实际执行的运算极少。

  • Island.cs:135：零重力零力 → v += 0
  • Island.cs:145-146：零阻尼 → v *= 1.0f / (1.0f + 0) = v *= 1.0f
  • Island.cs:220：c += h * v —— 一次乘加
  • 你自己的 sqrt 与除法（ResolvePlayerOccupancy）

这些全是 IEEE-754 严格定义的操作。风险低的原因依然是「功能被削减到极限」，不是「设计防住了」 —— 和第四章同一个模式。

未定论项：IL2CPP / HybridCLR 在各目标平台的 C++ 编译器是否开启了破坏 IEEE 一致性的浮点优化（FMA 合并、fast-math 类）。这决定上表第三行的实际等级，无法从 Box2D 源码断定，需查 Unity 的 IL2CPP 编译参数与工具链默认值并实机验证。

一个容易误判的细节

PhysicsBodySnapshot 提供了 float 参数的构造重载，内部做 (Fixed64) 转换。Fixed64 是 Q32.32，精度 2⁻³² ≈ 2.3e-10，远细于 float 在 [1,100) 区间的约 1e-5 精度 —— 所以 float → Fixed64 → float 往返在本项目量级下无损。

这一项本身安全，但它容易让人误以为快照是定点精度的。实际精度上限由源头的 float 决定，定点只是一个更细的容器。

七、面试怎么讲

可以主动讲的（有深度、可验证）

问：你的物理是怎么做确定性的？

不要答「用定点数保证确定性」。可以这样答：

「gameplay 层是 Fixed64，物理内核是 float 版 Box2DSharp，是混合架构。定点在物理这一层实际只覆盖了输入归一化， 进 Box2D 之前会转 float。之所以目前能保持一致，是因为我把 Box2D 的使用面压得很窄 —— 零重力、零阻尼、关掉玩家间碰撞，实际只用到按速度积分位置这一步乘加，都是 IEEE-754 严格定义的操作。 真正的风险在旋转：一旦引入非零角度就会走到 Math.Sin/Cos，那个跨平台不保证逐位一致。」
问：回滚的时候物理状态怎么恢复？

「body 的位置、速度、角速度、Awake、Enabled 全部入快照，恢复时重建整个世界。

但我知道这不是完备的 —— Box2D 有个跨帧状态叫 warm starting 累积冲量，存在 Contact.Manifold 上， 第 N 帧的求解结果依赖第 N-1 帧的冲量。这个字段是 internal，没有公开 API 能存取， 所以在 Box2D 上做严格 bit-exact 回滚本来是个难题。

我的项目目前不受影响，因为我用 GroupIndex=-1 关掉了所有碰撞，contact 从不产生，冲量字段从不被写入。 但这是绕过而不是解决 —— 如果加静态碰撞体，这一项会立刻变成 P0。届时我倾向直接关掉 warm starting， 用多几轮迭代换掉这个隐藏状态。」
问：玩家之间的碰撞怎么处理的？

「没用 Box2D 的碰撞响应，自己写了一套占位解算。原因是所有玩家等质量， Box2D 的位置求解器按质量倒数分摊分离量，只会各退一半 —— 会出现站着不动的人被推开的反手感现象。 而 Box2D 没有 per-contact 的权重钩子，PreSolve 改不了位置求解的分配。

所以我按移动意图分配：主动移动的一方吃满位移，双方都在推则按意图分量加权。 这是游戏手感规则不是物理规则。代价是我实际上替换掉了 Box2D 的整个位置求解器， 也因此必须自己用几何距离重建接触关系。」

不该说的

表述禁区
  • 不要说「用 Box2D 保证物理确定性」 —— Box2D 在这个项目里实际只做了一次乘加
  • 不要说「用定点数保证确定性」 —— 定点在物理层只覆盖了归一化那一步
  • 不要说「回滚是 bit-exact 的」 —— 当前成立，但成立的原因是碰撞被关掉了，不是设计防住了
  • 不要说「跨平台确定性已验证」 —— 只有单平台证据，IL2CPP 浮点优化未查
  • 不要把 12/8 说成调优结果 —— 当前配置下这两个参数不产生任何效果。如果当初是「调大点保险」，就直说调参经验
  • 不要说「用了 Box2D 的碰撞检测」 —— GroupIndex=-1 把它关了，接触关系是自己算的
一个通用的讲法策略 这个项目最有说服力的不是「我用对了 Box2D」，而是「我知道我用它的哪一小块、绕过了哪些问题、以及一旦扩展会激活什么」。
