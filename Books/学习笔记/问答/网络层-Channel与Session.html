网络层 · Channel 与 Session 的区别

来源：网络层一-TCP讲解.html ／ 命名空间：Fantasy.Network ／ 状态：✓ 完成

读 INetworkChannel 时卡住：接口里有 Session，Session 里又有 Channel，这俩到底什么关系？是同一个东西的两个名字吗？

2026-07-28 · 相关：Fantasy.Unity/Runtime/Core/Network/Session/Session.cs、Protocol/Interface/INetworkChannel.cs

线索

  • 一句话：Channel 管物理连接（怎么发字节），Session 管逻辑会话（发什么、谁接收、RPC 配对）
  • 这是「传输 vs 业务」的经典分层，不是同一物的两个名字
  • 互相持有 ≠ 同级：Session 持有 Channel 是 internal，Channel 反向持有 Session 是 public

核心理解

Channel 是传输层抽象，Session 是业务会话层。Channel 只懂「发字节」—— 它的 Send 签名 Send(uint rpcId, long address, MemoryStreamBuffer, IMessage, Type) 全是为打包服务的参数，没有任何业务语义，它不知道这条消息是什么、谁该处理。 Session 才懂「消息分发」和「RPC」：Session.Receive 交给调度器分发， Session.Call<T> 用 _rpcId + RequestCallback 实现「请求-响应配对」—— 这层逻辑 Channel 完全不参与。

分两层的真正理由是底下会换：同一个 Session，今天挂 TCPClientNetwork， 明天换 KCPClientNetwork，后天出 WebGL 换 WebSocketClientNetwork—— Session 一行代码都不用改。Channel 是可替换的传输插件，Session 是不动的业务外壳。

证据 —— 两者职责的对照

维度Channel（INetworkChannel）Session（Session）
是什么传输抽象（13 行最小契约）逻辑会话（继承 Entity）
对外方法只有 Send + DisposeSend / Call（RPC）/ Receive / Dispose
协议痕迹实现里有 socket、Pipe、SAEA（TCP 版 427 行）完全没有协议痕迹，底下换 TCP/KCP/WS 它都不动
谁持有谁反向持有 Session 属性（public）持有 Channel（internal，外部碰不到）

证据 —— 数据流向上各自的活

接收方向：Channel 交付字节，Session 负责分发

// Channel 这边：UnPack 凿出完整包，交付出去
UnPack 凿出完整包 → Session.Receive(packInfo)
                        ↓
                      // Session 这边：更新心跳 + 交给调度器分发
                      NetworkMessageScheduler.Scheduler(this, packInfo) → Handler

// 发送方向：Session 配 rpcId，Channel 负责发字节
session.Call<T>(request)  // Session 用 _rpcId + RequestCallback 配对 RPC
      → channel.Send(rpcId, address, ...)  // Channel 只管把字节发出去

对比表 —— 客户端的「一人分饰两角」

形态客户端服务端
Channel 实现Network 类自己就是 Channel（TCPClientNetwork : AClientNetwork, INetworkChannel）Network 和 Channel 分开（1 个 Network 管 N 个 Channel）
原因客户端只有一条连接，没必要再分层服务端要管多条连接，必须分层
Session始终独立——不管 Channel 是独立的还是合体的，Session 都是外面那层业务壳
可迁移的类比 「Channel vs Session」和这些是同一类思路：
• HttpClient（传输） vs HttpRequest（语义）
• TCP 里 socket（传输） vs connection（会话）
• 数据库 DbConnection（传输） vs DbTransaction（会话）
可见性不对称不是偶然 Session.Channel 是 internal（外部碰不到），INetworkChannel.Session 是 public。 这个不对称说明：业务代码应该只通过 Session 交互，Channel 是框架内部细节，不该被业务直接操作。 如果你发现业务代码在想办法拿 Channel，多半是分层用错了。
自测：为什么 INetworkChannel 和 Session 要互相持有？

接收方向需要 Channel → Session（Channel 收到字节后要回调 Session.Receive 分发）；发送方向需要 Session → Channel（Session.Send 要转调 Channel.Send 发字节）。去掉任一方向，数据流就断了。互相持有是因为数据是双向流动的。

自测：新增一个 QUIC 传输层，需要改 Session 类吗？

不需要。只需新增 QUICClientNetwork : AClientNetwork, INetworkChannel 实现传输细节，Session 一行不改。这正是分层抽象的价值——传输层是可插拔的。需要改的只有协议选择处（如 GameClient.cs 里写死 NetworkProtocolType 的地方）。
