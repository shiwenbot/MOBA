Channel 和 Session 到底什么关系？互相持有，各自具体干什么？

2026-07-28 · 相关：Network/Session/Session.cs、Protocol/Interface/INetworkChannel.cs、Protocol/Interface/AClientNetwork.cs

线索

  • 一句话：Channel 管传输（怎么发字节），Session 管会话（发什么、谁接收、RPC 配对）
  • 方法数量不对称就是分层最硬的证据：Channel 接口只有 1 个 Send，Session 有 5 个 Send + 1 个 Call
  • 业务层的多种发送语义，全被 Session 翻译成 Channel 那同一个底层调用
  • 互相持有 ≠ 同级：Session.Channel 是 internal，INetworkChannel.Session 是 public

核心理解

Channel 是传输层抽象，Session 是业务会话层。Session 的 5 个 Send 重载按「数据是未打包还是已打包」分两大类： 未打包的是业务层最常用的入口（发消息、发 RPC），已打包的是服务端「零序列化转发」用的。 无论哪个重载，最后都汇成一个调用：Channel.Send(rpcId, address, memoryStream, message, messageType)。 Channel 这一个签名要应付 TCP/KCP/WebSocket 三种协议，但发送策略各不相同——TCP 要自己排队串行化，KCP 直接交给 KCP 内部队列。

分两层的真正理由是底下会换：同一个 Session，今天挂 TCPClientNetwork，明天换 KCPClientNetwork， 后天出 WebGL 换 WebSocketClientNetwork——Session 一行代码都不用改。Channel 是可替换的传输插件，Session 是不动的业务外壳。

证据 1 —— Session 的 5 种发送方式

按「未打包 / 已打包」分两大类（Session.cs:101-202）

// ===== A. 未打包：业务层最常用，客户端服务端都能用 =====

// Send 4：非泛型，手动传 Type
public virtual void Send(IMessage message, Type messageType, uint rpcId = 0, long address = 0)
    → Channel.Send(rpcId, address, null, message, messageType);   // memoryStream 传 null

// Send 5：泛型，自动推断 Type（最常用）
public virtual void Send<T>(T message, uint rpcId = 0, long address = 0)
    → Channel.Send(rpcId, address, null, message, typeof(T));

// Call<T>：RPC，要回包（Session.cs:210）
public virtual FTask<IResponse> Call<T>(T request, long address = 0)
{
    var rpcId = ++_rpcId;                          // ① 取唯一序号
    var task = FTask<IResponse>.Create();
    RequestCallback.Add(rpcId, task);              // ② 存进字典，等响应来配对
    Send<T>(request, rpcId, address);             // ③ 走 Send 5 把 rpcId 塞进包头
    return task;                                // ④ 返回，await 它等回包
}

// ===== B. 已打包：服务端框架内部转发用，全包在 #if FANTASY_NET 里 =====

// Send 1：转发 APackInfo（不释放，调用方负责）
public virtual void Send(uint rpcId, long address, Type messageType, APackInfo packInfo)
    → Channel.Send(rpcId, address, packInfo.MemoryStream, null, messageType);

// Send 2：转发 ProcessPackInfo（自己 using 释放）
public virtual void Send(ProcessPackInfo packInfo, uint rpcId = 0, long address = 0)
    → using (packInfo) { Channel.Send(rpcId, address, packInfo.MemoryStream, null, ...); }

// Send 3：转发裸 MemoryStream
public virtual void Send(MemoryStreamBuffer memoryStream, uint rpcId = 0, long address = 0)
    → Channel.Send(rpcId, address, memoryStream, null, null);

引用：Session.cs:178-202（A 类，公共）、:101-144（B 类，#if FANTASY_NET）、:210-222（Call）。RPC 响应配对在 ProcessScheduler.cs 的 ResponseHandler 里完成——按包头 rpcId 从字典取出 Task 调 SetResult。服务端为什么要 B 类那么多转发重载？因为它是「消息中转站」——从客户端 A 收进的消息可能要原样转给 map 进程再转给客户端 B，每转一次都反序列化再序列化是白烧 CPU，所以传 memoryStream（已序列化好的字节）只回填包头里的 rpcId/address 就直接发，零序列化转发。

证据 2 —— Session 的两种形态

形态类用在哪Send 最终调什么
普通会话 Session（基类） 客户端连接、服务端外网连接 Channel.Send（走 socket）
进程内会话 ProcessSession : Session（sealed） 服务端进程内派发（#if FANTASY_NET） 绕过 Channel，直接 this.Scheduler(...) 进程内派发
ProcessSession 禁用了两个方法 ProcessSession.Send(MemoryStreamBuffer, ...) 和 Call<T> 都被 override 成 throw new Exception("不支持")（ProcessSession.cs:66,71）。原因：进程内派发不需要 RPC 配对走网络——响应在同一个进程里直接 ResponseHandler 就完成了，根本不需要 Call 那套「发包-等回包」机制。

证据 3 —— Channel 的 1 个签名，3 种发送策略

接口只有一个签名，但入队之后因协议差异巨大：

协议发送机制自建队列？为什么
TCP（客户端/服务端） SocketAsyncEventArgs 事件链 + _isSending 单飞 有 _sendBuffers socket 不能并发 SendAsync，必须串行化
WebSocket 服务端 SendAsync await 有 _sendBuffers 同理
KCP 直接 Kcp.Send 无 KCP 内部已有可靠传输+发送队列，Channel 层不用再造

引用：TCPClientNetwork.cs:333-375（TCP，有队列）、KCPClientNetwork.cs:571（KCP，无自建队列，靠 KCP 内部）。这个差异被 Channel 接口屏蔽了——Session 调的都是同一个 Channel.Send，底下 TCP 要排队还是 KCP 直扔，Session 完全不感知。

证据 4 —— 客户端的「一人分饰两角」

形态客户端服务端
Channel 实现Network 类自己就是 Channel（TCPClientNetwork : AClientNetwork, INetworkChannel）Network 和 Channel 分开（1 个 Network 管 N 个 Channel）
原因客户端只有一条连接，没必要再分层服务端要管多条连接，必须分层
Session始终独立——不管 Channel 是独立的还是合体的，Session 都是外面那层业务壳

证据 5 —— address 参数：客户端恒为 0，服务端才用

  • 客户端：用 Outer 协议，包头不含 address，传 0 被丢弃。所以 session.Send(msg) 从不传 address。
  • 服务端间：用 Inner 协议，包头 20 字节含 address，用于进程间路由（把消息送到正确的 gate/map 进程）。服务端转发时 address 才是必须的。

引用：ReadOnlyMemoryPacketParser.cs 的 InnerReadOnlyMemoryPacketParser（写 address）vs OuterReadOnlyMemoryPacketParser（忽略 address）。

数据流向：各自干什么的活

接收方向：Channel 交付字节，Session 负责分发

// Channel 这边：UnPack 凿出完整包，交付出去
UnPack 凿出完整包 → Session.Receive(packInfo)
                        ↓
                      // Session 这边：更新心跳 + 交给调度器分发
                      NetworkMessageScheduler.Scheduler(this, packInfo) → Handler

// 发送方向：Session 配 rpcId，Channel 负责发字节
session.Call<T>(request)  // Session 用 _rpcId + RequestCallback 配对 RPC
      → channel.Send(rpcId, address, ...)  // Channel 只管把字节发出去

引用：Session.cs:42（Channel 属性，internal）、:210（Call）、:224（Receive）；INetworkChannel.cs（13 行全文，Session 属性 public）。

「5 种发送」对应「5 种业务语义」 不要被 5 个重载吓到。它们本质只对应几种业务诉求：
• 发普通消息 → Send<T>
• 发 RPC 要回包 → Call<T>
• 服务端转发收到的消息（不重新序列化）→ Send 1/2/3（带 memoryStream/packInfo）
客户端只会用到前两种，后三种是服务端框架内部的转发优化。
可见性不对称不是偶然 Session.Channel 是 internal（外部碰不到），INetworkChannel.Session 是 public。 这个不对称说明：业务代码应该只通过 Session 交互，Channel 是框架内部细节，不该被业务直接操作。 如果你发现业务代码在想办法拿 Channel，多半是分层用错了。
可迁移的类比 「Channel vs Session」和这些是同一类思路：
• HttpClient（传输） vs HttpRequest（语义）
• TCP 里 socket（传输） vs connection（会话）
• 数据库 DbConnection（传输） vs DbTransaction（会话）
自测：为什么 Channel 接口只有 1 个 Send，Session 却有 5 个？

因为它们在不同抽象层。Session 是业务层，要表达「发消息/发 RPC/转发已打包数据」等多种业务语义；Channel 是传输层，只关心「把字节发出去」，所以一个签名够用。Session 的每个重载都把不同的业务语义翻译成同一个 Channel.Send 调用——这正是分层抽象的意义：业务层的复杂语义在传输层被归一化。

自测：为什么 KCP 的 Channel 不需要 _sendBuffers 队列，TCP 却需要？

因为 KCP 协议内部已经有可靠传输 + 发送队列，调一次 Kcp.Send 数据就进了 KCP 的发送缓冲，由 KCP 的 update 循环负责分包、重传、拥塞控制。而 TCP socket 不能并发 SendAsync（会乱序或异常），所以 TCP 的 Channel 必须自己用 _sendBuffers + _isSending 把多次业务调用串行化成一次次的 socket 发送。这个差异被 Channel 接口屏蔽了——Session 调的都是同一个 Channel.Send。

自测：客户端代码里 address 参数为什么总是 0？

因为客户端用的是 Outer 协议（NetworkTarget.Client），OuterReadOnlyMemoryPacketParser 的包头里根本没有 address 字段，传进去也会被忽略。address 是 Inner 协议（服务端间通信）才用的，表示「目标 Scene/进程的地址」，用于把消息路由到正确的服务器。客户端的连接对象只有一个服务端，不需要路由，所以 address 恒为 0。

自测：为什么 INetworkChannel 和 Session 要互相持有？

接收方向需要 Channel → Session（Channel 收到字节后要回调 Session.Receive 分发）；发送方向需要 Session → Channel（Session.Send 要转调 Channel.Send 发字节）。去掉任一方向，数据流就断了。互相持有是因为数据是双向流动的。

自测：新增一个 QUIC 传输层，需要改 Session 类吗？

不需要。只需新增 QUICClientNetwork : AClientNetwork, INetworkChannel 实现传输细节，Session 一行不改。这正是分层抽象的价值——传输层是可插拔的。需要改的只有协议选择处（如 GameClient.cs 里写死 NetworkProtocolType 的地方）。

AClientNetwork 只有 37 行还都是壳，到底为什么存在？读不出逻辑啊

2026-07-28 · 相关：Protocol/Interface/AClientNetwork.cs、ANetwork.cs、TCP/Client/TCPClientNetwork.cs

线索

  • 读这种「空壳类」不能逐行读，要读它通过继承关系强制了什么
  • 它同时继承 ANetwork 又实现 INetworkChannel——客户端「一人分饰两角」的代码落点
  • 它只有 Dispose 一处有"逻辑"，那是在定销毁顺序
  • 抽象基类的价值不在"干了什么"，而在"约束了什么"

核心理解

AClientNetwork 不是"没逻辑"，而是把"客户端形态"的共性约束固化在继承链里，让 TCP/KCP/WebSocket 三个具体子类不用重复写。 它的存在解决三个矛盾：(1) 客户端既要"是 Network"又要"是 Channel"（一人分饰两角）； (2) Session 属性该挂在哪一层（只有客户端形态才需要持有 Session，监听器不该有）； (3) Dispose 的级联顺序（先断会话、再释放传输资源，不能反）。 它是约束声明，不是实现。

证据 1 —— 它在继承链里的位置

Entity                    // Fantasy 实体基类
  └─ ANetwork             // 共享设施（消息调度器、对象池、三个身份标识）
      └─ AClientNetwork   // ← 你问的这个（37 行壳）
          ├─ TCPClientNetwork      // 真正的实现（427 行）
          ├─ KCPClientNetwork
          └─ WebSocketClientNetwork

关键那行：AClientNetwork : ANetwork, INetworkChannel（AClientNetwork.cs:15）——同时继承 Network 又实现 Channel。这就是教材说的「客户端的 Network 自己就是 Channel」的代码落点。

证据 2 —— 它解的三个矛盾

矛盾 1：客户端既要"是 Network"又要"是 Channel"

服务端的 ANetwork（监听器）和 INetworkChannel（连接）是分开的两个类——一个端口监听器管 N 条连接，Network : Channel = 1 : N。但客户端只有一条连接，没必要分。所以 AClientNetwork 同时继承两者，让一个对象同时扮演 Network 和 Channel 两个角色。

矛盾 2：Session 该挂在谁身上？

INetworkChannel 接口要求实现 Session 属性（Channel 要反向持有 Session）。但放哪儿合适？

  • 写在 TCPClientNetwork？那 KCP/WS 三份实现各写一遍，重复
  • 写在 ANetwork？但服务端的 ANetwork（监听器）根本不该有 Session——监听器管的是端口，不是会话

所以放在中间的 AClientNetwork 里——只有客户端形态才需要持有 Session。这就是 Session 属性在 :18 行的原因。

矛盾 3：Dispose 的级联顺序（全类唯一有"逻辑"的地方）

AClientNetwork.cs:21-36 —— 销毁顺序：先断会话，再释放传输资源

public override void Dispose()
{
    IsInit = false;
    if (Session != null)
    {
        if (!Session.IsDisposed) Session.Dispose();  // 先销毁 Session
        Session = null;
    }
    base.Dispose();  // 再销毁基类（ANetwork 的对象池等）
}

这个顺序不能反——Session.Dispose 内部会触发 OnDispose（连着 channel.Dispose），如果先释放传输资源再销毁 Session，Session 想发最后的断开包就发不出去了。先断会话、再放资源是网络代码的通用纪律。

证据 3 —— Connect 和 Send 为什么是 abstract

public abstract Session Connect(...);     // :19
public abstract void Send(...);           // :20

这两个方法是纯契约，AClientNetwork 自己不知道怎么连、怎么发——TCP 用 Socket.ConnectAsync，KCP 用握手协议，WebSocket 用 ClientWebSocket.ConnectAsync，完全不同。所以留给子类实现。AClientNetwork 只负责把"客户端"这个身份的共性抽出来：有 Session、只能 Connect 一次（IsInit 标志）、Dispose 要级联。

对照表 —— 客户端 vs 服务端的形态差异

维度客户端（AClientNetwork）服务端（ANetworkServerChannel）
Network 和 Channel合一：AClientNetwork : ANetwork, INetworkChannel分离：ANetworkServerChannel : INetworkChannel（不继承 ANetwork）
数量关系1 个对象 = 1 个 socket = 1 个 Session1 个 ANetwork（监听器）: N 个 Channel = N 个 Session
Session 创建时机Connect 成功后（TCPClientNetwork.cs:154）Channel 构造时就建好（ANetworkServerChannel.cs:39）
Session 持有方直接放在 AClientNetwork 上放在独立的 ANetworkServerChannel 上
怎么读"空壳抽象基类" 读这种代码时，别问"它干了什么"，要问"它通过继承关系强制了什么"。三件事值得看： (1) 它继承谁、实现谁——这决定了它在形态分类里的位置；(2) 它把哪些成员从子类"上提"到这一层——那些是三个子类的共性，提上来避免重复； (3) 它的 abstract 方法——那是它故意不实现的部分，意味着"这块三种协议各不相同，留给子类"。抽象基类的价值是约束，不是实现。
自测：为什么 Session 属性不放在 ANetwork（更上层）里？

因为 ANetwork 同时是服务端监听器的基类，而监听器管的是端口，不是会话——一个监听器下面有 N 条连接、N 个 Session，把单个 Session 属性放监听器上语义就错了。Session 是"一条连接"的属性，只有客户端形态（合一）和 Channel 形态（每条一个）才该持有。所以放在 AClientNetwork 这一中间层最合适。

自测：为什么 Dispose 要先销毁 Session 再调 base.Dispose？反过来会怎样？

Session.Dispose 内部触发 OnDispose 委托（连着 channel.Dispose），Session 在销毁过程中可能还要通过 Channel 发最后的断开/清理包。如果先 base.Dispose（释放了 socket、清空了对象池），Session 再想发就发不出去了，甚至可能踩到已释放的资源。先断会话、再放资源是网络代码的通用纪律，和"先停业务、再关连接"一个道理。

自测：Connect 和 Send 为什么是 abstract 而不是 virtual 给默认实现？

因为 TCP/KCP/WebSocket 三种协议的连接和发送机制完全不同：TCP 用 Socket.ConnectAsync + SocketAsyncEventArgs，KCP 用握手协议 + Kcp.Send，WebSocket 用 ClientWebSocket.ConnectAsync + SendAsync。没有"默认实现"可以给——任何默认实现都只对一种协议成立。所以用 abstract 强制每个子类必须自己实现，承认这一层没有共性可提取。
