求解器「算了 8 轮」到底是累加 8 次，还是以当前帧为基础值算 8 次？

2026-07-29 · 相关：ContactSolver.cs:402-408、Testbed Stacking → Pyramid 实验

线索

  • 「帧」和「迭代」是两个不同颗粒度——迭代在帧内部
  • 8 轮迭代之间是 in-place 更新，不是累加；但有「累积冲量」这个量是真累加
  • Vel Iters=1 为什么塔会塌（warm starting 关掉时）

核心理解

答案是迭代收敛，不是累加。「算了 8 轮」= 同一个问题（接触冲量该多大）反复用上一轮算完的最新状态当初值重新算，向稳定解逼近，直到收敛。这是 Gauss-Seidel 的 in-place 更新特性。

颗粒度要分清：帧 / Step 是画面动一次（World.Step），迭代是帧内部把所有接触点扫一遍。Vel Iters=8 表示这一帧里扫 8 遍，不是 8 帧。迭代对画面不可见——它改的是求解器临时数组 _velocities[]，全跑完才写回 body。类比拍照：按快门前的对焦测光去噪（迭代）看不见，只看到成片（一帧）。

容易混的地方：有一个量确实在累加——NormalImpulse（累积冲量）。它是内部「账本」，存「这帧总共给了多少」，为钳制（max(x,0) 只推不拉）和 warm starting 跨帧复用服务。但真正推动物体的是增量 lambda（累积值的差分），不是累积值本身。所以物理结果（速度、位置）是收敛出来的，不是加出来的——「累加感」只来自累积冲量这个账本。

「基础值」其实有两层：① 帧开始时 = 上一帧的速度 + warm starting 的累积冲量（跨帧种子）；② 帧内每轮迭代时 = 上一轮算完的速度和冲量。8 轮迭代对应第 ② 层。一句话：不是分 8 份加起来，是同一个问题反复用上轮结果当初值，直到收敛。

实验印证（Testbed，warm starting 关掉）

Stacking → Pyramid 场景，关 WarmStarting，把 Vel Iters 从 8 调到 1：塔直接塌下来。 这是「迭代不足」最干净的可视化——剥离了跨帧累积变量，只剩纯粹的「一轮够不够」问题，答案是不够。

为什么塌：求解器每轮按 ①地面-A → ②A-B → ③B-C 顺序扫。解 ① 时 A 的速度还没反映 B、C 压在上面（②③ 尚未解），于是地面给 A 的冲量 偏小，抵消不了三层重力。Vel=1 扫过就停，这个偏小冲量定在那不动 → 这一帧重力没被抵消干净 → 箱子下沉 → 每帧都欠一点 → 累积成塌。把 Vel Iters 从 1 一档档拖回 8，能肉眼看塔一点点「硬」起来，冲量向真实值收敛。

对比：同样的 Vel=1，WarmStarting 开着时症状是箱子像弹球一样乱飞而非软塌——一轮 over-correct 出的偏大冲量被 warm starting 跨帧复用、不做钳制地放大，能量凭空增长。关掉它才显出「纯迭代不足 = 冲量给少了」的真面目。

证据

ContactSolver.cs:402-408 —— 钳累积值，施加增量

vn = dot(dv, normal);
lambda = -vcp.NormalMass * (vn - vcp.VelocityBias);

newImpulse = Math.Max(vcp.NormalImpulse + lambda, 0.0f);  // 钳「累积值」
lambda     = newImpulse - vcp.NormalImpulse;              // 反解实际增量
vcp.NormalImpulse = newImpulse;

vcp.NormalImpulse + lambda = 累加（账本）；真正施加到速度的是反解出的 lambda（增量）。源码注释（:439-440）： the iterative nature of the solver which only requires that the accumulated impulse is clamped and not the incremental impulse。 官方推荐值 Vel Iters=8 / Pos Iters=3（test/Testbed.Abstractions/TestSettings.cs:19-20）。

一句话 「以当前帧为基础值算了 8 轮」——对，但要精确：帧内部每轮以上一轮输出为初值反复算，向稳定解收敛。累加只发生在累积冲量这个内部账本上（为钳制和 warm starting 服务），推动物体的是它的差分。

为什么「单位尺度」是第一个必须知道的坑？

2026-07-30 · 相关：src/Common/Settings.cs:11,29,36-47,67,80

线索

  • Box2D 的内部容差全部假设 1 单位 = 1 米写死了（MKS）
  • 钥匙：LinearSlop 的「双重要求」
  • 尺寸太大 / 太小，崩法相反——而且症状都不像尺度问题

核心理解

整个库的容差常量都以「米」为量纲硬编码。核心是 LinearSlop = 0.005 米，它被设计成必须同时满足两个相反的要求：数值上显著（不能被浮点误差淹没，否则求解器分不清接触了没、会抖）和视觉上不显著（不能大到肉眼看到缝）。

这两个要求同时成立的唯一条件，就是物体尺寸在米量级：物体 1 米时，0.005 相对它是 0.5%（看不见）且本身足够大（浮点误差 ~1e-7 淹不掉）。一旦偏离米制，两个要求就一起崩。

尺寸太大（典型：用像素当单位，角色 50 单位）：① LinearSlop 相对变得无意义（万分之一），临界状态反复抖；② -9.8 作用在"50 米角色"上像慢动作，人会去调重力到 -300 掉进下一个坑；③ MaxTranslation=2.0 变致命钳制——"每帧 5 像素"被理解成"每帧 5 米"，跑快被静默限速，不报错。

尺寸太小（典型：0.05 单位的小弹珠）：① PolygonRadius=0.01 占体积 20%，方块间有肉眼可见的缝；② LinearSlop 占 10%，明显互嵌；③ 最阴险——PolygonShape.Set 焊接距离平方小于 (0.5*LinearSlop)² 的顶点，小物体顶点被直接焊掉，形状静默退化。

反推的安全区间：0.1 ~ 10 米（弹珠到卡车，Box2D 就是按这个调的）。正确做法不是改 LengthUnitsPerMeter（它是 const，且派生常量是乘法链、相对关系精心调过），而是物理世界用米、渲染时乘缩放系数：screenPos = physicsPos * 32f。Unity 默认单位就是米，不乱缩放天然对齐。

证据

Settings.cs —— 核心常量（全部 × LengthUnitsPerMeter，即 × 米）

⚠️ 为什么是「第一个」坑 尺度错误的症状（抖动、穿透、堆不稳、重力手感不对、速度被限）看起来都不像尺度问题——你会去调迭代次数、调 Baumgarte、调重力，全治不了根。它是唯一一个「一开始定错、后面全部要重做」的决策，所以必须在写第一行代码前搞定。

Box2D 为什么是 World / Body / Fixture / Shape 四层，不是两层？

2026-07-30 · 相关：src/Dynamics/Fixture.cs:13-17、src/Dynamics/Body.cs

线索

  • 新手直觉：「直接给 Body 一个形状不就行了？」——为什么要中间夹个 Fixture
  • Shape 管几何，Fixture 管「几何 + 装在谁身上 + 表面性质」
  • 分离是为了让 Shape 可复用

核心理解

一个箱子被拆成四个零件，像搭积木：World（舞台：重力、Step、谁和谁碰）→ Body（一个「东西」：在哪、速度、多重，但没有形状）→ Fixture（给 Body 装的装备：把 Shape 钉在 Body 上 + 表面性质）→ Shape（纯几何，可脱离世界单独存在）。

为什么不直接 Body + Shape 两层：因为形状和表面性质是两件事，要分开。Shape 只管「长什么样」（一个半径 0.5 的圆），Fixture 管「这个圆装在谁身上、摩擦多少、弹力多少、是不是 sensor」。分开的收益是 同一个 Shape 可被多个 Fixture 共享复用——100 个一样的球只存一份几何，但各有独立的摩擦弹力。源码里 Fixture.Create 会 Shape = def.Shape.Clone()（Fixture.cs:118），所以传进来的 Shape 是被拷贝的，可以是临时对象、可以复用。

最直白的链路：World → Body → (Shape + FixtureDef) → Fixture 装到 Body 上。Body 在被装上 Fixture 之前，它不知道自己是圆是方。

证据

Fixture.cs:13-17 —— 这层存在的理由（类头注释）

A fixture is used to attach a shape to a body for collision detection.
A fixture inherits its transform from its parent.
Fixtures hold additional non-geometric data such as friction, collision filters, etc.
@warning you cannot reuse fixtures.

建立四层对象的伪代码

World world = new World(gravity);            // 1. 搭舞台

Body body = world.CreateBody(bodyDef);       // 2. 造个东西
bodyDef.BodyType = Dynamic;                  //    告诉它「你会动」

PolygonShape shape = new PolygonShape();     // 3. 画个形状
shape.SetAsBox(0.5f, 0.5f);                  //    1×1 方块

FixtureDef fd = new FixtureDef();            // 4. 配装备
fd.Shape = shape;
fd.Density = 1.0f;  fd.Friction = 0.3f;
fixture = body.CreateFixture(fd);            //    装上去 → body 这才有形状

引用：Fixture.cs:13-17,118；BodyType 默认值见 Body.cs:73（默认 Static）。

一句话 World 管全局调度，Body 管运动身份证（但无形状），Fixture 把 Shape 钉到 Body 上并带上表面性质，Shape 是纯几何可复用。夹一层 Fixture 的唯一理由：形状和表面性质是两件事，分开才能复用几何。

三种 BodyType 各是干嘛？默认是 Static 这个坑？island 种子、CCD 又是啥？

2026-07-30 · 相关：Body.cs:14-17,73,336-395,1214-1220

线索

  • Static = 环境、Kinematic = 自走平台、Dynamic = 真物体
  • 碰撞至少要一个 Dynamic；不显式设 BodyType 默认是 Static（静默失效，不报错）
  • 两个术语：island 种子 = 分岛算法的起点；CCD = 连续碰撞检测，防高速穿墙

核心理解

源码注释（Body.cs:14-17）是最好的一手定义： Static（质量零、速度恒零、只能手动搬，用于墙/地面/台面边框）、 Kinematic（质量零、速度你设、引擎按你设的速度推它走，用于移动平台/传送带/旋转搅拌器）、 Dynamic（质量正、受重力/力、能被冲量推动，球/箱子/玩家，90% 用这个）。

关键规则：碰撞至少要有一个 Dynamic。源码 Body.cs:1214-1220 的 ShouldCollide 第一句就是 if (_type != DynamicBody && other._type != DynamicBody) return false;。 所以 Dynamic↔任何都碰；Static↔Static、Static↔Kinematic、Kinematic↔Kinematic 全部不碰。两个 Kinematic 平台互穿。

第一个必踩的坑：默认是 Static。BodyDef.BodyType 默认 StaticBody（Body.cs:73，枚举 0 值）。 不显式设，物体不会掉落，而且不报任何错——你会以为重力设错了、World 坏了，其实是 Static 不受重力。典型 debug 盲区。

两个术语澄清（它们是第七、八章内容，这里只为看懂行为对照表）：

  • island（岛）种子：Box2D 求解前先把「互相接触/连着」的物体分成一组组（岛），从某个物体开始顺着接触关系往外爬。 这个起点物体叫「种子」。Static 不传播岛（否则地面会把全场站着的物体连成一个巨型岛），所以只有 Kinematic/Dynamic 能当种子。
  • CCD（Continuous Collision Detection，连续碰撞检测）：防止高速物体「穿墙」——一帧移动 5 米、墙只有 0.1 米厚时， 帧间会跳过墙，引擎插值出帧内轨迹来检测。Dynamic 默认不开 CCD（贵），只有打 IsBullet=true 才开；Static/Kinematic 总有。

行为对照 Static=环境（墙/地面，手动搬）｜Kinematic=自走平台（你设速度，引擎推着走）｜Dynamic=真物体（受力受重力，90% 用这个）。碰撞至少要一个 Dynamic；默认 Static 是静默坑。island 种子=分岛起点，CCD=防高速穿墙（Dynamic 要打 IsBullet）。

四种 Shape 各是什么？怎么选？

2026-07-30 · 相关：src/Collision/Shapes/{Circle,Polygon,Edge,Chain}Shape.cs

线索

  • Circle=圆 / Polygon=凸多边形(≤8顶点) / Edge=线段 / Chain=折线地形
  • SetAsBox(hx,hy) 参数是半宽半高 —— SetAsBox(1,1) 建的是 2×2
  • Chain 内部就是一串 EdgeShape，靠幽灵顶点让接缝不绊物体

核心理解

四种 Shape 一句话：CircleShape（一个圆，Radius 默认 0 要自己设，是唯一能直接设 Radius 的）；PolygonShape（凸多边形，必须凸、顶点 ≤ 8，SetAsBox 参数是半宽半高）；EdgeShape（单线段，无内部、TestPoint 恒 false、零质量，双面或单面）；ChainShape（折线/闭环地形，单面碰撞、不能自相交）。

弹球项目怎么选：球用 CircleShape；方形挡板/台面边框用 PolygonShape + SetAsBox；直线斜坡用 EdgeShape；曲线地形用 ChainShape。

ChainShape 的内部实现：它就是一串 EdgeShape 的集合。GetChildEdge（ChainShape.cs:124-137）取出的每段 EdgeShape 恒为 OneSided = true，且 Vertex0/Vertex3（幽灵顶点）从相邻段自动取。这正是为什么物体滑过 ChainShape 接缝不会被「绊住」——每段都知道自己的邻居在哪。

ChildCount：Circle/Polygon/Edge 都是 1，只有 ChainShape 是 Count - 1（点数减 1 = 线段数）。因为内部是 N-1 个 EdgeShape，碰撞检测时要遍历 child。

质量从哪来？为什么运行时改 Density 不生效？

2026-07-30 · 相关：Body.cs:997,1042-1106、Fixture.cs:36,222-225

线索

  • 质量 = 密度 × 几何，Body 累加所有 Fixture；不是你直接给的
  • Static/Kinematic 质量恒 0；Density=0 的 Fixture 不贡献质量但仍参与碰撞；FixedRotation 靠惯量置零
  • 坑：ResetMassData 在 0.6 是 private，运行时改 Density 质量不变 → 用 SetMassData 绕过

核心理解

质量链路：Fixture.Density + Shape 几何 → Shape.ComputeMass → Fixture.GetMassData → Body.ResetMassData 累加所有 Fixture → _mass/InvMass/_inertia。即质量是密度和形状算出来的，Body 把身上所有 Fixture 的质量加起来。

三个关键行为（对着 Body.cs:1042-1106）：① Static/Kinematic 在 :1052-1059 直接 return，质量恒 0；② Density==0 的 Fixture 在 :1067-1070 被 continue 跳过——仍参与碰撞（Shape 还在），只是不贡献质量（静态体 fixture 通常这么建）；③ FixedRotation 不是开关挡旋转，而是把 _inertia=0（:1092-1096），所有角速度增量被乘 0 抹掉。

0.6 的坑：运行时改 Density 不生效。Fixture.Density 注释（Fixture.cs:36）写着「要调 b2Body::ResetMassData 更新质量」，但 Body.ResetMassData 在 0.6 是 private（Body.cs:1042），你调不到。质量重算只在四个内部时机自动发生：切 BodyType、切 IsFixedRotation、CreateFixture（density>0）、DestroyFixture。运行时改 Density，质量纹丝不动。

绕过方案：用 public 的 SetMassData（Body.cs:997）直接给定质量数据，绕开 density 链路：body.SetMassData(new MassData { Mass = 2.0f, ... })。弹球项目里不同材质的球，运行时换质量别动 Density，用 SetMassData；或一开始就建好不同 density 的 fixture。

  • 更新之后：move buffer 里的物体去查树 → 产出 pair → 创建 Contact → 每帧 Collide 算真实几何

核心理解

动态 AABB 树解决「几千个会动的 AABB 如何快速查重叠」。它是一棵二叉树，每个节点装一个 AABB：叶子装真实物体，内部节点装「包住它两个孩子的框」。从根往下查时，和某子树不重叠就整棵剪掉 → 查询 O(log n) 而非 O(n²)。

物体在动怎么不崩：三机制配合。① 物体进树时存的不是真实框，而是故意做大的 fatAABB（四周各 +AABBExtension=0.1）；② 每帧 MoveProxy 检查物体还在不在胖框里——在、且没大得离谱就 return false，树完全不动（源码 :176-189）；③ 只有 return true（真需要更新）的物体才进 moveBuffer，每帧只遍历 move buffer 去查树配对。收益：静止和小幅运动的物体几乎零开销——这就是 1000 个静止箱子不耗 CPU 的原因。

还有个 AABBMultiplier=4.0（:154-171）：把这一帧位移 ×4 朝运动方向单向拉伸胖框，预测未来几帧位置（单向是因为反方向物体不会去，拉了浪费体积）。CreateProxy（首次进树，无位移）只用 AABBExtension；MoveProxy（已知位移）两者都用。

更新之后发生什么（完整链条）：物体动了 → MoveProxy 判定 → 不在胖框里 → 更新树 + 进 move buffer → UpdatePairs 用胖框查树产出 pair（注意：用胖框查，所以会多报）→ pair 经同body/重复/过滤检查后创建 Contact → Contact 每帧被 Collide 算真实几何 → 真碰了 IsTouching=true 进求解，没碰 IsTouching=false 挂着。

Contact 存在 ≠ 正在接触——为什么场上会有一批「幽灵 Contact」？

2026-07-30 · 相关：ContactManager.cs:289-294、Contact.cs:298

线索

  • 两个「碰」：fatAABB 重叠决定 Contact 在不在；真实形状决定 IsTouching
  • 单向包含：真碰 → 胖框必重叠；但胖框重叠 → 真形状不一定碰
  • 因为胖框比真形状大 0.1，场上常态有「挂着但没真碰」的幽灵 Contact

核心理解

「碰」这个词太模糊，Box2D 里其实是两个不同判定：① fatAABB 重叠（胖框比真形状大 0.1）决定 Contact 对象是否存在；② 真实形状接触（窄相位 Manifold.PointCount>0）决定 IsTouching。两者单向包含：真碰了胖框必重叠（真形状在胖框里），但胖框重叠真形状不一定碰。

后果：场上会常态存在一批 IsTouching == false 的「幽灵 Contact」——它们只是「胖框碰上了，真实形状还差一点」。这批每帧跑窄相位算真实几何，但不参与求解、不触发 BeginContact/EndContact，是「预备役」，等真碰了才激活。

为什么不销毁它们：留着养着有持续窄相位开销；但「没真碰就销毁、真碰再建」会让物体反复轻微分离/接触时 Contact 反复建销（对象池 churn + 线性去重扫描），反而更贵。Box2D 选前者——宁可养预备役也不反复建销。

影响写代码两处：① BeginContact/EndContact 只在 IsTouching 跃变时触发（上一帧没碰+这帧碰了），不是「Contact 创建=BeginContact」——球靠近墙（幽灵 Contact 存在）时不会触发，要等真碰；② 求解器只碰 IsTouching==true 的 Contact，幽灵 Contact 不进 island（第七章）。

touching = Manifold.PointCount > 0;   // 真实几何有没有接触点

一句话 两个「碰」：fatAABB 重叠决定 Contact 在不在，真实形状决定 IsTouching。胖框比真形状大 0.1，所以场上常态有一批「挂着但没真碰」的幽灵 Contact，不求解不触发事件，只为避免反复建销。BeginContact 只在 IsTouching 跃变时触发，监听它判断「球撞墙」是对的。
