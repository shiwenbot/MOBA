# 断线重连最小版（S9）验收测试指南

对应计划：`Plan/Gameplay状态同步演示/S9-断线重连最小版-实现计划.md`。

本指南只把 Unity Editor、真实双客户端、拔网线和画面判断留给项目负责人。服务端构建、125 条共享自测、19 条服务端 harness、Mongo 集成和静态检查由实现 agent 完成，结果见第 10 节。

## 1. 验收目标

必须同时证明：

1. 未登录不能进入战斗；自动化也通过 Authentication 真实注册/登录取得 token。
2. client B 主动断开后，在 150 帧宽限期内以同账号认领同一个 playerId，不创建新玩家。
3. 断线期间不复用旧输入，但服务端世界、Buff、体力、在途 Dash 和外部击退继续演化。
4. 重连先等待权威属性/Buff 全量，再恢复预测和玩法输入。
5. client A 在宽限期内始终看见 client B；超出宽限期未认领时才看到玩家移除。
6. HUD 能区分连接、重连、等待全量、成功、鉴权失效和失败。

固定机械判据：

| 字段 | 通过标准 |
|---|---|
| `reconnectCount` | 恰好 `1` |
| `selfPlayerId` / `playerIdBeforeAutomationDisconnect` | 相等且大于 0 |
| `automationControlledDisconnectCount` | 恰好 `1` |
| `awaitingFullSnapshot` | 最终为 `false` |
| `framesToConvergeAfterReconnect` | `0..30` 帧 |
| 重连后 `stateMismatchCount` 增量 | `<= 3` |
| 重连后 `rollbackCount` 增量 | `<= 3` |
| `gameplayInputMessagesSentWhileAwaitingFullSnapshot` | `0` |
| observer 最终状态 | `activePlayerCount >= 2`，且仍含 actor playerId |

## 2. 环境前置

在 Windows PowerShell 中执行，工作目录固定为仓库根目录：

应看到 `9.0.x`。没有则先安装 .NET 9，或把后续命令中的全路径替换为另一套含 9.0 SDK 的 `dotnet.exe`。若报 `NETSDK1045`，先查这里，不要改项目目标框架。

## 4. 主动断开重连场景

这是录屏和主验收入口。它会创建/复用 ParrelSync clone，启动服务端和两个 Unity Editor，client B 在固定帧调用真实 `GameClient.Disconnect()`，随后用同一账号 token 重连。

```powershell
cd D:\unity\Tencent\TEngine
powershell -ExecutionPolicy Bypass -File '.\Tools\AutomationAcceptance\Run-BattleAcceptance.ps1' `
  -Scenario 'two-client-reconnect' `
  -Bridge 'puerts' `
  -InteractiveEditor `
  -ClientAUserName 'battle-auto-client-a' `
  -ClientBUserName 'battle-auto-client-b' `
  -TestAccountPassword 'BattleAutomation-20260809!'
```

`-InteractiveEditor` 会显示 Unity 窗口；不带该开关时使用隐藏 batchmode。脚本结束会打印 `Combined JSON` 和 `Combined Markdown` 的绝对路径，文件位于 `_codex_tmp\battle-automation\<timestamp>`。

通过时应看到：

- 两个 report 都是 `passed=true`。
- client B reason 含 `reconnect-actor`，playerId 前后相同、`count=1`、`converge<=30`、`recoveryInputs=0`。
- client A reason 含 `reconnect-observer-continuity`，宽限期内未观察到 player drop。
- combined report 的 `ReconnectEvidence` 为通过，且列出同一 actor playerId。

失败先按 reason 定位：

| 症状 | 先查文件 |
|---|---|
| 账号注册/登录失败、token 为空 | `DataCenterSys.cs`、`C2A_LoginRequestHandler.cs`、`LoginSessionStore.cs` |
| `join-account-online` 一直重试 | `BattleComponent.cs`、`BattleClientController.cs` |
| playerId 变化或建了新球 | `BattleComponent.Join`、`C2B_JoinBattleHandler.cs` |
| 卡在等待全量 | `BuildAttributeSyncPlans`、`BuildBuffSyncPayload`、`ConvertSnapshot` |
| 恢复期仍发玩法输入 | `BattleSimulation.TickAwaitingFullSnapshot`、`BattleClientController.Tick` |
| Puerts 没触发断开 | `two-client-reconnect.js.txt`、`PuertsBattleAutomationBridge` |
| combined report 断言失败 | `Run-BattleAcceptance.ps1` 的 `Get-ReconnectEvidence` |

## 6. 弱网叠加重连

逻辑层注入固定双向 100ms 延迟和 30ms 抖动，再执行同一次受控断开：

```powershell
cd D:\unity\Tencent\TEngine
powershell -ExecutionPolicy Bypass -File '.\Tools\AutomationAcceptance\Run-BattleAcceptance.ps1' `
  -Scenario 'two-client-reconnect' `
  -Bridge 'puerts' `
  -InteractiveEditor `
  -EnableNetworkSimulation `
  -NetSimUplinkDelayMs 100 `
  -NetSimDownlinkDelayMs 100 `
  -NetSimUplinkJitterMs 30 `
  -NetSimDownlinkJitterMs 30 `
  -NetSimSeed 20260804
```

仍须满足第 1 节全部重连判据。重连后前几帧 `leadFrames` 从 `MinLeadFrames` 重新爬升是预期：RTT tracker 以新 sessionId 建立，没有旧连接样本。

## 7. 宽限期满

`two-client-disconnect` 会让 client B 正常结束进程而不重连，client A 必须先持续看见其实体，150 帧宽限期满后才看到 `activePlayerCount` 下降：

```powershell
cd D:\unity\Tencent\TEngine
powershell -ExecutionPolicy Bypass -File '.\Tools\AutomationAcceptance\Run-BattleAcceptance.ps1' `
  -Scenario 'two-client-disconnect' `
  -Bridge 'puerts' `
  -InteractiveEditor
```

actor report 应通过，observer report 应为 `disconnect-observer-finished`。observer 永远不 drop，先查 `CleanupExpiredDisconnectedPlayers` 和断线条目的幂等帧号；立即 drop 则查 grace 标记是否被绕过。

## 8. 主动断开与拔网线

主动断开的标准操作就是第 4 节命令。controller 调用 `GameClient.Disconnect()`，服务端观察到 disposed session 后立即开始宽限期，因此 HUD 的“断线重连”状态应几乎立即出现。

真实拔网线必须让客户端与服务端位于不同机器或至少经过非 loopback 网卡。服务端与客户端都在 `127.0.0.1` 时，拔物理网线不会切断本机回环连接，这种结果不能计入验收。远端拓扑准备好后：

1. client B 已加入且 client A 能看见它时，拔掉 client B 网线或在 `Windows 设置 > 网络和 Internet > 高级网络设置` 中禁用当前物理适配器。
2. 保持断网约 6 秒。默认 RTT 探测需要约 5.7 秒形成连续超时判据，6 秒内没有马上出现提示不算缺陷。
3. 在 150 帧宽限期内恢复网卡，让 client B 重新连接并确认同一 playerId。
4. 另跑一次保持断网超过“探测时间 + 150 帧宽限”，确认 client A 最终看到实体移除。

推定断开可以被同一旧 session 的迟到包撤销；disposed 主动断开不可撤销。抖动后恢复但实体仍被误删，先查 `ServerRttTracker` 连续超时计数和 `BattleComponent.RevokeInferredDisconnect`；主动断开被旧包复活则查断线来源标记。

## 9. 画面检查

在 client B 的开发 HUD 中依次观察：

1. `连接战斗` / `已连接`。
2. `断线重连 x/y | 宽限约 n.n s`。
3. `已认领，等待全量状态`。
4. `重连完成 x1 | 收敛 nf`。

画面上不能出现重复的自身球、旧球残影、长时间默认体力、Buff 瞬时乱跳或首包前自行移动。重连后的第一次权威修正允许硬校正；S10 才负责远端插值空洞的视觉平滑。

三个容易误判的预期行为：

- 新观察者加入时，属性全量只发给新 session，不再迫使既有观察者一起全量，因此带宽尖峰会比 S9 前更小。
- 重连后 lead 从最小值重新爬升是新 session RTT tracker 的正常行为。
- “冻结输入”不等于“位置绝对不变”：已起手 Dash 会跑完，断线玩家仍可被别人击退。只有无 Dash、无外部碰撞的隔离场景才要求主动输入位移为零。
