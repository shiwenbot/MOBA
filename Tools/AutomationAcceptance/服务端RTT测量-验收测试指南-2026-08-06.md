## 3. 测量准确性（含两帧偏差）

| 注入 | 期望测得区间 |
|---|---|
| 双向各 100ms | `[200, 200 + 2×FixedDeltaMilliseconds]`（≈`[200, 267]`） |
| 仅下行 100ms | `>= 100`（`rtt-probe-passes-downlink-gate`） |

**两帧偏差来源**：下行泵在 Tick 前、上行泵在 Tick 后，各至多晚一帧（≈33.3ms×2）。

## 4. 阶跃响应（需实机/弱网注入）

运行中把注入延迟 `0 → 200ms → 0`：

1. 上升沿：首个 200ms 样本后 `ControlRttMs >= 200`（envelope peak-hold，非 EMA）
2. 下降沿：按 `TightenRateMsPerSec=20` 限速回落，不得一步到位
3. HUD：`controlRtt` 与 `rttMin` 分离可见；`targetLead` 与实际 `leadFrames` 并列且可不等

## 5. 零误报

诚实客户端在 0 / 200 / 400ms 下：

- `LeadOutOfBoundsCount == 0`
- 无头用例 `rtt-honest-lead-never-warns` PASS

## 6. 「测量确实在跑」断言清单

总开关未生效时所有判据都会假通过。验收必须看到：

- `rttProbeAcksSent > 0`（客户端 snapshot）
- `serverControlRttMs > 0` 或 `HasSample=true`（有真实链路时）
- `appliedTargetLeadFrames > 0`（`BATTLE_RTT_AUTHORITATIVE_LEAD=1` 且有样本）

关闭探测对照：

```bash
BATTLE_RTT_PROBE=0
```

此时不应再发 `S2C_RttProbe`，`rttSampleCount` 保持 0。

## 7. per-session 归因

只给一端注入延迟时，两个客户端 report 的 `serverControlRttMs` **必须不同**。  
相同 → 统计消息被广播复用（回归 S7 Step 4 错误写法）。

## 8. 无样本语义

`SimulatedClient` 永不回 Ack：

- 5 个 scenario 零告警
- 无头 `rtt-no-sample-does-not-warn` PASS
- 前馈项退回兜底 / `TargetLeadFrames=0`

## 9. 抗篡改边界（不判 FAIL）

| 已知上限 | 说明 |
|---|---|
| 延迟回 Ack 换更宽超前量 | 本阶段不 enforce；envelope cap 把单次 5000ms 污染从 4 分钟压到约 48 秒 |
| 沉默即无样本 | 不回 Ack → 无样本分支，不告警 |
| envelope 单样本 cap | cap 生效后约 48 秒恢复；关 cap 则顶到 5000、约 4 分钟 |

## 10. 语义声明（验收 agent 必读）

**target 是 feedforward 下限 + 软上限，不是硬目标。**

- 不要按「实际 lead 收敛到 target」判 FAIL
- feedback 环仍可因服务端缓冲深度突破 baseline
- `effectiveMaxLead = min(MaxLeadFrames, target + slack(5))`

## 12. 失败排查顺序

1. 哈希基线变了 → 是否误改 `BattleLogic` / 无样本当 rtt=0
2. 延迟用例测出约一半 → 探测包是否没过下行 gate（缺 `TryAcceptRttProbe`）
3. 全线刷告警 → 无样本分支 / `SimulatedClient` 未隔离
4. 两端 report 相同 → `S2C_RttStats` 是否 per-session 构造
5. target 提前生效 → 是否在 `EnqueueConvertedSnapshot` 回调外应用
6. `MSB3027` → 停服务端再 build
