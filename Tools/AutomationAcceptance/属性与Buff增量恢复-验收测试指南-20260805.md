# 属性与 Buff 增量恢复（B1）验收测试指南

对应实现计划：`Plan/Gameplay状态同步演示/缺陷修复/B1-属性与Buff增量丢包恢复-实现计划.md`。

## 1. 验收目标

验证属性与 Buff 的增量包丢失后不会永久分叉：属性客户端能用 `AttributeBaselineFrameIndex` 发现并拒绝错位增量，属性与 Buff 都能在后续周期性全量包成功送达时恢复。

实现口径固定为：

- 全量间隔 `F = 60` 帧，30Hz 下约 2 秒。
- 同一玩家的属性与 Buff 使用同一全量帧。
- 不同玩家按 `frameIndex % 60 == playerId % 60` 错峰。
- 服务端属性与 Buff baseline 均按 `(observerSessionId, targetPlayerId)` 隔离；新 session 对房间内所有玩家获得一次全量，但既有观察者继续使用自己的增量 baseline。
- 属性 baseline 帧号只在非空增量或全量时推进；空包不推进、不判分叉。
- Buff 强制全量时必须同时推进服务端 baseline 的内容与帧号。

## 2. 恢复上界

设 `C` 为本次测试允许连续丢失的全量包数量，`H = 30` 为哈希上报间隔：

```text
恢复窗口上界 = (C + 1) × F 帧
单次分叉的哈希失配上报窗口 = ceil((C + 1) × F / H)
F = 60，H = 30
```

例如 `C = 1` 时，恢复窗口不超过 120 帧，最多跨 4 个哈希上报周期。验收判据是 mismatch 可以发生但必须有界停止，**不是 mismatch 必须等于 0**。

随机丢包必须使用固定 seed，并在报告中写明 seed、实际 `C`、分叉帧和恢复帧。连续丢失全量包会把窗口按 `(C + 1) × F` 拉长，这是预期退化；若不约束 `C`，就不能声称存在确定的时间上界。

## 6. 失败排查

1. 属性全量后仍分叉：检查 `All` 是否绕过旧 baseline 帧号校验，并把客户端 baseline 帧号更新为当前快照帧。
2. 属性空包触发告警：检查服务端是否每帧无条件推进 baseline，或客户端是否在 `None` 分支比较了帧号。
3. Buff 全量后下一增量被拒绝：检查强制全量分支是否只改 payload、漏掉 `BuffBroadcastBaseline.Update(...)`。
4. 新观察者首帧属性不是全量：检查 `_attributeBaselinesByObserverTarget` 是否以新 `session.Id` 查询。新观察者必须收到房间内所有玩家的属性全量，但这次全量不能波及既有观察者。
5. 恢复时间超过上界：先按固定 seed 统计是否连续丢了更多全量包，并据此修正 `C`；成功送达全量后仍未恢复才判实现失败。
