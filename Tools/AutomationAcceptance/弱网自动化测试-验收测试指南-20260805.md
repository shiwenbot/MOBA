# 弱网自动化测试（S4）验收测试指南

对应实现计划：`Plan/Gameplay状态同步演示/S4-弱网自动化测试-实现计划.md`（执行编号 **S4**）。

## 1. 目的

验证延迟、抖动、丢包可以在客户端逻辑收发层被确定性注入，并能观测预测、回滚、最终一致和哈希对账：

1. 关闭注入时发送仍在调用点同步直通，既有 29 条预测用例的行为与 `fixed-physics-bit-exact` 基线不变。
2. 启用注入时，上行和下行各自按配置排队、丢弃、释放，队列有上限，种子可复现。
3. 时间源可注入；无头用例使用帧时钟，真实客户端使用同一个系统时钟完成 Ping/Pong RTT 计算。
4. 下行丢包在 `ConvertSnapshot` 之前生效，能够复现当前属性脏同步缺陷。

## 2. 范围与边界

支持的条件是单向延迟、`[0, jitter)` 抖动和永久丢包；上行/下行可以分别配置。不注入乱序，不改 Fantasy/KCP，不注入 Join RPC，也不改输入冗余或属性同步协议。

这里的丢包是“消息从未到达”的逻辑层模型，不会进入 KCP ARQ，因此不能对外描述为真实 KCP 丢包。它比可靠传输下的最终表现更严酷，目的在于稳定暴露同步缺陷。

真实 KCP ARQ 行为验证属于阶段性的人工补充手段，不在本指南的自动化范围内；未执行该项不判 FAIL。

哈希判据必须分成三条：

| 条件 | `HashMismatch` 判据 | 解释 |
|---|---|---|
| 零丢包，可有延迟/抖动 | 必须为 0 | 验证权威快照往返和增量重建无损 |
| 仅上行输入丢包 | 必须为 0 | 客户端上报的仍是服务端权威快照哈希；`ReusedInputCount` 应大于 0 |
| 下行快照丢包 | 大于 0 记录为待查缺陷 | 丢失脏属性增量会使客户端基线错位；不能写成“弱网下预期告警”而静音 |

## 3. 前置条件

1. S1、S2、S3 已合入；服务端项目声明 `net9.0`，执行机需要 .NET 9 SDK。
2. Unity 2022.3.62f2、Fantasy 客户端和 ParrelSync clone 仅在真实客户端验收时需要。`Run-BattleAcceptance.ps1` 会自动选择带 .NET 9 SDK 的 `dotnet`，也可用 `-DotnetExePath` 显式指定。

## 5. 通过标准

### 无头

- `netsim-disabled-is-passthrough`：不调用 Pump 也立即执行发送委托。
- `netsim-uplink-pump-after-tick-has-no-extra-frame`：帧 N 的输入在 Tick 后同一合成时刻可被服务端接收。
- 既有 29 条用例全部通过；`fixed-physics-bit-exact` 仍为 `0xD2120B5F0F5A5FE5`。
- 同一种子重复运行时丢弃序列、释放计数和 lead 结果逐字段一致。
- 上行丢包场景：`ReusedInputCount > 0`、最终位置逐 raw 值收敛、服务端 `HashMismatchCount == 0`。
- 下行延迟场景：走完整 Ping → Uplink Pump → Pong 下行队列 → RTT → `ProcessPong`，`leadFrames` 高于初始值。
- 下行丢包场景：`HashMismatchCount > 0`，并在报告中记录种子与丢包计数，作为属性基线缺陷证据。

### `report.json`

每个 `BattleAutomationClientSnapshot` 必须回显 `networkSimulationEnabled`、六个延迟/抖动/丢包配置、`networkSeed`，以及 `networkUplinkSent`、`networkUplinkDropped`、`networkDownlinkDelivered`、`networkDownlinkDropped`、`networkMaxQueueDepth`、`networkOverflowDropped`。弱网场景不能只凭“客户端仍能移动”判定通过，必须有上述注入生效证据。

### 真实客户端三条判据

- `two-client-weaknet-delay`：两个客户端的 `leadFrames > 3` 且 `networkMaxQueueDepth > 0`。
- `two-client-weaknet-uplink-loss`：两个客户端 `networkUplinkDropped > 0`；服务端日志不应出现 HashMismatch。
- `two-client-weaknet-downlink-loss`：两个客户端 `networkDownlinkDropped > 0`；服务端若出现 HashMismatch，按待查缺陷记录，不把它改写成通过理由。

## 6. 失败排查顺序

1. 先看 `networkSimulationEnabled`、`networkSeed` 和 dropped/queue 计数；计数全为零时先查 `-CustomArgs` 是否进入客户端。
2. 检查 `BattleClientController.OnSnapshotMessage` 的丢包判定是否在 `ConvertSnapshot` 之前，以及两个 Pump 是否放在正确 Tick 侧。
3. 检查 Ping 发出和 Pong 释放是否使用同一 `IBattleClock`；到达时不能提前计算 RTT。
4. 检查 `NetworkConditionSimulator` 是否使用 `DeterministicRandom`、队列是否有 1024 上限、关闭配置是否同步直通。
5. 上行丢包出现 HashMismatch 时，先查是否误把预测态当成上报哈希；按 S3 语义客户端上报的是权威快照哈希。
6. 下行丢包没有 HashMismatch 时，确认丢包发生在转换前且测试确实改变了属性；这条用例是暴露当前缺陷，不是修复缺陷。
7. 出现 `NETSDK1045` 时换用带 .NET 9 SDK 的 `dotnet`；不要修改项目目标框架。
