# 哈希上报与服务端告警（S3）验收测试指南

对应实现计划：`Plan/Gameplay状态同步演示/S3-哈希上报与服务端告警-实现计划.md`（执行编号 **S3**，不属于任何 P 阶段）

## 1. 目的

验证四件事：

1. **快照与 Join 响应的定点字段往返无精度损失** —— 改传 `m_rawValue` 后，`Fixed64 → 网络 → Fixed64` 逐位一致。**这是最关键的一条**，S3 其余部分都建立在它之上。
2. **上报的哈希确实属于它声称的那一帧** —— 帧号与哈希不错位。这是第二关键的一条，错位会导致系统性 mismatch 或假匹配。
3. 服务端能查任意近期帧的权威哈希，三态（matched / mismatch / noRecord）判定正确。
4. 失配时打出含帧号与双方哈希值的告警；正常运行零告警。

## 2. 边界

本次**不**验收：告警回传客户端 UI（属 S9）、RTT 交叉校验（S5）、一致时跳过重放（S6）、Dash / 击退（S7）。

`StateHasher.cs` 的字段覆盖面本阶段**不改动**，若发现该文件有 diff，按第 6 节第 3 条处理。

## 6. 失败排查顺序

按以下优先级看：

1. **既有哈希基线变了** → Step 1 改错了世界态语义。优先查 `ConvertSnapshot` 里 `RotationRadians`/`IsAwake`/`IsEnabled` 等字段是否填了与 `FixedPhysicsBody.cs:11-16` 不一致的值，其次查 `Contacts` 是否被误删（计划明确要求保留）。**这是必须停止验收并退回实现的一类。**

2. **`hash-report-matches-reported-frame` FAIL，或 4.1 第 5 条顺序不对，或服务端 mismatch 计数接近上报总数** → **帧号与哈希错位，这是本阶段最可能出现的 bug。** 三种表现同源：采样点放错了位置。正确位置是 `BattleSimulation.Tick` 内 `AdvancePredictionTo`（`:223`）之后、`return`（`:225`）之前，当场 `TakeSnapshot()` + `Hash()`。错误做法是在 `SendPingIfNeeded`（`:214`）附近发送（那时本帧预测还没跑），或去读 `SnapshotManager` 的历史（`SnapshotManager` 的 `Priority` 是 `int.MaxValue`，在 `BattleClientController` 之后才跑，此刻 N 帧哈希还没存）。

3. **`snapshot-raw-roundtrip-bit-exact` FAIL** → 精度未消除。查 proto 是否真的改成 `int64`、两侧是否都用 `m_rawValue` / `FromRaw`。**也可能是用例本身写错了**：若用整数坐标构造，float 能精确表示，用例会假通过而非失败；失败反而说明用例是对的，问题在实现。

4. **noRecord 占上报总数的多数** → 不是「正常现象」，是信号。可能是帧号错位（同第 2 条），也可能是服务端历史容量 64 不够。先看 4.1 第 5 条的顺序，再考虑容量。

5. **`StateHasher.cs` 或 `SnapshotManager.cs` 有 diff** → 两者本阶段都不该动。`StateHasher` 被改会让基线变化与精度修复混在一起无法区分；`SnapshotManager` 被改说明实现者仍在用「存历史再读」的错误方案（且该文件在 `GameLogic/FrameSync/`，**未被链进服务端 csproj**，改了服务端也编译不到）。要求还原。

6. **既有基线变了但新用例全过** → 大概率是 `ConvertSnapshot` 的死字段填值与本地构造不一致。这是最隐蔽的一种，因为新用例走往返路径、既有用例走手工构造，两者可以同时「自洽」却互相矛盾。

7. **新用例名只出现一次** → 漏加 `AllCaseNames` 或漏加 switch 分支。前者导致静默跳过，后者导致抛 `ArgumentException`。`TestRunner.cs` 不需要改，若改了要问清原因。

8. **`Scenario 3` 分离量不是 `0.9000`** → 与 S3 无关的物理回归，说明误改了 `FrameSyncPhysicsWorld.cs`。计划里该文件在「不需要改」清单中。

9. **服务端 mismatch 计数为 0 且上报计数也为 0** → 链路没通，不是「没有失配」。查发送节奏是否真的注册、handler 是否被反射发现（Fantasy 靠基类反射，无需注册表，但类必须 `public sealed` 且继承 `Message<C2B_StateHashReport>`）。

10. **`C2B_JoinBattleResponse` 或 `GetSpawnPosition` 仍是 float** → 4.1 第 1 条会命中。当前出生点是 ±3.0 的倍数（float 可精确表示），所以漏改**不会**在无头测试里暴露成失败——只能靠静态检查抓。漏改本身即判 FAIL，不要因为「测试全过」就放过。

11. **跨测试计数污染（前一场景的失配计入后一场景）** → 计数器被做成了静态字段，或在错误位置清零。正确做法是普通实例字段，靠 `TestRunner` 每场景 `new BattleLogic()` 自然归零；`JoinPlayer` 里**不应**有清零逻辑。

12. **proto 有 diff 但生成文件无 diff** → 忘了跑 `GameServer/Tools/ProtocolExportTool/Run.bat`。

13. **opcode 冲突或客户端收不到** → 新消息插在 proto 中间了。必须追加到末尾，opcode 按声明顺序分配，插中间会让后续消息全部改号。

14. **旧客户端连新服务端读出垃圾值** → 属预期。字段 2/3/6/7 从 `float` 改 `int64` 改变了 wire type，不支持混版本运行。两侧必须同批编译，这一条不是 bug。

15. **`MSB3027` / `MSB3021`** → 服务端还在跑，先停掉。或只 build `Entity.csproj`（不受进程锁影响）。

16. **`NETSDK1045`** → PATH 里的 dotnet 没有 net9.0 SDK。先 `dotnet --list-sdks` 确认，再换另一个候选全路径（家里 `C:\Users\shiwe\.dotnet\dotnet.exe`、公司 `C:\Program Files\dotnet\dotnet.exe`），报告实际 SDK 列表。**两台机器装的位置不同，别假定某一个一定存在或一定不存在。**
